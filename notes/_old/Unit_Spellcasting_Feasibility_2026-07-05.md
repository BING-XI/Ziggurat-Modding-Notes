# Unit Spellcasting — Feasibility Investigation (2026-07-05)

> **Offsets here are class-keyed and canonical in [`Ghidra_Field_Catalogue.md`](Ghidra_Field_Catalogue.md)** (generated by `re_tools/ghidra_fields.py`, bounds-checked against measured instance sizes). If this file and the catalogue disagree, the catalogue was measured and this was not. ⚠ An offset means nothing without its class — five aliasing traps were found on 2026-08-03 where one offset meant different things on sibling classes.


**Question:** Can the Spellcasting ability be made functional on ordinary (non-hero) units — mana
generation, opening the spellbook, casting in manual/tactical combat, and casting on the strategic
map? Is this (a) not feasible, (b) feasible inside AoWEPACK.dpl, (c) in need of a new .dll, or
(d) something else?

**Verdict: FEASIBLE — as file patches to the existing binaries. No new DLL is required.**
The bulk of the work is in AoWEPACK.dpl (data + cave patches); a bounded set of companion patches
is needed in AoW.exe (strategic/combat UI gates) and AoWTCPCK.dpl (tactical-combat UI gates).
The prior conclusion that a new DLL was needed is wrong — it presumably stemmed from the
"units have no casting-state fields" problem, which is solved cleanly by a 4-byte data patch
(see §4.1, instance-size growth). A helper DLL remains an optional *convenience* (more room for
cave code in a high-level language), never a requirement.

Evidence level: everything below was read directly from the binaries via Ghidra decompilation of
AoWEPACK.dpl (full Delphi 3 symbols present) plus PE import/export/VMT analysis of AoW.exe,
AoWTCPCK.dpl, aowInt.dpl, HSEPack.dpl, AbilityP.dpl. All addresses are preferred-base VAs
(AoWEPACK.dpl base 0x55700000; file offset = VA − 0x55700000 for the CODE/DATA sections, subject
to section raw offsets — use build_patch.py's existing RVA mapping).

## 1. Architecture map (how spellcasting actually works)

### 1.1 Module topology

| Module | Role | Casting-relevant content |
|---|---|---|
| **AoWEPACK.dpl** | All game logic | THero/TUnit/TSpell/TSpellCastingAbility/TPlayerMagicControl, TEs (networked commands), AI |
| **AoW.exe** | Host + ALL strategic & shared UI screens | Imports THero class-ref (7 code refs) + THero.CastSpell/CastCombatSpell/CancelCasting/Casting\*/CanCastSpellInstantly thunks + CastingPoints/Cost/Ready strings |
| **AoWTCPCK.dpl** | Tactical combat engine/screen | Imports THero class-ref (22 code refs), THero.CanCastSpellInstantly, TSpell.CombatSpellCast, TSpellControl.GetSpell |
| aowInt.dpl / HSEPack.dpl / Enginep.dpl / AbilityP.dpl | UI widgets / map engine / core engine | **Zero** casting-related imports — not involved |

Delphi packages import/export everything **by name**, and class references (`is`/`as` checks) go
through import slots — this is what makes cross-module patching tractable and enumerable.

### 1.2 Unit class hierarchy (verified from VMT metadata on disk)

```
TCustomAbilityList (0x10) ← TAbilityOwner (0x14) ← TAbstractUnit (0x3C)
                                                      ├─ TUnit           0x48   ← ordinary map units
                                                      ├─ TAdjustableUnit 0x48   ← editor-customized units
                                                      ├─ TWallUnit       0x40   ← combat walls
                                                      └─ THero           0x9C
                                                           └─ TLeader    0xA4
```

VMT header layout (empirical, Delphi 3): class-ref slot → VMT pointer; `[VMT−0x20]` = class-name
ptr, `[VMT−0x1C]` = **instance size**, `[VMT−0x18]` = parent class-ref ptr.

Key locations in AoWEPACK.dpl:

| Class | class-ref slot | VMT | instance-size word |
|---|---|---|---|
| TAbstractUnit | 0x55710700 | 0x55710740 | 0x55710724 (=0x3C) |
| TUnit | — | 0x55710CAC | 0x55710C90 (=0x48) |
| TAdjustableUnit | — | 0x55712A54 | 0x55712A38 (=0x48) |
| THero | 0x55711FAC | 0x55711FEC | 0x55711FD0 (=0x9C) |
| TLeader | (parent-ref @ 0x55712220) | 0x55712238 | 0x5571221C (=0xA4) |
| TCombatUnit | 0x55715A54 | — | (combat wrapper; +0x4C → strategic unit ptr) |

### 1.3 The casting state lives in FIVE THero fields — nothing else

| Offset | Type | Meaning | Serialized as tag (THero.ReadWrite) |
|---|---|---|---|
| +0x7C | ptr | THeroPowerSource (mana-gen registration object) | not serialized (rebuilt) |
| +0x80 | byte | current casting points ("channeling points" in combat) | 0x0D |
| +0x84 | int32 | spell ID being cast strategically (0 = none) | 0x0E |
| +0x88 | int32 | accumulated casting progress | 0x1F |
| +0x8C | int32 | total mana required for the spell in progress | 0x22 |
| +0x90 | int32 | casting-ready event-log ID (default −1) | 0x23 |

TUnit's own fields are +0x3C/+0x3D/+0x3E (bytes; experience/medal data) and +0x40
(TUnitResource ptr) — serialized with tags 7,8,9,10. Tags ≥0x0B are FREE in TUnit's stream.

### 1.4 Relevant virtual method slots (TAbstractUnit VMT, offsets from VMT base)

| Slot | Method | TAbstractUnit impl | THero override |
|---|---|---|---|
| +0x128 | GetCastingPointsMax | returns 0 (0x5577FDB8) | ability-driven (0x55788614) |
| +0x12C | GetCastingPoints | returns 0 (0x5577FDBC) | reads +0x80 (0x55788644) |
| +0x130 | SetCastingPoints | no-op (0x5577FDC0) | writes +0x80 (0x5578864C) |
| +0x134 | GetPowerGeneration | returns 0 (0x5577FDB4) | → TLeader impl (0x5578B43C) |
| +0x138 | NewDay | 0x5578120C | — |
| +0x13C | NewTurn | 0x55780D4C | casting refill/progress (0x55787FCC) |
| +0x144 | GetAbilityLevel | 0x5577F658 | |
| +0x148 | GetAbilityEnabled | 0x5577F5E0 | |

**Critical fact:** `THero.GetCastingPointsMax` and `TLeader.GetPowerGeneration` contain **no
hero-specific field access at all** — they call `GetAbilityEnabled(0x34)` / `GetAbilityLevel(0x34)`
through the VMT and map the ability level through a table. They are class-agnostic and can be
installed directly into TUnit's VMT.

Spellcasting = ability ID **0x34**; singleton `TSpellCastingAbility` in the global ability control
(`AoWHSSet+0x80`). Level tables (both identical): level 1→10, 2→20, 3→40, 4→60, 5→90.
(Casting points fit the byte at +0x80.)

### 1.5 The five usage paths, end to end

**(A) Mana generation** — `THeroPowerSource.Power` (0x557867D0) calls owner's virtual +0x134
(GetPowerGeneration). The power-source object is created in THero.Create (+0x7C), registered with
`TPlayerMagicControl.RegisterPowerSource` in `THero.Activate` (0x557873E8) / `THero.SetPlayer`, and
unregistered in `THero.Deactivate` (0x5578754C). THeroPowerSource itself accesses its owner ONLY
through virtuals — it is unit-compatible as-is.

**(B) Strategic ability activation ("open spellbook")** — UI invokes ability virtuals:
`TSpellCastingAbility.CanActivate` (0x5576DEAC) → **`return unit is THero`** ← THE main gate.
Base `TAbility.Activate` (0x5574EF68) then fires a `TActivateAbilityInfo{abilityID, unitID}`
notification on global event list `AoWHSMap+0x1E4`; the handler (in AoW.exe) opens the casting UI.
Fully ID-based and generic on the DPL side.

**(C) Strategic casting** — `THero.CastSpell` (0x55789854): validates via `CanCastSpell`
(player-mana + spell checks); if cost ≤ current points → instant: spell virtual +0x68/+0x6C
(CanActivate/Activate → target selection → `TSpellTE`). If cost > points → multi-turn: creates
networked `THeroUpdateTE{unitID, subtype=2, spellID}` → token manager →
`THeroUpdateTE.Execute` (0x55789CDC) — **no class check, plain FindUnit(id)** — calls
`THero.ExecuteStartCasting` (0x55789130): deducts full mana from the PLAYER pool immediately,
progress accrues each turn in `THero.NewTurn` (0x55787FCC: points refill to Max, then pour into
progress), completion raises `TSpellCastEventLog{player, unitID, spellID}`;
`TSpellCastEventLog.Execute` (0x5577A1C8) re-finds the unit, **checks `is THero`**, then invokes
ability virtual +0xB4 → target selection → `TSpellTE`.
`TSpellTE.Validate` (0x557798B8) calls `THero.CanCastSpellInstantly` on the source unit **without
any class check**. On completion `TSpell.CastingDone` (0x557794BC) **checks `is THero`** then
`THero.CastingDone` (0x557893E8) clears the cluster / deducts points+mana (instant case).

**(D) Manual/tactical combat casting** — UI (AoW.exe + AoWTCPCK) → `THero.CastCombatSpell`
(0x55789BC8) → `THero.CanCastCombatSpell` (points byte +0x80 vs cost, player mana; strings
"NotEnoughChannelingPoints"/"NotEnoughMana") → spell virtual +0x70/+0x74 (CanActivateCombat/
ActivateCombat). `TSpell.ActivateCombat` (0x557793B4) creates `TCombatSpellCaster{spellID,
casterUnitID}` and fires an event on the combat controller — ID-based, generic. After the combat
action resolves, AoWTCPCK calls `TSpell.CombatSpellCast` (0x5577954C) →
`TSpell.CombatCastingDone` (0x557794E8): **checks `combatUnit is TCombatUnit` AND
`combatUnit+0x4C is THero`** → `THero.CastingDone`.

**(E) Fast (auto-resolve) combat** — `TSpellCastingAbility.fcPrefetchCombatCommands` (0x5576E2BC):
per combat unit, reads `unit+0x84` (NB: vanilla already performs this read on non-hero units —
out-of-bounds garbage read that instance growth would actually FIX), then per researched spell
**checks `combatUnit+0x4C is THero`** (0x5576E412) → `THero.CanCastSpellInstantly` → spell combat
command. Sibling gate in `CombatSpells.TCombatSpell.fcPrefetchCombatCommands` (0x557F76E5) and in
`TSpellCastingAbility.CanCastBreachWallSpell` (0x5576DF11). `TSpellCastingAbility.
AICanCastCombatSpell` (0x5576DFF4) is already hero-free (field-compatible reads only).

**Spell list:** `THero.ListSpells` (0x557879F0) = `TPlayerMagicControl.ListSpells` — heroes cast
from the **player's researched spellbook**. Units need no spell storage of their own; they would
share the wizard's book exactly like heroes do. Casting spends the *player's* mana, throttled by
the unit's casting points. This is the single most feasibility-friendly fact in the design.

### 1.6 Why unit Spellcasting is currently dead — the complete gate list

Every dysfunction traces to exactly two mechanisms:

1. **`is THero` class checks** at the entry points listed above (§1.5 B–E) — the ability button
   is disabled (`CanActivate`=false), completion accounting is skipped, AI prefetch skips units.
2. **Missing state/overrides on TUnit** — instance too small for the +0x7C..+0x93 cluster, and
   TUnit inherits the `return 0` stubs for GetCastingPoints/Max, GetPowerGeneration, and the plain
   TAbstractUnit.NewTurn (no refill). Max points = 0 → every check fails even if gates passed.

Interesting corroborating detail: `TSpellCastingAbility.Expand/Remove` (0x5576DE14/0x5576DE60)
already call `TPlayerMagicControl.Update` for **any TAbstractUnit** — the developers half-plumbed
generic support (the ability itself is grantable to units and notifies the magic system), they just
never finished the non-hero side.

## 2. The storage problem and its clean solution

Units need the +0x7C..+0x93 cluster. Delphi allocates every object via
`vmtInstanceSize` — a **data word in the file** (`[VMT−0x1C]`), used by NewInstance/GetMem, with
the whole instance **zero-filled** on construction. Subclass field offsets are compile-time
constants *per class*, and TUnit is a leaf class (no descendants — verified by full-file VMT
parent scan: only TUnit/TAdjustableUnit/TWallUnit/THero/TLeader descend from TAbstractUnit).

**Patch:** grow `TUnit` instance size 0x48 → **0x94** (word at 0x55710C90), and likewise
`TAdjustableUnit` (word at 0x55712A38). New bytes are zero-initialized automatically. Place the
casting cluster at **the same offsets THero uses** (+0x7C..+0x93). Consequences:

- All THero casting methods that touch only the cluster + virtuals become directly reusable on
  grown TUnits (verified per-function: CanCastSpell, CanCastSpellInstantly, CanCastCombatSpell,
  CastSpell, CastCombatSpell, CastingMana (touches only spell data!), Casting, CastingReady,
  CastingTurns/Left, ExecuteStartCasting, ExecuteCancelCasting, CastingDone,
  RemoveCastingReadyEventLog, CreateHeroUpdateTE — none touch hero-only fields
  (+0x3C..+0x7B items/inventory/skills) — they are safe to call on a grown TUnit).
- No save-format impact from the size itself (saves serialize fields, not instances).
- Memory cost: +76 bytes per unit — negligible.
- No relocation issues: the instance-size word has no reloc entry (plain constant).
- Vanilla's existing out-of-bounds `unit+0x84` read in fast combat becomes well-defined.

This is the insight that eliminates the "new DLL" theory: there is no need for side-table storage
or external state management — the game's own allocator provides per-unit storage for free.

death/XP/item handling that must NOT be touched. Same triage method.

## 4. What already works with NO patch (verified)

- `THeroUpdateTE.Execute` (MP casting command): FindUnit + dispatch, no class check.
- `TSpellTE.Validate/Execute/GetSource`: unit-ID based, no class check.
- `TAbility.Activate` event plumbing (`TActivateAbilityInfo` carries unit ID, explicitly handles
  any TAbstractUnit).
- `TSpell.CanActivate/Activate/ActivateCombat/CanActivateCombat` + sampled subclass
  (TUnitSpell): caster-agnostic (combat-context checks only).
- `TSpellCastingAbility.AICanCastCombatSpell`, `THero.CastingMana`, spell-cost/sphere logic.
- `TSpellCastingAbility.Expand/Remove` already notify the magic control for any unit.
- Multiplayer determinism: all casting is TE/token-based with unit IDs; refill logic runs in
  deterministic turn processing — identical guarantees to heroes (both peers must run the modded
  binaries, standard for this mod line).

## 5. Alternatives considered

| Approach | Verdict |
|---|---|
| **File patches to AoWEPACK.dpl + AoW.exe + AoWTCPCK.dpl** (instance growth + VMT redirect + gate caves) | **Recommended.** Smallest risk, uses engine's own machinery, proven workflow (build_patch.py, cave technique). |
| New companion DLL | Not needed. Storage problem is solved by instance growth. Could be revisited ONLY if cave space runs short (it won't for this scope) or for developer comfort. Costs: import-table surgery in 3 binaries or a loader, PIC/reloc discipline across modules, distribution complexity. |
| Runtime injector (memory patching at launch) | Viable variant of the same patch set, but diverges from the established on-disk workflow; no advantage here. |
| vmtParent swap (make TUnit "inherit" THero for RTTI) | **Rejected** — would make every `is THero` in the game true for units (items, leveling, joins, death handling) — unbounded behavioral fallout. |

## 6. Phasing and effort estimate

- **Phase 0 — external triage:** load AoW.exe + AoWTCPCK.dpl in Ghidra; classify the 7 + 22 THero
  refs and the casting-thunk call sites. (Half a session.)
- **Phase 1 — combat-only MVP:** D1–D7, G2/G3/G5/G7 (+G8 triage), TCPCK cast-button gate. Units
  with Spellcasting cast in tactical + fast combat; points refill via C1. No persistence yet
  (points reset to full on load — acceptable interim). This alone delivers the most gameplay value.
- **Phase 2 — strategic casting:** G1, G4, G6, C1 event-log part, C2 persistence, EXE spellbook
  triage/patches.
- **Phase 3 — mana channeling:** C3.
- **Phase 4 — optional AI:** C4.

Each phase is independently testable and revertible (keep the .bak workflow).

### Recommended effort level for implementation: **Extra (max), at least for Phases 0–2.**

Rationale: the implementation is precision binary surgery with cross-binary invariants (three
patched modules must agree), save-format and multiplayer-sensitive serialization, PIC cave code
under the known rebasing constraint, and byte-vs-int field subtleties (+0x80 is a byte; tag IDs
must not collide; VMT slot indices must be exact). The investigation repeatedly hit traps that
lower-effort passes would plausibly get wrong (slot arithmetic, TUnit's existence being masked by
a search-limit artifact, tag semantics). Phases 3–4 and mechanical re-application of an already
worked-out patch plan can run at High.

## 7. Risks / open items for the implementation phase

1. **EXE casting-window behavior for units** — biggest unknown; bounded by ≤20 sites (§3.4).
   Worst case: small shim to route unit casters into the same dialog.
2. **AoWTCPCK triage discipline** — 22 THero refs, most must remain untouched.
3. **TAdjustableUnit overrides** — check whether it overrides NewTurn/ReadWrite before installing
   VMT redirects (TUnit verified: no NewTurn override; ReadWrite override at 0x55782CEC).
4. **Save compat check** — confirm reader-side default behavior for absent tags on real old saves.
5. **Editor/data side** — granting Spellcasting to unit types is already possible (the user's
   original observation); no library format work expected.
6. **UI polish** — unit info panel casting-points display uses virtuals so it may Just Work;
   cosmetic gaps acceptable in early phases. Event-log text says "hero" in strings (cosmetic).
7. **TWallUnit** deliberately excluded (not grown): G-gates use ability check, walls have no
   Spellcasting; fast-combat's raw +0x84 read on walls remains as in vanilla (pre-existing).
