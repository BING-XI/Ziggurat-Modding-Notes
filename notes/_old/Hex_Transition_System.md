# Map-hex terrain transitions — how they work

> **Offsets here are class-keyed and canonical in [`Ghidra_Field_Catalogue.md`](Ghidra_Field_Catalogue.md)** (generated by `re_tools/ghidra_fields.py`, bounds-checked against measured instance sizes). If this file and the catalogue disagree, the catalogue was measured and this was not. ⚠ An offset means nothing without its class — five aliasing traps were found on 2026-08-03 where one offset meant different things on sibling classes.


> Part of the terrain/map system — **start at `Terrain_System_INDEX.md`** for the map of these docs.

Status: **analysis only, verified against disassembly 2026-07-24** (no patch applied; nothing to
test in-game). Covers terrain-blend edges, water shores, **roads, and bridges** (both kinds). Sources: `HSEPack.dpl` (engine, base 0x55600000, capstone via `re_tools/dasm.py` —
NOT in Ghidra) and `AoWEPACK.dpl` (game subclasses).

The "transition" is the sprite that blends one hex's terrain into its neighbour's (grass→desert
edge, lava rim, shoreline). Two layers:

- **HSEPack.dpl `HSEngine`/`Hexagon` units** — the generic hex-scape engine: field caches, the
  update/notify plumbing, and the drawing.
- **AoWEPACK.dpl `AoWHex` unit** — the AoW-specific rule table (`TAoWHexagon.UpdateTransition`)
  that picks which image goes on which edge, plus the water/shore override.

Class chain: `TAbstractHexagon` → `THexagon` → `TIsometricHexagon` (upper/lower) →
`TAoWHexagon` / `TAoWWaterHexagon` / `TAoWBorderHexagon` (AoWEPACK), `THexagonBridge` (HxBridge).
Roads and bridges reuse the same VMT slots (+0x11C `UpdateTransitions`, +0xA4
`NeighbourTerrainChanged`) but keep a *connection mask* instead of per-edge images — see the
"Roads" and "Bridges" sections at the end.

Relevant VMT slots (hexagon classes): **+0x4C** `GetTerrain`, **+0x58** overlay/show-type,
**+0x9C/+0xA0** TerrainChanged pre/post pass, **+0xA4** `NeighbourTerrainChanged`,
**+0x11C** `UpdateTransitions`, **+0x120** `UpdateTransition(dir)`.

## Object layout (TAoWHexagon / THexagon)

- `+0x04` → owning `TMapField` (field: `+0x10`=x, `+0x11`=y, `+0x04`→`TMapLevel`,
  `+0x14`=**cached terrain byte**, `+0x15`=cached overlay).
- `+0x08` → hexagon resource. Resource `+0x20` = base-tile ILB, `+0x34` = **transition ILB**
  (image count at ILB`+0x44`).
- `+0x10..+0x12` — per-edge transition **image index** (byte; `0xFF` = none).
- `+0x13` — flags: **bits 0–2** = "edge 0/1/2 has a transition image",
  **bits 3–5** = "draw that edge's image displaced onto the neighbour's side".

## Edge ownership: each hex owns only 3 of its 6 edges

`THexagon.UpdateTransitions` loops `UpdateTransition(d)` for **d = 0,1,2 only**. Edge `d` looks at
the neighbour in HN direction `{6,1,2}[d]` (table `558E8DD8`). The other three edges belong to the
neighbouring hexes — no shared edge is computed twice.

When a hex's terrain changes, neighbours are told (see chain below) and
`THexagon.NeighbourTerrainChanged` reacts **only for the HS in HN slot 0** and only when the
incoming walk direction is 1, 2 or 6, remapping **1→edge 0, 2→edge 1, 6→edge 2** and re-running
just that one edge.

## The rule table (`TAoWHexagon.UpdateTransition`, AoWEPACK 5579A9E0)

Per edge `d`: clear slot (`idx=0xFF`, `flags &= mask[d]`), find the neighbour field via
`HNtoHX`/`TranslateHX`/`TMapLevel.GetField`, read `N` = neighbour terrain (field`+0x14` cache) and
`O` = own terrain (virtual `+0x4C`). Terrain IDs per `Terrain_Changing_Spells_Map.md`: 0 Water,
1 Grass, 2 Desert, 3 Snow, 4 Steppe, 5 Wasteland, 6 Ice, 7 EarthWall, 8 RockWall, 9 Lava,
A CaveWater, C Dirt, D CaveIce; F = void/none.

**No transition** when: off-map, `N==O`, either negative, `N ∈ {7,8,F}`, `O==F`; also (in the
generic tail) when `N ∈ {0 Water, 6 Ice}` — water/ice edges are handled by the water hex itself.

The transition ILB is organized in **blocks of 16 images per terrain type** `T`:

| ILB index | Meaning |
|---|---|
| `T*16 + 0..2` | edge d, terrain `T` is the **neighbour** (drawn in place) |
| `T*16 + 3..5` | edge d, terrain `T` is **this hex** (drawn displaced, flag bit d+3) |
| `T*16 + 6..14` | generic land-land edge: `+6 + d + 3*RandInt(3)` — 3 random variants per dir |
| `0xB6 + d + 3*RandInt(3)` | shared special block: Lava ↔ CaveWater/CaveIce |

**Which blocks are cliffs vs blends** (image names via `re_tools/ilb.py`): ids `0xA0..0xA5`
`tu_xx-wa.BMP` = the **CaveWater cliff** (underground water lies below the floor, so its edge is
a drop-off) and `0x90..0x95` `tu_xx-la.BMP` the same for lava; ids `0xB6..0xBE` `tu_wl.BMP` are
only the underground-**wasteland** soft blend. To give any terrain cliff edges, make the rule
table treat it as CaveWater (0xA) — see `Chasm_Sky_Terrain_Design.md` step 4.

Special-case order (first match wins):
1. `O==Lava`: N∈{A,D} → `0xB6+d+3*rand`; N∈{7,8} → none; else `0x93+d` +flag.
2. `N==Lava`: O∈{A,D} → `0xB6+d+3*rand`; O∈{7,8} → none; else `0x90+d`.
3. `O==CaveIce`: N==CaveWater → `0xD0+d`; else `0xD9+d` +flag.
4. `N==CaveIce`: O==CaveWater → `0xD3+d` +flag; else `0xD6+d`.
5. `O==CaveWater` → `0xA3+d` +flag.  6. `N==CaveWater` → `0xA0+d`.
7. `N==Water|Ice` → none.
8. `O==Ice`: N==Water → `0x60+d`; else `N*16+3+d` +flag.
9. `O==Water` → `0x03+d` +flag.
10. default → `O*16 + 6 + d + 3*RandInt(3)` (no flag).

Afterwards: if the computed index is `< ILB count` and `ImageLib.Get` returns non-null, set flag
bit `d` (and bit `d+3` if flagged). A missing image silently yields no transition — **adding a new
terrain type means supplying its 16-image block in the transition ILB or edges just don't blend.**

## Drawing (`THexagonResource.Show`, HSEPack 55611FA4)

Called from `THexagon.Show` with the hex's pixel position (`HXtoHP`, then x−?, y−8 fixup). Draws
the base tile from ILB res`+0x20`, then for each set bit 0–2 in hex`+0x13` draws
transition-ILB image `[hex+0x10+d]` at:

| Edge | plain (bit d) | displaced (bit d, d+3) |
|---|---|---|
| 0 (`+0x10`) | `(x−9, y−6)` | `(x−9−0x10, y−6−0x20)` |
| 1 (`+0x11`) | `(x−9, y−6)` | `(x−9−0x20, y−6)` |
| 2 (`+0x12`) | `(x−9, y−6)` | `(x−9−0x10, y−6+0x20)` |

The displaced offsets are exactly the pixel deltas to the edge's neighbour hex — a flagged image
(the `T*16+3..5` "terrain T is me" variants) straddles onto the neighbour's tile.

## Update/notify chain (why edits redraw correctly)

`TAbstractHexagon.ChangeTerrain` (5560A548): bail if terrain unchanged; pick a random hexagon
resource for the new terrain (`TMORTerrainControl.GetRndResource` 5560E94C); virtual `+0x110`
(set resource) then `+0x11C` (`UpdateTransitions`); `THSMap.InvalidateStaticScene` redraws.

`TMapField.TerrainChanged` (55607CB4): re-entrancy guard bit in field`+0x0F`; calls `+0x9C` on
every HS on the field; **re-derives the cached terrain/overlay bytes** field`+0x14`/`+0x15` from
the HSes' `GetTerrain`(+0x4C)/+0x58 (0xFF = ask next HS); calls `+0xA0` on every HS; then
`UpdateNeighbourTerrain` (55607F9C): `InitHNWalk` over the 6 neighbours (dir table `5562E248`),
for each in-bounds field call `TMapField.NeighbourTerrainChanged` (55607F34) → virtual `+0xA4` on
each HS there, with the HS's own HN slot in `dl` and the walk info (dir at info`+8`) in `ecx`.

Note `UpdateTransition` reads the **neighbour field's `+0x14` cache**, not the neighbour hexagon —
so anything that writes terrain without going through `TerrainChanged` leaves stale transitions
until the next `UpdateMapField`/change (the terrain-spell paths all go through it).

## How terrain gets changed (producer side, summary)

Two idioms feed the chain above (full detail incl. per-spell behaviour in
`Terrain_Changing_Spells_Map.md` § "The two write paths"):

1. **`THSMap.ChangeTerrainEx`** (HSEPack `5560C888`; map VMT +0xD0 single-hex / +0xD4
   area-with-callbacks) — a 3-pass transaction over a hex spiral: *mutate* (save old
   terrain/overlay, run the spell's per-hex callback, write raw to `field+0x14/+0x15`),
   *validate* (every HS on each field votes via virtual +0x98 `CanChangeTerrain`; a veto rolls
   that hex back — structures and armies veto, mountains deliberately don't), *commit*
   (`TMapField.TerrainChanged` per surviving hex + a second spell callback that gets the OLD
   terrain — where e.g. Freeze Water spawns its melt-timer `TFrozenWaterHS`). The AoW wrappers
   (`55778D84`/`55778DCC`) first reseed the VCL RNG from the synced game RNG so cosmetic
   variant picks stay multiplayer-deterministic.
2. **Raw byte write + `TMapField.TerrainChanged`** (`55607CB4`) per hex — what the storm loops
   and Flood (`TFloodControl.Flood/Restore` `557F13D0`/`557F15CC`) do. No veto pass; the caller
   owns the consequences (Flood skips structures itself but NOT armies, kills roads on flooded
   hexes, and un-floods + re-places roads/decorations on Restore).

Either way, `TMapField.TerrainChanged` is the fan-out that makes the world react: field cache
re-derive → own hexagon re-links its resource → 6-neighbour notify → transitions, shore masks,
roads, bridges (self-delete if unsupported), and terrain-adaptive MOs (re-skin or die) all
update. **Writing `field+0x14` without calling it is the stale-cache bug idiom.**

## Water/shore (`TAoWWaterHexagon.UpdateTransitions`, AoWEPACK 5579AD98)

Water ignores the 3-edge scheme and walks **all 6 neighbours** itself:

- hex`+0x14` = 6-bit **open-water mask** (bit dir−1 set when the neighbour field has no
  `TLowerIsometricHexagon` land hex and no `TBorderHexagon`);
- hex`+0x15` low 6 bits = **coast mask** (neighbour has a land hex whose terrain ≠ own; top 2 bits
  preserved);
- hex`+0x19+dir` = per-direction shore tint offset: `0x28` if the land neighbour is Snow(3),
  `0x50` if Wasteland(5), else 0 (recolours the shoreline for frozen/ashen coasts);
- then creates its dynamic hexagon (`[+0x10]`) for the animated water if missing.
`TAoWWaterHexagon.Show`/`ShowDynamic` (5579AEAC/5579AFB4) consume these masks.

## Roads (`Road.TRoad` HSEPack + `AoWRoad.TAoWRoad` AoWEPACK)

Roads don't blend terrains — they keep a **1-byte connection mask** at road`+0x10` and draw
segment sprites toward each connected neighbour.

| What | Where |
|---|---|
| `TRoad.UpdateTransitions` (build mask) | HSEPack `55616F8C` |
| `TAoWRoad.UpdateTransitions` (AoW override, msg 0x1131) | AoWEPACK `5579B84C` |
| `TRoad.UpdateNeighbourTransitions` (6-dir re-kick) | HSEPack `55617064` |
| `TRoad.PlaceHX` (dedupe + both updates) | HSEPack `55616F24` |
| `TRoadResource.Show` (mask → segment sprites) | HSEPack `5561713C` |
| `TAbstractRoad.NeighbourTerrainChanged` = just `UpdateTransitions` | HSEPack `5560A8D8` |
| `TAbstractRoad` class-ref global (connection test) | HSEPack data `55604CEC` |

**Mask** (bit `d−1` = HN dir `d` 1..6 connected), then two composites: dirs **2+6 both set →
clear both, set 0x80**; dirs **3+5 both set → clear both, set 0x40** (straight-through pieces).

- Base `TRoad`: neighbour connects iff `FindOwnedHS(field, TAbstractRoad-class)` — so roads
  connect to roads *and* engine bridges (`TBridge` is in the same family; both are found by
  ClassID `0x20164` in the neighbour re-kick loop at `556170DC`).
- **`TAoWRoad` adds**: a neighbour also connects if its field answers map-field **message
  `0x1131`** ("do you connect roads?" — `SendMapFieldMsg`, result at msg`+0xC`; this is how
  city/structure hexes join the road net). If the mask changed it calls
  `InvalidateStaticScene` for its own hex, so runtime road-building repaints immediately.
- `PlaceHX` first **frees any existing road HS** on the field (no stacking), then
  `UpdateTransitions` + `UpdateNeighbourTransitions`.

**Drawing** (`TRoadResource.Show`): road ILB at res`+0x20`, base index 1. Image = `1 + code`:
dir `d` → image `d`; `0x40` (3–5 straight) → image 7; `0x80` (2–6 straight) → image 8;
**empty mask → image 7** (an isolated road hex renders as a straight piece). Draw order is
far-to-near: dirs 5,3 (or 7), then 2,6 (or 8), then 1, then 4.

## Bridges — two different things

### Engine bridge (`Bridge.TBridge`, HSEPack) — road-carrying, multi-sprite

State: **word** at bridge`+0x10`, **2 bits per HN direction** (dir `d` → bits `2(d−1)`):
`0` = nothing, `1` = deck/road connection, `2` = bank ramp.

`TBridge.UpdateTransitions` (`55617B60`): per direction classify — road-family HS present → 1;
else if neighbour terrain ≠ the bridge resource's own terrain (`res+0x28` →
`TTerrainList.GetTerrain(0)`) and no border hex → provisional bank-group code (2+n; consecutive
dirs share a group, first/last dir merged around the wrap); else 0. A post-pass then keeps, per
bank group, only the single direction **farthest (circular dir-distance) from the deck** as
code 2 and zeroes the rest — one ramp per shore, opposite the deck. Packs into the word.

`TBridgeResource.Show` (`55617E8C`): ILB res`+0x20`; always draws base image `0x13`, then per
direction the 2-bit code picks fixed deck/bank sprite indices (e.g. dir 1 deck → images 7 and
0xD, dir 3 deck-part → +2, banks from +8/+2 group), same far-to-near ordering as roads.

### AoW hexagon bridge (`HxBridge.THexagonBridge`, AoWEPACK) — one-hex span over water

- Orientation byte at `+0x11`: **axis** 0/1/2 = opposite dir pairs (1,4)/(2,5)/(3,6); `0xFF` =
  no valid span.
- `DirectionValid` (`55799C04`): axis valid iff **both** opposite neighbours along it are in
  bounds and `AoWE.Land` (5575AEA4) on their cached terrain byte — the bridge itself sits on
  water, its ends must be land.
- `UpdateTransitions` (`55799FD8`): keep the current axis if still valid, else try axes 1, 2, 0
  in that order; if none valid (gated on `AoWHSMap+0x3C` bit 1) set `0xFF`. Always ends with
  `UpdateExclusiveMoves` (`55799CD4`) — the movement-blocking side of the bridge.
- `NeighbourTerrainChanged` (`5579A054`): recompute; if the orientation ended `0xFF` the bridge
  **frees itself** (`call [vmt-4]`) — terraforming away a bank silently demolishes the bridge.
  (Relevant to any terrain-changing mod: raising water/removing land near a hexagon bridge is a
  legitimate object-deletion path, not a leak.)

## Mountains & terrain-adaptive map objects (2026-07-24)

Mountains are neither hexagons nor terrain bytes — they are **map objects** (`TMapObject` family,
HSEPack) that sit *on top of* fields and interact with the terrain system through three channels:
the field caches, the change-veto pass, and per-terrain re-skinning.

| What | Where |
|---|---|
| `TMountainMO` (ClassID `0x20168`) / `TMountainMOR` | AoWEPACK `557A27B0` / `557A28A0` |
| `TMountainMO.CanChangeTerrain` = **`return 1`** | AoWEPACK `557A2DDC` |
| `TMountainMO.GetOverlay` (clamps to 0) | AoWEPACK `557A2DC8` |
| `TMountainMO.ValidMountainOverlap` | AoWEPACK `557A2DE0` |
| `TMultiHexMO` (footprint machinery, `UpdateTerrain`) | HSEPack `55604678` / `5560AED8` |
| `TILTerrainMO` (terrain-adaptive: re-skin or die) | HSEPack `55618334` |
| `TILTerrainMO.TerrainChanged` (the re-skin/self-free) | HSEPack `55618888` |
| `TFixedILTerrainMO.CanChangeTerrain` (the veto variant) | HSEPack `55618CA8` |
| `TRaisedMountain` (Raise Terrain spell MO) : `TILTerrainMO` | AoWEPACK `557A2A8C` |
| `TMORTerrainControl.GetRndResource` (resource-per-terrain picker) | HSEPack `5560E94C` |

**Footprint**: a multi-hex MO's resource carries a `TTerrainList` — per footprint cell a
`(terrain, overlay)` signed-byte pair; a cell with both negative isn't part of the footprint
(`TMountainMO.CanPlace` `557A2E54` skips those). On place/remove, `TMultiHexMO.UpdateTerrain`
spiral-walks the footprint and calls `TMapField.UpdateTerrain` (`55607E9C`) on every cell where
the MO publishes a value — that's how an MO's declared terrain/overlay enters the **field caches**
(`+0x14`/`+0x15`) that everything else (transitions, Flood, movement) reads.

**Overlay identity**: `TMountainMO.GetOverlay` returns the list value if negative, else **0** —
mountain cells present overlay 0 on the field. That is why Flood's overlay shield-set {0, 2, 7}
protects mountain hexes. `ValidMountainOverlap`: two mountains may share a cell only if their
overlay codes differ (0 = core vs 1 = fringe); same-code overlap is rejected.

**Terrain changes under a mountain — re-skin or die, never veto**:
- The generic terrain-adaptive base `TILTerrainMO` keeps `+0x18` = current terrain type and
  `+0x14` = the image/sequence index for it (virtual `+0x12C` maps terrain→image; `+0x128`
  `ValidTerrainType` asks "does my resource have an image for terrain T?"). `Show` (`55618940`)
  draws image `[MO+0x14]` (single image) or passes it as the sequence index to
  `TMapObjectResource.ShowComplexImage` (`5560A134`) — which walks a **linked chain of image
  sequences** (each with own ILB, x/y offset, next-ptr at `+0xC`), using the global frame counter
  phase-shifted by `x + 16·y` so multiple instances don't animate in sync.
  **So "one resource renders per-underlying-terrain" = the resource holds an image set per
  terrain type and the MO switches `+0x14`** — this resolves the open note in the
  raise-terrain analysis (`aow1-terrain-changing-spells` memory).
- `TILTerrainMO.TerrainChanged` (called per cell from `TMapField.TerrainChanged`): if the new
  terrain has an image → adopt it (`+0x18`/`+0x14` updated, mountain re-skins in place); if
  **not** → the MO **frees itself** — changing terrain to something the resource can't draw
  silently deletes the object (same pattern as the hexagon bridge).
- Veto behaviour differs by class: `TFixedILTerrainMO.CanChangeTerrain` refuses changes it can't
  display, but **`TMountainMO` overrides to always-allow** (`mov al,1; ret`) — mountains rely on
  re-skin-or-die instead. (Exact parent chain TMultiHexMO→ILTer family inferred from call
  patterns, not from a VMT dump — Ghidra was down; the per-method behaviour above is
  disassembly-verified.)

**Partial footprint changes** (one cell of a multi-hex mountain altered) — semantics from
`TILTerrainMO.TerrainChanged`/`ChangeTerrain` (`55618888`/`556188D8`, identical bodies; the field
fires +0x9C with the raw new byte and +0xA0 with the re-derived cache, so the handler runs twice):

1. **Cell gate**: the handler first checks `resource.TTerrainList.GetTerrain(cellHN) >= 0`. A
   cell that declares only an overlay (terrain = −1) triggers **nothing** — change terrain under
   such a cell and the mountain neither re-skins nor dies. Only cells with a declared terrain
   entry qualify. (Which cells those are in the real mountain resources is **data we have not
   parsed** — the `.hss` resource content, not code. `TTerrainList.UsedTerrain==1` seen on the
   Call-Mountains resource suggests real mountains declare exactly one terrain type.)
2. **Whole-object skin, keyed by the last qualifying cell**: `+0x18`/`+0x14` are single per-MO
   fields — there is no per-cell skin. `ValidTerrainType(newT)` = "does the resource's
   ILB/sequence list contain an image for newT" (`5561873C`). If yes, the ENTIRE mountain
   re-renders as a newT mountain even though its other cells still sit on the old terrain.
3. **Area spells → last-writer-wins**: each footprint field fires the handler separately as the
   spiral walk reaches it, re-skinning the MO each time; the final appearance matches whichever
   qualifying cell was processed **last** in walk order. A mixed result (e.g. a storm ring
   crossing the footprint) leaves one uniform skin that matches some cells and not others.
4. **One bad cell kills the whole mountain**: if any single qualifying cell's new terrain has no
   image in the resource, the MO frees itself mid-loop — even if every other cell kept a
   supported terrain. Later fields in the same sweep simply no longer find the HS. The veto pass
   cannot prevent this for mountains (`CanChangeTerrain` = always-allow).

**Splitting — decorations split, mountains don't** (2026-07-24). The engine HAS a
split-into-single-hex mechanism, but it lives in the *other* MO branch:
- `THSMap.ClearTerrain` (`5560CBEC`) broadcasts **map-field msg `0x10`** ("terrain cleared at
  cell N") over an area, then optionally ChangeTerrainEx's the centre.
- `TTerrainMO` (Terrain unit, ClassID `0x20167` — the decoration/vegetation family) handles it in
  `MapFieldMsgProc` (`55616A6C`) → `ClearTerrain` (`556168F8`): if its resource covers **>1**
  terrain cell, it searches the resource registry for a **single-cell variant** (same resource
  ClassID, same `+0x44`/`+0x45` priority bytes, `UsedTerrain==1`, same overlay type), frees
  itself, and **re-places one single-hex MO on every other terrain cell of the old footprint**
  (skipping the cleared cell) — a true split. No single-cell variant found → the whole object is
  freed instead.
- **Mountains are in the parallel branch and do NOT split.** Static parent calls in the Mountain
  unit prove the ancestry `TMapObject` → `TMultiHexMO` → `TILTerrainMO` (→ mountains):
  `TRaisedMountain.ReadWrite` → `TMultiHexMO.ReadWrite`, `.Show` → `TILTerrainMO.Show`,
  `.MapFieldMsgProc` → `TMapObject.MapFieldMsgProc` — never anything in the Terrain unit. The
  inherited `TMapObject.MapFieldMsgProc` (`55609E30`) response to msg `0x10` is: cleared cell
  declares terrain, or is the anchor (cell 0) → **free the whole mountain**. So a partly
  cleared mountain vanishes entirely; only decorations degrade gracefully into singles.

**Raised mountains** (Raise Terrain spell): `TRaisedMountain : TILTerrainMO` (its `Show`
`557A30D8` tail-calls `TILTerrainMO.Show` directly, hidden while flag `+0x1C` bit 0 during the
raise animation). Owner-turn countdown at `+0x1E` (`NewTurn` `557A3064`) → `RestoreTerrain`
(`557A302C`): frees the MO and, if the saved size byte `+0x1F` > 0, calls
`TAoWHSMap.PlaceTerrain` (`55778EEC`) over the area with the field's *current* terrain — forcing
a clean resource re-place/re-blend where the mountain stood.

## Where the hexagon images live (Border terrain et al.) — 2026-07-24

The base tile image of a hexagon (drawn from its resource's ILB at `res+0x20`, index 0 for the
border hex — `BorderHx.TBorderHexagon.Show` `55617688`) is **not** an external file: hexagon
resources carry their image library **embedded in `Release/Release.hss`** as self-contained
mini-ILB blobs (`\x04ILB\x00` header, ~3.4 KB each, one 8-bit hex bitmap).

- **Border terrain** (the impassable map edge, `TAoWBorderHexagon`): **12** embedded ILBs with
  internal bitmap name **`H_Border.BMP`**, at `Release.hss` offsets ≈ 294,724–335,356 (spacing
  3,453 = 3,414-byte blob + record wrapper). 12 resources = the random-variant pool
  (`TMORTerrainControl.GetRndResource`).
- Same pattern for all terrain hexes: `H_gr.BMP` ×14 (grass), `H_Wa2.BMP` ×15 (water),
  `H_Wl.BMP` ×15, `H_st.BMP` ×10, `H_de.BMP` ×9, `H_sn.BMP` ×8, `H_co.BMP` ×8, `H_Ic/H_ic` ×5.
- ⚠ **`Images/BORDER.ILB` is a decoy** — despite the name it holds the *structure ownership
  border* sprites (`B_buildg.bmp`, `B_farm.bmp`, …) used by `TStructure.Get*BorderImage`, not
  the map-edge terrain. Structure/decoration resources reference external `Images/*.ILB` by
  filename; hexagon tiles are embedded in the .hss.
- Hexagon tile RLE (`re_tools/ilb_rle16.py`): per-row `u32 reclen` + optional margin markers,
  and **records are 4-byte aligned** — the next record starts at `align4(start+reclen)`, so
  odd-width tiles carry padding (ILPACK `55210AC7`). Drive it with `clipw`/`cliph`, not `w`/`h`.
- To reskin the border terrain: replace the 12 embedded blobs in `Release.hss` — **and then
  repair the trailing CRC-32 with `re_tools/hss_crc.py --fix`, or the game and editor die
  silently with an unhandled `Invalid HSSET`** (see `Chasm_Sky_Terrain_Design.md` step 3). (the
  `IlbMaker_Release_1.0.2.7.7z` tool in the game dir builds ILBs) — or fewer, if you also shrink
  the variant pool.

**The two storage modes, and why** (verified 2026-07-24). The resource system supports both
inline (streamed) ILBs and by-filename references; the split is systematic:
- **Embedded in `Release.hss`** — static surface tiles, one image per variant resource (grass,
  desert, snow, steppe, wall, Border). A resource is a self-contained Delphi-streamed object;
  for a single ~3.4 KB bitmap, embedding keeps the editor's resource-set workflow dependency-free
  (copy/distribute a set, images travel with it). These tiles exist **nowhere else** — no
  external file holds them.
- **External `Images/*.ILB` by filename** — anything shared or multi-image:
  - `Waterhex.ILB`/`IceHex.ILB`: 16 animation frames (`H_Wa2`/`H_Ic2`) + **32-frame animated
    shoreline sets per bank terrain** (`gr/sn/wl.BMP`) — shared by every water/ice hex; each
    referenced exactly once from `Release.hss`. Embedding per resource would duplicate the whole
    frame set and defeat sharing.
  - `EARTHHEX.ILB`/`ROCKHEX.ILB`: the underground solid-earth / rock-wall tiles — 28 variants in
    ONE shared library (index-picked) instead of 28 embedded resources; referenced once each.
  - `HexTrans.ILB`: the terrain-blend transition library — filename **hardcoded in HSEPack's
    Hexagon unit** (string at `0x556112A0`), because the T*16 index scheme is engine logic; every
    hexagon resource's `+0x34` points at this one shared library. Contains exactly the expected
    counts (e.g. `T_GR.BMP` ×9 = 3 dirs × 3 variants; `la.BMP` ×6 = lava's two 3-entry rows).
  - `MOUNTAIN.ILB` (65 refs), structures, `Targhex.ILB` (target-cursor overlay, code-loaded).
- The `_`-prefixed `Images/_*.ILB` files are pre-Ziggurat originals (the installed mod replaced
  the external libraries — the external route is the moddable one; `Terrain_Ziggurat_TheGroll1.ilb`
  is the modder's own addition).

## Modding notes

- To force a re-blend after a raw terrain-byte write, call the field's `TerrainChanged` (55607CB4)
  or route through `ChangeTerrain`; writing field`+0x14` alone leaves neighbours stale.
- The per-edge image bytes at hex`+0x10..0x12` and flags at `+0x13` are plain state — a cave can
  repaint an edge by writing them and invalidating the scene, but the next terrain change on
  either side recomputes them.
- Random variants come from `RandInt(3)` at pick time (UI-side RNG, not the game-state RNG —
  consistent with the non-lockstep RNG note in the combat-math doc).
- To make a structure/HS join the road network visually, answer map-field msg `0x1131` with a
  non-zero result — no road HS needed.
- Road/bridge connection masks (`road+0x10` byte, `bridge+0x10` word) are plain state; caves can
  rewrite them + `InvalidateStaticScene`, but any neighbour terrain change recomputes them.
- Enchanted Roads (`GlobalEnchantmentSpells.TEnchantedRoads*`, AoWEPACK 557EFCB4+) is a movement
  enchantment — it does not touch the road visual system.
