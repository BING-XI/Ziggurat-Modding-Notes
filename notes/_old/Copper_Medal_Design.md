## Why this was cheap: rank is derived, never stored

`TUnit.GetRank` recomputes the rank from the XP byte (`unit+0x3C`) and the unit's tier
(`unittype+0x2F`) on every call. Nothing caches or serialises it — `TUnit.ReadWrite` stores XP
only. So **old saves and maps load unchanged** and simply re-derive their medal from the new
ladder, and the whole feature is "new thresholds + remap the handful of consumers of the rank
number".

### v5 — cumulative bonuses + HP/MV revived (APPLIED, UNTESTED 2026-08-07)

Medals stopped being a flat "+1 if decorated" and became a ladder you climb:

|---|---|---|---|---|---|---|
| Copper | +1 | — | — | +1 | +2 | +1 |
| Silver | +2 | +1 | — | +2 | +4 | +2 |
| Gold | +3 | **+2** | +1 | +3 | **+6** | +3 |

(v6, 2026-08-07: Damage moved down to silver and gold gained +1 Defence. v5 had Damage at

HP +1/+2/+3 → **+2/+4/+6**, so a medal keeps its worth against doubled damage and doubled pools.
ATK/DEF/RES were **not** touched — they were already doubled by the 5% conversion, which medals sit
on top of. **Movement never scales** (`K_MV` stays 1). See `DamHP_Double_Decisions.md`.

- ATK / DAM / DEF / RES: `STAT_TABLES` here — Attack and Resistance `(0,1,2,3)`,
  Damage `(0,0,1,2)`, Defense `(0,0,0,1)`.
  Re-applied as a rewrite-in-place; no revert was needed.

⚠ The design workbook is now stale on three rows — it still records silver/gold as +1 ATK
/+1 RES and MV as +1 per 2/4/6/8. The manual drops those rows rather than contradict itself

**The ladder is copper = tier×2, silver = tier×6, gold = tier×15** (`LADDER = (2, 6, 15)`,
`TIER_SCALED = True`), replacing the install's previous silver=tier×2 / gold=tier×6.
**All three medals grant the same stat bonus** (+1 Attack, +1 Resistance — the value silver already
gave; gold's +2 is gone).

⚠ Because silver and gold both moved *up*, existing units demote: XP in [t×2, t×6) was silver and is
now copper, XP in [t×6, t×15) was gold and is now silver. Saves still load fine (they store XP, not
rank) — they just re-derive a lower medal.

accepts the pristine bytes, the target bytes, *or the output of any earlier tuning* — prior tunings
are regenerated from `PRIOR_TUNINGS`, so **re-tuning never needs a revert**. Add a tuple to that
list whenever the tuning changes again.

### Side effect: what the Warmonger enchantment now produces

**Warmonger** is a *city enchantment* (`ceiWarmonger` / `CitySpells.TWarmonger`); the rank grant
fires off city flag bit 3 (`city+0x5C & 8`). Its cave at **0x5580C029** grants a flat **15 XP**
(`mov edx,0xF` at 0x5580C02D), so with a tier-scaled ladder the result depends on tier:

| unit tier | copper (t×2) | silver (t×6) | gold (t×15) | 15 XP lands on |
|---|---|---|---|---|
| 1 | 2 | 6 | 15 | **gold** |
| 2 | 4 | 12 | 30 | **silver** |
| 3 | 6 | 18 | 45 | **copper** |
| 4 | 8 | 24 | 60 | **copper** |

Change that one immediate if a different result is wanted. Arena training costs remain tier-scaled,
since `UnitTrainCost = (nextRankXP − XP) * 5`.

### The three traps this feature had to route around

1. **`TUnitResource` had no fourth ability-set slot**, because `type+0x44` — the slot the
   contiguous `+0x38 + i*4` array would need — was the transport-capacity byte (pfs tag 0x18), and
   `type+0x48` is another object. Letting a grant loop reach set index 3 in that state derefs a
   byte as a pointer. Resolved by *moving* transport capacity to the dead `+0x32` gap (see below),
   after which rank→slot is the identity. The three loop sites share an identical 11-byte tail
   (`8B 54 82 38 | 8B C6 | E8 <UpdateDefaultAbilities>`) with EAX=index, EDX=type, ESI=unit — one
   cave serves all three.
2. **The painter's dead gold block is left alone on purpose.** `TUnit.ShowEx` had two 39-byte
   near-duplicate draw blocks (silver `mov edx,5`, gold `mov edx,6`). The new head dispatches
   rank→ECX through a cave and falls into the *first* block, whose `mov edx,5` became `mov edx,ecx`.
   The gold block at 0x5578272F is now unreachable — and **must not be reused or zeroed**: it
   carries a `.reloc` entry at 0x55782734 (the absolute `[0x558FA044]` image-list global), so the
   loader will rewrite those bytes at load time regardless of what is there.
   Every range displaced by this patch was `.reloc`-scanned first and is entry-free.
3. **`ImageLib.TCustomImageLibrary.Get` has NO bounds check** (ILPACK 0x5521A8B8): it indexes
   `lib+0x48` straight by image id (`table[id] = {ptr, alias}`; alias −1 → nil). `GetSafe`
   (0x5521A8E0) is the bounds-checked twin, and the painter calls `Get`. So pointing copper at an
   absent image id reads past the table — **the new icon had to actually exist**, it is not
   cosmetic polish.

### ⚠ VA→file-offset is per section

`AoWEPACK.dpl` CODE is `file_off + 0x55700C00`, but **DATA is `file_off + 0x55701200`**. The stat
tables are in DATA; using the CODE delta reads 0x600 bytes past them. The first build attempt did
exactly this and verify-before-write caught it — the script now resolves offsets through the PE
section table. Any script touching `0x558E8xxx`+ must do the same.

### Pre-existing undocumented caves in this area (leave alone)

`TUnit.GetHits` (vmt+0xD0) and the vmt+0xD4 movement getter are already hooked to caves at
**0x5580BE00–0x5580BE73**: `stat = base + rank*K + XP/(tier+1)` for HP and `XP/(2*tier)` for
movement, with **K = 0** (imm8 knobs at 0x5580BE27 and 0x5580BE10). BXL replaced medal HP/move
bonuses with smooth XP growth — which is why the Hits rank table above is dead. Both caves treat
rank arithmetically, so a 4th rank needed no change there. The two imm8 bytes are the knobs if
medals should grant HP/move again (copper K, silver 2K, gold 3K).

The Warmonger enchantment also runs through a cave: `TCityProductionControl.CreateUnitProduction@0x557A8DA0`
does *not* call `SetRank(unit,1)` (Ghidra's stale image says so — it is wrong); the live code calls
**0x5580C029**, which grants a flat **15 XP** via `SetExperience`. **No patch was needed there** —
see the table above for what that now yields per tier.

## The copper icon (`Images/Combat.ILB` image id 8)

`Images/Combat.ILB` is a **2× HD art pack** (id 0 is 25×2 where vanilla is 13×1); `_Combat.ILB` is
the vanilla original. Both got the new image so swapping either in stays safe. The game loads the
loose file — `Release.hss` only *references* the name `COMBAT.ILB` and embeds no copy (it contains
neither `testbmp` nor `PartyShield`), so **no .hss CRC repair was needed**.

- ids 8 and 9 were holes (ids run 0..7, 10..146) and lookup is by the **id field**, not list order.
- The medals are id 5 (silver) / id 6 (gold), `PartyShield.BMP`, Sprite16 — 21×19 with a 7×13 clip
  in the HD file, 11×10 with a 3×6 clip in vanilla.
- **Sprite16 (type 22) is uncompressed RGB565 of the clip rectangle**: the five trailing dwords are
  `[clipw, cliph, clipx, clipy, transparent]` and the payload is exactly `clipw*cliph*2` bytes.
  So copper is id 5's pixels pushed through a luminance→copper ramp (`COPPER_RAMP` in the script),
  preserving the silhouette and every transparent pixel exactly.
- **⚠ The medal sprite is a RIBBON on top and a circular DISC below, and only the DISC carries the
  rank colour.** Silver is neutral grey throughout; gold is warm *only* in the disc. So the recolour
  is masked to the disc and the ribbon is copied byte-identically from silver — the first version
  tinted the whole sprite and looked wrong in-game. The split is derived from the **gold** sprite at
  build time (`disc_start()`: the bottom-most contiguous run of rows holding a pixel with
  saturation ≥ 50), not hardcoded, so it lands correctly on both arts: **disc = rows 7–12 of 13 in
  the HD file, rows 3–5 of 6 in vanilla.** Note gold also has a few warm pixels up in the ribbon
  (row 1, edge columns); those are deliberately excluded.
- Re-running after an art tweak **rewrites the id-8 pixels in place** (identical geometry ⇒ identical
  payload size ⇒ no directory or size change); the splice path below only runs on a fresh install.
- Splice mechanics: image offsets are relative to the header's `imgdir` (data start), so the new
  directory record is inserted after id 6, `imgdir` and `filelen` are bumped, and the payload is
  appended at EOF. The script asserts byte-identity of everything outside the splice *and*
  re-parses to confirm all 85 pre-existing images come back field-for-field identical.
- `subid` (143/144 for silver/gold; 145 for copper) is authoring metadata only — the engine's
  lookup path never reads it, and duplicate subids already exist in the shipped file.

`re_tools/ilb.py` was fixed along the way (it mis-parsed Sprite16 tails and drifted); it now stops
cleanly at the first composite entry rather than desyncing, and documents the format above.

## Copper bonus abilities — **APPLIED, UNTESTED (2026-07-30)**

Silver and gold bonus abilities are per-unit data (`Unitres.pfs` tags 0x1E / 0x1F, delta sets).
Copper now has the same: **`TUnitResource` carries a 4th ability owner**, serialised as new pfs
tag **0x20**, editable on a 4th tab in AoWDevEd. Driven by `COPPER_GRANTS_ABILITIES` in the build
script; turning it off restores every site the script owns.

### What made it cheap

1. **The editor already indexes ability owners generically.** `AbilityRankTabsChange`
   (AoWDevEd.exe **0x004111E0**) forwards to **0x00410F40**, which does:
   `edi = TabIndex & 0x7F` … `eax = [form+0x214]` (the TUnitResource) …
   **`eax = [eax + edi*4 + 0x38]`** → populate `AbilityListBox`. It is *not* hardcoded to three —
   add a 4th tab and it reads owner slot 3 by itself.
   (Published method table also gives `FormCreate` = 0x00410D60, `OKBtnClick` = 0x00411040.)
2. **`Unitres.pfs` tag 0x20 is free** — highest tag in use across all 180 unit records is 0x1F.
3. **The DLL's loops are plain counts of 3**, not unrolled: `TUnitResource.Create@0x55784C44`
   (`do {...} while (bVar2 != 3)` creating owners at `+0x38 + i*4`),
   `TUnitResource.Destroy@0x55784CC8` (same shape), and `ReadWrite`'s
   `ValidateOwnerTypeAbilities` loop.
4. **A 4th contiguous slot can be freed cheaply.** `TUnitResource` instance size is **0x54**
   (Delphi VMT 0x55710A70, `vmtInstanceSize` at VMT−0x28), and **+0x32..0x37 is a 6-byte gap** that
   no pfs tag maps to and the constructor never initialises.

### The single blocker, and what it actually is

Slot 3 of the contiguous array would be **`+0x44`, which is already the transport-capacity byte**
(pfs tag 0x18). Identified by data: only **11 of 180 units** carry tag 0x18, and every one is a
transport (Galley 4, Carrack 7, Cog 7, Dragon Ship 2, Air Galley 7, Guild Zeppelin 7, Dwarven
Balloon 5, Aether Barge 5, Supply Caravan 7, Sandworm 7, Giant Frog 1).

**Its direct readers are few and all located.** Capacity is reached through the accessor
`TUnitResource.GetTransportCapacity@0x55784D24`, which returns
`max(Transport-ability level (id 0x32), [res+0x44])` — the only field read is
`mov dl, byte ptr [ebx+0x44]` at **0x55784D44**. All 10 xrefs are calls to that accessor, never to
the field (AI production planning `TAutoProduceAIPA.*`, `GetUnitIndexAIPriority`,
`TUnit.GetTransportCapacity@0x55782BB8`, `TUnit.GetTransporter`). The editor has a
`TransportCapacityEdit` TSpin and imports the accessor.

### The audit that made the field move safe

The move was only defensible because the footprint is *fully enumerated*, via
`re_tools/fieldrefs.py` (written for this, and validated against a field known to be read):

**`TUnitResource+0x44` is touched in exactly three places, total, across both binaries:**

| Where | Site | Change |
|---|---|---|
| `TUnitResource.GetTransportCapacity` | 0x55784D44 `mov dl, byte ptr [ebx+0x44]` | disp → 0x32 |
| `TUnitResource.ReadWrite` (tag 0x18) | 0x55784ECE `lea edx, [edi+0x44]` | disp → 0x32 |
| AoWDevEd.exe spin write | 0x00411166 `mov byte ptr [esi+0x44], al` | disp → 0x32 |

All 10 xrefs to capacity go through the *accessor*, never the field. The editor's own field map
(profiled through its `[form+0x214]` resource pointer) covers every serialised field —
0x1C, 0x20, 0x24, 0x28, 0x29–0x2F, 0x30, 0x31, 0x44, 0x48, 0x4C, 0x50, 0x51 — and **0x32..0x37 is
absent from it**, corroborating the gap. The `lea` form only showed up after the scanner was fixed
to match address-taking without a size prefix; without that, the ReadWrite site would have been
missed and saving would have corrupted the new pointer.

**The pfs format is unchanged for capacity** — still tag 0x18, just stored at a different offset —
so old and new data load identically in both directions.

### ⚠ Slot order IS rank order — the bug this got wrong once

Both the grant loops and the editor index owners as **`[unitres + rank*4 + 0x38]`**, so the slots
must read **base / copper / silver / gold**:

| slot | offset | pfs tag |
|---|---|---|
| 0 (no medal) | +0x38 | 0x19 base |
| 1 copper | +0x3C | **0x20 (new)** |
| 2 silver | +0x40 | 0x1E |
| 3 silver→gold | +0x44 | 0x1F |

The first build appended copper at the far end (+0x44) and left silver/gold where they were. That
compiles, applies and *looks* fine — but it shifts every rank by one: the editor's **Copper tab
listed silver's abilities, Silver listed gold's, and Gold was empty**, and in-game a copper unit
would have gained silver's abilities. Caught by the user in the editor. Fix: silver's serialisation
offset moves to +0x40 (one byte at **0x55784F33**) and the cave writes gold→+0x44, copper→+0x3C.
The script now derives every offset from an `OWNER_SLOTS_ON` table and asserts it is in rank order,
so the two can't drift apart again.

Note the pfs tags stay bound to the same *ranks* they always were, so existing `Unitres.pfs` data
keeps working: tag 0x1E still means silver, 0x1F still gold — only the memory slot each lands in
changed.

### What was patched for this

**AoWEPACK.dpl** (all in `TUnitResource`): the three displacement/loop-count edits above plus
`Create@0x55784C8E` and `Destroy@0x55784CEA` `cmp bl,3`→`4` (allocate/free 4 owners),
`ReadWrite@0x55784F66` validation loop `3`→`4`, silver's owner offset at `0x55784F33`, and the
15-byte gold-owner block at **0x55784F3B** replaced by a call to cave **0x55813060**, which
serialises gold from +0x44 and then copper from +0x3C as tag 0x20. Because `ReadWrite` is Delphi's
single read *and* write path, patching it makes the editor **save** tag 0x20 as well as load it.

**The grant cave becomes the identity mapping** (rank r → set r: base/copper/silver/gold), since
there are now 4 contiguous owners. ⚠ That identity mapping is only valid *with* the 4th owner —
with 3 owners, rank 3 would index +0x44 and deref the transport byte. This is exactly why the flag
lives in the same script as the medal work rather than in a separate one: no cross-script ordering
hazard is possible.

**AoWDevEd.exe** — the 4th tab is an **in-place DFM edit**, not a runtime `Tabs.Add` cave. Tabs are
now **`None / Copper / Silver / Gold`**, mapping to owner slots 0..3 because the editor indexes
`[unitres + tabIndex*4 + 0x38]`.

⚠ **The DFM cannot grow.** Its RCDATA resource (`TUNITRESOURCEEDITFORM`, file 0xDA3C4, size 0x12B8 =
4792 B) is packed against its neighbour with **zero padding** — the next form's `TPF0` begins at the
very next byte — so lengthening a caption has to be paid for from *inside the same form*. Full-word
captions cost 28 bytes where the abbreviated `Cu/Ag/Au` set cost 20. The 8 bytes come from **deleting
`AbilityRankTabs.TabOrder = 0`** (11 bytes): that control is the **first child** of its group box, so
creation order gives it TabOrder 0 anyway (verified — its sibling `AbilityBtn` sets 1 explicitly), and
the editor never reads the property. Net effect: the DFM shrinks by 3 bytes, which are zero-padded at
the end of the fixed-size resource; the DFM reader stops at the form's terminator, so padding is never
read. **No resource-directory surgery, no new section, no cave, no VCL calls.**

Two things ruled out along the way, worth not re-trying:
- **Shorter integer encodings are not a source of free bytes** — Delphi already emits `vaInt8`
  wherever the value fits (measured: 0 re-encodable `vaInt16` properties in this form).
- **A runtime `Tabs.Add`/`Insert` cave** would mean deriving VCL internals and hand-building a Delphi
  string literal, because the editor imports neither `TCustomTabControl.GetTabs` nor
  `TStrings.Insert`. Far more risk for the same result.

The edit is done by `re_tools/dfm_edit.py` (new: a DFM walker that records each property's byte span)
as a **normalising transform** — "make the tabs look like this" rather than an old→new byte pair — so
it is idempotent and reaches the target from the pristine 3-tab form, the abbreviated 4-tab form, or
the target itself. It re-walks the result and asserts that **no unrelated property changed**, that the
captions round-trip, and that the padding is clean.

`re_tools/pfs.py`'s `UNIT_OWNERS` now includes `(0x20, "copper")` so the tooling reports it.

### ⚠ Scanner caveat (cost me a wrong answer once already)

`capstone.disasm()` is a **generator that stops at the first undecodable byte** — disassembling a
whole CODE section in one call silently covers only the first handful of instructions and reports
**zero** hits for everything. A field scan must resync (`while pos < len: for i in disasm(code[pos:])
… else pos += 1`) and must be **validated against a field you know is read** (tier +0x2F) before any
zero is believed. Also note such a scan tracks *any* `[reg+0x40]` load, so results mix in other
classes — good for proving presence, weak for proving absence.
