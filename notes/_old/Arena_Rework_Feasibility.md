## 1. What the Arena is today

### 1.1 Purpose

An Arena is a single-hex, unowned `TStructure`. Park an army on it, double-click, and you get a
dialog listing your ≤8 units with a checkbox each; ticking units and pressing Select pays gold and
**promotes each ticked unit to its next medal instantly**. Description string (Dict/Release.txt
:7565): *"Training at the arena increases the skills of your units."*

**Training cost per unit = 5 × (XP needed for the next medal)** —
`TArena.UnitTrainCost @0x557D6704`:

```
if unit is THero            -> -1   (heroes cannot be trained here)
if unit is not TUnit        -> -1
if TUnit.GetRank(unit) == 3 -> -1   (already max rank)
else  cost = (unit.GetNextLevelExperience() - unit.GetExperience()) * 5
                 vmt +0x164                        vmt +0x15C
```

`TArena.ExecuteTrainUnit @0x557D6768` is literally `SetExperience(GetNextLevelExperience())` then
`Changed()` (vmt `+0x160`, `+0x90`). Heroes take the same code path in `ExecuteTrainUnit` but are
filtered out by `UnitTrainCost` returning −1 before it, so they are never eligible.

### 1.3 TArena's VMT — what is overridden and what is free to override

VMT `0x557D6240`, last slot `+0x1EC` (`CanRaze`). **TArena overrides only 4 slots**; everything else
is inherited from `TStructure`, and because each Delphi class owns a *physical copy* of its VMT with
`.reloc` entries on every slot, repointing any slot to a cave is **arena-only and rebase-safe** —
this is exactly the `TTower` slot-`0x1B0` trick the raze-battle feature already uses successfully.

## 2. The decisive precedent — a structure CAN run a real battle

`TExplorationSite` is the blueprint, and the raze rework already transplanted it once.

`TExplorationSite.ExecuteSearch @0x557C1A20`:

```
army = field.vmt[0x80](0x20217)                 ; the visiting army
if site[+0x34].Count == 0 -> vmt[0x1F8](ExecuteSearchDone, 1, 3)   ; walkover
LockGameOverEvent @0x55776830
combat = TAoWHSMap.CreateCombat(map, 0x202B0)   ; 0x202B0 = fast, 0x220110 = tactical
vmt[0x1F4] = SetupCombat(combat, army)
TCombat.LockExecuted @0x55728100
run vmt slots 0x68 / 0x70 / 0x64 / 0x74 / 0x6C  ; 0x64 returns 1 = went modal (tactical only)
build TCombatEventLog, SetCombatLogbook @0x55728F2C, TEventLogbook.AddEvent @0x557FDB90
  (show only if map[+0xA5]==actor and player[+0xA7]==0, i.e. local human)
TCombat.UnlockExecuted @0x55728104 ; DestroyCombat @0x557787F8 ; UnlockGameOverEvent @0x55776774
```

`TExplorationSite.SetupCombat @0x557C1960`:

```
combat[+0x2C] = CombatExecuted   (the completion callback)
combat[+0x30] = site             (the context passed back as EAX)
combat.vmt[0x60] = TCombat.Setup @0x55727310 (attacker player/team, defender player/team, coords)
TCombat.AddArmy   @0x55727804  (visitor,  side 0, at site coords)
TCombat.AddArmyEx @0x557279D0  (defenders, side 1, -1,-1,-1 = NO map field)
combat[+0x40] = 1
```

`TExplorationSite.CombatExecuted @0x557C1894` → survivors of player 0 (independents) go back into the
hidden army, then `vmt[0x1F8] = ExecuteSearchDone(type, combat[+0x14])`. **Result byte
`combat[+0x14] ∈ {3,6}` = attacker won** (3 = defender conquer-objects wiped, 6 = walkover;
4 = attacker wiped, 5 = mutual, 2 = unresolved, 8/9 = wall/objective standing).

**This is live and working here.** `TTower` VMT slot `0x1B0` reads `0x5580C910` in the live DLL
(vanilla: `0x5575FFC8`) — `cave_towerraze`, whose header records *"STAGE 1 already CONFIRMED WORKING
in-game 2026-07-10"*: build a hidden `TDefendersArmy`, construct a fast `TCombat`, run it
synchronously, take a callback, log it. See `Raze_CombatPredictor_Analysis.md` §12b and
`build_scripts/build_razebattle_tower.py`.

Roster generation, also already used by four vanilla callers:

* `TUnitIndexListCollection.GetRndCollection @0x557835B4` (`GetCollectionCount 0x557834D8`,
  `GetU 0x5578352C`) — pick a random roster template out of a collection.
* `FillWithRandomUnits @0x5575B160(list, army, maxLevel=4, budget, flags)` — fills an army to a
  strength budget; `GenerateRazeDefenders` then trims to 8 units.
* Budget convention: exploration sites use **`tier × 50`** (tier 1..3, plus 4 = "Random").
* `TDefendersArmy` class-ref `0x557C1274`; `TUnitIndexList.Create 0x5578506C` (class-ref `0x557110D8`).
* **Every** `TStructureResource` carries `+0x5C` = a raze-defender `TUnitIndexListCollection` and
  `+0x60` = a budget — including `TArenaResource`. Whether the arena's `+0x5C` is populated in
  `Release.hss` is **unverified**; if it is empty, `GetRndCollection` returns −1 and nothing spawns.

## 3. Element-by-element verdict

### 3.1 "Three categories — weak / medium / strong — with the stacks described"

**Feasible. Medium-heavy — this is the biggest chunk, and almost all of it is UI.**

**Training is abolished (user, 2026-07-30)**, which simplifies this further than first estimated:

* The entire training path is **replaced, not extended** — `UnitTrainCost`, `ExecuteTrainUnit`,
  `CanTrainUnits`, `TrainUnits`, and `TEnterArenaEventLog`'s `Train` / `CanTrain` /
  `GetSelectionInfo` / `SetSelection` all become dead. Keep `TrainUnits` as a *reading* reference for
  the token pattern; nothing needs to call it.
* **`TE[+0x18] == 1` can be reused** rather than minting command 2 — nothing else issues an arena TE.
* **All eight checkboxes are free**, so the three category rows have room and `SelectionInfoLbl` +
  `SelectionLbl` can both carry roster text. The earlier worry about needing two dialog modes is gone.
* ⚠ Housekeeping: `build_copper_medal.py`'s byte at `0x557D673A` (`cmp al,2`→`cmp al,3` in
  `UnitTrainCost`) becomes **dead code**. Harmless, but note it in that doc so a future session does
  not go looking for a live effect.

*Engine side (easy).* Nibble-pack the payload into `TE[+0x20]` exactly as the raze work does
(`player | category<<4 | combatType<<6`; player ≤ 11 fits the low nibble). `TArena.ExecuteTE
@0x557D67D8` is already an override, so this is a cave on its body — **no VMT change and no new TE
field**. `TrainUnits` (§1.4) is the ready-made template for the
`CanX → GetBusy → CreateTE/SetupTE → TokenManager` action, so MP correctness comes for free.

*Roster — resolved, and it needs no game data at all.* `FillWithRandomUnits @0x5575B160` takes a
plain **`TUnitIndexList`**, not a collection: `GenerateRazeDefenders` merely *builds* one from a
collection first (`GetRndCollection` → `GetCollectionCount`/`GetU` → `TIntegerList.Add`). So the cave
can create a `TUnitIndexList` (`Create @0x5578506C`, class-ref `0x557110D8`), fill it from a
**hardcoded index table in the build script**, and call `FillWithRandomUnits(list, army, maxLevel=4,
budget, flags)` with the tier budget. `GenerateRazeDefenders`'s tail then trims to 8 units.

That is the recommended route, because the data alternatives are all worse:

* `arenaResource[+0x5C]` is created **empty** by `TStructureResource.Create @0x5576046C`
  (`+0x60` also defaults to `0x32` = 50) and is only populated from `Release.hss` via ReadWrite tag
  `0x1C` (`rwStreamProc` with `TUnitIndexListCollection.Load/SaveFromStream`). Unverified whether the
  Arena's is populated at all.
* There is **no editor form that edits it** for a plain structure: `AoWEd.exe`/`AoWDevEd.exe` carry
  `TExplorationSiteResourceEditForm` (DefendersSheet) and `TDungeonResourceEditForm`
  (`TUnitIndexGrid DefendersGrid`, PrisonersSheet) — both editing the *site* collections at `+0x64` /
  `+0x68` — but no `TStructureResourceEditForm` and nothing arena-specific. Making the roster
  editable would mean growing `TArenaResource` (0x64 → 0x68) **and** building an editor form.
* Patching the collection into `Release.hss` directly is possible (repair the CRC afterwards with
  `re_tools/hss_crc.py` — see [[aow1-hss-crc]]) but buys nothing a build-script table doesn't.

For a curated mod a hand-picked arena roster is arguably better than a random collection anyway, and
retuning it is a one-line edit in the build script.

*Storage — the real decision.* Two options:

| | store 3 armies | store a seed |
|---|---|---|
| what persists | three `TDefendersArmy` objects on the arena | 1 dword seed + 1 flag byte |
| instance grow | `0x30` → ~`0x40` | `0x30` → `0x38` |
| `ReadWrite` | 3 object properties (`stream.vmt[0x0C]`) | 2 scalar properties |
| survivors persist between visits | yes (site-style) | no |
| description shown == stack fought | trivially | **only if regeneration is deterministic** |

**Recommendation: the seed.** `TExplorationSite.GenerateDefenders` already shows the idiom — install
`System.RandSeed` from a stored value, then draw. Store one seed, derive all three rosters from it,
regenerate the chosen one at fight time; the dialog's description and the actual stack are then
guaranteed to match, and nothing but 5 bytes has to serialise. (Cost: you cannot have weakened
stacks persist across visits — which the proposal doesn't ask for, since the arena empties.)

*UI (the bulk).* Repurpose `TArenaDlg` rather than build a new form — adding controls means adding
published fields to the form class, which is painful; **hiding and relabelling existing ones is
cheap**. `U1..U3` become the three category rows, `U4..U8` hidden, `SelectionInfoLbl` carries the
roster description, `SelectBtn` becomes "Fight". That is a DFM edit (offset `0x7471C`) plus a
rewrite of `U1Change` / `SelectBtnClick` / `MapViewDraw` (≈1.7 KB of `AoW.exe`). Per
[[aow1-copper-medal-design]], byte-exact DFM edits beat VCL caves; per [[aow1-party-random-generator]]
there is also a proven recipe for building a VCL dialog from a cave if the repurposing gets too tight.

To *describe* a stack you need unit names: generate the `TUnitIndexList`, resolve each index through
the unit resources, and format. Note the description must be computed on the **client** that opens
the dialog, from the stored seed — do not send it over the wire.

### 3.2 "Fought as player vs independents" — **tactical** (user decision, 2026-07-30)

**Feasible.** Straight transplant of §2. Independents = **player index 0**
(`TCombatObject.GetPlayer @0x557268E4` reads `obj[+0x45]`; `CombatExecuted` filters on `== 0`); a
fresh `TDefendersArmy` defaults to player byte `+0x12 = 0`, team `+0x16 = 0xFF` — **do not overwrite
these**. Wire war relations the way `TStructure.SetupRazeDefenderAG @0x5575FE0C` does only if the
stack must be hostile outside the fight; a hidden arena stack never is.

Tactical = `CreateCombat(map, 0x220110)`; slot `0x64` returning 1 means the combat went **modal** and
the callback in `combat[+0x2C]` fires later. `CombatExecuted` is written once and serves both modes —
it branches on `IsClass(TFastCombat)` — so choosing tactical costs nothing in the reward code.

**The dialog-freeze history, precisely** (`Raze_Dialog_Freeze_Fix.md`): the freeze was an **AI razing
its own city** under simultaneous turns with `Combat Resolve Mode = Ask`, which popped the
quick-vs-tactical dialog on the *local human*, a non-participant. **City rebellions were explicitly
cleared** — §2 of that doc shows `cave_rebellion` passes `owner|0x50` and `cave_lootbattle`
`owner|0x90`, so their choice nibble is always ∈ {1,3} and never 0 (= Ask); they cannot reach the
dialog at all. Fixes are applied and tactical raze battles work in play, so the path is proven — but
it is proven *with the hardening*, and the arena must copy the hardening, not vanilla.

⚠ **`TExplorationSite.Search @0x557C1EBA` is an unguarded landmine and is exactly what one would
naively copy.** It raises a `TCombatTypeRequestEventLog` with **no type, seat or participant check**,
and is safe in vanilla only because `TStructure.ExecuteAI` is a stub so the AI never searches. A new
arena that reuses `Search`'s pattern verbatim re-opens the same hole. Copy `cave_typechosen`'s
hardened contract instead:

1. **Producer must set `eventlog[+0x24] = 1`** (request-live), plus `+0x19` = acting player,
   `+0x1A` = defender. Vanilla's own handler `RequestCombatTypeCallBack @0x557489CC` bails on
   `[+0x24]==0` — copying the *check* without the *set* silently swallows every choice (this exact
   half-a-contract regression happened and is written up in §8 of that doc).
2. **Read `[+0x18]` as a BYTE** (`movzx`). The bytes above it are live (`+0x19` player, `+0x1A`
   defender, `+0x1B/1C/1D` x/y/l); a dword read turns Cancel into a bogus pick and can re-raise the
   dialog forever.
3. **Take the player from `eventlog[+0x19]`, never from a global.** The dialog is asynchronous; a
   global races with any other battle raised in between.
4. **Before `CreateCombat`:** require `map[+0x120] == 0` (else `CreateCombat` raises *"Combat already
   created"*), and require the local seat to actually be a participant. Check *before*, not after —
   a tactical `CreateCombat` has already disabled the map turn timer by then, and declining to run it
   modal is precisely what leaves the world frozen with sound running.
5. **Add the SEH frame** razebattle Stage 1 deliberately omitted. A throw that skips `DestroyCombat` /
   `UnlockGameOverEvent` leaves `map[+0x120]` non-null for the rest of the session, after which every
   later battle raises.

Distribution note: map VMT slot `0x12C` = `TAoWHSMap.TriggerExecuteEventLog @0x55776624` with `CL=1`
is an **immediate, re-entrant notify with no player filter**, and `TCombatTypeRequestEventLog` is
absent from `GetSimultaneousWindowPopupEvents`, so the simultaneous-turn popup mask cannot suppress
it. Filtering is the producer's job, always.

*Suggested staging anyway:* get it working fast-combat-only first (synchronous, one sitting, no
dialog, no async), then switch the mode constant and add the type request. The combat construction
and the reward code are identical either way, so nothing is thrown away.

### 3.3 Rewards: flat **+100 / +200 / +300 gold** and **+5 / +10 / +15 XP to every survivor**

*(Design revised by the user 2026-07-30 — was per-slain-unit gold and a ×4 XP multiplier.)*

**Easy, and a large de-risking.** Everything now happens in **one place, the completion callback**.
Concretely this deletes three of the riskiest items from the earlier plan:

* **no edit to `cave_5580C390`** — that cave belongs to an existing feature, and rewriting another
  feature's cave in place was the only cross-feature surgery in the whole design. Gone.
* **no per-death hook** on `DoDamage` / `DestroyObject`, so no need for the combat-callback-pointer
  trick to recognise an arena battle, and no per-hit cost.
* **no interaction with `TFastCombatUnit` vs `TCombatUnit` duplication** on the damage path.

*Gold* — one call: `TPlayerList.GetPlayers @0x557544D0` off `map[+0x140]`, gold is `player[+0xC4]`,
write via `TPlayer.SetGems @0x55751F38`. Amount from the category nibble in the TE.

*XP to survivors* — enumerate the combat data at callback time, exactly as `CombatExecuted` does:

```
data = combat[+0x0C]
n    = TCombatData.GetCount   @0x55728BEC
obj  = TCombatData.GetObjects @0x55728BF8 (data, i)
  IsClass(obj, [0x55715A54] = TCombatUnit VMT 0x55715A94)   <-- MANDATORY, see below
  obj.GetPlayer() == arenaPlayer            ; vmt, reads obj[+0x45]
  (obj[+0x47] & 1) == 0                     ; still in the fight
  unit = obj[+0x4C]                         ; the strategic TUnit
  unit.vmt[0x160]( unit.vmt[0x15C]() + N )  ; SetExperience(GetExperience() + 5|10|15)
```

Four traps on that loop, all of them already paid for elsewhere in this project:

* ⚠ **Type-gate before reading `+0x4C`.** `+0x4C` is a `TCombatUnit`-only field; `TCombatWall`
  (instsize 0x50) reuses the offset for *packed bytes*, so on a wall it reads as a small integer that
  passes a NIL check and then access-violates on `mov ecx,[eax]`. This exact defect caused two
  separate game freezes here (`Raze_Dialog_Freeze_Fix.md` §8 and §9 — `build_combatlog_dll.py` and
  `build_replaylog.py` each had a copy). Arena battles are wall-less today, but that is luck, not a
  guarantee. Use `System.@IsClass @0x557010C0`. Note `TFastCombatUnit` **derives from**
  `TCombatUnit`, so the gate correctly admits both.
* ⚠ **`+0x47` bit 0 means "out of the fight", not strictly "dead".** Verified: both
  `TCombatUnit.DestroyObject @0x557256F0` (`0x557257B4` = 0x01) and `TCombatUnit.Surrender
  @0x557257B8` (`0x55725828` = 0x01) set the **same** bit. So a surrendered unit is filtered out
  along with corpses. Probably what you want; call it out if not.
* ⚠ **Use the virtual slots, not `TUnit.SetExperience` directly.** `unit.vmt[0x160]` dispatches to
  `TUnit.SetExperience @0x557828B4` for units and `THero.SetExperience @0x55787674` for heroes;
  `TUnit.SetExperience` also drives the rank-up → `UpdateDefaultAbilities` path, which is what makes
  a medal actually grant its ability (see [[aow1-leadership-disable-rootcause]]). A raw field write
  would award XP that never becomes a medal.
* ⚠ **Alternative worth knowing:** walk the visiting army's `TUnitList` instead
  (`army[+0x1C]`, count `vmt[0x54]`, `TUnitList.GetUnit @0x5578309C`) — dead units are already gone
  from it. Fewer traps, but it assumes the army is pruned by callback time, which the combat-data
  walk does not have to assume. Prefer the combat-data walk; keep this as the fallback if the walk
  turns out to include stale entries.

*MP determinism* — the callback runs inside combat resolution, so gold and XP land identically on
every peer, same as the exploration site's own reward. **The item roll does not come free**: seed it
from the map RNG first, exactly as `TItemExplorationSite.Generate` does
(`RandSeed = TAoWHSMap.Random(map, 0xFFFFFF)` before `GenerateItem`), or peers diverge.

*Still-valid machinery from the superseded per-kill design*, kept because it is reusable and was
verified this session: the sole kill-XP site is `cave_5580C390`, hooked from
`TCombatObject.DoDamage @0x55726B1C` at `0x55726B6F`, reached only past
`test byte [victim+0x47],1` (`0x55726B43`) plus two no-XP ability filters (`0x81`, `0x80`); it
computes `attackerXP += min(lvl,10)² + victimXP/2` where vanilla did `+= victim.GetLevel()`.
`TUnit.GetUnitLevel @0x55782B8C` = `unitResource[+0x2F]`, combat-side `vmt[0xA0]`.
`[combatObject+8]` is the owning `TCombat`, so `[[obj+8]+0x2C] == our callback` is a stateless
"is this an arena battle?" test if one is ever needed again — better than a BSS flag, which is the
bug class `AI_Raze_v4_Leak_Analysis.md` and §7 of the freeze doc both had to chase.

**Gold is paid on a win only** (user, 2026-07-30) — gate the payout on
`combat[+0x14] ∈ {3,6}`, the same test `ExecuteSearchDone` uses. This closes the
"sell your army for 300 gold" exploit that flat-on-loss would have opened. The XP half needs no gate:
lose ⇒ no survivors ⇒ no XP, automatically.

**Easy.** Verbatim from `TItemExplorationSite`:

### 3.5 "Empties when fought; 10 % chance to refill each turn"

**Feasible, moderate — this is the only element needing new persistent state.**

*Serialisation is the risk, and it checks out.* AoW's save format is a **property table indexed by
numeric id**, not a positional blob: `Engine.TPropertyTable` with `FindOffset @0x5550FE70`, and
`TEReadStorageStream.rwByte/rwByteEx/rwData` all do `if FindOffset(id) == -1 -> skip the read`.
So **adding new tagged properties is backward- and forward-compatible**: old saves simply lack the
tag and the field keeps its default. Stream vtable (deduced from the call sites, consistent across
`TStructure` / `TExplorationSite` / `TWizardsTower`): `+0x0C` object, `+0x1C` `rwData(ptr,size,id)`,
`+0x2C` integer, `+0x30` byte, `+0x38` bool, `+0x44` `rwByteEx(ptr,default,id)`.

*Plan:*
1. `TArena` instance size `0x557D6224`: `0x30` → `0x38`. Delphi's `InitInstance` zero-fills, so
   **make `0` mean "full / battles available"** and every pre-existing arena is correct on load with
   no `Create` override.
2. Repoint VMT `+0x018` (`ReadWrite`) to a cave: call `TStructure.ReadWrite @0x5575E658`, then
   `rwByte(self+0x30, id)` for the empty flag and `rwData(self+0x34, 4, id)` for the seed.
   ⚠ **Property ids share one namespace down the whole inheritance chain.** Observed in use:
   `TMultiHexMO` 3 & 4, `TStructure` 0 / 0x62 / 0x63 (`TExplorationSite` 5 & 6 and `TWizardsTower`
   0x1E–0x21 are siblings, not conflicts). Take ids ≥ `0x70`, and enumerate `TMapObject.ReadWrite`
   and `TMultiHexMO.ReadWrite @0x5560AAB8` fully at build time before committing.
3. Repoint VMT `+0x174` (`NewDay`, currently an empty `ret`) to a cave: if empty,
   `TAoWHSMap.Random(map, 10) == 0` → refill (fresh seed from `TAoWHSMap.Random(map, 0xFFFFFF)`).
   **`TAoWHSMap.Random @0x5577827C` is the MP-safe RNG** — it installs `map[+0x230]`, draws, and
   writes the advanced seed back, so every peer walks the same sequence. `NewDay` is a synchronised
   once-per-game-day event (same guarantee `TExplorationSite.NewDay` relies on).
   ⚠ Advancing the shared map RNG once more per arena per day shifts every later consumer — harmless,
   but a game started with this patch will not reproduce an unpatched draw sequence. Same caveat as
   `build_sitedefender_vary.py`.
4. Surface the state: override `GetDescription` (VMT `+0x144`) so an empty arena reads differently,
   and/or let `CanDblClick` still open the dialog so the player is told "empty" rather than getting
   a dead double-click.

⚠ **"each turn" is ambiguous.** `NewDay` = once per **game day**; `NewTurn` (VMT `+0x178`) fires
**per player**, so with 6 players a 10 % roll would refill ~47 % of the time per day. Decide which
you mean — the write-up assumes game day.

### 6.3 The battle

`cave_fight` is entered by `jmp` from inside `TArena.ExecuteTE`, builds **its own stack frame** (so
ExecuteTE's managed-string locals and its `[ebp-5]` result byte are untouched), and exits by jumping
to ExecuteTE's own epilogue `0x557D6967` with ESP/EBP exactly as found. Verified ExecuteTE's frame
tail at `0x557D6991`: `mov al,[ebp-5]; pop edi; pop esi; pop ebx; mov esp,ebp; pop ebp; ret`.

Sequence, transplanted from the confirmed-working `cave_towerraze`:
bail if `EMPTY` → container `= self[+4].vmt[0x80](0x20217)` → `TArmy.Create(TDefendersArmy)` →
`TUnitIndexList` from the roster table → `RandSeed = arena[+0x34]` →
`FillWithRandomUnits(list, militia, 4, budget, 7)` → trim to 8 → bail if empty →
bail if `map[+0x120] != 0` → `LockGameOverEvent` → `CreateCombat(0x202B0)` → `combat[+0x30]=self`,
**`combat[+0x2C]=0`** → `Setup` (vmt `0x60`, 9 stack args) → `AddArmy(side 0)` +
**`mov byte [party+0x18],0`** → `AddArmyEx(side 1, −1,−1,−1)` → `combat[+0x40]=1` →
`Lock/0x68,0x70,0x64,0x74,0x6C/Unlock` → latch `combat[+0x14]` → `TCombatEventLog` filed and shown
to the local human → `DestroyCombat` → `UnlockGameOverEvent` → set `EMPTY`.

Three decisions worth knowing:
* **`combat[+0x2C] = 0` = no completion callback.** Safe: `TCombat.UnlockExecuted @0x55728104`
  fires it only when `word [combat+0x2E] != 0` — that word is the *high half of the callback
  pointer*, so a null pointer is a no-op. Fast combat is synchronous, so the result is read inline.
  Stage 3 replaces this with a real callback.
* **Wall-less**, via `mov byte [party+0x18],0` on `AddArmy`'s returned party — the only input to
  `TCombat.Initialize`'s wall branch. Keeps stage 3's survivor walk away from the `TCombatWall`
  `+0x4C` alias that froze the game twice.
* The **militia army is leaked** per battle, deliberately, exactly as the raze cave does: a
  never-touched `TArmy` cannot fault, whereas the unverified `TDefendersArmy` destructor could
  double-free combat-owned units.

weak = Wolf 237, Giant Frog 236, Wild Boar 235, Black Spider 222, Kobold 167, Goblin Spearman 183 ·
medium = Minotaur 173, Werewolf 190, Troll 184, Giant Slug 60, Scorpion 27, Great Eagle 234,

### 6.4 Rewards (stage 3 — APPLIED, UNTESTED 2026-07-31)

Done **inline** in `cave_fight`, not from a completion callback: the fast path is synchronous, and
the insertion point — after `UnlockExecuted`, before `DestroyCombat` — is exactly where vanilla's
`CombatExecuted` → `ExecuteSearchDone` fires, so `combatData` is alive and the ordering matches the
engine's own. Stage 5 moves this block into a real callback for the tactical/async path.

| reward | amount (weak / medium / strong) | gate |
|---|---|---|
| XP to every **surviving** unit of the arena player | +5 / +10 / +15 | any outcome |
| Gold | +100 / +200 / +300 | **win only** — `combat[+0x14] ∈ {3,6}` |
| Random item, dropped on the arena hex | 1 | **strong only, and only on a win** |

Tables live at `0x558149C0` (budget), `0x558149D0` (gold), `0x558149E0` (XP) — three dwords each,
indexed by category, so retuning is a one-line edit + re-run.

**⚠ The XP award must come from the STRATEGIC side, not from the combat data.** The first
implementation walked `combat[+0x0C]` (`TCombatData`) filtering on `IsClass(TCombatUnit)` +
`GetPlayer()` + `!(obj[+0x47] & 1)`. Gold worked, XP silently did nothing (observed in-game
2026-07-31). Root cause, from the Ghidra decompile of **`TCombatUnit.Finalize @0x55724D44`**:

```c
if (obj[+0x47] & 1 || hasAbility(0x82) || hasAbility(0x83)) { (*vmt-4)(obj,1); return; }  // Destroy
if (phase == 2) {
    party = GetParty(...);
    if (party == 0 || party[+0x0C] != -1) {          // party HAS a map field
        TAbstractUnit.Place(obj[+0x4C], ...);        // put the survivor back on the map
        (*vmt-4)(obj,1);                             // ...then DESTROY the combat object
        return;
    }
    ...                                              // off-map party: left alone, NOT destroyed
}
```

`vmt−4` is Delphi 3's `vmtDestroy`. So by the time our block runs — after slot `0x6C` — **every
combat object belonging to a party with a map field has been freed**, i.e. all of the player's.
Only the off-map militia party survives (its `party[+0x0C] == -1`, from `AddArmyEx`'s `-1,-1,-1`).

That is precisely **why vanilla's `TExplorationSite.CombatExecuted` only ever touches
`GetPlayer()==0` objects** — those are the only ones still alive at that point. A detail that reads
like a thematic filter is actually a lifetime constraint.

The fix re-fetches the army from the arena's field (`self[+4].vmt[0x80](0x20217)` → `[+0x1C]`,
owner-checked against the arena player) and walks it with `vmt[0x54]` / `TUnitList.GetUnit`, then
`unit.vmt[0x15C]() + N` → `unit.vmt[0x160]()`. Finalize has just re-placed the survivors and the
dead were removed during combat, so the list *is* the survivor set — no type gate, no player filter
per unit, no combat objects, and no `+0x4C` dereference anywhere.

One semantic worth knowing: a **stalemate (result 2) still pays XP**, because the spec is "XP to all
surviving units" with no win condition — only gold is win-gated.

`GenerateItem` turned out **not** to construct an item: it builds a weighted candidate list from
`TItemControl`'s existing unplaced items and returns one, or 0 when the pool is exhausted. So the
item is already registered and `TItem.PlaceOnMap` alone completes the award — no ownership fix-up,
no leak. Seed `System.RandSeed` from `TAoWHSMap.Random` **first**, as `TItemExplorationSite.Generate`
does, or MP peers diverge.

⚠ **keystone trap, hit and fixed here:** `push 0xFFFF` assembles as `6A FF` = `push imm8 -1`
(= `0xFFFFFFFF`), not `68 FF FF 00 00`. As `GenerateItem`'s value cap that would reject every item
and award nothing, silently. The cave goes through `EAX` instead, and `build_all()` asserts the
encoding. Audited 2026-07-31 across all 73 `build_*.py`: no other script pushes a `>imm8` literal
that keystone truncates. See [[aow1-keystone-push-imm8-trap]].

### 6.4b Category selection — stage 4a (APPLIED, UNTESTED 2026-07-31)

**Zero changes to `AoW.exe`.** The vanilla dialog already does everything needed; only the meaning
of the checkboxes changes. `TArenaDlg.U1Change @0x0044C450` is one shared handler for all eight
boxes, keyed on `Sender[+0x0C]` (the box index). It calls `SetSelection(old | bit)` when ticking and
`SetSelection(old & ~bit)` when unticking, **then re-reads all eight box states back out of
`ev[+0x1C]`**, and finishes by calling `CanTrain` (to enable `SelectBtn`) and `GetSelectionInfo`
(to fill `SelectionInfoLbl`). So owning those three DLL exports owns the whole interaction.

| # | site | VA | becomes |
|---|---|---|---|
| E1 | inside `TArena.Enter`, before Show | `0x557D6C3F` | `ev[+0x1D] = 7` if stocked, `0` if empty |
| E2 | `TEnterArenaEventLog.SetSelection` | `0x557D6DA4` | radio: keep only the newly-set bit |
| E3 | `TEnterArenaEventLog.Train` | `0x557D6DAC` | issue the arena-battle TE with the category |
| E4 | `TEnterArenaEventLog.CanTrain` | `0x557D6E28` | stocked **and** something chosen |
| E5 | `TEnterArenaEventLog.GetSelectionInfo` | `0x557D6EA4` | the per-category description text |

All five are `.reloc`-clean (verified). Caves: `avail` 31 B @`0x55814600`, `radio` 38 B
@`0x55814640`, `train` 263 B @`0x558146A0`, `cantrain` 25 B @`0x558147C0`, `selinfo` 65 B
@`0x55814800`, string table @`0x558149F0`, literals @`0x55814A00`.

*Radio without touching the exe.* `SetSelection` computes `new = mask & avail & ~old`; if anything
just turned on it keeps **only the lowest set bit** (`x & -x`), otherwise it takes the mask as
given (an untick). `U1Change`'s write-back then unchecks the other boxes by itself.

*E1 is what makes three categories always offered.* Vanilla filled `+0x1D` with one bit per
*trainable unit*, so a 1-unit stack could only ever tick box 1. Now it is the constant `7` — and
`0` when the arena is fought out, which greys every box and, through E4, the Select button too.

*E3 replaces the token dance rather than reusing `TrainUnits`.* It mirrors it
(`GetBusy` → `CreateTE` → `SetupTE` → `TokenControl.vmt[0x10]`) but writes
**`TE[+0x20] = player | category<<4`** and skips the unit-id list, which the arena branch of
`ExecuteTE` no longer reads. Reusing `TrainUnits` was rejected: it takes the player in `BL` and
uses that same register for `GetPlayers`/`GetBusy`, so a packed byte would have looked up player 33.
The nibble packing is the raze rework's convention, and `cave_fight` already unpacks it
(`& 0x0F` → player, `>>4 & 3` → category) — that half shipped in stage 2.

*E5 assigns literal AnsiStrings*, built with the Delphi `[refcount −1][len][chars][NUL]` header so
`@LStrAsg` just stores the pointer and never tries to free it. Pointers are stored as link-time VAs
and rebased with the load delta.

It returns **one line, selected by category** (`INFO_LINES`), or "Choose an opponent." when nothing
is ticked. `DISPLAY_UNITS` is kept in step with the first unit named on each line
(Wolf / Minotaur / Basilisk — strong was Hydra 240 before the wording was fixed).

⚠ **`TAOWLabel` IS STRICTLY SINGLE-LINE — and an earlier note here claimed otherwise.** The claim
rested on `ImageLib.ParseFontText @0x552147A0`, which really does split on `0x0A`/`0x0D`/`0x20` —
but it has **no callers in any code section**. It is dead code. The renderer `TAOWLabel.Draw`
actually reaches is `0x55214320`: a per-character loop that indexes the font's glyph table
(`font[+0x48]`) by byte value and **silently skips anything with no glyph**, CR and LF included.
A CRLF-joined string therefore draws as one long line and runs off the panel edge — observed
in-game 2026-08-02, where only the first sentence appeared, itself clipped.

**To get all three offers visible at once you need three real label controls.** That means cloning
`TAOWLabel` components in the DFM, which cannot grow in place (§6.4e), so the resource must be
relocated and grown — the `build_herodlg_columns.py` technique. Worth noting: the clones would need
**no class growth and no code access**, because the three row captions are static text that can live
entirely in the DFM; only `SelectionInfoLbl` needs a published field, and it already has one.

### 6.4c Box artwork — stage 4b, DPL-only (APPLIED, UNTESTED 2026-07-31)

First in-game look (screenshot 2026-07-31) showed two problems: every box drew one of the player's
**own** units, and `SelectionInfoLbl` **clips at both ends** — a 90-character line came out as
*"- hydras, giants, basilisks, beholders, red dragons.  Reward: 300 gold and ar"*. It is centred and
fits roughly 76 characters, so `DESCRIPTIONS` are now ≤ 40.

**How the box is painted** (`0x0044C24C`, reached from `TArenaDlg.U1PreDraw @0x0044C634`):

```
if GetCount(eventlog) <= index -> draw NOTHING and return
unit = GetUnit(eventlog, index)
frame  = ImageLib.Get(lib, unit.vmt[0xFC]() & 0x7F)   ; vmt+0xFC = TUnit.GetAlignment -> frame colour
         ShowClipped(frame, ...)
sprite = unit.vmt[0x1A4]()                            ; TUnit.ShowEx -- the actual unit art
if !(ev[+0x1D] >> index & 1) -> ShowClipped(lib image 7)   ; the "disabled" cross
```

⚠ `vmt[0xFC]` is **`GetAlignment`, not an image index** — it only selects the coloured frame. The
sprite comes from `ShowEx`, so **the box needs a real `TUnit`**, which is what makes this DPL-only
instead of an exe cave.

`cave_avail` therefore builds one `TUnit` per category (`DISPLAY_UNITS` = Wolf 237, Minotaur 173,
Hydra 240) with `TAbstractUnit.Create @0x5577EB28` + `TUnit.SetUnitResource @0x55782BE4` — the pair
`FillWithRandomUnits` itself uses — and stores the raw pointers in `ev[+0x20]` (`F1` makes `GetUnit`
return them directly instead of via `FindUnit`; `F2` frees them in the event log's destructor).

**Exactly three, on purpose.** The painter skips any index ≥ `GetCount`, so a three-entry list makes
boxes 4–8 draw *nothing at all* — no frame, no sprite, no cost number. A six-entry list (two units
per category, for the overlapping look) lit up boxes 4–6, which are not categories.

Safe to draw an unregistered unit: `TAbstractUnit.ShowEx @0x557812EC` reads the GFX resource,
ability flags, `+0x25` and the global animation counter `AoWHSMap[+0x40]` — **no player deref and no
map-field deref** (checked in Ghidra before applying), so a unit that was never `Activate`d and has
no id renders fine.

⚠ **Bug found and fixed 2026-07-31 — a rejoining hook must resume PAST its own displaced bytes.**
In-game: *"Access violation at address 00EB6D3E in module 'AoWEPACK.dpl'. Read of address
00000020"*, on pressing Train, sometimes with a freeze. The module is rebased, but the crash RVA
must end in `6D3E`, and enumerating the 30 candidate load bases put exactly one inside a plausible
function: **`Arena.TEnterArenaEventLog.Destroy +0x6`** = `0x557D6D3E`, i.e. `mov eax,[esi+0x20]`
with `ESI` null-ish. That is our own hook site. The prologue is

```
557D6D38 53       push ebx        \
557D6D39 56       push esi         |  E9 rel32 covers 0x557D6D38..0x557D6D3C
557D6D3A 8B DA    mov ebx,edx      |
557D6D3C 8B F0    mov esi,eax     /   <-- 5 bytes ends MID-INSTRUCTION here
557D6D3E 8B 46 20 mov eax,[esi+0x20]
```

`F2` displaced 5 bytes but resumed at `0x557D6D3A` — which after patching is **inside its own
`E9`'s rel32 operand**. The cave jumped into its own jump, ran the displacement bytes as code, and
arrived at `mov eax,[esi+0x20]` with `ESI` wrecked. Fixed by displacing **six** bytes
(`E9 rel32` + `NOP`), replaying all four prologue instructions, and resuming at `0x557D6D3E`.
The cave now also saves `EAX`/`EDX` at entry and restores them before the replay.

`build_arena.py` asserts this at build time for every rejoining hook (`RESUMING_HOOKS`): the resume
address must not fall inside the displaced range. The other two rejoining hooks were checked and are
correct — `E1` displaces `0x557D6C3F..43` and resumes at `0x557D6C45`; `D5` jumps to a far epilogue.

### 6.4d Empty state — map sprite and dialog (APPLIED, UNTESTED 2026-07-31)

**Investigation: how dungeons / exploration sites change look with status.** There is no
"animation state" machinery. A site simply asks for a **different image sequence**, and the whole
mechanism is five lines — `ExploreS.TExplorationSite.GetTerrainTypeImage @0x557C1848` (VMT `+0x12C`):

```c
if (GetExplored()                            /* vmt +0x1F0 */
    && map[+0x174] != 0                      /* in-game, not the editor */
    && TImageSequenceList.GetImageSequence(resource[+0x24], idx + 100) != 0)
        idx += 100;
return idx;
```

⇒ **the convention is "base index + 100 = the alternate look"**, and the `GetImageSequence` guard
means it degrades silently to the normal sprite when the resource has no such entry. Because the
alternate is an *image sequence*, it can be animated — that is all "alternating animations" means
here. `TDungeon` and `TItemExplorationSite` inherit this and only override `GetExplored`.

Separately, `TStructure.GetTerrainTypeImage @0x5575E6A0` already switches whole image sets by
status: **razed → `0x16/0x17/0x18`**, **under construction → `0x19/0x1A/0x1B`**, else the terrain
default. Exploration sites bypass that entirely; the Arena does not (see below).

**G1 — `TArena` VMT `+0x12C` → `cave_terrimg`.** Same shape, keyed on `arena[+0x30] & EMPTY`
instead of explored. If an alternate exists at `idx+100` it returns it; otherwise it **falls through
to `TStructure.GetTerrainTypeImage`**, so a razed or under-construction arena keeps its proper
rubble/scaffold imagery — strictly better than the exploration-site version, which loses those.

⚠ **This is a no-op until the art exists — by design, and the slot is ready.** To make an emptied
arena look different, add an image sequence at **base index + 100** to the Arena resource's
`TImageSequenceList` (`resource[+0x24]`) in the resource editor. Nothing else changes: the cave
already looks it up every frame and falls back cleanly while it is absent, and because the entry is
a *sequence* it may be animated. No rebuild of `build_arena.py` is needed when the art lands.

**G2 — `TArena.Enter` → `cave_enterempty`.** Hooked over the 6-byte `je` after `CanEnter`
(`0x557D6BC3`, pure rel32, no reloc). When the arena is fought out it shows
*"The arena is empty. New challengers will arrive in time."* through the map's own notification slot
— `map.vmt[0x110](map, string)`, the same one `ExecuteTE` uses for "%d units trained" — and returns
without building the event log, so the battle dialog never opens. Three exits: message + `Enter`
returns true (`0x557D6C55`), normal path (`0x557D6BC9`), `CanEnter` failed (`0x557D6C59`).

### 6.5 ⚠ Replay assert: `AoWAb.PAS line 46181` — a PRE-EXISTING engine defect

**Symptom** (2026-07-30, first arena battle): rewinding the fast-combat record raises
*"Assertion failure (D:\AoWDev\AoWE\inc\AoWAb.PAS, line 46181)"*. Non-fatal — but it greys out the
replay transport arrows for the rest of the session.

**The assert, located exactly.** The filename literal is at VA `0x5576596C`; only two asserts
reference it, and line 46181 (`0xB465`) is the one at `0x557658DC`, inside
**`AoWE.TUnitEnchantmentAbility.Expand @0x55765894`**:

```
557658C6  GetAbilityData(owner, self[+0xC])
557658D4  jne  ...                          ; already has data -> fine
557658D6  cmp dword ptr [edi+0x18], 0       ; edi = owner unit
557658DA  jg   ok
557658DC  mov ecx, 0xB465 ; ...  call @Assert     <-- line 46181
```

So the assert is **`ownerUnit[+0x18] > 0`**, and `+0x18` is the **unit id** (the same field
`TArena.Enter` collects and `TUnitControl.FindUnit` resolves).

**Why an arena defender fails it — and why every other off-map defender does too:**

* `TAbstractUnit.Create @0x5577EB28` initialises `[self+0x18] = 0xFFFFFFFF` (**−1**).
* An id is only ever assigned by `TUnitControl.RegisterUnit @0x5577E988` (`if id == -1 ->
  GetFreeID`), and **its sole caller is `TAbstractUnit.Activate @0x5577FBC7`** — i.e. a unit gets an
  id only when it is brought onto the map.
* Hidden defenders are *never* activated: they are joined with `AddArmyEx(..., -1,-1,-1)` = no map
  field. Their id stays **−1**, which fails `> 0`.

⇒ **Any code path that expands a unit enchantment onto an unregistered defender asserts.** That is
identical for exploration-site defenders, dungeon prisoners, raze militia and arena militia — the
arena patch neither introduces nor worsens it. It surfaces on *replay* because the replay re-drives
the strategic-side `Expand`, whereas the live fast combat carries the enchantment on the
`TCombatUnit` (the `Expand` vs `ExpandAbility` split in [[aow1-status-debuff-stat-cache]]).

**Confirm it is vanilla in 30 seconds:** search a *guarded* exploration site (one with defenders),
then rewind that battle's replay. Same assert = vanilla, and the arena is exonerated.

**Fixed by `build_scripts/build_enchant_assert.py` — APPLIED 2026-07-30, UNTESTED** (backup
`.pre-enchassert`, layer 48). **One byte**: `0x557658DA` `7F`→`EB`, turning the `jg 0x557658F0` that
guards the assert into an unconditional `jmp` to the same target. Verified in the live DLL:

```
557658D6  cmp dword ptr [edi+0x18], 0
557658DA  jmp 0x557658F0                <- was  jg 0x557658F0
557658DC  mov ecx, 0xB465 ; ... call @Assert     (intact, now unreachable)
557658F0  xor ecx, ecx    ...
```

**Retest:** fight an arena battle in which something gets enchanted (the weak roster's Black Spider
is the reliable source), then rewind the replay — the transport arrows must stay live. Then repeat
on a guarded exploration site to confirm the same fix covers the vanilla case.

That is not merely "good enough", it is *exactly* the scoped fix, because `id <= 0` ⟺ unregistered:

* `TUnitControl.Create @0x5577E850` starts the id counter at **1** (`mov [esi+8], 1`), and
  `GetFreeID @0x5577E95C` wraps back to **1**, never 0 — so a registered unit's id is always ≥ 1.
* Therefore no reachable legitimate case can fail `id > 0`, and skipping loses no debug coverage.
* Nothing after `0x557658F0` reads `[edi+0x18]`; the code just builds the ability-data record.

**Sibling sweep:** of the **56** `call System.@Assert` sites in `AoWEPACK.dpl`, exactly **one** is
guarded by the unit-id invariant (`cmp dword [reg+0x18],0 ; jg` within 26 bytes) — this one. The
other AoWAb.PAS assert (line 46175 @`0x557658B3`) is the `owner is TAbstractUnit` type check and is
deliberately left alone.

Kept as its own script rather than folded into `build_arena.py`: it repairs exploration-site,
dungeon, raze **and** arena replays together, and each feature's `--undo` stays single-purpose.

Rejected alternative: registering the militia via `Activate` to give it real ids — the arena militia
is deliberately leaked (§6.3), so that would leak *registered* units into `TUnitControl` where
`FindUnit` and the per-day passes would find them.

### 6.6 Test procedure (to promote this to CONFIRMED)

Needs a hand-made map — **no shipped scenario contains an Arena**. In AoWDevEd place an Arena, put a
stack of your own on its hex, save, load in `AoW.exe`.

1. **Double-click the Arena** → the vanilla training dialog opens. Every checkbox should be
   *enabled* (D4 makes every unit cost 0), including gold-medal units and heroes, which vanilla
   greys out. That alone proves D4 is live.
2. **Tick any unit, press Select** → a fast battle should resolve against a weak independent stack
   (wolves/boars/spiders), with a combat-log entry you can replay. *This is the stage-2 milestone.*
   The category comes from `TE[+0x20]`'s high nibble, which vanilla `TrainUnits` leaves 0 = weak.
3. **Double-click it again** → dialog opens, Select does nothing. The arena is now `EMPTY`.
4. **Save and reload** → still empty. That proves the new `ReadWrite` properties round-trip.
5. **End turns** → roughly 1 day in 10, the arena restocks and step 2 works again.
7. **Stage 3 rewards** (note the roster is always *weak* until stage 4, so expect the tier-0 row):
   note your gold before the fight → **+100 on a win, nothing on a loss**; every unit that survived
   should gain **+5 XP** (visible on the unit card / medal progress); **no item** — the item is
   strong-tier only and unreachable until stage 4 wires the category nibble. To exercise the item
   path early, temporarily set `ROSTERS`/`BUDGETS` aside and change the `and edx, 3` category clamp,
   or simply wait for stage 4.
6. Watch for **"Combat already created"** on any later battle — that would mean a throw escaped
   between `CreateCombat` and `DestroyCombat` (no SEH frame; see §6.5).

If step 2 does nothing at all, the likely causes in order: the militia rolled empty
(`FillWithRandomUnits` rejected the indices), `map[+0x120]` was non-zero, or the field selector
`0x20217` returned no container. All three are single `jz` bails in `cave_fight`.
