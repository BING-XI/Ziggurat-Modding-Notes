# Spellcasting — Three Extra Features (Investigation, 2026-07-08)

> **Offsets here are class-keyed and canonical in [`Ghidra_Field_Catalogue.md`](Ghidra_Field_Catalogue.md)** (generated by `re_tools/ghidra_fields.py`, bounds-checked against measured instance sizes). If this file and the catalogue disagree, the catalogue was measured and this was not. ⚠ An offset means nothing without its class — five aliasing traps were found on 2026-08-03 where one offset meant different things on sibling classes.


Feasibility / RE investigation for three requested extensions to the (already-working) unit-hero
spellcasting mod. **INVESTIGATION ONLY — nothing patched, no build script run with `--apply`.**
Builds directly on `Unit_Spellcasting_INDEX.md` and its linked docs; read those first for the
existing caves, cluster layout (`unit+0x7C..+0x93`), and the exe `cave_bookfilter`.

All AoWEPACK.dpl addresses are preferred-base VAs (base `0x55700000`, rebased at runtime → DLL caves
must be position-independent). AoW.exe / AoWCompat.exe are fixed-base `0x400000` (absolute OK).
Evidence: Ghidra decompilation of AoWEPACK.dpl + `re_tools/pescan.py iatrefs` on AoW.exe.

## 0. Shared primitives discovered (reused across all three features)

**Unit instance fields (TUnit / grown TAdjustableUnit)**

| Offset | Type | Meaning | Witness |
|---|---|---|---|
| `+0x18` | int | unit ID (network/FindUnit key) | `TUnitEnchantmentAbility.Expand` writes it to `ench+0x18` |
| `+0x24` | byte | owner **player index** | used all over (`GetPlayers(...,unit+0x24)`) |
| `+0x3d` | byte | **current movement points** | `TUnit.GetMovePoints` @ `0x5578276c` = `[unit+0x3d]` |
| `+0x3e` | byte(signed) | **current hit points** | `TUnit.GetHitPoints` @ `0x557827c0`; `SetHitPoints` writes it |
| `+0x40` | ptr | **TUnitResource\*** (per-species flyweight) | `TUnit.GetUnitLevel/Type/TransportCapacity` all deref it |
| `+0x80` | byte | casting points (mod cluster) | prior work |
| `+0x84/+0x88/+0x8c` | int | spell-in-progress / progress / mana-required | prior work |

**TUnitResource fields (`unit+0x40`)**

| Offset | Type | Meaning | Witness |
|---|---|---|---|
| `+0x04` | ptr | resource **list** object; `list.vtable[0x84]()` = **UnitResourceIndex** (the *stable* per-species ID, e.g. 226 Fire Elemental) | `build_firefeed.py` `cave_fireheal` |
| `+0x2f` | byte | **unit level** | `TUnit.GetUnitLevel` @ `0x55782b8c`; `TUnitResource.GetUpkeep` = `[+0x2f]+1` |
| `+0x30` | byte | unit **type** enum | `TUnit.GetUnitType` @ `0x55782808` |
| `+0x38` | ptr | ability data (transport) | `TUnitResource.GetTransportCapacity` |
| `+0x44` | byte | **base transport capacity** | `TUnitResource.GetTransportCapacity` @ `0x55784d24` |

**Position-independent "which species is this unit" idiom** (from `cave_fireheal`, eax=unit):
```asm
mov edx,[eax+0x40]        ; resource
test edx,edx / jz ...     ; null guard (heroes/walls)
mov ecx,[edx+4]           ; resource list
mov eax,ecx / mov ecx,[ecx]
call dword ptr [ecx+0x84] ; -> eax = UnitResourceIndex (226, 228, ...)
```
Works from both the DLL and the exe (pure vtable dispatch). **This is the canonical table key.**

**Unit vtable slots** (already documented): `+0xa0` `GetUnitLevel`, `+0xD0` `GetMaxHP`,
`+0xE4` `SetHitPoints`, `+0x128/12C/130` casting points, `+0x144` `GetAbilityLevel`,
`+0x148` `GetAbilityEnabled`. New this pass: **`+0xa0` = `GetUnitLevel`** (confirmed: `TCombatUnit.GetLevel`
and `TSummonedAbility.GetDefaultManaUpkeep` both call `unit.vtable[0xa0]` and treat it as "level").

# FEATURE 1 — Per-unit intrinsic spellbook (cast regardless of research)

**Verdict: FEASIBLE, but HARD (moderate). Confidence 72%.** No fundamental blocker; the cost is one
non-trivial engineering problem (inserting into the spell list from the exe) plus a new data table.

### Current mechanism (how the casting book is assembled)
- The human "Cast Global Spell" book is filled by the exe calling **`TPlayerMagicControl.ListSpells`
  @ `0x5577d148`** directly (5 sites, already wrapped by `cave_bookfilter` @ exe `0x0060C0A8`).
- `ListSpells(magic, &collector, mask)` iterates the **player's researched spell-ID list at
  `magic+0x30`** (a `TIntegerList`), resolves each via `TSpellControl.GetSpell`
  (`AoWHSSet+0x84`, @ `0x55779ac8`), category-filters on `spell+0x22` vs `mask`, and appends with
  `TSpellList.Add`. **Research is the only gate here** — the list is literally "what the player
  researched." (`THero.ListSpells` @ `0x557879f0` just forwards to the player's `ListSpells`; the
  exe does not call it.)
- **KEY ENABLER — casting itself does NOT require research.** `THero.CanCastSpell` @ `0x55789710`
  checks only: not-already-casting, **player mana ≥ `CastingMana`**, then the spell's own
  `CanActivate` (`spell.vtable[0x68]`). There is **no "is this researched?" check** anywhere on the
  cast path (`CanCastSpell` → `CastSpell` → TE). Research gating lives *entirely* in the book. So if
  an intrinsic spell is made to *appear* (or is cast by ID directly), the existing machinery will
  cast it — subject only to mana, the spell's target validity, and the mod's **M2 tier gate**
  (`level ≥ spell+0x21`) injected at `0x5578974D`.

### Is there an existing per-unit spell field? — NO
The unit resource has no spell-list field (checked `TUnitResource` accessors). Intrinsic spells are
a genuinely **new mapping**: `UnitResourceIndex → [spellID,…]`, hard-coded in the mod (keyed by the
species idiom above — the same 226/228-style index the fire mod uses).

### Proposed patch approach
Two parts:
1. **Data:** a static table `{UnitResourceIndex → spellID list}` (e.g. Yaka Avatar → Fireball). Lives
   in a cave (exe `.sc` section or DLL cave).
2. **Injection — extend `cave_bookfilter`** (exe, it already has the caster at `[EDX+8]` and runs
   after `ListSpells`): compute the caster's `UnitResourceIndex`, look it up in the table, and for
   each intrinsic `spellID` **that isn't already present**, resolve `TSpellControl.GetSpell` (exe
   **imports it**, IAT `0x0045DD90`) and insert it into the collector's `TSpellList`.

**The crux = inserting into the list.** `pescan iatrefs` confirms AoW.exe imports
`TSpellList.GetCount/GetSpell/Clear/Delete/Create/SortOnLevel` **but NOT `TSpellList.Add`**
(Add exists in the DLL @ `0x5577a03c`, just isn't imported). Three viable routes, in order of
cleanliness:
- **(a) Manual `TList` append in the cave.** The inner list is `TSpellList[+4]=TList`;
  `TList[+4]=items[]`, `[+8]=count`, `[+0xC]=capacity`. If `count < capacity` (Delphi TList
  over-allocates, so usually true right after `ListSpells`), just `items[count]=spellPtr; count++`.
  Guard the `count==capacity` case by skipping (accept "intrinsic hidden when list is exactly full")
  — a low-risk MVP. `cave_bookfilter` already rewrites this exact array during compaction, so the
  code is a 6-instruction extension.
- **(b) Call `TSpellList.Add@0x5577a03c` directly via the rebase-delta trick** — compute AoWEPACK's
  load delta from any existing import thunk and call the export with **no import-table changes at
  all**. See `Party_Random_Generator.md`. *(Superseded the original suggestion here of import-table
  surgery, which is unnecessary now.)*
- **(c) DLL handshake:** exe cave stashes `caster` into a fixed exe global; a DLL cave wrapping
  `ListSpells` reads it (exe base is fixed → DLL can use the absolute address) and appends via the
  in-module `TSpellList.Add`. Most robust for growth, most moving parts.

Recommended: **(a)** for a first cut, escalate to **(b)** if the capacity edge case matters.

### Interactions / risks
- **M2 tier gate.** An intrinsic spell above the caster's Spellcasting level is blocked by the M2
  cave at cast time even if shown. Either give intrinsic casters adequate Spellcasting level, or add
  an M2 bypass for table-listed (species,spell) pairs.
- **Combat book is NOT separate** (corrected 2026-07-30). `TSpellBook` in AoW.exe serves all three
  tabs off the same five `ListSpells` sites — `TSpellBook+0x222` is the mode byte (0 = Combat,
  1 = Unit, 2 = Global; see `CombatBtnClick@0x004306C8` / `UnitBtnClick@0x00430634` /
  `GlobalBtnClick@0x004305A8`), and the per-site `System.@SetElem` category mask is what differs.
  So `cave_bookfilter` already covers strategic **and** combat. `TTacticalCombatUnitHS.SelectSpell`
  (AoWTCPCK.dpl, exe IAT `0x0045EBBC`) is the combat-side *targeting* handoff, not the list builder.
- **AI** lists via `ListSpells` directly and won't see exe-side additions (same limitation the M4
  Cosmos filter already accepts).
- The unit still needs the **Spellcasting ability** (for points + to open the book). "Intrinsic
  spells" = Spellcasting-unit + this table; it doesn't grant casting to non-casters by itself.

# FEATURE 2 — HP or MV cost for casting (instead of / in addition to points)

**Verdict: FEASIBLE for "in addition to points"; HARDER for "instead of". Confidence 85% / 60%.**
The deduction chokepoints are known and the HP/MV fields are single bytes.

### Current mechanism (where cost is deducted)
Two deduction sites, both already mapped:
- **Instant cast → `THero.CastingDone` @ `0x557893e8`** (dispatched from `TSpell.CastingDone`
  @ `0x557794bc`, arg `param_3 = cost`). It does, when not cheating:
  ```c
  SetMana(playerMagic, mana - cost);      // player mana pool (magic+0x24)
  *(char*)(unit+0x80) -= (char)cost;      // unit casting points
  ```
- **Multi-turn cast → `THero.ExecuteStartCasting` @ `0x55789130`:** pays the **full mana up front**
  (`SetMana(mana - CastingMana)`), copies current points into progress (`+0x88`), zeroes points
  (`+0x80`). Per-turn accrual (mod's `cave_unit_newturn`) then refills points into progress.

`cost` originates from `CastingMana` @ `0x557894ec` = `spell+0x14` (×2 if
`GetSphereManaDoubled(spell+0x20)`); target-independent.

### The HP / MV fields (deduction targets)
- **HP:** `unit+0x3e` (signed byte). **Do not write it raw** — use the virtual
  **`SetHitPoints` (vtable `+0xE4`, `TUnit` impl `0x557827c4`)**, which clamps to `[0, GetMaxHP]`
  and calls `UpdateDefensiveStrength`. Read via `GetHitPoints` (vtable, `[unit+0x3e]`).
  ⚠ `SetHitPoints` clamps at **0** (never negative) — HP cost can drive a unit to 0 (dead-ish) but
  won't kill cleanly; gate the cost so `HP - cost ≥ 1` (or accept 0-HP as "can't afford").
- **MV:** `unit+0x3d` (byte), `TUnit.GetMovePoints` @ `0x5578276c`. No clamping accessor; a cave
  `sub byte [unit+0x3d], k` with a `≥0` guard is fine (movement bytes are treated as signed
  elsewhere per the move-predictor notes — guard against underflow).

### Proposed patch approach
- **"In addition to points" (recommended, clean):** one cave hooking **`THero.CastingDone`
  @ `0x557893e8`** right after the existing point/mana deduction. Read `GetHitPoints`/`GetMovePoints`
  via vtable, subtract a cost `k` (flat, or `= cost`, or scaled), write back MV directly / HP via
  `SetHitPoints`. Because `CastingDone` is the shared instant sink, this covers combat + strategic
  instant casts in one place. **Mirror in `ExecuteStartCasting`** for multi-turn (deduct HP/MV at
  channel-start alongside the up-front mana), or accept "multi-turn charges points only."
- **Scope:** `CastingDone` is shared with heroes. To charge only *units*, gate the extra deduction
  with the `IsClass(caster, THero)` idiom (skip if hero) or the `cave_iscaster` pattern; or apply to
  all casters by design choice.

### "Instead of points" — why it's harder
Points aren't just deducted, they **gate affordability**: instant-vs-multi-turn is chosen by
`cost ≤ points` in `CastSpell`, and `CanCastSpellInstantly` reads points. To make HP/MV *the*
currency you must also redirect those reads (several sites) or the unit will still be throttled by
points. Doable but multi-site and easy to desync. Recommend delivering "in addition" (points remain
the throttle; HP/MV is an extra sacrifice), which is the low-risk 85% path.

### Risks
- Byte width: HP/MV/points are all bytes — large `k` underflows; clamp.
- `SetHitPoints`'s `UpdateDefensiveStrength` recompute is cheap and correct; prefer it over raw
  writes so combat stats stay consistent.
- MP determinism unaffected (deduction rides the existing TE/turn path).

# FEATURE 3 — Enchantment cast cost / upkeep scaled by target size / level / capacity

**Verdict: UPKEEP scaling FEASIBLE (85%); CAST-COST scaling HARDER (55%, Needs-more-RE for the
combat path). SIZE is a dead axis — use LEVEL or TRANSPORT CAPACITY.**

### The three candidate attributes on the target unit
| Attribute | Source | Notes |
|---|---|---|
| **LEVEL** | `unit.vtable[0xa0]` = `GetUnitLevel` = `[resource+0x2f]` | Best axis. Already what gold upkeep (`GetUpkeep`=`level*2`) and summon upkeep (`(level+1)*2`) scale by. |
| **TRANSPORT CAPACITY** | `TUnit.GetTransportCapacity` @ `0x55782ba0` (max of Transport-ability level and `resource+0x44`) | Meaningful only for transports; niche. |
| ~~SIZE~~ | `TAbstractUnit.GetUnitSize` @ `0x5577f184` **returns constant 1** | AoW1 units are all 1 hex — **not a usable scaling axis.** |

**Proven scale-by-level template already in the engine:** `TSummonedAbility.GetDefaultManaUpkeep`
@ `0x557bb1b8`: `IsClass(u,TUnit) ? (u.vtable[0xa0]()+1)*2 : 0`. Copy this shape.

### Current mechanism — unit-enchantment upkeep
- A unit enchantment is a **`TUnitEnchantmentAbility`** granted to the unit. `Expand`
  @ `0x55765894` (target unit = `param_2`) creates a `TUnitEnchantment` (via vtable `+0x11c`
  `CreateEnchantment`) and sets `ench+0x18 = unit ID` (the binding) and `ench+0x1c = abilityID`.
- `TEnchantment.Create` @ `0x5577beac` initializes **`ench+0x10 = 1`** (upkeep, int),
  `ench+0xc = 0xff` (source player). **Upkeep field = `ench+0x10`**, set/changed via
  `TEnchantment.SetUpkeep` @ `0x5577c10c` (which also fires `PlayerMagicControl.Update`).
- `TAbstractUnit.RegisterEnchantments` @ `0x5577f29c` registers each unit enchantment with the
  owning player's magic control.
- **Player-wide total: `TPlayerMagicControl.GetManaUpkeep` @ `0x5577c964`** = `Σ ench+0x10` over the
  enchantment list at `magic+0x3c`, **plus** `TGlobalMagicControl.GetEnchantmentUpkeep`
  @ `0x5577e424` (global enchantments). So scaling any unit-enchantment's `+0x10` flows straight
  into the player's upkeep automatically.
- Per-unit display path: `TAbstractUnit.GetManaUpkeep` @ `0x5577fc90` reads ability `0x9b`'s
  data → `enchData+0x10 → +0x10`.

### Current mechanism — cast cost
`CastingMana(spell)=spell+0x14` — **takes only the spell, not the target.** But at the *resolution*
site **`TUnitSpellTE.Process` @ `0x5577ab24`**, the target unit *is* in hand (`piVar6`) right before
`TSpell.CastingDone(spell, caster=TE+0x2c, cost=TE+0x1c)`. So target-scaled cast cost is reachable
*for strategic unit-target spells* by adjusting the cost there — but combat unit-enchants use a
different path (`TCombatSpellCaster`), and the cost is pre-committed in the TE.

### Proposed patch approach
- **Upkeep scaling (recommended — clean, one hook):** cave at the tail of
  **`TUnitEnchantmentAbility.Expand` @ `0x55765894`**, where the target unit (`param_2`) and the
  fresh enchantment (`ench`, from vtable `+0x11c`) are both live. Compute
  `upkeep = base × f(param_2.GetUnitLevel())` (or `GetTransportCapacity`) and either write `ench+0x10`
  directly (before `RegisterEnchantments`) or call `SetUpkeep(ench, upkeep)` (cleaner — triggers the
  recompute). Because `Expand` belongs to `TUnitEnchantmentAbility`, this **only** affects unit
  enchantments; globals/summons are untouched. `GetManaUpkeep`'s sum then scales for free.
- **Cast-cost scaling (partial):** hook `TUnitSpellTE.Process` @ `0x5577ab24` to scale the `cost`
  passed to `CastingDone` by `piVar6`'s level. Covers the strategic unit-spell path; **does not**
  cover combat-cast enchants → flag as Needs-more-RE (locate the `TCombatSpellCaster` cost commit).
- **Identify "which enchantment"** if you want per-spell base values: `ench+0x1c` = abilityID.

### Risks / unknowns
- Vanilla unit-enchant upkeep defaults to **1** (`TEnchantment.Create`); confirm whether specific
  enchants override it before multiplying (multiply the effective `+0x10`, don't assume 1).
- `SetUpkeep` calls `PlayerMagicControl.Update` — safe, but ensure the target unit's fields are valid
  at the hook (they are: `param_2` is the just-validated unit).
- Save/load: upkeep lives on the enchantment object, which is already serialized with the unit — a
  scaled value persists as-is (no extra persistence work), but a *re-derived* value on load would
  need the same cave to run at deserialize (prefer storing the computed value).
- Cast-cost combat path (`TCombatSpellCaster`) not yet traced — real gap for "more expensive to
  cast" in tactical combat.
