## Architecture

```
AoWEPACK.dpl (rebases!)                          AoW.exe / AoWCompat.exe (fixed base 0x400000)
┌──────────────────────────┐                     ┌───────────────────────────────────────────┐
│ cave_loggen / loggenex   │  absolute writes    │ .clog section @ VA 0x60D000 (RWE):        │
│ (tail hooks on           │ ───────────────────>│  ring buffer: hdr 0x20 + 64 slots × 64 B  │
│  TDamageCA.Generate/Ex)  │                     │  clone VMT 'TCombatLogWin' + method table │
│ format line via IDStr/   │                     │  RCDATA dir v2 (82 entries) + new DFM     │
│ IntToStr/LStrCat thunks  │                     │  cave_createwin (+1 CreateForm)           │
└──────────────────────────┘                     │  cave_drain (memo OnUpdate handler)       │
                                                 │  cave_hotkey (toggle visibility)          │
                                                 └───────────────────────────────────────────┘
```
- DLL formats **complete text lines** at capture time (it has all combat data); exe only drains slots into
  the memo's TStringList. No cross-module data reaching; the DLL writes to fixed exe VAs (exe never
  rebases), guarded so it's inert in any other host process (AoWDevEd.exe also loads the DLL!).
- **AoW.exe ≡ AoWCompat.exe byte-identical except ONE byte** (foff 0x3BB7C / VA 0x43C77C: 0x0F vs 0x05) —
  one address table, byte-identical patches for both. (The "different builds" caveat is about AoWDevEd.)

### v7 (2026-07-17) — replay dim fix + FINISHING THE CUT STEP-BUTTONS
**Replay dimming SOLVED — it is not a shader, it is PRIORITY.** `TAOWWinManager.SetOverPri @aowInt
0x598060AC` sets a threshold (`mgr+0x110`, prev at `+0x10c`); every modal screen calls it with its own
priority and **everything BELOW the threshold renders dimmed**. Call sites confirm it's the engine's one
universal "dim the background" mechanism (city screen, spellbook, production, target-selection,
`TFastCombatWindow.FastCombatWindowDestroy` restoring it, …). The replay's `FCWin` is **Priority=55,
Modal=True**; our log was 11 ⇒ dimmed with the map/minimap/Events. **Fix: our Priority 11 → 56** (just
above the line; still above the unit card's 10 in combat; no spatial overlap with the centred replay).

**PrevSeqBtn / NextSeqBtn were unfinished dev content — now completed.** Evidence from the TFASTCOMBATWINDOW
DFM: **no `OnClick` at all** (hence unclickable), `Visible=False` (so what's on screen is the RCtrlPnl art
behind them, not the buttons), `ILIndexLit=0` (no hover art), and a **copy-pasted PlayBtn tooltip**
("Plays battle from current position"). Intent is unambiguous from the names + the `SequencePositionSld`/
`SequenceSpeedSld` pair: **step the replay BACK/FORWARD one action ("sequence")** — vs PlayBtn (continuous)
and InitialView/FinalView (jump to start/end). Ironically the abandoned feature is the perfect companion to
a combat log (step one blow, read the line).
**Implemented with NO resource surgery** — `OnClick` is a plain TMethod on the button object, so we poke it
at runtime from a hook on `FastCombatWindowCreate @0x435244` (the form's OnCreate; fires once, after the
DFM has built the children; displaced bytes `53 8b d8 b2 01` = push ebx/mov ebx,eax/mov dl,1 → cont
`0x435249`). Field map (from `TAOWButton.CheckMouseUp` dispatch @aowInt 0x598117BE:
`mov edx,ebx(Sender); mov eax,[ebx+0x13c](Data); call [ebx+0x138]` ⇒ **`Handler(eax=Data, edx=Sender)`**):
`+0x74 CaptureInput · +0x75 Visible · +0x124 ILIndexUp · +0x12c ILIndexLit · +0x134 btn-dirty ·
+0x2c validated-dirty · +0x138 OnClick.Code · +0x13c OnClick.Data`.
`cave_fcwinit` wires both buttons: OnClick.Code→our cave, OnClick.Data→the window, **Lit := Up** (so they
get hover art instead of looking dead), Visible=1, then dirties `+0x134`/`+0x2c` to force re-setup.
**The step handlers reuse the game's own machinery** (`cave_prevseq`/`cave_nextseq`, delta -1/+1):
click sound `0x455DFC(eax=[[0x45A420]], edx=0)` → viewer `[self+0x144]` guarded by `test byte[viewer+4],1`
→ `TCombatViewer.Pause 0x402254` (stepping implies paused) → `SetFPos 0x4031CC(eax=[self+0xEC] sld,
edx=pos±1)` — **SetFPos clamps internally** against Min/Max/NumberVisible, so no bounds logic needed —
→ `SequencePositionSldChange 0x436218(eax=self)` which does `TCombatViewer.SetPosition(sld.Pos)` + refresh.
Replay model reference: `[self+0xEC]` SequencePositionSld (pos `sld+0x148`) · `[self+0x144]` TCombatViewer ·
SetPosition `0x402244(eax=viewer, edx=pos)` · GetEndPosition `0x402234` · Play `0x40224C` · Pause `0x402254`.

### ⚠⚠ v3's SILENT WIRE-FORMAT BUG — the single most important lesson here (fixed in v4)
**Symptom in-game:** first line correct, then **every later unit shows the FIRST unit's name or a blank**,
**duplicated line fragments**, and **`Runtime error 216` / shcore EAccessViolation on exit**.
**Cause:** the ring is a wire format split across TWO build scripts. v3 widened `SLOT_SZ` 64→128 in the DLL
(**writer**) but left the exe (**reader**) at 64 with a hard-coded `shl eax,6`. It fails *silently*: slot 0
lands (both agree at offset 0) and every later line is read from the MIDDLE of an earlier line — the
"duplicate fragment" was literally the tail of line 0. The byte at that offset is a text character, so the
reader takes it as the shortstring length and **over-reads past the buffer ⇒ heap corruption ⇒ the exit
crash**. Past ~32 lines the writer would also have overwritten the clone VMT (ring 0x1020 but writes needed
0x2020).
**Fix:** `SLOT_SZ=128` both sides; `SLOT_SHIFT` **derived** (`SLOT_SZ.bit_length()-1`) never hard-coded;
ring `0x20+64*128 = 0x2020` (slots now end 0x60F020, clone VMT moved to 0x60F060 — no overlap); and
`_check_wire()` in the DLL script greps the exe script's constants and asserts they match, so the two can
never drift again. **Rule: any shared-memory contract split across two build scripts must be asserted, and
BOTH scripts re-applied together after any change.**

### v4 (2026-07-16) — stock-DFM edit: FUTILE, removed (v5 proved why); one parser trap kept
v4 tried to shrink the stock unit card by editing the TTCUNIT DFM in place. v5's live measurement proved

## 0. AoW1 COMBAT MATH — fully decoded (2026-07-16, agent; reusable far beyond the log)

### To-hit: a pure linear formula, no table
**`hit% = clamp(50 + 10×(attack − defense), 10, 90)`**, i.e. −3→20% · 0→50% · +3→80% · **+4 and up→90% (pinned)**.
- `AoWE.HitRole @0x55725D98` (EAX = attack−defense → AL bool): `diff*10 + 50`, clamp 10..90, `RandInt(100)`.
  **RNG = VCL30 `System.@RandInt` (thunk 0x55701080) = Delphi's global RandSeed — NOT the MP-lockstep
  `TAoWHSMap.Random @0x5577827C`.** (Vanilla quirk; relevant to any lockstep reasoning.)
- `AoWE.HitRoleProbability @0x55725DCC` (EAX=diff → float32 in st(0), 0..1): same curve ×0.01 (const
  @0x55725E08). Exists but NOT worth calling from a cave (float → needs a writable temp + fistp);
  28 bytes of inline integer math is cheaper. `TouchRoleProbability @0x55768130` /
  `CombatTouchRoleProbability @0x55768234` are strategic-unit wrappers over it — not usable for the log.

### The damage roll — `AoWE.ExecuteDamageRole @0x55725EAC` (EAX=damage, EDX=diff → AL)
```
if damage <= 0 -> 0
R = RandInt(20)                     ; call @0x55725EBC, R lands in ECX @0x55725EC1
if R <= 1   -> 0                    ; @0x55725EC8  FLAT 10% AUTO-MISS ("fumble"), ignores attack
if R >= 18  -> damage               ; @0x55725ED1  FLAT 10% AUTO-MAX ("critical"), BYPASSES to-hit
T = 10 - 2*diff
if T > R    -> 0                    ; @0x55725F05  normal miss
damage = 1 + round((damage-1)*(R-T)/(18-T))   ; @0x55725EEB..F02
```
The R≤1 / R≥18 branches are exactly what produce HitRole's 10%/90% clamps — the two functions agree by
construction (verified identical over diffs −10..+10). **Only 4 callers; no class overrides `+0x110`/`+0x114`
(TCombatObject/TCombatUnit/TFastCombatUnit all inherit) ⇒ universal.**
- **No critical-hit mechanic in the ID'd sense**: zero `crit`/`Critical` matches in symbols OR raw bytes of
  AoWEPACK/AoWTCPCK/aowInt/AoW.exe; no multiplier/double-damage branch anywhere. The user's "critical" =
  the **R≥18 auto-max branch** (flat 10%, no multiplier, never exceeds normal max).
- P(max damage) ≥10% and rises with diff (≈15% at +1..+5, 20% at +6..+10) **purely from formula rounding** ⇒
  `rolled == max` CANNOT identify the auto-max branch (would ~2× over-report). Must capture R itself.
- **Gameplay insight:** past +4 diff accuracy is pinned at 90%, but damage keeps improving (T≤0 pulls low
  rolls up; at +10 the minimum non-miss damage is 3, not 1). Excess attack converts accuracy→damage silently.
  ⭐ **Fully quantified in `Excess ATK minimum damage bonus.md`** (2026-08-18) — per-diff tables, the
  damage-rating dependence (the gain is **zero** at damage 1, +50% at damage 12), the reachable range
  (⚠ **vanilla clamps ATK/DEF to [1,10] so vanilla `diff` cannot exceed +9** — the dramatic numbers are a
  Ziggurat-only regime), city walls being hard-coded **DEF 0**, and the fact that the AI models the curve
  (`DMDCtoDV @0x55725E30`) while the UI shows nothing. It also flags two traps that bite here:
  **weapon strikes never call `HitRole`** (this function *is* the hit test), and the `T≥18` guard at
  `0x55725EE6` — omitted from the pseudocode above, correctly — is **dead code**; `cmp esi,ecx / jg` at
  `0x55725EE2` is what zeroes the middle rolls at diff ≤ −4.

### Which defensive stat the roll uses — ⚠ FIXES A LIVE BUG
`TCombatObject.ExecuteDamageRole @0x557269F0` (ret 4; EAX=target, EDX=attack, ECX=damage, [ebp+8]=types)
uses **`[vmt+0x70] GetDefense`**. `ExecuteDamageRoleEx @0x55726A6C` (ret 8; [ebp+8]=extra byte,
[ebp+0xc]=types) uses **`[vmt+0x74] GetResistance` iff extra byte == 1** (@0x55726A99), else GetDefense.
⇒ the **GenerateEx path (Turn Undead, combat spells) rolls vs RESISTANCE**. The v1 log printed
`GetDefense` unconditionally = WRONG for those lines. Both return a SIGNED byte in AL — `movsx`.
Both roles also: (a) return 0 early if `types & ~GetImmunityTypes(vmt+0x7c) == 0` (fully immune);
(b) HALVE the result if all remaining types are in `GetProtectionTypes(vmt+0x80)`, with round-half-toward-zero
(`inc/sar/jns/adc` — correctly handles NEGATIVE damage, which the fire-heal mod depends on).
**Immunity is free at the hook: `word[CA+0x11] == 0` ⇒ fully immune** (set @0x55729C88 / @0x55729D04) —
print "immune", skip the math, no virtual call.

### Roll-capture design (to report crit/fumble precisely)
Repoint the 5-byte `call RandInt` @**0x55725EBC** → tiny cave: `call RandInt; store EAX -> SCRATCH_R; ret`
(caller already set EAX=20 and consumes the return in EAX). Store R in the **DLL's own BSS**, not the exe
ring, so the cave needs no host guard and stays inert under AoWDevEd. The Generate/GenerateEx tail then
classifies and **resets SCRATCH_R = -1**, so a Generate with no roll (immune / damage≤0 → returns before
RandInt) correctly reads -1 = "no roll". Ordering verified safe: `ExecuteDamageEffectsRole` does NOT call
the global roll (only 4 callers), and TStrikeCA.Generate's side-effect `HitRole`s run AFTER the base tail.
**BSS scratch allocation** (page slack; BSS vsize ends 0x558FA231 but the page is mapped RW to 0x558FAFFF):
`0x558FA800` simfly · `0x558FA804`/`0x808`/`0x80C` raze caves · **`0x558FA810` = SCRATCH_R (this feature)** ·
0x558FA814+ free. Access is PIC (call/pop anchor + delta) — the DLL rebases.

### Ring-buffer protocol (@0x60D000, exe-hosted)
`+0 magic 'CLG1'` (file-initialized in .clog) · `+4 wrIdx` dword (total written, DLL-owned) · `+8 rdIdx`
dword (total drained, exe-owned) · `+0xC..0x1F reserved` · `+0x20: 64 slots × 64 B`, slot = shortstring
(len byte + ≤63 chars). Writer: if `wrIdx-rdIdx ≥ 63` → drop line (bounded, no tear); else fill slot
`(wrIdx & 63)`, THEN increment wrIdx. Reader drains `rdIdx..wrIdx-1`, converts to LStr, Add()s, sets
rdIdx=wrIdx. x86 store ordering suffices (effectively same-thread anyway).

## 5. v8 — missed touch attacks, touch ATK-vs-DEF, and clear-on-exit (2026-07-17, APPLIED-UNTESTED)

Three user requests. All three are in the two existing build scripts; no new script.

### 5a. Why missed touch attacks were invisible (the root cause)

A touch attack is a **two-stage roll**, and only stage 2 was ever hooked:

| stage | where | rolls | logged before v8? |
|---|---|---|---|
| 1 — the touch lands | `CreateTurnUndeadCA@0x5576B528` | `attacker.GetAttack`(vmt+0x6c) − `target.GetDefense`(vmt+0x70) → `AoWE.HitRole@0x55725D98` | **no** |
| 2 — the damage | `GenerateEx` → `ExecuteDamageRoleEx` | `GetTouchAttack(level)` vs **RESISTANCE** (vmt+0x74) | yes |

```
5576B547  call [edx+0x6c]        ; attacker GetAttack
5576B552  call [edx+0x70]        ; target GetDefense
5576B559  xchg edx, eax          ; eax = attack, edx = defense
5576B55A  sub  eax, edx          ; eax = attack-defense, edx STILL = defense
5576B55C  call 0x55725D98        ; HitRole  <-- v8 hook site (clean 5-byte E8)
5576B561  test al, al
5576B563  je   0x5576B5A5        ; MISS -> stores ids into the CA and STOPS.
                                 ;         GenerateEx is NEVER called.
```

So a stage-1 miss **structurally cannot** reach the `Generate`/`GenerateEx` tail hooks — the damage funnel is
only entered on a hit. This is also why the stage-1 ATK-vs-DEF never appeared: the line the log *did* print
for a landed touch is stage 2, which rolls against **RES**, not DEF.

### 5b. `cave_touch` @0x5580E798 (74 B, in `build_combatlog_dll.py`)

Hook: `TOUCH_HOOK = 0x5576B55C`, `TOUCH_ORIG = call AoWE.HitRole` (computed, never read from the live file
— see the v3 lesson in §4). Registers at the site (verified by disassembly):

```
EAX = attack-defense · EDX = defense · ESI = attacker · EBP = target · EDI = the CA · EBX = the ability
```

The cave calls `HitRole` itself, passes the result through untouched in AL, and on a **miss** re-uses the
**normal worker** rather than duplicating the formatter — it hands the worker the *fresh* CA:

| CA field | fresh value | worker reads it as | action |
|---|---|---|---|
| `+0x10` damage | 0 | "misses" | correct, leave |
| `+0x0c` bit0 | 0 | not a retaliation | correct, leave |
| `+0x11` types | 0 | **" - immune"** — wrong | force `0xFFFF`, **restore after** (feeds the miss animation) |
| `SCRATCH_R` | stale | possible bogus **" - fumble"** | force `-1` (HitRole uses RandInt(100), never sets R) |

`useRes = 0`, so the worker re-reads `GetDefense` and prints the real stage-1 roll:
`Hero misses Zombie  (70%, 9 ATK vs 4 DEF)` — satisfying both "report missed touches" and "report the
ATK vs DEF part". `attack` is recovered as `diff + def` from the stack (both saved before `HitRole` clobbers
eax/edx). PIC via `call/pop eax` anchor for `SCRATCH_R`; every other reference is rel32.

**Scope:** Turn Undead only. `TTouchAbility.CombatTouchRole@0x557681B0` does the same ATK-vs-DEF HitRole and
is the shared virtual, but it has **zero rel32 callers** (it is dispatched through a VMT slot), and
`CreateTurnUndeadCA` *inlines* the roll instead of calling it. Generalising to the whole touch family means
hooking `CombatTouchRole` too, or its VMT slot — not done yet.

### 5c. Clear on battle end / replay close (`build_combatlog_exe.py`)

No new hook: `cave_drain` already latches the display mode in `BSS_LASTMODE` (0 = neither, 1 = tactical,
2 = replay). The **1→0 / 2→0 transition is exactly "battle ended or replay closed"**, so the clear lives in
the `_m_none` path and covers both cases at once:

```asm
_m_none:
    cmp  dword ptr [BSS_LASTMODE], 0
    je   _drain                      ; already none -- nothing to do
    mov  dword ptr [BSS_LASTMODE], 0 ; also forces a re-place on the next show
    mov  eax, [ebx+0x48]             ; ebx = our instance -> memo ctl
    ...
    mov  eax, [eax+0x118]            ; -> the TStringList
    call dword ptr [edx+0x40]        ; TStringList.Clear
_cleared:
    mov  eax, [RING+4]               ; rdIdx = wrIdx -- discard pending slots
    mov  [RING+8], eax
    jmp  _drain                      ; MUST fall into _drain, NOT _done (see below)
```

**`jmp _drain`, not `jmp _done`.** `_done` is past `_vis`, the visibility state machine that *hides* the
window. Jumping straight to `_done` leaves the window on screen until the next map pump tick — and forever if
that was the last tick. Falling into `_drain` costs nothing (rdIdx==wrIdx → it immediately takes `je _vis`)
and hides on the same frame.

### 5d. VMT slots — verified, not assumed

`TAOWMemo.Create@0x59818838` shows `+0x118` is a **stock `VCL30!Classes.TStringList`** (`mov eax,[0x598404d4]`
→ `TObject.Create`), not a custom aowInt class. **VCL30.dpl ships symbols**, so the VMT is directly dumpable
and worth trusting over Delphi-declaration-order reasoning (which predicts `Add` at 0x54 and is *wrong* here):

```
Classes..TStringList VMT @0x4131BC98
  +0x34 -> Classes.TStringList.Add     <- what cave_drain already used (confirmed in-game)
  +0x40 -> Classes.TStringList.Clear   <- v8
  +0x44 -> Classes.TStringList.Delete
  +0x50 -> Classes.TStringList.IndexOf
```
`Clear` calls `Changed` → fires OnChange → the memo repaints itself. Reusable: **dump VCL30.dpl's VMTs by
symbol** whenever a VCL object's slot is needed.

`TPossessAbility.CreatePossessCA@0x55769BEC` and `TWebAbility.CreateWebCA@0x5576A210` are identical in shape —
create the CA, `call [ebx+0x110]`, feed the result to `Initialize`. TCharm/TSeduce/TDominate carry no
`Create*CA` of their own (they inherit Possess's). So **hooking the function itself** covers the family;
chasing `call [reg+0x110]` sites is useless (that offset collides with unrelated classes — TSaveGameTE,
TCheatTE, … — and the real dispatch is virtual anyway).

Two abilities stay outside it, correctly: **`CreateHealingCA@0x5576C0A4` never rolls** (healing always lands)
and **`TTurnUndeadAbility` inlines its own roll** (§5, still hooked separately at `0x5576B55C`).

### 6b. `CombatTouchRole` is itself a two-roll gate

```
CombatTouchRole(eax=self ability, edx=attacker combat obj, ecx=target combat obj) -> AL = success
  ROLL 1 @0x557681D6   attacker.GetAttack(vmt+0x6c)   - target.GetDefense(vmt+0x70)     -> HitRole
         @0x557681FA   fail -> return 0
         @0x557681FC   GetTouchAttack == -10 -> return 0   (sentinel: cannot touch)
  ROLL 2 @0x55768216   self.GetTouchAttack(vmt+0x10c) - target.GetResistance(vmt+0x74)  -> HitRole
         @0x5576821F   fail -> return 0
  epilogue: mov eax,ebx; pop edx/edi/esi/ebx; ret    (plain ret, result in AL)
```

Both rolls must pass, so a failure has **two distinct causes** — *missed* (never connected) vs *resisted* —
which the log now distinguishes. Both roll sites carry the identical `sub eax,edx` / `call HitRole` shape as
Turn Undead (`EAX`=diff, `EDX`=the opposing stat), so each is captured with the same tiny cave.

### 6c. As built — `trole` unit @0x5580E7E8 (943 B)

| part | addr | role |
|---|---|---|
| `_entry` | `0x5580E7E8` | trampoline: resets scratch, calls the original, logs |
| `_stub_orig` | `0x5580E835` | the 7 relocated entry bytes + `jmp 0x557681B7` |
| `_troll1` | `0x5580E841` | ROLL 1 capture → `SC_T1` |
| `_troll2` | `0x5580E873` | ROLL 2 capture → `SC_T2` |
| `_tworker` | `0x5580E8A5` | the sentence builder |
| `_tstats` | — | shared `  (P%, A ATK vs D DEF/RES)` emitter |

Hooks: entry `0x557681B0` (`jmp` + 2 nops over the 7 relocatable `push`es — note `0x557681B7` must survive,
it is a jump target from inside the function), `0x557681D6` → `_troll1`, `0x55768216` → `_troll2`.
Scratch: `SC_T1=0x558FA820`, `SC_T2=0x558FA82C` (each `+0 ok(-1 = not rolled) +4 diff +8 stat`).

Output (`s`/`es` conjugation off the ability name's last char — `Possess`→`Possesses`, `Charm`→`Charms`):
```
Incarnate Possesses Giant  (70%, 9 ATK vs 4 DEF)  (60%, 8 ATK vs 5 RES)
Saint fails to Charm Swordsman  (70%, 9 ATK vs 4 DEF) - missed
Saint fails to Charm Swordsman  (70%, 9 ATK vs 4 DEF)  (30%, 8 ATK vs 5 RES) - resisted
```
A stage-1 miss shows only stage 1 — stage 2 never rolled, and its scratch stays `-1`, so the builder skips it.
The ability name comes from `TAbility.GetName` (**VMT slot +0x58**, `eax=self, ecx=@out`), which is merely
`@LStrLAsg(out, [self+8])` — the name is an AnsiString at `ability+8`. Called virtually anyway, since
`THealingAbility` overrides it.

### 6d. The trap: FOUR PIC anchors in one unit

The unit has **four independent `call/pop` anchors** (`_entry`, `_troll1`, `_troll2`, `_tworker`). The first
draft passed a single `anchor` to the emitter, which would have silently corrupted three of the four
displacement sets — the kind of bug that writes garbage to random BSS at runtime and never trips an assert.
The emitter now takes one base per section (`sc0`/`sc1`/`sc2`/`sc`), and the build:

- emits pass 1 with **deliberately distant dummy bases** so every displacement encodes as `disp32` and the
  unit's size cannot move between passes (a `disp8` in pass 2 would shift every later label),
- locates the anchors by pattern (`e8 00000000 5f` ×2 = `_entry`,`_tworker`; `…5a` ×2 = the trolls),
- re-emits with the real bases and **asserts both the size and the anchor offsets are unchanged**,
- finds the sub-entries via the prologue bytes **taken from `_entry` itself** (not a hard-coded encoding),
  and cross-checks `_troll1` against the independent `stub_orig + 7 + 5` path.

Verified in the live file: `edi+0xec02a → 0x558FA820`, `edi+0xec036 → 0x558FA82C` (entry);
`edx+0xebfcb → 0x558FA820` (troll1); `edx+0xebfa5 → 0x558FA82C` (troll2); both roll hooks resolve to their
caves; `stub_orig` replays 7 bytes and returns to `0x557681B7`.

## §11. The effect-landing roll — DECODED + **APPLIED, UNTESTED 2026-07-21**
Built as `build_scripts/build_effectroll.py` (cave `0x5580F600`, backup `.pre-effectroll`).
**Simpler than the plan below:** each stub emits its OWN log line immediately, so the BSS
table and the entry clear-hook proved unnecessary — those were only needed to append to the
damage line, which would have meant patching the log worker and rewriting the whole
combat-log image. Effect lines therefore appear just ABOVE their damage line (the roll runs
inside Generate, before the worker's epilogue hook); each names its own effect so it reads
fine either way.

**User request:** the log says *whether* an effect landed (`+vertigo`) but never shows **the roll vs RES
that decided it**. Decoded below; implementation not yet built.

### The mechanic
`TAbstractUnit.ExecuteDamageEffectsRole @0x55781BA4` — reached as combat-object **vmt+0x118** via
`TCombatUnit.ExecuteDamageEffectsRole @0x55724C3C`, a one-line forwarder to the *strategic* unit
(`combatObj+0x4c` — the same field the log already uses for names). `TCombatObject`'s own
@`0x55726B10` is a stub returning a constant, so only real units roll for effects.

```
types &= ~self.vmt[0xEC]()                  ; drop fully-immune types
if types:
    baseRes = self.vmt[0xCC]()              ; GetResistance (strategic)
    partial = self.vmt[0xF0]()              ; PARTIAL protection mask
    for (bit, statusId) in the fixed order below:
        if types & bit:
            if self.vmt[0x148](statusId): continue      ; ALREADY has the status -> no roll at all
            res = (partial & bit) ? baseRes + 2 : baseRes
            if HitRole(5 - res): result |= bit          ; <-- THE ROLL
```

⇒ **effect chance = `clamp(50 + 10*(5 - res), 10, 90)` = `clamp(100 - 10*res, 10, 90)` %**, using the
same `HitRole @0x55725D98` as to-hit. RES 5 → 50%, RES 7 → 30%, RES 9 → 10% (floor), RES ≤ 4 → capped 90%.
Partial protection is worth a flat **+2 RES** against that one type.

| order | type bit | status id (`vmt+0x148`) | effect | `call HitRole` site |
|---|---|---|---|---|
| 1 | `0x01` fire | 7 | burning | `0x55781C37` |
| 2 | `0x04` lightning | 9 | stunned | `0x55781C97` |
| 3 | `0x10` poison | 10 | poisoned | `0x55781CE9` |
| 4 | `0x20` death | 11 | cursed | `0x55781D3B` |
| 5 | `0x40` holy | 12 | **vertigo** | `0x55781D8D` |
| 6 | `0x02` cold | 8 | frozen | `0x55781DED` |

Lightning and holy carry an extra `self.vmt[0x114]() != 2` guard (stunned is skipped entirely; vertigo is
rolled but discarded if the guard fails).

**Two consequences that explain confusing log output:**
1. **A repeat hit on an already-afflicted target prints no `+effect`** — `vmt+0x148` short-circuits before
   the roll. Absence of `+vertigo` does NOT mean "resisted"; it may mean "already vertigo'd".
2. A resisted effect is currently **completely invisible** — no roll, no odds, nothing.

### Implementation plan (7 hooks, exact)
Each of the six `call HitRole` sites is a clean standalone 5-byte `E8 rel32` with **EAX = `5 - res`** on
entry and **AL = landed** on return — so a per-effect stub gets both the odds and the outcome exactly,
including rolls that failed.
- **6 × call-site repoint** → tiny stubs (`tag effect index; call HitRole; record (diff, AL); ret`),
  writing a 6-entry table in BSS scratch.
- **1 × entry hook** at `0x55781BA4` to clear the table (it runs exactly once per damage CA, before the
  `TDamageCA.Generate`/`GenerateEx` epilogue where the formatter already sits — so the data is ready).
- Formatter appends per rolled effect, e.g. `… +vertigo [30% vs res 7]` and, for failures,
  `… vertigo resisted [30% vs res 7]`.
(Cave-space claim updated 2026-07-25: `0x5580F180`/`0x5580F600` are now occupied by replaylog/effectroll;
allocate new caves from `0x55810000+` — DLL cave space is ~880 KB, not scarce. The relocated log cave sits
at `0x55811000`.)

⚠ Worth pairing with the existing scouted gap: `CA+0x18` strike flags (panicked / entangled / lifesteal)
are still unlogged — they are set by `TStrikeCA.Generate` *after* the base returns, needing a hook at its
exit `0x55766969`. The panic roll there is the same shape: `HitRole(5 - RES)` @`0x5576691B` (Cause Fear
`0x33`, skipped if the target is Fearless `0x43`) and `HitRole(7 - RES)` @`0x55766955` for ability `0x77`.

## §12. Replay re-display — **CONFIRMED WORKING in-game 2026-07-21**

`live_ui.py` on a running animated replay settled it with hard numbers (not theory):
```
ring: wrIdx=67 rdIdx=48 tacticalFlag=0 ; slot0/1/2 = b'[replay tick]'
TCombatLogWin: visible=1, placed mid-left (mode 2 applied)
```
So, ALL VERIFIED WORKING: the `TDamageCA.Play` hook fires during a manual-battle replay (the diag
markers are in the ring), the guards pass, and mode-2 visibility/placement works. **The one broken link:
`cave_drain` is STARVED during the replay.** It pumps off `TMWindow.MapWindowUpdate`, and the map window
does not tick while the fast-combat replay window animates — so `rdIdx` froze at 48 while the hook pushed
`wrIdx` to 67, the 19 pending lines were never drained, and closing the replay (mode 2->0, `_m_none`)
clears the memo before the map ever pumps again. Nothing to do with the hook, the global, or the exe.

**FIX (DLL-side, CONFIRMED):** `TDamageCA.Play` runs ONLY during a replay (Play is never called live —
that is why the diag markers only ever appeared here) and on the main thread, so `cave_replaylog` writes
the line **directly into our window's memo** via `TStringList.Add` instead of into the ring. That is the
exact call `cave_drain` already makes (`inst 0x45B2E0 -> memo +0x48 -> TStringList +0x118 -> Add [vmt+0x34]`,
eax=list, edx=lstr) — just moved to where the data already is, removing the drain-pump dependency entirely.
Self-refreshing (Add -> Changed -> repaint), so it needs no pump. No ring, no exe patch, no section-size
limit. `_m_none`'s clear-on-close still fires (map pumps again once the replay closes) so each replay
starts fresh. Live combat still uses the ring+drain untouched.

### §12b. Implementation spec — `build_replaylog.py` (BUILT 2026-07-21; kept as the as-built record)

**Standalone additive DLL patch. Touches nothing that already works** — no exe change, no edit to the
combat-log image (then at `0x5580E440`, since relocated to `0x55811000`), so it cannot regress the
confirmed log. Own cave at `0x5580F180`; own backup `.pre-replaylog`, one layer deep.

**Hook — 5 bytes @`0x55729D97`** (`8b 53 08 8b c6` = `mov edx,[ebx+8]; mov eax,esi`), continue at
`0x55729D9C`. Reached only on the trigger tick (`0x55729D95 jne` guards it), so it fires **once per
action**. State there: **`ESI` = CA**, **`EBX` = TCombatViewer** (prologue `mov ebx,edx; mov esi,eax`
@`0x55729D7B`), `[EBX+8]` = playback TCombat, `[[EBX+8]+0xc]` = TCombatData.
Preserve everything: the displaced pair feeds the `call [ecx+0x50]` two instructions later.

**IDs → objects:** `FindID @0x55728C68 (EAX = TCombatData, EDX = id) -> EAX = combat object`, exactly as
the vanilla code does at `0x55729DA6..0x55729DAC`. Attacker id = `byte[CA+0x0d]`, target = `byte[CA+0x0e]`.
Guard both for NIL (FindID returns 0 if absent).

**Fields:** `+0x10` rolled damage (0 = miss) · `+0x11` word effective types · `+0x13` word effect landings
(bit→effect table as in §11 / the DLL script) · `+0x0c` bit0 = retaliation ("hits back at").

**Names:** strategic unit = `combatObj+0x4c` (guard NIL → "?"), then `GetName` at unit **vmt+0xF8**
(`eax = unit, edx = @out LStr`). Delphi ref rules: zero the LStr temps on the stack first and
`@LStrArrayClr` them after — see the worker's prologue/epilogue for the exact idiom and the thunk table.

**Commit — directly into the memo, NOT the ring** (the §12 fix; the drain never pumps during the replay
animation): DevEd-host guard (exe SizeOfImage ≥ 0x20E000 + `'CLG1'` magic @0x60D000), then
`[0x45B2E0]` instance → `+0x48` memo → `+0x118` TStringList → `Add [vmt+0x34]` (`eax`=list, `edx`=LStr).
Self-refreshing (Add → Changed → repaint), main-thread only, so no pump dependency.

**Line format (no stats tail — see §12 for why it is unrecoverable):**
`Valkyrie hits Shadow for 5 damage +vertigo` · `Shadow hits back at Valkyrie for 3 damage` ·
`Valkyrie misses Shadow`.

**PIC:** one `call/pop` anchor; every literal/table reference anchor-relative (the DPL rebases). The only
absolute addresses allowed are the EXE's (`0x40003C`, `0x60Dxxx`) — correct, AoW.exe is fixed-base.

**Why not reuse the log worker:** its contract is `EAX = attack, EDX = attacker, ECX = useRes,
ESI = target, EBX = CA`, and it *always* prints the `(N%, A ATK vs D DEF)` tail from EAX. Replay has no
attack, so reuse would need a skip-the-tail sentinel patched into the worker. At the time that meant the
destructive `.pre-combatlog` revert; the DLL script can now rewrite its own cave in place (2026-07-22),
so this constraint is gone for future work — the standalone formatter stands as built, with the
duplicated name/damage assembly as the price paid.

### §12c. Post-mortem of the replay-log investigation — compressed to the reusable facts

The full narrative is deleted; the general lessons live in the memory notes (`aow1-investigation-traps`,
`aow1-instrument-boundaries-over-static-analysis`). What stays, because it is machinery or a
tempting-to-re-derive error:

- **`GVAR_FASTCOMBAT = 0x45B1B0` is CORRECT and alive.** `xref.py` shows no references because the exe
  reaches many BSS gvars through a **DATA pointer table** (`[0x45A4F0] = 0x45B1B0`; the table at
  `0x45A4D0..` mixes BSS-gvar and .idata slots). Absence of xrefs ≠ dead gvar — check the pointer tables.
- **Register liveness is a per-site fact.** The drain loads `EAX=[ctl+0xCC]` *before* its mode head and
  consumes it after; the original mode head deliberately uses only ESI. Editing that head to use EAX as
  scratch crashed every tick — twice. Audit liveness across any edit point in an existing cave.
- **`TStrikeCA.Play` DOES call base** (@`0x557668AC`) — don't re-derive the opposite.
- **An in-place apply is a full re-release**, not a constant tweak: it ships every byte of current source
  and bypasses the "different build already applied — refusing" guard.
- **What cracked it:** a read-only `live_ui.py` snapshot of the ring mid-replay
  (`wrIdx=67 rdIdx=48 slots=[replay tick]`) — hook fires, ring fills, drain starved, all in one line.
  A probe that shares the suspect path (the `--diag` marker) can only narrow, never localise. The ring
  being non-zeroed on consume is what made the boundary observable — preserve that property.
- Leftover artifacts: `AoW.exe.pre-clogfix` / `AoWCompat.exe.pre-clogfix` snapshot bytes identical to the
  then-live exes — harmless.
