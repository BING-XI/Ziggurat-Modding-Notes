## 0. ⚠ PROVENANCE — the live binary is NOT vanilla in CanRaze (discovered 2026-07-09)

Diffing live `AoWEPACK.dpl` against `Modding Resources/AoWEPACK_original_backup.dpl` (assumed
vanilla) shows a **previous-session raze mod**: three byte spans inside `CanRaze`, nothing else in
the predictor / strike / fast-combat code (those are vanilla; the other diffs in nearby regions are
the known slayer/XP/rebellion mods — see §0b). The Ghidra project was imported from the *modded*
image, so §1–§4 below describe the **live (modded)** bytes. Vanilla decode:

| site | vanilla | live (old mod) |
|---|---|---|
| `0x5575FC3B` call (loop over the razing player's units) | `CALL AddUnit` → **side 0** | `CALL AddOpponent` → side 1 |
| `0x5575FC7F` call (loop over generated raze defenders) | `CALL AddOpponent` → **side 1** | `CALL AddUnit` → side 0 |
| `0x5575FCA8..B2` gate tail | `CMP EAX,0x32; JG pass; XOR EBX,EBX; JMP; MOV BL,1` | `CMP EAX,0x64; JGE fail; MOV BL,1; JMP; XOR EBX,EBX` |

(The result-decode bytes at `0x5575FC96–9F` are identical in both; but note the `JNZ 0x5575FCAD`
lands on **fail** in vanilla and **pass** in live, because the old mod also swapped which of
`0xFCAD`/`0xFCB1` is the pass arm.)

**Vanilla semantics** (sides: razers = side 0, militia = side 1 — matching the class convention,
see §9): pass iff `Result ∈ {3,4,6}` **and** `Superiority > 50`, where
* Result 3 = militia wiped → superiority measured on the razers = `100·total/losses` ≥ 100 → always
  passes ("I wipe them ⇒ raze").
* Result 4 = **razers wiped** → superiority = % of *militia* strength destroyed → passes if > 50 —
  vanilla allows **suicide-razing**: your stack may die, so long as it credibly burns down more than
  half the militia's strength.
* Result 2 (stalemate) → **fails** in vanilla.

**Live (old mod) semantics** — what §1–§2 document: sides swapped (militia = 0, razers = 1); pass
iff `Result ∉ {3,4,6}` or `Superiority < 100`. Net effect of the old mod: it *removed* vanilla's
suicide-raze allowance (annihilated razers now fail) but *added* a stalemate-passes hole (Result 2).
**The Great-Eagle exploit exists identically in both** — the eagle wipes the militia in-sim
(vanilla: Result 3 → auto-pass; live: Result 4, tiny losses → pass). The old mod's motivating
theory ("razers were the defenders, letting raze-defenders retreat") was half-right: razers *are*
the "defender-ish" side 0 in vanilla (side 1 is the wall-attacking side in `FinishCombat`, and the
militia does attack *after* the raze) — but the predictor contains no retreat/flee logic at all
(§3), so the swap changed only the gate arithmetic, not the sim.

**Revert:** restore the three spans above from `AoWEPACK_original_backup.dpl` (bytes:
`0x5F03C←C4B5`, `0x5F080←C0`, `0x5F0AA←327F0433DBEB02B301`). Folded into the fix plan as step 0
(§8). All layered `.pre-*` backups postdate this old mod, so only the original backup has the
vanilla bytes.

## 1. The gate

Razing is gated by exactly one function:

| Symbol | VA | Notes |
|---|---|---|
| `AoWE.TStructure.CanRaze` | `0x5575FB80` | VMT slot **0x1EC**. `(Self; Player: Byte; var Msg: string): Boolean` |
| `AoWE.TStructure.Raze` | `0x557602F8` | player click → confirm dialog. Calls slot 0x1EC first |
| `AoWE.TStructure.RazeEx` | `0x5576023C` | issues the turn event. Calls slot 0x1EC again |
| `AoWE.TStructure.ExecuteRaze` | `0x5575FFC8` | executes. Calls slot 0x1EC a third time |
| `City.TCity.ExecuteRaze` | `0x557AB414` | inherited + race relation −30 |

`AoWE_NotEnoughForcesRStr` (resource ptr `0x55707704`) is loaded in **exactly one place**:
`0x5575FCBA`, inside `CanRaze`. So the user-visible "your forces are not sufficient" warning ⇔ `CanRaze = False`.

(Note: `TStructure.Raze` *discards* the returned message string; the UI text must be surfaced by
`AoW.exe`, which is not in the Ghidra project. Unverified.)

### CanRaze, in pseudocode

```pascal
if GetRazed then Exit(False);            // slot 0x150
if not GetRazeable then Exit(False);     // slot 0x154

P := TCombatPredictor.Create;
ListUnits(tmp);                          // slot 0x1D4 — every unit in every army standing on
for u in tmp do                          //             any hex of the structure's footprint
  if u.PlayerID = Player then P.AddOpponent(u);   // -> side 1
GenerateRazeDefenders(Player, def);      // slot 0x1A8
for u in def do P.AddUnit(u);            // -> side 0
P.Execute;

Result := not ( (P.Result in [3,4,6]) and (P.GetSuperiority >= 100) );
if not Result then Msg := 'not enough forces';
```

Encoding of the test at `0x5575FC93`: `AL := Result; ADD AL,0xFD; SUB AL,2; JC take; SUB AL,1;
JNZ skip` → `Result in [3,4,6]`; then `CALL GetSuperiority; CMP EAX,0x64; JGE fail` (`0x5575FCA8`).
Return value is `BL`, moved to `EAX` at `0x5575FD10`.

`AddUnit` (`0x5572B204`) → `AddUnitEx(..., side=0)`; `AddOpponent` (`0x5572B244`) → side=1.
So **side 0 = the raze defenders, side 1 = the razing player's stack.**

## 2. What `Result` and `Superiority` actually mean

`TCombatPredictor.FinishCombat` (`0x5572AF4C`) is the *only* writer of the result byte (`this+0x14`).
A byte-scan of the predictor's code range confirms only `2, 3, 4, 8` are ever stored:

| Result | Meaning | Reachable from CanRaze? |
|---|---|---|
| 3 | side 0 (defenders) has survivors, side 1 (attacker) wiped | yes |
| 4 | side 1 (attacker) has survivors, side 0 wiped | yes |
| 2 | **both sides still have living units** (nobody can act any more) | yes |
| 8 | wall still standing | no — `CanRaze` never calls `AddWall`, so `this+0x20 = 0` |
| 6 | never produced by `TCombatPredictor` | **no — dead condition** |

(The only `mov byte [reg+0x14],6` in the DLL is at RVA `0x44AC9`, inside `TFastCombat` — a different
class that happens to share the `TCombatResult` enum.)

`TCombatPredictor.GetSuperiority` (`0x5572B798`) is **asymmetric**:

* `Result = 3` → measured on side 0: `100 * total / (total − remaining)`, i.e. *strength ÷ losses*.
  Losses ≤ total, so this is **always ≥ 100** (999 if losses = 0).
* `Result in [2,4,8]` → measured on side 1: `100 * (total − remaining) / total`, i.e. the
  *percentage of the attacker's strength that was destroyed*, clamped to 100 when `remaining < 1`.

"Strength" here is `TCombatPredictorUnit+0x38` = the sum of that unit's per-round damage against
every enemy it can hit (accumulated in `SetupRoundTargets`). `remaining = hp*strength div maxhp`
(integer division).

### Therefore the gate reduces to:

* **Result 3** (defenders wipe your stack) → superiority ≥ 100 by construction → **always blocked**.
* **Result 4** (you wipe the defenders) → blocked only if `remaining < 1`, i.e. every one of your
  survivors is at under ~1 % HP. A "pyrrhic victory" clause. Otherwise → **allowed**.
* **Result 2** (mutual stalemate, both sides alive) → **allowed**. Not in `[3,4,6]`.
* Result 6 → unreachable dead code.

So: *you do not need to win convincingly. You need to not be annihilated.*

## 3. The prediction model (`TCombatPredictor`)

An abstract, position-free slugfest. No hexes, no movement, no morale, no retaliation, no round cap.

| Function | VA |
|---|---|
| `Create` | `0x5572ABA8` |
| `Execute` | `0x5572B028` |
| `SetupCombat` | `0x5572AD54` |
| `ExecuteCombatRound` | `0x5572AE68` |
| `FinishCombat` | `0x5572AF4C` |
| `GetSuperiority` | `0x5572B798` |
| `TCombatPredictorUnit.Setup` | `0x5572A5E8` |
| `...UpdateTargets` | `0x5572A664` |
| `...SetupRoundTargets` | `0x5572A954` |
| `...SortRoundTargets` | `0x5572AA34` |
| `...ExecuteRound` | `0x5572AAA0` |

Object layout (`TCombatPredictor`): `+04` all units, `+08` active units this round,
`+0C` side 0 list, `+10` side 1 list, `+14` result, `+18` cached superiority, `+20` wall, `+24` rounds.

`TCombatPredictorUnit`: `+04` real unit, `+10` maxHP (= `HitPoints × 100`), `+14` side index,
`+1C` enabled, `+20` all targets (quad list), `+34` round targets, `+38` outgoing dmg total,
`+40` incoming dmg total, `+44` "how many enemies can't hurt me", `+48` priority, `+4C` current HP,
`+50` flags (bit set on death).

**Rules that matter:**

1. `UpdateTargets` scores every enemy with `TAbstractUnit.GetCombatValue` (`0x5577F9A8`):
   `CV = max over the unit's abilities of  a² div (d + a)`, min 1 if `a > 0`, where `(a, d)` come
   from `Ability.GetDamageValueEx` (**VMT slot 0xDC**) as `rec[0]`, `rec[2]`.
2. `SetupRoundTargets` (`0x5572A954`) **deletes any target with `CV < 1`** from the round-target list,
   and bumps that target's `+44` counter.
3. `SetupCombat` (`0x5572AD54`) only adds a unit to the active list if it is enabled **and its
   round-target list is non-empty**. A unit with nothing it can damage **never acts at all**.
4. `ExecuteRound` (`0x5572AAA0`): the unit deals `CV` damage to **one** target per round — the last
   entry of its sorted round-target list. There is **no retaliation**.
5. `SortRoundTargets` (`0x5572AA34`): priority `= dmg*100000 div target.incoming + target.priority*100
   + dmg`, **except a target whose own outgoing total (`+38`) is 0 gets priority 0** → sorted first →
   attacked **last**. Harmless enemies are killed last.
6. `ExecuteCombatRound` loops until no unit acts. Damage within a round is applied unit-by-unit but
   corpses are only removed after all have acted → effectively simultaneous.

## 4. The flying hole

`AoWE.TStrikeAbility.GetDamageValueEx` @ **`0x55766C90`** (VMT slot 0xDC — the one `GetCombatValue`
calls), first four instructions of the body:

```
55766CA7  MOV EDX,1
55766CAC  MOV EAX,EDI            ; EDI = target
55766CB0  CALL [ECX+0x148]       ; target.GetAbilityEnabled(1)
55766CB8  JZ  compute            ; target not flying -> normal
55766CBA  MOV EDX,1
55766CBF  MOV EAX,[EBP-4]        ; attacker
55766CC4  CALL [ECX+0x148]       ; attacker.GetAbilityEnabled(1)
55766CCC  JZ  zero               ; attacker not flying -> AttackerDV := 0, DefenderDV := 0
```

**Ability id 1 = Flying.** (Cross-checks: `Investigation_Combat.md` §Move — "Walking 0, Flying 1";
and `TStrikeAbility.CanExecuteMelee` @ `0x55766AF8` applies the identical `id 1` test to gate real
combat melee.) Note it checks **only id 1** — Floating (`0x3B`) and WindWalking are *not* covered,
in the predictor or in real combat.

Consequences:

* A melee-only unit's `CV` against a flyer is **0** → rule 2 drops the flyer from its target list →
  its list is empty → rule 3 excludes it from combat entirely. **It never deals a single point of
  damage, and it isn't "beaten" — it simply isn't in the simulation.**
* `TRangedAttackAbility.GetDamageValueEx` @ `0x5576E7FC` has **no** flying check, and it sets
  `rec[2] := 0` — so a ranged unit's `CV` is its **full DV** (`a² div (0+a) = a`), whereas melee `CV`
  is discounted to `a² div (a+d)` by the defender's retaliation DV. Retaliation exists in the
  predictor **only as this value discount**, never as damage.
* Rule 5 makes the flyer shoot the units that *can* hurt it (the archers) first, and mop up the
  melee units last.
* The flyer therefore takes damage only from the defenders' ranged/breath units, and grinds
  everything else down for free → `Result = 4`, superiority = % of its own strength lost ≈ 0 →
  **CanRaze = True.**

## 5. Who the raze defenders are

| | Generic structure | City |
|---|---|---|
| Entry | `TStructure.GenerateRazeDefenders` `0x5575FD1C` | `TCity.GenerateRazeDefenders` `0x557AB408` → `TCity.GenerateRebelUnits` `0x557ABCAC` |
| Roster | structure def's `TUnitIndexListCollection` (`def+0x5C`), random collection | the city race's unit list (`TRaceResource+0x38`) |
| Max unit level | 4 | **2** |
| Cost budget | `def+0x60` | **`25 × City.GetSize`** |
| Unit cap | 8 (excess trimmed) | **none** |
| RNG seed | `x + Map[0x22C] + y` (seed left dirty) | `x*10 + Map[0x22C] + y` (seed saved/restored) |

Filler: `AoWE.FillWithRandomUnits` @ `0x5575B160` —
`(IndexList, OutList, MaxLevel: Byte; ClassMask; CostBudget)`. Picks random entries, and when the
next pick would overshoot the budget it samples 20 more and keeps the closest fit. Unit cost is VMT
slot `0x174`.

`Map[0x22C]` **(verified 2026-07-09)** is the **per-game map seed**: `TPlayerControl.NewDay`
(@`0x55754DA4`, store at `0x55754F51`) sets it once on day 1 (`Randomize(); Map[+0x22C] := RandSeed`;
skipped when scenario flag `Map+0x13A` is set; `Map+0x230` gets a copy; second writer @`0x557E0FDA`
≈ savegame load). So the defender/rebel roster of a given structure is **fixed for the whole game**
— "semi-random" across games, deterministic within one.

Two consequences:
* City raze defenders are **level ≤ 2 only** — no matter how big the city.
* `GenerateRebelUnits` is shared with `TCity.CheckRebellion` (`0x557AB534`), which on a failed
  loyalty roll (75 % at civil status 0, 25 % at status 1) spawns the same roster as *real* units.
  Rebellion and raze-defence draw from the same generator, but rebellion is otherwise unrelated.

## 6. Verdict on the "Great Eagle" theory

**Mechanism: correct. Framing: wrong.**

* ✔ There *is* a simulated combat, and it *is* what produces "not enough forces".
* ✔ The eagle wins because flying units cannot be damaged by non-flying melee in the simulation.
* ✔ The sim does prioritise killing the units that can hurt the flyer (archers) first.
* ✘ There is no attacker/defender asymmetry, no morale, and no "withdraw". Melee units don't give up —
  `SetupCombat` never enters them into the fight.
* ✘ Retaliation is not simulated, so "the eagle must forbear from attacking" is not a real constraint;
  it attacks with total impunity. Retaliation only appears as a divisor in the melee `CV` formula.
* ✘ The eagle doesn't merely "survive to a draw". It reaches `Result = 4` (total victory). A draw
  (`Result = 2`) *would* also pass the gate — that's a separate, independent hole.
* ✘ "Survive" isn't literally enough either: `Result = 4` with all survivors under ~1 % HP is blocked.

The real defect, if one wants to call it that, is **rule 3**: a unit that cannot damage anything is
removed from the simulation instead of being modelled as a body that soaks attacks and retaliates.
A single flyer versus eight swordsmen is, to the predictor, a single flyer versus eight inert targets.

## 6b. How autocombat handles the same matchup (2026-07-09)

Autocombat is a **separate engine**: `TFastCombat` (`Execute` @`0x55744A0C`, `ExecuteCombatRound`
@`0x5574482C`) driving the abilities' `fc*` methods — VMT slot **0xE4** (`fcGetDamageValueEx`)
instead of the predictor's 0xDC. Findings:

* **Same flying gate exists.** `TStrikeAbility.fcGetDamageValueEx` @`0x55766D34` zeroes melee DV
  when target has ability id 1 and attacker doesn't (via slot 0xA8, the combat-object flavour of
  `GetAbilityEnabled`). Ground melee generates no attack option against a flyer in autocombat too.
* **But retaliation is real.** `TStrikeAbility.fcExecuteCombatCommand` @`0x55766FCC` builds a
  `TMeleeRound`, calls `Calculate(attacker, target)`, then executes **every strike in the round via
  `CreateStrikeCA`, including the defender's strikes** (`GetMeleeStrike` records whose strike each
  one is; the `==1` branch checks whether the *attacker* died). A flyer beating down ground melee in
  autocombat pays retaliation for every attack — exactly what the predictor never charges.
* **No free win by stalling.** `TFastCombat.ExecuteCombatRound`: if a full round passes with no unit
  acting and `round > GetRoundDistanceMax` (@`0x55744584`, max over units' distance need) →
  `TCombat.Terminate` @`0x557274B8` — the fight ends unresolved rather than as a defender wipe.
  Helpless *attacker-side* units with no commands issue a `TFleeCA` (see `fcExecute` @`0x55744268`).
  `fcExecute` also has a "desperation" re-roll: a unit with no commands sets a flag bit and
  regenerates its command list once (wall-siege related).

**Conclusion:** the predictor is uniquely broken. Autocombat and manual combat both make a lone
flyer *pay* (retaliation, round limits); the predictor charges it nothing. So a predictor fix does
not create an inconsistency with real combat — it removes one. (The broader game-design fact that
melee units can never initiate against flyers — id 1 only; Floating `0x3B` is not covered — is
vanilla combat design, shared by all three engines, and is *not* what this fix targets.)

## 7. Why the obvious small tweaks don't work

1. **`0x5575FCA8` (`CMP EAX,0x64`)** — superiority threshold. Only tightens the pyrrhic clause;
   the eagle's superiority is ~0. Useless alone.
2. **Blocking draws (Result 2) at `0x5575FC93`** — correct to do, but the eagle gets Result **4**
   (it wipes the defenders in-sim, cost-free). Useless alone.
3. **Unconditionally removing the flying gate in `GetDamageValueEx` @`0x55766C90`** — fixes razing
   but leaks: slot 0xDC feeds `TAbstractUnit.GetCombatValue` @`0x5577F9A8`, whose verified callers
   are `TCombatPredictorUnit.UpdateTargets/UpdateWallTargets` (all predictor uses, incl. **AI attack
   planning**), `TCombatUnit.GetTargetWallCV` @`0x55725438` (real tactical combat), and
   `GetUnitIndexAIPriority` @`0x5575BADB` (AI build/priority). AI behaviour would shift game-wide.
4. **Modelling true retaliation damage inside the predictor *unconditionally*** — same leak as (3):
   every predictor consumer (AI attack planning) changes. (Doing it *under a raze-only flag* turns
   out to be cheap — that is the chosen fix, §8. The earlier "needs per-pair reverse damage storage"
   objection dissolved: the `ExecuteRound` damage site has attacker/target/damage all live in
   registers, so retaliation can be *recomputed* per attack instead of stored.)
5. **Using `TFastCombat` as the raze oracle** — it executes real `TCombatAction`s (log entries,
   deaths, animations); not a side-effect-free query. RNG/desync risk. Rejected — but its *economics*
   can be replicated inside the predictor, which is exactly what §8 does.
6. **"Fair-fight flag" (first draft of this plan)** — let melee hit flyers every round in the raze
   sim. Rejected by the user, correctly: it over-weights melee defenders (in a real fast combat they
   only ever deal damage via retaliation, one engagement at a time), so it would deny razes that a
   real fast combat wins. Superseded by the fast-combat-equivalence design below.

### Original plan (kept for reference; B/C/D = implemented, 0/A/E = deferred)

**Rule implemented:** a stack may raze only if the predictor says it would kill the *entire*
defender roster under **fast-combat economics**: melee cannot initiate against flyers (vanilla),
but every melee attack charges the attacker the defender's retaliation DV — so a flyer *can* still
clear a ground stack "one by one", exactly as in a real fast combat, if and only if it can survive
the cumulative retaliations (plus ranged fire).

Why this is equivalent (per pair, per round): a real fast-combat melee exchange initiated by X deals
`AttackerDV(X)` to Y and `DefenderDV(Y)` back to X (`fcExecuteCombatCommand` executes both sides'
strikes, §6b; no lifesteal/charge — those are execution-time effects, absent from `TMeleeRound`'s
stat-expectation DVs). With Patches C+D below, one predictor round does exactly that. For mutual
melee (X and Y both active) the predictor charges X with `AttackerDV(Y) + DefenderDV(Y)-on-X's-attack`
per round — the same total as fast combat's two exchanges per round (each side initiates once).

Feature name `razefix`; script `build_scripts/build_razefix.py` (standard model: dry-run default,
`--apply`, verify-before-write, idempotent, backup `AoWEPACK.dpl.pre-razefix`). Four patches
(A + B/C/D), three caves, all inside `AoWEPACK.dpl`:

### Patch 0 — revert the old side-swap mod first (restore vanilla, see §0)

Restore from `AoWEPACK_original_backup.dpl`: `0x5F03C←C4 B5`, `0x5F080←C0`,
`0x5F0AA←32 7F 04 33 DB EB 02 B3 01`. After this, sides are vanilla again (razers = side 0,
militia = side 1) and the gate is vanilla (`Result∈{3,4,6} && sup>50` passes). The build script
treats these bytes as its expected "before" state — it verifies the *old-mod* bytes are present and
rewrites the spans, so the revert is part of the same idempotent apply.

### Patch A — strict outcome gate, respecified against VANILLA bytes (4 bytes, no cave)

On the vanilla decode, "kill the entire opposing stack" = **Result 3** (militia = side 1 wiped).
Vanilla already fails stalemates; the only change needed is to stop Result 4 (razers wiped = the
suicide-raze allowance) and the dead 6 from reaching the pass path. At `0x5575FC96`:

| | bytes | meaning |
|---|---|---|
| vanilla | `04 FD 2C 02 72 04 2C 01 75 0D` | `Result in [3,4,6]` → sup check, else fail |
| new | `3C 03 75 13 90 90 90 90 90 90` | `cmp al,3; jnz fail(0x5575FCAD)` — only Result 3 proceeds |

The vanilla superiority check (`sup > 50`, measured on the razers as `100·total/losses`) is kept:
for Result 3 it is ≥ 100, so it never blocks — **unless** `--strict N` raises the threshold byte
@`0x5575FCAA` to demand a *clean* win: `sup > 200` ⇔ "lose less than half your strength",
`sup > 300` ⇔ "less than a third". A natural, vanilla-shaped loss-cap dial.

### Patch B — raze flag infrastructure (one 5-byte hook + cave_exec ~30 B)

`0x5575FC8B` (`E8 98 B3 FC FF` = `CALL TCombatPredictor.Execute`, inside `CanRaze`) →
`CALL cave_exec`. Cave: set flag byte, `CALL Execute` (rel32), clear flag, `RET`. EAX holds the
predictor at the site and must survive to the inner call (cave's `call/pop` uses ECX — dead);
the caller ignores Execute's return value (it re-reads `+0x14` at `0x5575FC90`). The flag is only
ever set inside this synchronous, single-threaded call — nothing outside the raze sim can observe it.

### Patch C — melee CV = raw AttackerDV under the flag (one 5-byte hook + cave_cv ~20 B)

`0x55766CED` (`E8 72 13 00 00` = `CALL TMeleeRound.GetDefenderDV`, in the tail of
`TStrikeAbility.GetDamageValueEx` where it fills `rec[2]`) → `CALL cave_cv`. Cave: flag clear →
`JMP GetDefenderDV` (tail-call, byte-identical vanilla); flag set → `XOR EAX,EAX; RET` (rec[2] = 0).
`GetCombatValue`'s formula `a²/(d+a)` then yields **raw `a`** for melee during the raze sim.

Rationale: `a²/(a+d)` *is* the vanilla predictor's fuzzy retaliation discount. Once Patch D charges
retaliation as real damage, keeping the discount would double-count it — the flyer would need
`(a+d)/a` × more rounds (and eat proportionally more retaliation) than a real fast combat. `rec[2]`
has no other consumer on this path (verified: only the CV formula reads it).

**The flying gate itself stays 100 % vanilla** — melee still cannot target flyers, in the sim as in
every real combat engine (§6b).

### Patch D — retaliation charge per melee attack (one 5-byte hook + cave_retal ~90 B)

The `ExecuteRound` damage site is a perfect hook (verified disasm):

```
5572AACA  MOV ECX,[ESI+0x34]
5572AACD  MOV ECX,[ECX+4]
5572AAD0  MOV EDX,[ECX+EDX*8+4]     ; EDX = entry.dmg (this pair's CV)
5572AAD4  SUB [EAX+0x4C],EDX        ; target.hp -= dmg      ← hook these
5572AAD7  MOV BL,1                  ;                        ← 5 bytes exactly
5572AAD9  JMP 5572AAE5
```

At `0x5572AAD4` (`29 50 4C B3 01`) → `CALL cave_retal`. Live registers: **EAX = target cpUnit,
EDX = damage, ESI = attacker cpUnit**; EDI = loop counter (preserve); EBX = result (cave sets BL=1);
ECX dead; no flags dependency after the site (`TEST EDI,EDI` follows). Cave logic:

```
sub  [eax+0x4C], edx            ; replicate: target takes the hit
mov  bl, 1                      ; replicate: "acted" flag
<flag check via call/pop delta> ; clear → ret (vanilla)
save eax(target), edx(dmg); X = [esi+4], Y = [eax+4]        ; real TUnits
X.GetAbilityEnabled(0x15)?      ; vcall slot 0x148; no Strike ability → ranged attack → ret
hsset = [delta + 0x558FA044]    ; AoWHSSet via rebase delta
strikeAb = TAbilityControl.GetAbility([hsset+0x80], 0x15)   ; @0x557501C0
mr = [strikeAb+0x28]
TMeleeRound.CalculateUnit(mr, X, Y)                         ; @0x55767A3C
a = GetAttackerDV(mr)           ; @0x5576804C
if a < saved_dmg → ret          ; melee wasn't this unit's chosen (max-CV) attack ⇒ no retaliation
d = GetDefenderDV(mr)           ; @0x55768064
sub [esi+0x4C], d               ; attacker eats the retaliation
ret
```

The `a >= dmg` test works because under Patch C the stored melee contribution *is* `a`; a strictly
better ranged/other CV means the unit "fires" instead (no retaliation) — matching fast combat's
best-command selection. Delphi register convention preserves EBX/ESI/EDI across the helper calls;
EAX/ECX/EDX are saved in the cave. An attacker driven below 1 HP by retaliation is culled by
`ExecuteCombatRound`'s existing post-round sweep and counted dead by `FinishCombat` — no extra
bookkeeping. Perf: one `CalculateUnit` (pure stat math) per melee attack per round, ≤16 units,
raze checks are occasional — negligible.

## 9. Why the raze check has its own combat logic at all (design archaeology, 2026-07-09)

The short answer: **it doesn't have raze-specific logic — it reuses the AI's battle-outcome
estimator**, and that estimator *cannot* be the fast-combat engine for structural reasons.

`TCombatPredictor`'s verified creators (xrefs to `Create` @`0x5572ABA8`):

| caller | purpose |
|---|---|
| `TAIGroupControl.Create` @`0x55738931` | **every AI army group owns a predictor instance** |
| `TAIGroupTargetSelector.ValidateTargetRequirements` @`0x5573CC0D` | AI attack decisions: predict my group vs opponents adjacent to the target, pass iff `GetSuperiority > GetRequiredCombatPredictorSuperiority` (per-personality threshold), then `ListRequiredUnits` to *compose the attack force* |
| `TArmy.GetPartyStatus` @`0x5578F5A5` | army status estimate |
| `TCity.GetCivilStatus` @`0x557AC257`, `TCity.ListCivilStatusInfo` @`0x557ABEE9` | **city unrest status = garrison vs hypothetical rebels** |
| `TStructure.CanRaze` @`0x5575FBD5` | the raze gate |

So the raze gate is one consumer of a general planning primitive — and note that cities *already*
use the exact pattern "real units vs ghost `GenerateRebelUnits` militia" for the civil-status
display. `CanRaze` is that same query with a threshold on the answer.

Why the predictor exists separately from `TFastCombat` (each point is load-bearing):

1. **It's a pure, deterministic function; fast combat is not.** `CanRaze` runs up to three times per
   raze command (UI check, `RazeEx` re-check, `ExecuteRaze` re-check) and must return the same
   verdict on every multiplayer client. `TFastCombat` executes real `TCombatAction`s — strikes,
   deaths, XP, "Round X" logbook headers, animations, flees — and rolls the MP-lockstep RNG.
   Using it as a query would need a deep copy of full combat state (heavyweight Delphi-3 `TUnit`s
   wired into map/army/player) plus a forked RNG. The predictor instead wraps *references* in
   ~0x54-byte proxy objects with their own HP counters — zero side effects, zero dice.
2. **It runs on the AI's CPU budget.** `Execute` ends with
   `TAIExecuter.UseProcessTime(map+0x128, rounds×58)` — it literally bills its cost to the AI time
   accounting. It was engineered to be run *in bulk* during AI turns on 1999 hardware, hence
   closed-form expected damage (`StatisticsToLimitedDV`, `a²/(a+d)`), no positioning, no dice.
3. **The opposition may not exist.** Raze defenders (and civil-status rebels) are ghost units
   created and freed inside the check; the AI evaluates fights between armies that aren't adjacent
   yet. Fast combat needs an instantiated battlefield.
4. **The output is a margin, not a verdict.** AI thresholds need "how superior am I" as a scalar
   plus "which units do I need" (`ListRequiredUnits`/`ListUselessUnits`/`Usefullness`) — an
   analytic estimate gives that in one pass; a stochastic resolver would need Monte Carlo.

Why the fidelity gap (no retaliation, flyer exclusion) plausibly shipped: for the estimator's main
job — *relative ranking* of mixed armies — `a²/(a+d)` is a serviceable retaliation heuristic, and
the degenerate case (an entire roster melee-only against a flyer) barely matters for AI target
ranking. It only becomes user-visible through the raze gate, whose vanilla threshold was in any
case lenient *by design*: "wipe them, or die destroying more than half their strength" — the real
deterrent was meant to be the militia that spawns and attacks after the raze, not the gate. A
1-unit eagle raze slipping through is exactly the kind of corner a 1999 QA pass wouldn't have
caught. (Result 6 in the gate's pass set is a fossil — nothing in `TCombatPredictor` can produce
it; likely an enum member shared with `TFastCombat`'s result codes, where 6 *is* produced.)

**Could raze call real fast combat instead? (2026 re-assessment.)** Mostly yes, with a harness; the
1999 reasons rank differently today: CPU budget — irrelevant now. Margin-not-verdict — only matters
for the AI's force-sizing, not a raze verdict. Ghost units — already exist; not the obstacle.
The real remaining constraint is **context**: `CanRaze`'s first call runs in *UI context on one
client only* (enabling the action / showing the warning), before any synchronized command exists.
MP fast combats are fine because they execute inside the lockstep command stream on all clients; a
speculative one fired from the UI would consume the lockstep RNG on one client (desync — and
`TAoWHSMap.Random` asserts outside synchronized context, the exact popup hit during the lava→dirt
work) and would emit real side effects (`TCombatAction`s, XP, logbook, event distribution). A
"headless fast combat" harness = save/restore `RandSeed` + deterministic reseed (the pattern
`GenerateRebelUnits` already uses) + suppress action/event/XP emission + construct a `TCombat`/
`TCombatData` context programmatically. All patchable, but the TCombat-construction RE alone
exceeds the whole of §8. §8's B/C/D gets fast-combat *economics* into the existing safe estimator
for ~140 bytes instead.

## 10. Second bug, same roots: "Oppressed" cities with no garrison (2026-07-09)

`TCity.GetCivilStatus` @`0x557AC14C` (and its tooltip twin `ListCivilStatusInfo` @`0x557ABD34`)
runs the same predictor: **side 0 = garrison units with cached morale ≥ 41** (`unit+0x26`, written
by `UpdateMoraleValue` @`0x5577F058`, clamped [−25,125]), **side 1 = `GenerateRebelUnits` ghosts +
garrison units with morale < 41** (disloyal troops would join the rebels — nice vanilla design).
Then, for relation < 2: `if Execute() == 3 then bonus := sup≥300 ? +75 : sup≥104 ? +50 : +25 else
bonus := 0`; loyalty = relation base (−35/−25) + bonus; loyalty ≥ 10 ⇒ status 5/6 (the
"Oppressed" tier); `ListCivilStatusInfo` prints "Occupation forces: Strong/Average" on the same
`result==3` condition, "Weak" otherwise.

**The bug chain (all verified from code):** if `GenerateRebelUnits` returns an *empty* list and the
city has no garrison, the predictor runs with two empty sides → `FinishCombat`'s both-empty
tie-break (`hp0 < hp1 ? 4 : 3` with 0 < 0 = false) → **Result 3** → `GetSuperiority`'s
`total == remaining` special case (0 == 0) → **999** → bonus **+75** → loyalty −35+75 = 40 →
**status 6, "Oppressed", with zero troops in the city** (and "Occupation forces: Strong" in the
tooltip). Because `CheckRebellion` only rolls for status < 2, such cities also *never rebel*.

When is the rebel list empty? `FillWithRandomUnits` gives up after **50 consecutive invalid
draws** from the race's unit roster; a draw is valid only if the unit resource exists, **unit type
∈ mask `0x03`** and **level ≤ 2** (city rebels; generic-structure raze defenders use mask `0x07`,
level ≤ 4). Verified filter internals (2026-07-09): type = `TUnit.GetUnitType` (slot 0x114) =
**resource byte +0x30**; level = `TUnit.GetUnitLevel` (slot 0xA0) = **resource byte +0x2F**; the
final `CanAddUnit` check (list slot 0xA4 → unit slot 0x11C `CanAddToList`) is a verified
**`return 1`** — no combat-worthiness test of any kind exists.

**Likelihood correction (user roster data):** every race has ~4 tier-1 units (≥3 non-machine) plus
tier-2s in a ~12-unit roster, so ≥3–6 valid draws of 12 ⇒ 50 consecutive misses ≈ `(0.75)^50` ≈
6×10⁻⁷ at worst — **the empty-roster path is unreachable for standard races.** It remains real only
for degenerate rosters (editor-made city with an unset/exotic race byte whose list has zero valid
entries → *always* empty). The both-empty → Result 3 → 999 chain is therefore an edge-case
correctness hole, **not** the everyday explanation.

## 10b. The actual explanation: "Oppressed" is (partly) vanilla design — walls oppress

Verified label table (exe display code @`0x443477`: `TCivilStatusRStr[status]`, an AOWEPACK export
@VA `0x558E8E10`, strings decoded from RT_STRING): **0 Unruly, 1 Unrest, 2 Stable, 3 Content,
4 Cheerful, 5 Oppressed, 6 Enslaved.** So Oppressed/Enslaved = loyalty 10–29 / ≥30 under
relation < 2, as assumed.

The two mystery city bytes in the vanilla loyalty formula are now identified:
**`city+0x4C` = WallType** (written by `TCity.SetWallType` @`0x557AC984`) and **`city+0x4D` =
UpgradeLevel** (1..GetSize, written by `TCity.SetUpgradeLevel` @`0x557AC75C`). Vanilla:

```
loyalty = relationBase(−35/−25/0/+15/+25)
        + WallType×5 + UpgradeLevel×5
        − 10 if city terrain in race's penalty set, +10 if in bonus set
        + garrison bonus (predictor, only when relation < 2)
```

A developed size-4 city with stone walls contributes `2×5 + 4×5 = +30` (±10 terrain) with **no
garrison and no sim**: Dislike (−25) + 30 + 10 = **+15 → status 5 "Oppressed"**. That is the
everyday no-garrison "Oppressed" city: **vanilla design, not a bug** — fortifications and
development literally suppress the populace (which is also why razing walls/buildings ties into
loyalty). Hate (−35) tops out at +5 → Stable, so vanilla no-garrison Oppressed happens for
*Disliked* races in walled, developed cities.

**Note:** the user's old undocumented city mod (§0b) zeroed exactly these three terms — on the
current live build the vanilla path is dead, and loyalty = relation base + garrison bonus only.
So: sightings from vanilla-era play are fully explained; sightings on the *current modded build*
would require the exotic paths (empty-roster editor race, or a garrison standing on an outlying
city-footprint hex — `ListArmies` covers all the city's hexes). To be confirmed by the user which
build the observations came from.

**Remaining genuine bugs in this area:** (a) the flyer hole — a single Great Eagle garrison "wipes"
melee-only rebels in-sim → +50/+75 → Oppressed/Enslaved as a *garrison* bonus (same exclusion bug
as razing; fixed by the §8 B/C/D flag applied to these Execute calls); (b) the 999-on-empty edge
(fixed by Patch E); (c) mislabeled semantics if one expects "Oppressed" to mean garrison-only —
that's a design-taste knob (the old mod's zeroing *is* one possible answer).

**Fix (razefix Patch E, planned):** in `GetCivilStatus` and `ListCivilStatusInfo`, grant the bonus
/ "Strong" label only when `result == 3` **and the garrison side is non-empty**
(`TCombatPredictorSide` at `predictor+0xC` extends TList; count at `+8`). One shared cave, two
5-byte hooks at the `Execute`-result tests. Optionally set the §8 fair-economics flag around these
two `Execute` calls as well (same cave_exec), so a lone-eagle garrison stops counting as a
sufficient occupation force. Note `GetSuperiority`'s `0==0 → 999` could be fixed centrally instead,
but that changes every AI consumer — the scoped guard is safer.

## 12b. Raze-as-real-battle v2 — the EXPLORATION-SITE pattern (2026-07-09, verified blueprint)

User insight that changed the design: exploration sites can be **walked over freely** — their
defenders are NOT a placed army. Verified: `TExplorationSite.Create` @`0x557C17CC` builds a
**hidden `TDefendersArmy` (a `TArmy` subclass, class-ptr @`0x557C1274`) stored in `site+0x34`,
never placed on the map**; `GenerateDefenders` fills it (budget 50×site-level, level ≤ 4, seeded
from `Map+0x230`). The battle happens only when the player activates *Search* — co-located with
the visiting army. This is the raze-battle mechanism, wholesale:

* **`Search` @`0x557C1E5C`** (action entry): single/hotseat → shows **`TCombatTypeRequestEventLog`**
  (the vanilla manual/fast ask) with `RequestCombatTypeCallBack` @`0x557C1DBC`; MP → issues the
  structure TE directly (slot 0x160 CreateTE / 0x164 SetupTE, `TE[+0x18]=0` = search action,
  choice carried **inside the TE** → MP-safe).
* **`ExecuteTE` @`0x557C1D28`**: base `TStructure.ExecuteTE` first (raze TEs use `TE[+0x18]=-1`),
  then search: `slot 0x1FC = ExecuteSearch(combatType from TE[+0x20])`.
* **`ExecuteSearch` @`0x557C1A20`**: hidden army empty → `ExecuteSearchDone(1,3)` (instant win).
  Fast (type 1): `TAoWHSMap.CreateCombat(map, 0x202B0)` → `SetupCombat` → `LockExecuted` → run
  slots `0x68/0x70/0x64/0x74/0x6C` **synchronously**, combat logbook event, `DestroyCombat`.
  Tactical: `CreateCombat(map, 0x220110)` → `SetupCombat` → slots `0x68/0x70`; slot `0x64`
  returning 1 = combat went **modal** (resolution + callback happen later).
* **`SetupCombat` @`0x557C1960`** — the co-location core:
  `combat[+0x2C] := CombatExecuted` (completion callback), `combat[+0x30] := site` (context);
  `combat.slot 0x60` (Setup @`0x55727310`) with attacker player/team, defender player/team from the
  hidden army's `+0x12/+0x16`, and the site's x/y/l; **`TCombat.AddArmy` @`0x55727804`** (visiting
  army, side 0, at site coords); **`TCombat.AddArmyEx` @`0x557279D0`(hidden army, side 1, 1,
  -1,-1,-1)** — defenders join with NO map position; `combat[+0x40] := 1`.

## 12. Raze-as-real-battle: tower pilot design (2026-07-09, SUPERSEDED by §12b — kept for the machinery survey)

User direction: rework razing (ALL razeable structures eventually) so pressing Raze spawns the
defenders and the raze completes only by **winning an actual battle**, fightable as **manual or
fast combat** like any attack. Pilot target: **TTower / watchtower** (single hex, fixed
ruleset-defined defender roster via `TStructure.GenerateRazeDefenders`, no city overrides).

### Machinery discovered — almost everything already exists

1. **The attack pipeline is reusable wholesale.** `TArmyCombatMoveTE` (Setup @`0x55748918`,
   SetupCombat @`0x55748D18`, ExecuteCombat @`0x55749924`, CombatExecuted @`0x557496D4`) is the
   turn event that runs every attack: it decides/asks combat type via
   **`TCombatTypeRequestEventLog`** (the vanilla "manual or fast?" dialog —
   `RequestCombatTypeCallBack` @`0x557489CC`), honors the registry combat-resolve mode, handles
   hotseat "You are being attacked", network token activation, AI-vs-AI instant resolve, and builds
   the `TCombat` (`Create` @`0x5572708C`, `InitDefaultArmies`; structures are notified via map-field
   msg `0x1107` and can inject battlefield info — walls). **We never construct a combat ourselves:
   we arrange the map so a normal attack happens.**
2. **Exploration-site precedent:** `TExplorationSite.NewDay` @`0x557C20A4` generates defenders
   **once on day 1** as a real garrison army on the site — entering = ordinary attack. Confirms the
   engine-idiomatic way to make a location contested is "put a real army on it".
3. **Displacement primitive exists:** `TCity.MoveArmiesOutOfCity` @`0x557AA808` — used by
   `CheckRebellion` to shove garrison armies out before spawning rebels *inside*. Exactly the tool
   for the co-location problem (the razing army stands ON the structure it razes).
4. **Vanilla militia wiring:** `PlaceRazeDefenders` @`0x5575FE84` (places roster at the structure)
   + `SetupRazeDefenderAG` @`0x5575FE0C` (sets independents to war relation via
   `UnitsToIndependentRelation`, creates AI group kind 0xD = `TDefenderAG` — militia defends/attacks
   via the independents' AI turn).
5. **Save-persistence precedent:** a "raze pending (player P)" marker must survive save/load; the
   project has already shipped exactly this class of patch (`build_spellcast_persist.py` ReadWrite
   extension) — reuse the pattern for `TStructure`/`TTower`.

### Pilot flow (towers)

1. Raze clicked (army on tower) → confirm dialog, enriched with the **militia preview** (§11 —
   exact roster, since it's seed-deterministic).
2. `ExecuteRaze` (tower path): **do not** `SetRazed`. Instead: displace the razing army to an

4. **Completion hook** in the structure's combat-aftermath path (the `0x1107` msg family /

5. AI razing: same flow — the AI's group control already attacks hostile armies on its targets.

## 11. Militia preview + generator tunables (2026-07-09)

**Raze-preview ("show what would spawn before committing") is cleanly implementable** because the
roster is a pure function of `(structure position, per-game map seed)` — §5. Previewing at
click-time and spawning at commit-time provably yield the identical unit list (same game, any day),
and the generator save/restores `RandSeed` (city variant), so previewing is side-effect-free.
Implementation: the intermediary step already exists — the Yes/No confirm dialog built in
`TStructure.Raze` @`0x557602F8` (human path only; AI skips it). Hook the dialog-assembly sequence
(it already appends `RazeStructureWarning` + `DoYouWishToContinue` lines via
`msg[8].Add(string)`): a cave calls `GenerateRazeDefenders` (slot 0x1A8) into a temp list, appends
one line per unit (or grouped "N × Name" — `GetName` is slot-based, string ops via the same
`LoadResString`/`Translate`/`LStr*` helpers the surrounding code uses, all rel32-callable), frees
the ghosts. ~1 hook + a string-loop cave. Works identically under the current gate flow and the
spawn-first design (where it becomes the user's "intermediary step").

**Generator tunables** (all single-byte patches, shared by rebellion spawns, raze militia and the
civil-status sim — the three consumers of `GenerateRebelUnits`):

| knob | site | vanilla |
|---|---|---|
| city militia max level | the `2` passed by `GenerateRebelUnits` to `FillWithRandomUnits` | ≤ 2 |
| city militia budget | `GetSize() × 0x19` multiplier in `GenerateRebelUnits` (`0xABCC?`) | 25/size |
| city militia type mask | `DAT_557ABD30` | `0x03` |
| structure defender max level / mask / cap | `GenerateRazeDefenders` @`0x5575FD1C` | ≤ 4 / `0x07` / 8 units |

Raising budget does **not** fix empty rosters (budget is not the failure mode — the filler even
overshoots for its final pick); raising max level / widening the mask shrinks the empty case but is
a real balance change (tier-3/4 rebels). The correctness fix is a **fallback cave**: after the
50-draw loop, if the output list is empty, do a deterministic linear scan of the race roster and add
the first valid unit; if literally none is valid, return empty and let Patch E handle the status
display. Cities never trim their militia (structures trim to 8), so budget increases scale
head-count without limit — mind rebellion spawns.
