### The melee round — strike order, and why First Strike cancels Charge (read 2026-08-09)

`TMeleeRound` builds the whole round up-front as a strike list, then executes it. **Two parallel
copies of the same logic**, and a mod that touches one must touch the other:

| | real combat (`TCombatObject`, vmt `+0xA8`) | prediction (`TAbstractUnit`, vmt `+0x148`) |
|---|---|---|
| set-up | `Calculate` @`0x55767D24` | `CalculateUnit` @`0x55767A3C` |
| build | `CalculateStrikes` @`0x55767B24` | `CalculateUnitStrikes` @`0x557677CC` |

`Calculate(self, attacker, defender)` — `[self+0x10]` attacker, `[self+0x14]` defender (argument
order fixed by `TStrikeAbility.fcExecuteCombatCommand` @`0x55766FCC`, which passes its own unit then
`[cmd+0x18]`). Strike counts: `[self+0x28]` attacker = 2, **+1 for ExtraStrike `0x73`**;
`[self+0x2C]` defender = 2, **no ExtraStrike check** — matching the card's "when on the offense".
Either is forced to 0 by no melee damage types or by `GetLocked` (vmt `+0x64`).

It then computes one boolean and passes it on:

```
flip = defender.HasAbility(0x74 FirstStrike)
    && !attacker.HasAbility(0x74)        // both sides having it cancels out
    && [self+0x2C] != 0                  // a defender who cannot strike back cannot strike first
```

`CalculateStrikes(self, flip)` seeds `side = flip` and alternates. Total strikes are unchanged
(`SetCount([0x28] + [0x2C])`) — **it is a pure reordering, not an extra swing.** Inside, gated on
`i == 0 || (i == 1 && side != flip)`:

- **Charge `0x6F`** — `+2` damage vanilla, **`+5` live** (byte-checked 2026-08-27 at `0x55767BCA`
  and `0x55767872`: `83 43 04 05` live vs `83 43 04 02` pristine) only when `side == 0 && i == 0`, i.e. only on the
  round's opening strike *and* only when that strike belongs to the attacker.
- **Parry `0x71`** — `-2` attack vanilla, **`-8` live** (byte-checked 2026-08-27 at `0x55767BE1`
  and `0x55767889`: `83 2B 08` live vs `83 2B 02` pristine; `Ability.pfs` record 123 agrees — cost 8
  and card text rewritten to say `-8`, so it is deliberate, not a doubling artefact) on the target
  of the first strike of **each** side, so ordering does not affect it. At the live 5 pp slope that
  is **−40 percentage points**. ⚠ Parry's only two call sites in the whole DLL are
  `TMeleeRound.CalculateStrikes+0xB3` and `CalculateUnitStrikes+0xB3` — **it does not apply to
  ranged attacks at all**.

⚠ **So First Strike negating Charge is emergent, not a coded interaction.** With `flip = 1` the
defender takes index 0; the attacker's opening strike lands at index 1, where the `i == 0` test
fails, and the Charge branch is simply never reached. Nothing anywhere mentions Charge and First
Strike together — grepping for a link would find nothing and conclude wrongly.

**Live vs pristine** (byte-diffed against `AoWEPACK_original_backup.dpl`, and Ghidra's image is
vanilla so this is mandatory): `Calculate` and `CalculateUnit` are **byte-identical**;
`CalculateStrikes`/`CalculateUnitStrikes` differ only in the Charge and Parry **immediates** (both
copies retuned in step) plus the `build_assassin.py` cave jump at `0x55767C5C`. **The ordering and
gating logic is stock**, so the above describes the installed game as well as vanilla.

Only two combat consumers of `0x74` exist. Other id loads are red herrings: `0x5576761B`–`0x55767657`
is a run of `TAbilityControl.UnregisterAbilityID` teardown calls, and the `b2 6f` / `b2 74` hits at
`0x557E6F31` / `0x5574AF5B` disassemble as mid-instruction noise.

# FEATURE 1 — Make unit SIZE obstruct missiles / line-of-fire

> ⚠ **Corrected 2026-08-09 — see [`Missile_Trajectory_And_Interception.md`](Missile_Trajectory_And_Interception.md).**
> The 2026-07-08 verdict below ("no LOS code exists anywhere, blocking is net-new code") was derived
> **only from `AoWEPACK.dpl`** and is true only of **auto-resolve**. **Manual tactical combat already
> has a complete per-hex probabilistic missile-interception system** in **`AoWTCPCK.dpl`**
> (`AoWTC.MakeRangedPath` @ `0x00427630` builds a real pixel-space arc and an obstruction list;
> `CombatTE.TCAbRangedTE.NextStrike` @ `0x0040D290` rolls it and **retargets the shot onto the
> blocker**). Intervening units, wall segments, Obstacle-overlay hexes and EarthWall/Border terrain
> all block; the **flight arc height is the anti-blocking term**. So "make size matter" is now a
> ~2-byte-to-small-cave job in `MakeRangedPath`'s unit handler (`0x00427C0B`), not net-new LOS code.
> Read that doc before acting on anything in this section.

### Verdict (superseded, kept for the AoWEPACK addresses): **size does not block missiles**, and in **auto-resolve** nothing does. Adding intervening-unit blocking *to auto-resolve* = **Hard / Needs-more-RE (85%).** A size-based *cover penalty* = **Feasible (75%).**

### Where SIZE lives
- `TUnit.GetUnitSize` @ **`0x557827F8`** = `*(byte*)( *(unit+0x40) + 0x50 )` → **size byte at `TUnitResource + 0x50`** (unit`+0x40` = resource ptr, same ptr the fire mod uses). Base `TAbstractUnit.GetUnitSize` @ `0x5577F184` just returns 1.
- ⚠ **WRONG, corrected 2026-08-03 by decompile:** combat-object vtable `+0x90` is **`GetAlignment`**, not GetUnitSize — `AoWE.TCombatObject.GetAlignment` returns a constant 6 and `TCombatUnit.GetAlignment` forwards to `[cu+0x4C]->vmt[0xFC]`. `Slayer_Abilities_Design.md` had this right all along. Unit size comes from the resource byte (`TUnit.GetUnitSize` reads `[[unit+0x40]+0x50]`), not from this slot — so the "values ≈ 1–5" range recorded here was never measured from `+0x90` either.

### ⚠ The "slaying" abilities are keyed on ALIGNMENT, not size (corrected 2026-08-09)
`CreateStrikeCA` @ `0x557665E4`, `StrikeDV` @ `0x557664B0`, `TMeleeRound.CalculateStrikes` @ `0x55767B24`
all read the **target's** combat-object `vmt[+0x90]` for the "slaying" abilities:
- ability `0x92`/`0xA0` → `+2 atk/+2 dam` when `(byte)(v - 4) < 2`, i.e. `v ∈ {4,5}`.
- ability `0x93`/`0xA1` → `+2 atk/+2 dam` when `v < 2`, i.e. `v ∈ {0,1}`.

**`v` is `GetAlignment`, not unit size** — re-verified 2026-08-09 off the correct VMT bases
(`AoWE..TCombatUnit` = `0x55715A94`, `AoWE..TCombatObject` = `0x557158EC`; **both `+0x90` hold
`GetAlignment`**). This section previously described the same two comparisons as "slay large / slay
small", contradicting the `+0x90` correction recorded a few lines above it. Do not re-derive the
size reading.

**Unit size is not reachable from a combat object at all.** No `TCombatUnit` VMT slot holds either
`GetUnitSize`, and **neither `TUnit.GetUnitSize` @ `0x557827F8` nor `TAbstractUnit.GetUnitSize`
@ `0x5577F184` has a single code caller in `AoWEPACK.dpl`** — every xref is a DATA reference (VMT
entries + `.edata`). Size reaches the game through the unit-side VMT slot only; who calls *that* is
still unresolved (candidates: `AoW.exe` / `AoWDevEd.exe`, both of which import the DLL).

**Measured size data (installed `Release/Unitres.pfs`, .pfs tag `0x1C` = `TUnitResource+0x50`,
2026-08-09)** — this answers the "risks/unknowns" question at the end of this section:
`0` = 21 units (Frostlings, Halflings, Fairy, Leprechaun) · `1` = 81 (standard infantry) ·
`2` = 52 (cavalry, Beholder, Sandworm, war machines) · `3` = 25 (Elephant, Titan, Giant, dragons,
Air Galley). **Range is 0–3, never 4–5.** So had the slaying abilities been size-keyed, "slay large"
could never have fired — which is corroborating evidence that they are not.

### The AUTO-RESOLVE ranged path (no unit blocking) — this part is still accurate
- Fire loop: `TRangedAttackAbility.fcExecuteCombatCommand` @ **`0x5576EB70`** → builds N shots via
  `CreateRangedAttackCA` @ **`0x5576EAE4`** → `TCombat.ExecuteCombatAction`. No hex-walk, no
  intervening-object scan.
- The **only** line-of-fire term is **walls**: `TFastCombat.GetWallInBetween` @ `0x55744600` /
  `TFastCombatUnit.fcWallInBetween` @ `0x557441DC`, and `GetWallSituation` @ `0x5574468C` (called in
  fcExecuteCombatCommand) → sets a `−2` cover penalty (`local_14=2`, subtracted in CreateRangedAttackCA:
  `uVar4 = attack − param_4`). ⚠ `GetWallInBetween` is **not geometric** — it compares the two
  parties' "inside the walls" flags (`party+0x18`, party index = grid byte `>>4`), i.e. "are these two
  on opposite sides of the siege wall". No line is traced.
- The user's `cave_5580C240` adds only a **height/elevation −2** (reads `GetLocation` Z, waived if the
  target has NightVision `0x27`). Still not size.
- ⚠ **Do NOT repeat the 2026-07-08 search mistake:** grepping `AoWEPACK.dpl` for `Missile`, `LOS`,
  `Cover`, `Intercept`, `Obstruct` returns nothing, and that was read as strong negative evidence for
  the whole game. It is not — the tactical system lives in **`AoWTCPCK.dpl`** and is named
  `MakeRangedPath` / `MakeAbilPath` / `TRangedPathHS` / `EvalPath`. **Search every combat module, not
  just AoWEPACK, before concluding a combat mechanic does not exist.**
- Manual tactical combat calls the *same* `CreateRangedAttackCA` but always passes cover
  penalty **`0`** (`push 0` at `0x0040C41D` in AoWTCPCK) — so the −2 wall penalty is an
  auto-resolve-only effect.

### Proposed patch approach
1. **Cheap, feasible (recommended if the user accepts an approximation):** mirror the existing wall/height
   cover in `CreateRangedAttackCA` @ `0x5576EAE4`. It already has the shooter (`param_1`) and target

   ⚠ **The obvious spelling of this does not compile:** `param_2` is a **`TCombatObject`**, and there is
   **no `GetUnitSize` in any `TCombatUnit` VMT slot** (`+0x90` is `GetAlignment`). Getting from a combat

   `Missile_Trajectory_And_Interception.md` §6.
2. **True intervening-unit blocking:** ⚠ **already exists in manual tactical combat** — see the banner at

   needed if you want it in **auto-resolve too**, and even then the tactical implementation

### Risks / unknowns
- ~~Exact size enum values~~ **ANSWERED 2026-08-09: sizes are 0–3** (21 / 81 / 52 / 25 units across the

# FEATURE 2 — Lifesteal on Round-Attack hits, and on Defensive (retaliation) hits

### Verdict: **Round-attack lifesteal = Feasible (confidence 90%). Defensive lifesteal = Feasible (85%).** Root cause fully isolated.

### Mechanism (vanilla)
- **Life Stealing = ability `0x76`** (confirmed: `RegisterStrikeAbilities` @ `0x557672B4` registers it from
  `AoWE_LifeStealingRStr`). Effect: on a **landed melee hit**, heal the **attacker** (+1 HP vanilla; the
  user's `cave_5580C150` already bumped it to +2).
- It is driven by a **flag bit `0x02` in the StrikeCA at `CA+0x18`**:
  - **Set** only in `TMeleeRound.CreateStrikeCA` @ `0x55767E68`, **offensive branch** (`strike[0xC]==0`),
    at `0x55767EDA`: `mov edx,0x76 ; call [attacker+0xA8] (GetAbilityEnabled) ; or [CA+0x18], DAT_55767F54`
    where **`DAT_55767F54 = 0x02`**.
  - **Consumed** in `TStrikeCA.Execute` @ `0x55766792`: `test [CA+0x18],2` → (if strike landed & target is a
    TCombatUnit & `defenderUnit.[0x114]()!=2`) heal attacker via `GetHitPoints`/`SetHitPoints`
    (`+0x88`/`+0x8C`). In live this `test`+heal is redirected to `cave_5580C150`.

### Why it misses round-attack and defensive hits
- **Round attack** (`TRoundAttackAbility.fcExecuteCombatCommand` @ `0x55769458`, byte-identical to vanilla)
  builds every hit through the **global** `CreateStrikeCA` @ `0x557665E4` — **not** `TMeleeRound.CreateStrikeCA`.
  The global builder **never checks ability `0x76`**, so `CA+0x18` bit `0x02` is never set → no heal.
- **Defensive / retaliation** goes through `TMeleeRound.CreateStrikeCA`, but the **defensive branch**
  (`strike[0xC]==1`, code at `0x55767EFB+`) also **omits** the `0x76` check (only the offensive branch has
  it). So a retaliating lifestealer never sets the flag → no heal.

Both are the *same* omission: the ability-0x76→flag line only exists in one of the three StrikeCA builders.

### Proposed patch approach — AoWEPACK.dpl (both auto-resolve; mirror in AoWTCPCK.dpl if manual combat also needed)
- **Primary (round attack):** hook the tail of **global `CreateStrikeCA` @ `0x557665E4`** (just before it
  returns `piVar6`, the finished CA). Cave: `mov edx,0x76 ; mov eax,attacker(param_1) ; call [eax+0xA8] ;
  test al,al ; jz skip ; or byte [CA+0x18], 0x02`. Attacker = `param_1` (EAX at entry). This reuses the
  **existing** heal (cave_5580C150) automatically — no change to the consumer.
- **Secondary (defensive):** hook the defensive branch of **`TMeleeRound.CreateStrikeCA` @ ~`0x55767F47`**
  (after the `call [ + 0x68]` setup), same 3-line check but on the retaliator = `*(param_1+0x14)`, then
  `or [CA+0x18],0x02`. (Another modder wants this specifically.)
- Both caves are register-only + rel32 (position-independent). `DAT_55767F54` value `0x02` can be hard-coded.

### Risks / unknowns / notes
- The consumer still gates on `defenderUnit.[0x114]() != 2` and "strike landed" — lifesteal on round/defensive
  will (correctly) only trigger on hits that actually connect and on eligible target types, same as normal melee.
- Confirm the object passed to the flag-check is the **attacker** combat object (global CreateStrikeCA: `param_1`;
  defensive branch: `[param_1+0x14]`) so `+0xA8 GetAbilityEnabled(0x76)` resolves on the right unit.
- If the user wants round/defensive lifesteal to use the **same +2 (and 0xA9 tier)** as normal melee, nothing
  extra is needed — all three paths share `cave_5580C150` once the flag is set.
- Ability `0xA9` (the cave's 2nd heal tier) was not fully identified (not in the two registrars scanned; likely
  a class ability). Not required for the primary goal.

# FEATURE 3 — Enchanted Weapon for MUNDANE RANGED attacks (+atk/+dam like Marksmanship, + Magic damage type)

### Verdict: **atk/dam bonus = Feasible (confidence 85%). Magic damage-type OR-in = Feasible (85%).**

### Mechanism (vanilla)
- **Enchanted Weapon = ability `0x9A`** (`TEnchantedWeaponAbility`, `.Create` @ `0x557BB058` sets id at
  `+0xC=0x9A`). It overrides `GetAttack` @ `0x557BB0EC` = **2** and `GetDamage` @ `0x557BB0F0` = **2**.
- **Melee** picks these up two ways, both of which the **ranged path bypasses**:
  1. atk/dam: `TAbilityOwner.GetAbAttackAll` @ `0x5574F624` / `GetAbDamageAll` @ `0x5574F714` sum
     `ability.[+0x5C]` (GetAttack) / `ability.[+0x68]` (GetDamage) over all enabled abilities → EnchantedWeapon's
     +2/+2 land in the unit's melee attack/damage.
  2. magic type: `TStrikeAbility.GetDamageTypes` @ `0x55766DE4` ORs the **Magic bit `0x08`** (`DAT_55766F58`)
     when the unit has ability `0x14` **or `0x9A`** (checked via unit `+0x148`). `MeleeDamageTypes` @
     `0x55766420` just calls this, so round-attack/melee both get Magic from Enchanted Weapon already.
- **Ranged stats are computed independently** (that's the whole reason Enchanted Weapon does nothing to them):
  - attack: `GetAttackRA` @ `0x5576E65C` = `ability+0x2A` **+ marksmanship(0x20) only** (vanilla ladder
    L1/L2 +1, L3/L4 +2; live = user cave_5580C240). It does **not** call `GetAbAttackAll`.
  - damage: ranged-ability vtable **`+0x114`** getter (`GetDamageValue` @ `0x5576E764` reads it; base ranged
    damage field, marksmanship-adjusted) — also independent of `GetAbDamageAll`.
  - damage type: `GetDamageTypesRA` @ `0x5576E6B0` = `ability+0x2B` (2 bytes) — the unit's innate ranged
    type only; never consults ability `0x9A`.

### Marksmanship is the exact template
`GetAttackRA` reads the base then queries the shooter for ability `0x20` (`+0x88` enabled, `+0x84` level) and
adds a bonus. Duplicating that pattern for ability `0x9A` is the model the request asks for. The shot is
assembled in `CreateRangedAttackCA` @ `0x5576EAE4`, which **has the shooter as `param_2`** and calls the
ranged ability's `+0x110` (**damage** - measured `AoWE.TRangedAttackAbility.GetDamageRA` 2026-08-03; this doc previously said attack), `+0x114` (**attack**) and `+0x11C` (GetDamageTypesRA) to fill the CA — this is

### Proposed patch approach — AoWEPACK.dpl, one cave on `CreateRangedAttackCA` @ `0x5576EAE4`
1. **(a) +atk/+dam:** after the `+0x110`(attack) and `+0x114`(damage) results are read, if
   `param_2.GetAbilityEnabled(0x9A)` (combat vtable `+0xA8`) → add `+2` to each (mirror Enchanted Weapon's
   GetAttack/GetDamage constants; or read them live via the ability if you prefer to honour future data edits).
2. **(b) Magic type:** the final damage-type word comes from the `+0x11C` (GetDamageTypesRA) call inside the
   same function; OR-in **`0x08`** when `param_2.GetAbilityEnabled(0x9A)` before it is stored into the CA.
- Alternatively hook `GetAttackRA` (extend the existing cave_5580C240) and the `+0x114` getter and
  `GetDamageTypesRA` separately — but those getters don't all receive the unit, so the CreateRangedAttackCA
  hook is preferable.
- Binary: AoWEPACK.dpl (auto-resolve/fast). For **manual** tactical ranged, verify AoWTCPCK.dpl's ranged CA
  build (re_tools) and replicate; the type/stat model is shared but the driver differs per binary.

### Risks / unknowns / failed leads
- The `+0x110/0x114/0x11C` calls in `CreateRangedAttackCA` show inconsistent arg counts in the decompiler —
  read the real instructions at build time to place the OR/adds correctly (register + rel32, position-independent).
- Confirm whether the vanilla ranged **damage** getter (`+0x114`) already adds marksmanship (so "like
  Marksmanship" means matching it); if the user only wants attack, skip the damage add.
- Enchanted Weapon is a unit **enchantment** ability — confirm it is present/enabled on the shooter object the
  ranged CA is built for (it should be; `GetAbilityEnabled(0x9A)` is the same query melee uses).
- Do **not** globally alter `GetDamageTypesRA`/`ability+0x2B` (would give *every* ranged unit Magic); the
  condition must be per-shooter `HasAbility(0x9A)`.
- Watch cave placement vs the pre-existing caves (`0x5580C000–0x5580C3FF`, `0x5580D900+`).
