## The decisive discovery: movement cost is a (terrain × overlay) matrix

`TMoveControl.DefaultMoveOnMovePointProc` (`557454D8`):
`cost = table[0x31 + terrain*16 + overlay]` — terrain = `field+0x14` (row), overlay =
`field+0x15` (column, −1..0xE ⇒ the +0x31 bias). Each movement **ability** has its own 256-byte
16×16 base table, **static data in AoWEPACK.dpl** — directly file-patchable:

| # | VA | Ability (names per the user's movement-table notes) |
|---|---|---|
| 0 | `558E84FC` | Walking |
| 1 | `558E85FC` | Swimming / Water Walking / Liquid Form |
| 2 | `558E86FC` | **Flying / Floating / WW — ONE SHARED TABLE** |
| 3 | `558E87FC` | Forestry |
| 4 | `558E88FC` | Cave Crawling |
| 5 | `558E89FC` | Mountaineering |
| 6 | `558E8AFC` | Fire Immunity / Fire Halo |
| 7 | `558E8BFC` | Tunneling |

Full table/row/column reference: `Movement_Tables_Terrain_Types.md`. Two consequences for this
design: **(a) Flying and Floating automatically travel together** — the "can't be bothered to
split them" outcome is the engine default; splitting would mean a 9th table + movement-type
byte surgery. **(b) The installed tables are Ziggurat-rebalanced (277 cells differ from
vanilla)** — the build script must verify-before-write against installed values.

At startup `SUB_L55744B2C` (`55744B2C`) builds all 256 ability-combo tables into
`MovePointTables` (`558EA040`, BSS, 64 KB) by combining the base tables (best cost per cell).
**Patch the base tables in the file → every unit, the AI, and the path preview all follow.**

- 0xFF = impassable (sign-extended −1).
- Overlay identities decoded from the tables: ov0 mountain, ov1 forest, ov2 hills, ov4 & ov7
  road types, ov5 bridge-deck-on-water (walking 3!), rest partially known.
- **Overlay columns 0xA, 0xD, 0xE are all-0xFF in every one of the 8 tables — completely
  unused.** Free slots.

## CHOSEN ARCHITECTURE (2026-07-24, per user): appropriate terrain IDs 0xB and 0xE

**User ruling: `uWasteland` (0xB) and `Coast` (0xE) are unused-in-practice terrain types, free
to appropriate.** So Chasm and Sky get REAL terrain bytes after all:

- **Chasm = 0xB** (ex-uWasteland — already an underground-flavoured row)
- **Sky = 0xE** (ex-Coast — surface row; its water-variant config gets overwritten)

This beats the overlay plan on every player-facing axis: own tile art via hexagon resources,

normal editor terrain placement, and spells/storms can be taught about them by ID.

   ### ⚠ THE `.hss` CRC — why the first attempt failed, and how it is fixed
   `Release.hss` ends with a **CRC-32 of everything before it**:
   `HSEngine.THSEngine.LoadHSS` (HSEPack `5560F75C`) does
   `stored = *(u32*)(file+size-4)`, `calc = GetCRC32(file, size-4)`, and on mismatch raises
   `Exception('Invalid HSSET')` — unhandled during startup, so **AoWDevEd and AoW.exe both
   just vanish with no dialog**. `Engine.GetCRC32` (EngineP `5550E608`) is textbook reflected
   CRC-32, identical to `zlib.crc32`; **its table is built at runtime**, which is why scanning
   the binaries for a static CRC32 table finds nothing. Repair with
   `re_tools/hss_crc.py <file> --fix` (or `hss_crc.fix(bytes)`), which the build script does
   automatically after splicing. Verified: pristine `Release.hss` and the `Ziggurat upload`
   copy both validate; the patched file validates after repair and loads.
   - **Do not confuse it with `TEngine.ReadFromFileCRC`** (EngineP `5551C084`) — a *different*
     container used by other file types, which stores its CRC in the **first** dword and
     covers `file[4:]`. `.hsm`/`.csm` maps are neither (they start with the `"CFS\0"` magic).
   - Lesson recorded in [[aow1-investigation-traps]] terms: I spent a long detour concluding
     ".hss cannot be patched" from black-box A/B tests and wrote it up as fact. The answer was
     a single exported symbol away — **`EngineP.dpl!Engine.GetCRC32`** — and the user had it in
     their own 2021 notes. Search *every* loaded module's exports for the mechanism before
     declaring something impossible from symptoms alone.
   - ⚠ Also true: a stale `AoWDevEd.exe` from a previous launch will make a naive
     "is it still running?" check match the OLD process. `taskkill /F /IM AoWDevEd.exe` and
     wait before judging any launch.

   Measured against the user's live map ("Cooperative Map Project Bing+The Groll 3"):
   map deep water V=0.37 S=0.53 hue 220°; land S 0.41–0.48; vanilla pixel grain ~10–13
   neighbour-contrast; **saturated colour is reserved for small magical accents** (glows,

   So: Sky parks **between** the map's shadow overlays (0.28) and open water (0.37) at
   V 0.30 / S 0.49 / hue 242°, with a ±3% hash-dither that also kills RGB565 banding, and
   bright pixels capped to CREAM `(238,234,216)` — bright, never pure white. Chasm sits far
   **below** both, which is what makes it read as a hole rather than a surface.

   ### v2 grade (applied 2026-07-30) — two different pipelines, one per terrain
   v1 built both terrains the same way: window-sample the 256×256 source after a `shrink=2`
   **max-pool**, then grade per pixel. The user's verdict on the result was *"the stars are
   too high-frequency"*, and that is a structural fault, not a knob:
   - max-pooling by 2 means one 48×32 tile covers **96×64 source pixels ⇒ ~33 stars per
     hex**, and
   - it destroys the artwork's 4-point diffraction sparkles — each one is pooled down into a
     shapeless dot, and everything acquires 2×2 blocky steps.

   **Sky (0xE) — the two frequency bands are now generated separately.**
   | layer | how |
   |---|---|
   | nebula | source box-downscaled **8×** then blurred, sampled back **magnified** (`mag=2`). At down=8 even the brightest star (peak 214) spreads over 64 px = +3 of value, so the dust is gone *by construction*. |
   | stars | local maxima of the **original** art (37 of them, peaks 95–214) extracted at native size **with their painted spikes and halo**, stamped 1–5 per hex at hashed positions. |
   ⚠ **The nebula must be normalised per tile** (own mean removed, contrast scaled to
   `amp=0.045`) and painted in one fixed hue. Without that the 8 variants have visibly
   different mean brightness and a field reads as a **quilt of 8 stamps** instead of one sky —
   this was clearly visible in the first v2 attempt and is the non-obvious part of the recipe.
   Star count is jittered per tile (`vary`), because a fixed count per hex draws a visible
   grid across the field.

   **Sky variant mix — 85 / 15 (user's call, 2026-07-30).** Most hexes are the calm new sky,
   but a minority keep the v1 dense starfield so the field occasionally shows a *star-cluster*
   hex. `GetRndResource` picks among the 8 variants with **equal weight**, so `dense={7}` =
   one tile = 12.5%, the closest 8 slots can get to 15%. The dense tiles also get
   `dense_stars=2` stamped crosses so the two designs read as related.
   `SkyArt.dense_tile` is the **v1 recipe kept intact** (max-pool `shrink=2`, `boost=2.10`,
   `floor=0.168`, `slope=0.55`, `sat=0.669`, `hue_shift=+14.3°`, `grain=0.055`,
   `star_t=0.55`, `halo=0.45`) — including the max-pool's 2×2 steps, deliberately, since that
   is the look the user asked to retain. Set `shrink=1` there if the blockiness ever needs to
   go: it halves the dust density and keeps single-pixel stars sharp.

   **Chasm (0xB) — no longer a starfield at all** (user: it should read as *a very deeply
   darkened sea*). `Zigmod/Chasm.bmp` is **unused** now. Instead the 16 shipped surface-water
   tiles (`H_Wa2.BMP`, ids **140..155** of `Images/Waterhex.ILB`, read-only) are copied
   **1:1 — no resampling at all**, so the wave texture stays exactly as the artist drew it,
   and re-graded to `base_v=0.115`, `contrast=1.20`, `sat=0.55`, `hue_shift=+8°`
   ("abyss" depth, chosen by the user over a shallower `0.155 / 1.40` candidate).
   ⚠ **The grade is NOT the v1 `V' = floor + slope·V` form.** Plain darkening buries the
   waves: at V≈0.15 the crests and troughs quantise into the *same RGB565 step*, and the
   result reads as flat felt. The v2 grade removes the tile's own mean and **expands** the
   detail about a very low base — field mean far below open water (0.37) and below the map's
   shadow overlays (0.28), wave structure still legible. Reusable lesson for any
   "make it very dark" re-skin in this game.

   ### Judging frequency: render a real hex field, not a tile strip
   A strip of tiles cannot show whether a texture is too busy — the complaint that triggered
   v2 was only visible in a *field*. `--preview` now also renders a mosaic, placed by the
   engine's own transform `HSEngine.HXtoHP` (HSEPack `5560E3B4`):
   **`px = hx*32 + 8`, `py = hy*32 + (hx&1)*16`** — pitch 32, odd columns pushed down 16.
   ⚠ The tile is a hexagon of **area 1056 px** (rows widen 18→48 and back) but the lattice
   cell is only 32·32 = **1024**, so **adjacent hexes overlap slightly**. Do not "correct"
   the pitch to 33 to make those areas match: it is geometrically seamless but not what the
   engine does, and it renders hairline gaps the game never shows. (Cost me one wrong mosaic.)
   Retune loop: edit the knobs in `TARGETS` → `--preview` → `--apply`.

   ### ⚠ THE REAL GOTCHA: RLE row records are 4-BYTE ALIGNED
   The next record starts at **`align4(record_start + reclen)`**, so a row whose `reclen` is
   not a multiple of 4 is followed by padding. The engine does exactly this in the walker
   inside `ImageLib.TRLESprite16.RemapToPixelFormat` (ILPACK `55210AC7`):
   `lea esi,[esi+7] ; and esi,0xFFFFFFFC ; mov ecx,[esi-4]`.
   Almost every hex tile has all reclens divisible by 4, so the padding never shows — but a
   **47px-wide** tile gives `reclen = 4 + 47*2 = 98`, which is not, and it DOES pad.
   Missing this made the decoder desync mid-tile and look exactly like corruption:
   the one `Hu_wl` variant at blob@254993 was **never malformed** — my codec was.
   With alignment handled, **every hexagon tile in the shipped set decodes AND reskins
   byte-identically (0 failures)**, up from 121/131.
   - Two crashes came from this misdiagnosis, both fixed by understanding it rather than
     working around it: rebuilding that tile at 48px (EAccessViolation placing Chasm), then
     rebuilding it at 47px without padding (EAccessViolation in `ILPACK.dpl`
     `TRLESprite16.GrabImage`, "Write of address ..." — the remap walker running off the end).
     **Lesson: when a shipped asset looks corrupt, suspect the reader first.**
   - `clipw`/`cliph` still matter and are still the right dimensions to drive the codec with
     (that tile really is 47px wide by its own declaration) — but 47 vs 48 was never the
     problem, the missing padding was.  The `--rebuild-malformed` path is retained for genuinely
     unparseable tiles but is no longer needed here.
   - Tooling: `re_tools/ilb.py` (ILB directory parser), `re_tools/ilb_rle16.py` (RLESprite16
     codec — round-trip byte-identical on 121 of 131 shipped hex tiles; `reskin()` rewrites
     only literal pixel words so payload length cannot change), `re_tools/hss_crc.py`.
     Tile facts: 48x32, RGB565, type 17, transparent `0x594A`.

## Animation (twinkling stars / drifting gusts) — FULLY MAPPED, **NOT BUILT**

Asked 2026-07-30 ("can we make some of the larger stars animate in a twinkle… replicate
surface water's animation"). Investigated to a complete design, then **declined by the user
in favour of static art** — recorded here so it does not have to be re-derived.

### The blocking fact: a LAND hexagon has no per-frame draw at all
Two unrelated hexagon families render terrain, and only one can animate:

| class | size | parent chain | ShowDynamic |
|---|---|---|---|
| `TAoWHexagon` (all land, incl. Chasm/Sky today) | 0x14 | `Hexagon.THexagon` ← `TAbstractHexagon` ← `TMapObject` | **none — VMT ends at +0x120** |
| `TAoWWaterHexagon` (terrain 0/6, and 0xE in vanilla) | 0x20 | `IsoHex.TLowerIsometricHexagon` ← `TIsometricHexagon` ← `TAbstractHexagon` | `5579AFB4`, VMT slot **+0x124** |

`THexagon`'s VMT genuinely stops one slot short of `TLowerIsometricHexagon`'s (verified by
the class-name shortstring that follows the last slot), so there is no slot to hook. Land
terrain is composited into the cached background **once**; nothing revisits it per frame.
⚠ Do not be misled by the cliff edges being "displaced": a displaced land transition just
draws outside its own hex into the same static background. It is not a per-frame pass.

The dynamic pass is opt-in and self-registering: `TAoWWaterHexagon.UpdateTransitions`
(`5579AD98`), at its very end, does `if [hex+0x10] = nil then [hex+0x10] :=
DynamicIsometricHexagonClass.Create` (slots +0x120 then +0x20). That companion is a
`TDynamicIsometricHexagon`, whose `Show` (HSEPack `55619A00`) is one line —
`call [ [self+4]^.vmt + 0x124 ]`, i.e. "forward to my owner's ShowDynamic".
**So: no water hexagon ⇒ no companion ⇒ no animation.**

### The animation engine, decoded (`TAoWWaterHexagon.ShowDynamic`, `5579AFB4`)
Everything a twinkle needs already exists, as *data*:
- `[hex+0x18]` = **signed** frame counter, `inc`'d per frame. Negative ⇒ draw nothing, so
  0x80..0xFF is the idle wait. Reaching 0 starts a new animation.
- At counter 0 it rolls an animation id into `[hex+0x19]`: **20–29** (common), **30–39**
  (rare — `RandInt(300)==0`, gated on the hex having no land neighbour and a map flag),
  **50–58** (≈30% in the other branch). Open-water vs coastal animations.
- The id indexes the resource's `TImageSequenceList` (`resource+0x24`); each entry is a
  `TImageSequence` chained by `+0xC` (several may overlap), frames come from
  `GetUnloopedFrameIndex(counter)` and are blitted at the sequence's own `+0x24`/`+0x28`
  offset. Frame index −1 ⇒ finished.
- When nothing drew, the counter is reset to `0xEC − RandInt(25)` or `0xF6 − RandInt(25)`
  (≈20–44 idle frames) depending on `AoWEngine[+0x6D]` — which is also the master
  "animations on" flag tested at the top of the function.
- `[hex+0x14]` = 6-bit **land-neighbour mask — bit d set when the neighbour in direction d+1 IS
  land** (this doc was RIGHT; a "correction" to "open-water mask" on 2026-08-03 was itself wrong and
  is retracted). `UpdateTransitions` sets bit d only when the neighbour owns **no**
  `TLowerIsometricHexagon` and no `TBorderHexagon` — and `TLowerIsometricHexagon` is the **water**
  family (`TAoWWaterHexagon`'s own parent classref is `0x558FCD70`, the very classref passed to
  `FindOwnedHS`). No water hexagon there ⇒ the neighbour is land ⇒ bit set.
  `[hex+0x15]` bits 0/1/5 = differing-liquid
  edges, bits 6–7 = a per-hex tile phase seeded in `Create` by `RandInt(4)<<6`.
- `TAoWWaterHexagon.Show` (`5579AEAC`) picks its base tile as
  `0x8C + ((field>>3 + hx + 2·hy + (flags>>6)) & 0xF)` — **16 base variants, ids 140..155**.

### Where the art lives — loose ILBs, no `.hss` work needed
- `Images/Waterhex.ILB` — ids **140..155** the 16 `H_Wa2` base tiles; **0..31** `t_wa-gr`,
  **40..71** `t_wa-sn`, **80..111** `t_wa-wl` shore transitions (86×84); 35..37 ice-water.
- `Images/WaterAnm.ILB` — **97** frames `Water000..096.BMP`, type 22 **Sprite16 =
  uncompressed RGB565 of the clip rect**, so re-skinning or adding frames is a plain pixel
  write (`re_tools/ilb.py`).
- `Images/Effects/TwinkGr.ILB` already ships 233 twinkle sprites, incl. `STwinkBlue00.BMP`
  16×16 and a 9-frame 40×40 `GreenTwinkle` — ready-made twinkle art if this is ever built.
- `TLowerIsometricHexagon.ShowDynamic` (HSEPack `5561A400`) is what draws the shore
  transitions, from a hard-coded id table keyed on **combinations** of the neighbour mask
  bits (ids 6, 0xD, 0x19, `phase+3`, …) plus the per-direction base byte at `[hex+0x1A+d]`,
  which `UpdateTransitions` sets to 0 (grass) / 0x28 (snow) / 0x50 (wasteland) by neighbour
  terrain. **A cliff base would be one more `cmp` in that chain.**

### What building it would take (≈4 small caves + ILB art)
1. `TAoWHexagon.TerrainChanged` (`5579A94C`): let 0xB/0xE reach the water-replacement call
   and push terrain **0** so the existing *Water* resource is used — this is exactly what
   vanilla did for Coast at `5579A9A6`, and it is the branch `build_chasm_sky_movement.py`
   neutered (`75→EB` at `5579A962`).
2. Cave in `Show`: read the real terrain from `[hex+4]+0x14` (the field's terrain byte) and
   add a per-terrain delta to the base id → 16 Chasm + 16 Sky tiles appended to
   `Waterhex.ILB`. (Bonus: **16 variants each**, up from 15/8, and the `.hss` stops carrying
   the tile art entirely.)
3. Cave in `ShowDynamic`: for 0xB/0xE ignore the sequence list and play our own frames from
   new `Waterhex.ILB` ids, driven by the counter/id bytes the vanilla code already maintains.
4. Cave in `UpdateTransitions`: zero the land-neighbour mask for 0xB/0xE so no water
   shore-blend is drawn.

**Cost, stated honestly:** the cliff faces mostly survive — the *land* neighbour draws
`0xA0+d` from its own `TAoWHexagon.UpdateTransition`, and this mod's remap cave keys off
terrain **bytes**, not hexagon class, so it keeps working. What is lost is the **displaced
lip** (`0xA3+d`) that the void hex currently draws over its neighbour, because that side
becomes a water hexagon. Also to re-verify if ever built: Freeze Water (`5579E884`, gated to
terrain 0/A), Flood, ship pathfinding, and what tactical combat renders.

## Why a 17th terrain ID WOULD have been blocked (matrix full — moot now that 0xB/0xE are donated)

The terrain byte indexes a hard 16-row matrix; all 16 rows are allocated: 0–D the known
terrains, **0xE = a configured water-variant** (sailing 3 / flying 4; special-cased alongside
Water/Ice in `TAoWHexagon.TerrainChanged` `5579A94C` — likely deep/ocean water), **0xF = Border**
(all-ff in every table — that's precisely its "impassable to everyone"). A 17th terrain would
need every 16-stride table, the transition byte-index scheme (`T*16+…` overflows a byte at
T=0x10), resource registries, and the editor palette widened — a rewrite, not a patch.

## FALLBACK (superseded by the chosen architecture above): the mountain pattern ("overlay terrain")

Vanilla mountains ARE flying(+mountaineering)-only terrain, implemented as: a map object that
publishes an overlay value into `field+0x15` + cost-table columns + oversized art that carries
its own cliff skirts. Copy that pattern exactly:

- **Overlay choice — three free values + one vanilla gift**: Solid (0xA), Res-D, Res-E are
  all-0xFF everywhere. **Res-C (0xC) is already a vanilla flying-only overlay** — only the
  Fly/Float table has costs there (4 surface / 5 underground). Options: use 0xC for one of the
  pair and inherit its costs as-is, or claim 0xD + 0xE for a clean Chasm/Sky pair and copy the
  0xC column pattern into them. (0xC's vanilla purpose is unidentified — check nothing places
  it before adopting.)
- **Movement**: build script patches ONLY table 2 (Fly/Float, shared) in AoWEPACK.dpl data —
  set the chosen column(s) to cost 4 (or copy the 0xC pattern), leave 0xFF everywhere else. No
  code cave needed; the startup generator (`55744B2C` → `MovePointTables` `558EA040`)
  propagates it. Flying and Floating both pass by construction.
- **Visual + overlay publication in one object**: a new **decoration-MO resource**
  (`TTerrainMOR` family, ClassID `0x20167` — NOT `TMountainMOR`, whose `GetOverlay` `557A2DC8`
  clamps every declared overlay to 0!) with `TTerrainList` = {terrain −1 (inherit), overlay 0xD
  or 0xE}. `TMapObject.GetOverlay` (`556097B8`) publishes the raw value → field cache → movement.
  Resources are added with AoWDevEd into the set; no new classes, no new terrain byte.
- **Cliff edges**: baked into the MO sprite, oversized and straddling neighbours (exactly how
  mountains get dramatic edges), drawn via the complex-image chain
  (`TMapObjectResource.ShowComplexImage` `5560A134`). This avoids touching the hexagon
  transition system entirely for v1. (A v2 could extend the `UpdateTransition` rule table by
  cave + append cliff images to `HexTrans.ILB` for terrain-blended edges, but the sprite route
  is proven by vanilla.)
- **Two identities, one mechanism**: Chasm and Sky are just two resources with different art
  (and different overlay values, so their costs could even diverge later).

What comes free: AI pathfinding (uses the same MovePointTables), path preview, save format
(decoration MOs already serialize), multiplayer, the editor (places decorations natively).

## Known edge cases to resolve at implementation

1. **Flood**: overlay 0xD/0xE are not in Flood's shield set {0,2,7} (`TFloodControl.Flood`
   `557F13D0`) — a water-adjacent Chasm would flood (and Restore would re-place the decoration).
   Either acceptable (chasm fills with water!) or add ovD/ovE to the shield compare chain.
2. **Terrain spells**: storms change the *terrain byte*; the overlay MO survives via
   `TILTerrainMO`-family TerrainChanged only if… decorations are `TTerrainMO` family — verify
   their reaction to terrain change under them (`TTerrainMO.ChangeTerrain` `5561683C`,
   `CanChangeOwnTerrain` `55616730`) before shipping.
3. **Structure placement / summons**: check what vetoes placing buildings or summoning onto
   ovD/ovE hexes (`CanPlace` paths check the *top HS style*, not overlays; a unit-summon check
   probably uses CanMoveOn — verify).
4. **Combat map**: the tactical-combat terrain generator reads the strategic hex — check what a
   battle ON/adjacent-to a Chasm hex renders as.
5. Swimming-table oddity: table 1 has land ov0xC = 8 — unknown meaning; don't disturb.
6. The exact split of tables 1/4/5 (Swimming vs Sailing vs Floating naming) should be confirmed
   by checking one known unit's movement-type byte before patching.

## Rejected alternative: repurpose terrain 0xE

One row could be stolen (0xE, the water-variant) for a single real terrain: it already has
sailing/flying entries and a `TerrainChanged` special case to neutralize, needs new hexagon
resources, a transition-rule cave, and proof that no shipped map uses 0xE (scan scenarios —
they may be compressed). Higher risk, only ONE id available (Chasm and Sky would share it with
per-level resources), and the editor's terrain palette is unverified. Keep as fallback only if
the overlay route hits a wall.
