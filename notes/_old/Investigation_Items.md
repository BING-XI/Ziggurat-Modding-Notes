## 0. Shared foundation — the item system as reverse-engineered

### 0.1 `TItem` object (class VMT `0x5570FAFC`, **instance size `0x4C` = 76 bytes**, parent `TAbilityOwner`)

Field map (from `TItem.ReadWrite@0x557945c8`, `TItem.Create@0x55793e48`, `SetItemType@0x5579457c`,
and the stat getters):

| Off | Type | Meaning | Evidence |
|----|------|---------|----------|
| +0x14 | int | item instance ID | `Use` copies to token+0x10; `TItemTE.Execute` `FindItem(token+0x10)` |
| +0x18 | str | (name / drop text) | ReadWrite tag 8 |
| +0x1c | byte | flags (bit0 = activated) | `TItem.Activate` sets bit |
| +0x20 | int (=1) | "registered library item" marker | `GenerateItem` checks `+0x20==1` |
| +0x24 | int (=-1) | array-owner / owner index | `SetArrayOwner`, ReadWrite tag 0x15 default -1 |
| +0x2c | int | obtain value | `GetObtainValue@0x557945b4` = max(+0x2c,10) |
| +0x30 | str | library id/name | ReadWrite tag 9 |
| **+0x34** | **byte** | **ITEM TYPE (0–7)** | `SetItemType`, `CanUse`, `GetAbilitySelectionTypes` |
| **+0x38** | **int** | **SPELL ID** (useable items) | `CanUse`/`ExecuteUse` read it |
| +0x3c | TStringList | ability list | `Create` allocates it |
| +0x40 | int (=-1) | item GFX index | `SetItemType` sets via `FindItemTypeGFX` |
| +0x44 | ? (tag 0x10, distinct reader) | unknown enum/word | ReadWrite only; **not** read by use logic — candidate discriminator |
| +0x45 | byte | rarity / random-gen weight | `GenerateItem` `AddAB(item, item+0x45)` |
| **+0x46** | **byte** | **ATK bonus** | `THeroItems.GetAttack` sums it; `SetItemType` zeroes it |
| **+0x47** | **byte** | **DEF bonus** | `THeroItems.GetDefense` sums it |
| **+0x48** | **byte** | **DAM bonus** | `THeroItems.GetDamage` sums it |
| **+0x49** | **byte** | **RES bonus** | `THeroItems.GetResistance` sums it |
| **+0x4a** | **FREE** | (unused padding, zero) | last field is +0x49; instsize 0x4C ⇒ 0x4a,0x4b allocated & unreferenced |
| **+0x4b** | **FREE** | (unused padding, zero) | — |

**Key fact:** the four item stat bonuses are the contiguous bytes **+0x46 (ATK) / +0x47 (DEF) /
+0x48 (DAM) / +0x49 (RES)** — exactly the four bytes `SetItemType` zeroes and the four
`THeroItems.GetX` methods each sum. **+0x4a and +0x4b are free, zero-initialised bytes inside the
existing 76-byte allocation** (Delphi zero-fills the instance; nothing writes them). This is the
natural home for HP/MV bonus fields with **no instance-growth required** (contrast the spellcasting
mod, which had to grow `TUnit`).

### 0.2 Item type enum & equip slots

Item type (`item+0x34`) is the Delphi enum **`TItemTypes`**, and the engine ships its RTTI name
table — at file offset `0x8050` = **VA `0x55708C50`** in AoWEPACK.dpl (CODE; Delphi emits RTTI into
the code segment):

| value | RTTI name | equip slot | count in `Release/ITEMS.PFS` |
|-------|-----------|-----------|------------------------------|
| 0 | `itHead`    | 1    | 8 |
| 1 | `itTorso`   | 4    | 14 |
| 2 | `itAttack`  | 0    | 28 |
| 3 | `itDefense` | 2    | 14 |
| 4 | `itRing`    | 3    | 9 |
| **5** | **`itScroll`** | **0x0F = none** | **0** ← see Feature 1 |
| 6 | `itUse`     | 0x0F = none | 10 |

Type→equip-position table at `0x558e8db8` (live bytes `01 04 00 02 03 0f 0f`) is read via
`THeroItems.GetItemTypePosition@0x55786740`; the **separate** position→type table at `0x558e8db0`
(live bytes `02 00 03 04 01 04`) is read via `THeroItems.GetPositionItemType@0x55786734`.
`THeroItems.CanPlaceItem@0x5578674c` requires `slot < 6` **and** the slot empty **and**
`GetPositionItemType(slot) == item+0x34`, and `PlaceItem@0x55786788` refuses when it returns false —
so **every equipment position is type-locked; there is no generic wearable slot** (see §3.10).
The six positions are pos0 `itAttack`, pos1 `itHead`, pos2 `itDefense`, pos3 `itRing`, pos4
`itTorso`, **pos5 `itRing` (the second ring)**. **itScroll / itUse map to `0x0F` = no wearable
slot**. Unequippable items are
not lost: `THero.AutoPlaceItem@0x5578901c` falls back to
`THeroInventory.GetFreeSlot(hero+0x74)` — i.e. **a scroll is carried in the hero's inventory list at
`hero+0x74`**, distinct from the equipped aggregate `THeroItems` at `hero+0x70`.

`TItem.GetAbilitySelectionTypes@0x557944ac` switches on type (which ability categories each type may
carry): cases 0–4 and 6 each have their own constant; **type 5 falls into the `default:` arm**, i.e.
scrolls share the fallback category word with types ≥ 7.

The user-facing type *names* (Head/Torso/Attack/Defense/Ring/**Scroll**/Use) are the AoWDevEd item
dialog's combo items — see Feature 1 §"Editor".

### 0.3 Items are a HERO-only feature

Regular `TUnit`s do not equip items — only `THero`/`TLeader` (via `THeroItems`, `THero.PlaceItem`,
`THero.UseItem`). So every item→stat and item→use path lives on `THero`. This narrows both features
to `THero` methods.

### 0.4 How item stat bonuses reach the hero's effective stats — **TWO independent routes**

This was under-documented before 2026-07-30. An item can raise a hero's stats **two different ways**,
and they have *different* slot rules (see §0.7):

**Route A — the four flat bonus bytes (equipped slots only).**
`THeroItems` (the hero's *equipped* aggregate at **`hero+0x70`**, i.e. `heroFields[0x1c]`) exposes one
aggregator per stat, each looping the equipped-item array (`[items+2]→+4`, count via `vtable+0x54`)
and summing one item byte:

- `THeroItems.GetAttack@0x55786354` → Σ `item+0x46`
- `THeroItems.GetDefense@0x55786388` → Σ `item+0x47`
- `THeroItems.GetDamage@0x557863bc` → Σ `item+0x48`
- `THeroItems.GetResistance@0x557863f0` → Σ `item+0x49`
- **(no `GetHits`, no `GetMoves` — the aggregator set is 4-stat-only)**
- **`THeroInventory` (`hero+0x74`) has NO stat aggregators at all** → the four bonus bytes on an
  `itUse` / backpack item are dead data. See §0.7.

**Route B — abilities carried on the item (equipped *and* use-slot).**
Each `THero.GetX` getter also runs its own loop over **every ability id**, resolving the best owner
across self + equipped items + `itUse` inventory items, then adding that owner's per-ability term:

```
for id in 0 .. self.vtable[0x158]()      ; THero.GetAbilityCount (item-aware)
    owner = THero.GetSuperlativeEnabledAbOwner(self, id)   ; @0x55788144 — self / equipped / itUse
    if owner: total += owner.vtable[SLOT](owner, id)
```
with `SLOT` = **+0x68 `GetAbAttack`**, **+0x6c `GetAbDefense`**, **+0x70 `GetAbResistance`**,
**+0x74 `GetAbDamage`** (all `TAbilityOwner`, base impls @`0x5574fc3c/0x5574fc60/0x5574fc84/0x5574fca8`).
Because the *owner* is the item, the item's own ability-data list supplies the value — this is why
e.g. an Enchanted-Weapon item works from either slot type while its `+0x46` byte does not.

The effective hero stat getters (**clamps re-verified live 2026-08-31** with
`build_hero_clamps.py` — all seven rows AT TARGET; the four combat getters are themselves now
hooked by later features, the two HP/MV getters are still vanilla-shaped):

| Stat | THero getter | Formula | Clamp | Route A (bytes) | Route B (abilities) |
|------|-------------|---------|-------|-----------------|---------------------|
| Attack | `GetAttack@0x55788360` | res+0x24 + Σ`GetAbAttack` + **THeroItems.GetAttack** + hero+0x6a | [0,**40**] | equipped + itUse¹ | equipped + itUse |
| Defense | `GetDefense@0x557883e8` | res+0x25 + Σ`GetAbDefense` + **items** + hero+0x6b + morale table `0x558e83e0` | [0,**40**] | equipped + itUse¹ | equipped + itUse |
| Damage | `GetDamage@0x55788484` | res+0x26 + Σ`GetAbDamage` + **items** + hero+0x1b | [**2**,**40**] | equipped + itUse¹ | equipped + itUse |
| Resistance | `GetResistance@0x5578850c` | res+0x29 + Σ`GetAbResistance` + **items** + hero+0x6f + morale | [0,**40**] | equipped + itUse¹ | equipped + itUse |
| **Max HP ("Hits")** | **`GetHits@0x5578859c`** | **res+0x27 + hero+0x6d** | **[2,100]** | **NONE** | **NONE** |
| **Max MV ("Moves")** | **`GetMoves@0x557885c0`** | **res+0x28 + hero+0x6e** | **[1,80]** | **NONE** | **NONE** |

¹ **`build_useitems.py` (applied) changed the Route-A slot rule.** All four `THeroItems.GetX`
aggregators are now caves that walk the worn list *and* the `type==6` backpack list, so the flat
bytes reach the hero from an `itUse` item too. The vanilla "equipped only" rule no longer holds —
§0.7's matrix is the *vanilla* matrix; read it together with `build_useitems.py`'s P3/P4.

(`res` = hero's unit-resource flyweight at `hero+0x40`; base stats res+0x24..0x29.
Ceilings 40 / floor 2 / HP **100** come from `build_hero_clamps.py`; HP was 120 from the DAM/HP
doubling and was lowered to 100 on 2026-08-31 to buy margin under the 127 signed-byte wall —
see the overflow trap in FEATURE 2.)

Live bytes of the two Feature-2 targets (both **unpatched vanilla**, 34 bytes each, no slack — a hook
must overwrite the leading `mov edx,[eax+0x40]; mov dl,[edx+0x27]` = 6 bytes ≥ the 5 a rel32 `jmp`
needs):

```
5578859C  mov edx,[eax+0x40] / mov dl,[edx+0x27] / add dl,[eax+0x6d]   ; THero.GetHits
          mov eax,edx / movsx edx,al / cmp dx,2 / jge / mov al,2 / cmp dx,0x64 / jle / mov al,0x64 / ret
557885C0  ... identical with [edx+0x28] and [eax+0x6e], clamps 1 / 0x50   ; THero.GetMoves
```
(re-disassembled live 2026-08-31. The clamp immediates are **owned by `build_hero_clamps.py`** at
`0x557885AD/B1/B8/BC`; a hook placed at the function head does not overlap them, so the two features
compose — but never rewrite the clamp bytes from an item patch.)

**This table is the whole story of Feature 2:** HP and MV are computed by the *same additive shape*
as the four combat stats, but their getters simply **omit the `THeroItems.GetX` term** (and the
ability loop). They are not hardcoded constants and not "resolved once" — they recompute live on
every call, exactly like GetAttack. Items don't touch HP/MV solely because these two getters never
add an item aggregate.

**Terminology gotcha:** "Hits"/"Moves" = the **max** stat (additive, clamps [2,100] / [1,80]).
"HitPoints"/"MovePoints" = the **current** remaining value stored as a flat byte
(`THero.GetHitPoints@0x55787044` → hero+0x7a; `GetMovePoints@0x55787018` → hero+0x79;
`TUnit.GetHitPoints` → unit+0x3e). `TUnit.SetHitPoints@0x557827c4` writes current, clamping to
`vtable[0xD0]` (= GetHits/max).

### 0.5 VMT slots (verified)

`THero.GetHits` is referenced from the `TLeader` VMT (base `0x55712238`) at `0x55712308` =
**+0xD0** — matches the project's "GetMaxHP +0xD0". `THero.GetMoves` at `0x5571230c` = **+0xD4**
(adjacent). `TLeader` does **not** override either (both slots point at the `THero` impls, so one
patch per getter covers heroes *and* the wizard/leader). Confirmed the bonus reaches **tactical
combat**: `TCombatUnit.GetHits@0x5572504c` returns `[source+0x4c].vtable[0xD0]()` and
`TCombatUnit.GetMoves@0x55724fe0` returns `[source+0x4c].vtable[0xD4]()` — i.e. combat max HP/MV is
read straight from the source hero's GetHits/GetMoves, so patching those two getters flows into
combat with no extra work. (`TItem` VMT-slot dispatch for use: **+0x9c CanUse, +0xa0 Use,
+0xa4 ExecuteUse**.)

Unit-hierarchy VMT slots also needed by Feature 2 (live-verified): **+0xd0 GetHits, +0xd4 GetMoves,
+0xd8 GetMovePoints, +0xdc SetMovePoints, +0xe0 GetHitPoints, +0xe4 SetHitPoints**.
`TAbstractUnit.NewTurn@0x55780d4c` opens with `SetMovePoints(GetMoves())` — **so an MV bonus does
take effect on the next turn refill** (this closes the "verify NewTurn refills from GetMoves" open
item). It then regenerates HP by a fraction of `GetHits` (skipped if the unit has ability `0x5D` or
`0x31`), so **an HP bonus also speeds up healing**, not just the ceiling.

### 0.6 ⚠ THE BIG ONE — there are **two parallel ability-query APIs**, and only one sees items

This is the single most important fact for any item- or ability-related mod, and it explains every
"the ability is on the item but nothing happens" report. `THero` carries **two complete sets** of
ability accessors at different VMT slots, and **only the high-slot set searches items**:

| Query | `TAbilityOwner` set — **SELF-ONLY** | `TAbstractUnit`/`THero` set — **ITEM-AWARE** |
|---|---|---|
| has ability? | **+0x4c** `GetAbSet` → `TCustomAbilityList.GetAbSet` | **+0x14c** `GetAbilitySet` → `THero.GetAbilitySet@0x557882ac` |
| level | **+0x84** `TAbilityOwner.GetAbLevel@0x5574fd44` | **+0x144** `THero.GetAbilityLevel@0x5578831c` |
| enabled | **+0x88** `TAbilityOwner.GetAbEnabled@0x5574fd68` | **+0x148** `THero.GetAbilityEnabled@0x5578827c` |
| count | +0x54 `TCustomAbilityList.GetAbCount` | **+0x158** `THero.GetAbilityCount@0x55788114` |

**`THero`/`TLeader` never override the low set.** Verified by reading the live VMTs
(`THero` base `0x55711FEC`, `TLeader` base `0x55712238`): slot `+0x84` holds
`TAbilityOwner.GetAbLevel` and `+0x88` holds `TAbilityOwner.GetAbEnabled` in **both**, while
`+0x144/+0x148/+0x14c/+0x158` hold the `THero.*` overrides. (`TUnit` VMTs `0x55710740` /
`0x55710CAC` and `TItem` VMT `0x5570FAFC` carry the same low slots — for those classes the low set is
correct, because they *are* the ability owner.)

The item-aware overrides all funnel through two resolvers:
`THero.GetSuperlativeAbOwner@0x557881dc` and `THero.GetSuperlativeEnabledAbOwner@0x55788144`,
which pick the highest-level owner among **self → `THeroItems`(`hero+0x70`) → `THeroInventory`(`hero+0x74`)**
and return that object. `THero.GetAbilityLevel` then calls `ability.vtable[0x70](ability, thatOwner)`.

**⇒ A consumer that reads `+0x84`/`+0x88`/`+0x4c` on a hero sees ONLY the hero's innate abilities.
Item-granted abilities are invisible to it — from an equipped slot *or* a use slot.** This is a
vanilla design seam, not a corruption; see FEATURE 3 for the enumerated victims and the fix pattern.

There is also a third, explicitly items-blind accessor: **`THero.GetUnitAbilityEnabled@0x5578810c`**,
which just forwards to `TAbstractUnit.GetAbilityEnabled` — the engine uses it where only innate
abilities should count.

### 0.7 Equipped slot vs use slot — what an item can and cannot grant

`THeroItems` (`hero+0x70`, item types 0–4) and `THeroInventory` (`hero+0x74`, the 8 backpack slots)
are **not** interchangeable. `THeroInventory` implements only the *ability* half of the protocol, and
gates every method on the item's type:

```
THeroInventory.GetSuperlativeAbOwner        @0x557861f4   cmp byte [item+0x34],6   ; itUse ONLY
THeroInventory.GetSuperlativeEnabledAbOwner @0x557860c0   cmp byte [item+0x34],6
THeroInventory.GetAbilitySet                @0x557861a4   cmp byte [item+0x34],6
THeroInventory.GetAbilityEnabled            @0x55786154   cmp byte [item+0x34],6
THeroInventory.GetAbilityCount              @0x55786074
```
`THeroItems` runs the same loops with **no type gate** (any equipped item counts).

| What the item grants | Equipped (types 0–4) | Backpack `itUse` (type 6) | Backpack `itScroll` (type 5) |
|---|---|---|---|
| Abilities (→ hero's ability set/level/enabled) | **YES** | **YES** | **NO** (type gate is `== 6`) |
| ATK/DEF/DAM/RES via bytes `+0x46..0x49` | **YES** | **NO** — no aggregator | NO |
| ATK/DEF/DAM/RES via a carried ability | **YES** | **YES** (Route B, §0.4) | NO |
| Immunity types (`THero.GetImmunityTypes@0x55786fd8`) | **YES** — `\| THeroItems.GetImmunityTypes` | **NO** | NO |
| Protection types (`THero.GetProtectionTypes@0x55786ff8`) | **YES** | **NO** | NO |
| Move types (`THero.GetMoveTypes@0x55786fb8`) | **YES** — `\| THeroItems.GetMoveTypes@0x55786424` | **NO** | NO |
| Max HP / Max MV | NO (nothing reads items) | NO | NO |

The three type-word getters are all shaped `TAbstractUnit.GetX(hero) | THeroItems.GetX(hero+0x70)`
— **`hero+0x74` is simply absent from the expression**, so a use-slot item can never grant Flying,
Fire Immunity, Physical Protection, etc. `THeroItems.GetMoveTypes` works by calling
`TAbilityOwner.GetAbMoveTypesAll(item)` per equipped item, i.e. it reads the *item's own* ability
list — the self-only API used correctly, because the item is the owner.

## FEATURE 1 — Scrolls

### Verdict: **Scrolls are not an unimplemented idea — they are a COMPLETE, SHIPPED feature with no data.**

Investigated in depth 2026-07-30. Engine, in-game UI, editor authoring UI, artwork and localized
strings are all present in the retail files. The single reason no player has ever seen a scroll is
that **`Release/ITEMS.PFS` contains zero items of type `itScroll`** — plus one deliberate
one-byte lockout in the random-item generator (`itAll`, below).

So "make scrolls work" splits into two independent jobs:
- **Restoring them** — mostly *data*, not patching (§Restoring).
- **Changing what they do** (cast the spell instead of teaching it) — a small cave (§Cast variant).

### What a scroll does in the shipped engine: it is a one-shot spell TOME

`itScroll` is the **only** item type with a Use handler, and its behaviour is to *permanently
research* the spell, not to cast it once:

- UI → `THero.UseItem@0x55788ce0` (VMT) → `TItemControl.FindItem` → `item.Use` (vtable+0xa0,
  `TItem.Use@0x557941b4`).
- `TItem.Use`: calls `CanUse` (vtable+0x9c); if OK, builds a **`TItemTE`** token event
  (owner = `unit+0x24`, token+0x10 = `item+0x14` id, token+0x18 = hero id) and dispatches it
  (networked → runs identically on all peers, MP-safe).
- `TItemTE.Execute@0x55793de0`: re-finds the item + hero, calls `item.ExecuteUse` (vtable+0xa4).
- **`TItem.ExecuteUse@0x55793f68`**: if `CanUse && item.type==5` →
  `TPlayerMagicControl.ExecuteSpellResearched(player.magic, item.spellID)` (adds the spell to the
  player's researched list — `ExecuteSpellResearched@0x5577cbf8`), plays `MAGICB01.WAV`, shows the
  "%s researched" message **to the seated player only** (`map+0xA5` check), then **frees the item**
  (`vtable[-4]`, the destructor → one-shot consume).
  Live bytes @`0x55793FA9`: `mov al,[ebx+0x34]; sub al,5; jne …` — verified against the installed
  DLL, not just Ghidra's image.
- **`TItem.CanUse@0x557940ac`** (live @`0x557940D1`: `cmp byte [esi+0x34],5; jne` /
  `cmp dword [esi+0x38],0; je`): usable only if `type==itScroll && spell!=0 && spell NOT already
  researched`; otherwise it returns the message `"%s already researched"` or
  `"This is not an usable item"` (both are shipped resourcestrings —
  `AoWE.XAlreadyResearchedRStr`, `AoWE.ThisInNotAnUseableItemRStr`; the success message is
  `AoWE.XResearchedRStr` = `"%s researched"`).

The spell id is **already stored on the item** (`item+0x38`, save tag `0x14`) — a scroll needs no
new field for *which* spell.

### The in-game UI is wired — but its container panel is left hidden ⚠

`TUnitWindow` (AoW.exe) published fields: **`ItemUsePnl` +0x160, `ItemUseBtn` +0x164,
`ItemPic` +0x168** (from the class field table at file offset `0x68EF`). In the item-selection
handler:

```
0040A64E  mov  al,[edi+0x34]          ; selected item's type
0040A651  mov  [esi+0x220], al
0040A657  cmp  byte [edi+0x34], 5     ; itScroll?
0040A65B  jne  0040A66C
0040A65D  mov  dl, 1                  ;   -> ItemUseBtn.Visible := True
0040A65F  mov  eax,[esi+0x164]
0040A667  call [ecx+0x6c]             ; TAoWComponent.SetVisible
0040A66C  xor  edx, edx               ;   -> ItemUseBtn.Visible := False
```

Clicking it runs `TUnitWindow.UseItemClick@0x00409FFC` → `THero.CanUseItem` (thunk `0x40275C`) →
`THero.UseItem` (thunk `0x402764`); on refusal it shows CanUse's message. The button's DFM carries
`ToolTip = 'Uses selected item'`. **These are the only two call sites of CanUseItem/UseItem in
AoW.exe** (whole-CODE rel32 scan) — so the Use path is reachable *only* by selecting a scroll.

### The artwork ships too — but is registered under the wrong type

### `itAll` masks the scroll bit out of random generation ⚠ the clearest "cut" evidence

`TItemControl.GenerateItem@0x55794F40(itemControl, typeMask, minValue, maxValue)` picks a random

both pass the global set constant **`AoWE.itAll`**:

- `TItemHS.GenerateItems@0x55795F20` — item hotspots / treasure piles on the map
- `ItemExpS.TItemExplorationSite.Generate@0x557C2944` — items from exploration sites

**`itAll` is a one-byte `set of TItemTypes` at VA `0x558E803C` = AoWEPACK.dpl file offset
`0x1E6E3C`, and its value is `0x5F` = `{itHead,itTorso,itAttack,itDefense,itRing,itUse}` — bit 5
(`itScroll`) is cleared.** The constant named "all item types" was hand-edited to exclude scrolls,
which is why even a fully authored scroll could never turn up as treasure. `0x5F → 0x7F` is the
whole fix (1 byte, DATA section, no cave, no relocation concerns).

## FEATURE 1b — Scroll as a PERMANENT spellbook grant

### Status: **ROOT CAUSE FOUND + FIXED 2026-07-31 — fix applied, awaiting the first real scroll test**

**⭐ Root cause (found by in-game bisection, not by reading — five rounds):** the hero's inventory
array **can hold entries that are not live `TItem` objects**. These engine lists are sparse — removal
is sparse-or-compacting by style bit 8 — so `FCount` can exceed the live entries and a dead slot need
not be NULL. The scan's `cmp byte [entry+0x34], 5` matched one such slot, so `GetSpell` ran with a
garbage id, `TSpellControl.GetSpell` returned a bogus pointer (no bounds check), and that pointer was
appended to the spell book. The book then choked drawing an icon for it → spells and icons vanished,
an error naming a book control, then a freeze. **Not a crash — a poisoned list**, which is why every
static check passed.

**Fix:** before touching `+0x34`, require the entry's VMT to *be* `TItem`'s —
`cmp [entry], (0x5570FAFC + dll_delta)`, reached through the same rebase delta already used for
`TSpellList.Add` (the exe imports no `TItem` class reference). Paid for by dropping the dedupe pass,
since `.sc` is exhausted at 344/344 bytes; the only cost is that a scroll whose spell the player has
*also* researched now appears twice. Restore dedupe when the cave gets its own PE section.

**⚠ Generalise this:** any cave that walks an engine list and identifies entries by a *data byte*
is unsafe. Identify by class (VMT compare or `IsClass`) first. A type/id byte test alone will
eventually match a stale slot, and the damage shows up far away from the cave.

### ⚠ SECOND, SEPARATE DEFECT — do NOT retype the scroll GFX records

`build_scroll_gfx.py` (retyping `ITEMGFX.PFS` records 316–319 tag 8 from `6`→`5`) is **confirmed
harmful in-game 2026-08-01**: blank hero portrait, no spell icons, and all spell costs shown as
nonsense (1, 5, 0) though still castable — and **no error dialog**. Isolated by a clean
single-variable A/B (reverting that file alone, cave untouched, made every symptom vanish).

So `TItemGFX+0x20` is **not** a passive "which item type may use this graphic" filter, despite
`FindItemTypeGFX@0x55795C1C` comparing exactly that byte. Something in the image path also keys off
it, and moving four records into the previously-empty type-5 bucket poisons unrelated drawing. Root
cause not pinned down. **Do not retry as-is.** Better routes, all untested: set the item's own
graphic index (`item+0x40`, pfs tag 7 — `FindItemTypeGFX` only supplies a *default* when it is -1);
or **append** new type-5 records instead of retyping existing ones. ⚠ A scroll left at gfx index -1
is its own hazard — `ImageLib.Get` has no bounds check.

**Process lesson (cost a confusing round):** after five clean single-variable bisect rounds, three
changes were made at once — the VMT guard, dropping dedupe, and re-applying the GFX retype — and the
resulting symptoms were unattributable until they were separated again. Also, the bisect ladder's
default level was left at the old "full" number when a level was inserted, so a bare `--apply`
silently installed a *diagnostic* build instead of the feature. Keep one variable per test, and keep
the default in sync with the ladder.

**The bisect ladder that found it** (`--append-upto N`, results in-game):
`0 prune only` ✅ · `2 +[caster+0x74] +virtual GetCount` ✅ · `3 +array walk` ✅ ·
`4 +null test +byte[+0x34] read` ✅ · `5 full` ❌ → the fault was in what only runs when the type
byte matches. Keep the ladder: it is the fastest way to localise any future cave defect here.

### Verdict on the design (retained for reasoning)

Confidence was ~85% before building, and no new engine concept turned out to be needed: research
gating lives entirely in the book, the hook that builds the book was already ours, and the hero's
carried-item list is trivially walkable. The one thing the estimate got wrong was space — a
*separate* wrapper cave did not fit (`.sc` had only 0xD6 free bytes after the old cave), which forced
the in-place rewrite of `cave_bookfilter` and its "don't re-run the other script" hazard.

### Why it works — research is a book-only concept

| Function | Checks research? |
|---|---|
| `TPlayerMagicControl.ListSpells@0x5577d148` (fills the book) | **YES** — it *is* the researched-id list (`magic+0x30`, a `TIntegerList`), category-filtered on `spell+0x22` |
| `THero.CanCastSpell@0x55789710` | **NO** — not-already-casting, player mana ≥ `CastingMana`, then `spell.vtable[0x68]` (`CanActivate`) |
| `THero.CanCastCombatSpell@0x55789a3c` | **NO** — channelling points `hero+0x80`, player mana, then `spell.vtable[0x70]` |
| `CastSpell` → TE → execute | **NO** |

So a spell only has to *appear in the list*; everything downstream will cast it. (This is the same
key enabler as the per-unit-spellbook idea in `Investigation_Spellcasting_Extra.md` Feature 1 — the
two features share the hook and could share a cave.)

### Where to inject — `cave_bookfilter` already owns the site

`TSpellBook` (AoW.exe) calls `TPlayerMagicControl.ListSpells` **directly** at 5 sites
(`0x0042F0F9 / 0x0042F20C / 0x00430D58 / 0x00430DDE / 0x00430EDD`); the exe never calls
`THero.ListSpells`, so a DLL-side list hook is inert (lesson already paid for — see
`Unit_Spellcasting_Polish_2026-07-06.md` §M3). All five are **already redirected** to
`cave_bookfilter @0x0060C0A8` (verified live: each site reads `call 0x60c0a8`).

**All three book tabs go through those same five sites** — `TSpellBook+0x222` is the mode byte
(`0` = Combat, `1` = Unit, `2` = Global; from `CombatBtnClick@0x004306C8` /
`UnitBtnClick@0x00430634` / `GlobalBtnClick@0x004305A8`), and the differing `System.@SetElem`
category masks at each site are what distinguishes them. So one cave extension covers strategic,
combat and unit casting. *(This corrects "combat book is separate" in
`Investigation_Spellcasting_Extra.md` — `TTacticalCombatUnitHS.SelectSpell` is the combat-side
targeting handoff, not the list builder.)*

The cave already has everything: it runs the real `ListSpells`, holds `caster = [EDX+8]`, has an
`IsClass(caster, THero)` test (true for `THero` **and** `TLeader`), and rewrites the collector's
item array during its tier/Cosmos compaction.

### Walking the hero's scrolls (no imports needed)

Scrolls are unequippable (`GetItemTypePosition(5) = 0x0F`), so `THero.AutoPlaceItem@0x5578901c`
files them in **`THeroInventory` at `hero+0x74`** — 8 backpack slots (`GetSlot@0x55786284` accepts
slot 6..13 → index 0..7). The enumeration idiom is copied verbatim from
`THeroInventory.GetAbilityCount@0x55786074`:

```
inner  = [inv+8]                 ; inner TList
items  = [inner+4]               ; dword array of TItem*
count  = inv.vtable[0x54](inv)   ; GetCount  (slots may be NULL — null-check each)
for i in 0..count-1:
    item = [items+i*4]
    if item && byte[item+0x34] == 5:      ; itScroll
        spellID = dword[item+0x38]
```
All VMT-relative — **no new imports, no absolute addresses**. `TSpellControl.GetSpell` is already
imported by the exe (IAT `0x0045DD90`) to turn the id into a `TSpell*`.

### Appending to the collector

`TSpellList[+4]` = inner `TList`; `TList[+4]` = items, `[+8]` = count, `[+0xC]` = capacity. The exe
imports `TSpellList.GetCount/GetSpell/Clear/Delete/Create/SortOnLevel` **but not `Add`**. Two routes:

- **(a) Manual append** — dedupe against the existing entries, then `if count < capacity:
  items[count]=spell; count++`. Delphi's `TList` over-allocates so this nearly always has room, and
  the cave already manipulates this exact array. Low risk; the degenerate case is "scroll spell
  hidden when the list is exactly full".
- **(b) Call `TSpellList.Add@0x5577a03c` in the DLL via the rebase-delta trick** (see
  [[aow1-party-random-generator]] / `Party_Random_Generator.md`) — the exe can call any AoWEPACK
  export with no new imports by computing the load delta from an existing import thunk. Removes the
  capacity edge case entirely. **Preferred** now that the trick exists; the 2026-07-08 note calling
  this a blocker ("needs import surgery") is obsolete.

Append **after** the existing prune loop, so the tier/Cosmos filter doesn't immediately remove it.

### The M2 tier gate must be handled (DLL side)

The live DLL has `jmp 0x5580d95e` at **`0x5578974D`** inside `THero.CanCastSpell` — `cave_tiergate`,
which silently refuses any spell whose tier (`TSpell+0x21`) exceeds the caster's Spellcasting level
(ability `0x34`). A scroll for a tier-4 spell in the hands of a low-skill hero would therefore appear
in the book and then do nothing. Two options — **a design decision, not a technical one**:

1. **Keep the gate** — a scroll only works if the hero's Spellcasting level already covers the
   spell's tier. Zero extra work, and it stops a level-1 hero from wielding a tier-4 scroll.
2. **Bypass for scroll-granted spells** — `cave_tiergate` receives the hero, so it can run the same
   `hero+0x74` scan and allow the cast when some carried `itScroll` has `+0x38 == spellID`. ~25
   instructions, DLL-side, and it keeps the exe and DLL rules symmetric.

### Kill the vanilla consume-on-use path

Otherwise a player can still click Use and *destroy* the scroll while making the spell globally
researched — the opposite of "permanent". Both gates are single comparison bytes; retarget them to an
item type that does not exist (e.g. `7`):

- DLL `TItem.CanUse@0x557940D1`: `cmp byte [esi+0x34], 5` → `7` (Use then reports "This is not an
  usable item"; `ExecuteUse` becomes unreachable because it re-calls `CanUse` first).
- **[exe]** `0x0040A657`: `cmp byte [edi+0x34], 5` → `7`, so the Use button never appears.

(Do not rely on the `ItemUsePnl` visibility defect to hide it — that may be fixed later, and it is
unverified.)

### Remaining caveats

- **AI heroes get nothing — for TWO independent reasons, both fixable.** Traced 2026-07-30:

     `THero.AutoPlaceItem@0x5578901c`, or fall back to `THeroInventory.GetFreeSlot@0x5578601c`)

  2. **Candidate list.** The AI's spell candidates come from
     `TCastSpellAIPA.PrefetchCastSpellActions@0x5577ba54`, which creates its own `TSpellList`,
     fills it via `TPlayerMagicControl.ListSpells` **in the DLL**, then for each spell with
     `THero.CastingTurns(hero,spell) < 8` calls the spell's `vtable[0x5c]` to propose AI actions.
     The exe's `cave_bookfilter` never runs for the AI, so exe-side additions are invisible to it.
     **But `PrefetchCastSpellActions` takes the hero as `param_2`**, so a DLL hook right after its

- **MP:** the book is client-side and the cast token carries a spell id that the DLL executes without

- **Mana still applies** (`CanCastSpell` → player mana ≥ `CastingMana`); a scroll grants *access*,
  not free casting. Probably desirable.
- **Does the hero need the Spellcasting ability at all?** The book prunes on
  `GetAbilityLevel(0x34)`; a spell appended after the prune survives, but a hero with no Spellcasting
  has no casting points in combat. Decide whether scrolls are "any hero" or "casters only".
- **Item card text** is authored, not generated — name/describe the scroll in AoWDevEd so the player
  can see which spell it grants, or extend the item card cave.
- Steps 1–2 of §"Restoring scrolls" (author type-5 items; retype `ITEMGFX.PFS` 316–319) are still
  prerequisites. Step 3 (`itAll`) is optional — arguably scrolls should be **hand-placed only** if
  they permanently grant spells.

### Cast variant — making a scroll cast once instead of teaching (alternative, NOT requested)

The cast machinery is already present (unchanged from the original analysis):

From `THero.CastSpell@0x55789854` and `THero.CanCastSpell@0x55789710`, casting a spell = get the
`TSpell` flyweight and invoke two vtable methods with the caster:

```
spell = TSpellControl.GetSpell(*(AoWHSSet+0x84), spellID)   // @0x55779AC8
ok    = spell.vtable[0x68](spell, caster, &msg)             // CanActivate: validate + target-select
if ok:  spell.vtable[0x6c](spell, caster)                   // Activate: execute the spell effect
```

- `TSpell` vtable **+0x68 = CanActivate** (`TSpell.CanActivate@0x557792d0`) — validates and does
  target selection, returns bool + message.
- `TSpell` vtable **+0x6c = Activate** (`TSpell.Activate@0x55779354`) — executes.
- Calling these **directly bypasses the mana/casting-points/research gate** that
  `THero.CanCastSpell` enforces above them — exactly what a free one-shot scroll wants.

#### Proposed patch approach (SPECULATIVE — not built)

Binary: **AoWEPACK.dpl** (all logic here). Two hooks, position-independent caves (reuse the
spellcasting cave region ~`0x5580D900`+, borrow already-relocated globals).

1. **`ExecuteUse@0x55793f68`** — in the `type==5` branch, replace the `ExecuteSpellResearched` call
   with the cast sequence above (`GetSpell(item+0x38)` → `CanActivate(spell, hero, &msg)` →
   `Activate(spell, hero)`). Keep the existing item-free for the one-shot consume, but **gate the
   free on cast success** (`CanActivate` true) so a scroll isn't destroyed when the spell can't
   legally resolve.
2. **`CanUse@0x557940ac`** — drop the "already-researched" rejection (a cast-scroll is usable
   whether or not you know the spell); optionally forward to `spell.CanActivate` so the button
   greys out when the spell can't be cast from the current context.

**No scroll-vs-tome discriminator is needed** unless both behaviours must coexist. Since the data
ships zero type-5 items, whatever `itScroll` is made to do *is* the definition of a scroll — nothing
existing is converted or broken. (If both are wanted later, `item+0x44` — save tag `0x10`, written
by `ReadWrite` and read by nothing in the use path — is the obvious spare field; verify its real
meaning first. `item+0x4a/+0x4b` are also free, but Feature 2 below claims them for HP/MV.)

#### Risks / unknowns / leads

- **Which spells work as scrolls.** `CanActivate` (+0x68) may require a target or a legal context.
  Strategic self/global spells (summons, global/city enchantments, healing, terrain) resolve
  cleanly with the hero as caster on the strategic map. Combat-only or target-selection spells hit
  the *same* castability constraints the unit-spellcasting mod documented — reuse its sphere/tier
  gating insight (`Unit_Spellcasting_Polish_2026-07-06.md`: spell `+0x20` sphere, `+0x21` tier,
  `+0x22` category; `+0x22==2` = global enchantment; the "cannot cast in combat" check in
  `CanCastSpell` keys on `+0x22==2 && map+0x11c!=0`).
- **Target-selection UI** from `CanActivate` may expect the interactive caster path; a scroll used
  by the AI or in fast-resolve may need the non-interactive variant. Verify against the
  spellcasting mod's instant-cast path.
- **The AI will never use a scroll.** Per `Investigation_AI_Item_Pickup.md`, item acquisition and
  the Use path are both UI-only; the DLL has no AI-side caller of `UseItem`. Scrolls are a
  human-player feature unless that changes.
- `THero.UseItem`/`CanUseItem` have **no direct callers in the DLL** (VMT-dispatched) — the "Use"
  button is `TUnitWindow.UseItemClick@0x00409FFC` **[exe]**, calling `CanUseItem` @`0x40A05A` and
  `UseItem` @`0x40A078` via named-import thunks `0x40275C`/`0x402764` (not VMT). The authoritative
  effect runs in the DLL via the `TItemTE` token, so **the DLL hook alone is sufficient** and MP-safe.
  Full exe-side UI map in `Investigation_AI_Item_Pickup.md` §2.3.

### Loose end — `Frost Wand` carries a spell id it can never use

Of the 83 items in the installed `ITEMS.PFS`, exactly one has a spell field: **Frost Wand**
(record 34) has tag `0x14` = **spell 72** — but its type is `6` (`itUse`), so `CanUse` rejects it
("This is not an usable item") and the spell id is dead data. Either a leftover from when that item
was authored as a scroll, or the editor wrote the combo's value while the type was still Scroll.
⚠ `ITEMS.PFS` here is **Ziggurat**, not vanilla, so this may be the mod author's own leftover rather
than a Triumph one — ask before drawing conclusions from it.

## The Dispel Magic Expand arm, and what actually gates the hero chooser (2026-08-28)

Surfaced adjudicating Inioch's `build_item_healing_daily.py` (checklist S4-03). Adversarially
re-verified after two wrong drafts; both are deleted rather than annotated, but the cause of the
error is kept at the end because it was a tool bug that will recur.

### What gates an ability appearing at hero level-up — TWO tests, not one

`THeroUpgradeDlg`'s Available-abilities fill (pristine `Ziggurat upload/AoW.exe` inline at
`0x004469DF`; in our exe relocated by `build_herodlg_columns.py` to cave `0x00623E72`) applies:

    call [ecx+0xC4]           ; TAbility.CanExpand(hero)        <- gate 1
    test byte [eax+0x21], 1   ; ability mask & 0x0100 astHeroUpgrade  <- gate 2

and `TAbility.CanExpand @0x5574E8B8` is `(owner.GetAbilitySelectionTypes() & ability.mask) != 0`
after rejecting an ability the owner already has. The owner masks are exhaustive:

    TAbilityOwner 0x0000 · TAbstractUnit 0x0001 · THero / TLeader 0x0200 · TItem = slot jump table

So **a hero needs BOTH 0x0100 and 0x0200**. The mask word is `Ability.pfs` tag 9 → `[ability+0x20]`
(`TAbility.ReadWrite @0x5574F07C`), and tag 6 → `[ability+0x14]`, which `TAbility.ExpandCost
@0x5574E908` returns verbatim for any class not overriding it.

| ability | tag 6 | tag 9 | offered to a hero? |
|---|---|---|---|
| Healing `0x2F` | **12** | **0x03FF** | **yes** — Ziggurat made it so |
| Healing, vanilla | 10 | 0x0181 | **no** — 0x0181 lacks 0x200, so `CanExpand` refuses |
| Dispel Magic `0x3C` | *absent* | 0x0001 | no — fails both gates |
| Transport `0x32` | *absent* | 0x0001 | no |

Corroboration: in Ziggurat's `Ability.pfs` **102 abilities carry 0x100 and all 102 also carry
0x200** — the two gates never disagree, so the shipped hero list is exactly those 102.

⚠ **Never read the DLL's `ExpandCost` as evidence of purchasability.** `TDispelMagicAbility
.ExpandCost @0x5576D130` returns 5 and is dead code on that path.

### The Expand defect: real, vanilla, and unreachable in normal play

* `TDispelMagicAbility.SetEnabled @0x5576CE18` creates the record when absent and writes **only**
  the flag `[rec+0xC]`; the level `[rec+0xD]` is left 0 by `NewInstance`.
* `TDispelMagicAbility.Expand @0x5576D180` record-present arm: `inc [rec+0xd]`, `cmp ==1`,
  `mov 2` — and **never** calls `SetAb`, so no ability bit. (The `mov 2` is deliberate, not the
  bug: `GetLevel @0x5576CEFC` returns 1 for bit-set-no-record, so 1 is the "no record" state. The
  defect is only the *combination* with a level-0 record.)
* Byte-diff vs `AoWEPACK_original_backup.dpl`: all of `SetEnabled`, `GetLevel` and `Expand` bar
  the level cap are **identical to vanilla**. The `5` at `0x5576D163`/`0x5576D1D0` is ours
  (vanilla 3). So the defect is vanilla's, not this project's.

Unreachable in play: `Expand` is reached only via VMT +0xD0 ← `TAbilityOwner.ExpandAbility
@0x5574F5B4` ← owner VMT +0x94. Every caller was enumerated — both purchase screens are
mask-blocked, `THero.ExecuteUpgradeHeroAI` is hard-coded to 0x2E/0x7A/0x34, and every spell,
mastery and damage route passes a fixed non-0x3C id. No item grants `0x2F` or `0x3C` either.

⚠ **The one residual, PLAUSIBLE NOT PROVEN: AoWDevEd.** `TAbilitySelectionDlg.AddBtnClick`
(`0x004106B8`) and `THeroEditForm.AddBtnClick` (`0x004162B4`) pass an arbitrary listbox id to
`ExpandAbility` with **no mask test at the click**, and their fills gate on `CanExpand` alone.
For any unit-like owner (mask 0x0001) `TDispelMagicAbility.CanExpand` succeeds. Applied to
**Astra (133), Druid (238), Necromancer (239), Hydra (240)** — which already carry Dispel Magic
*level records* while never setting bit 0x3C — Expand takes the record-present arm, silently
bumps the stored level and adds no bit. Confirming needs a live probe of the dialog's owner class
(`[dlg+0x214]`, `[form+0x384]`) or five minutes in the editor.

⚠ **`ExpandAbility` does not call `CanExpand`** — every caller must gate itself. Relevant to any
future "give the AI more skills" patch.

### Data anomalies found in passing (Ziggurat `Unitres.pfs`)

* Astra, Druid, Necromancer, Hydra: Dispel Magic level records (1/2/3 across base/silver/gold)

### ⚠ The tool bug that caused both wrong drafts

**A `.pfs` record that reports zero tags or fails to parse is a parser mismatch, not an empty
record.**

## FEATURE 3 — Abilities on items: why some do nothing / misbehave (investigated 2026-07-30)

**Status: root causes CONFIRMED BY CODE against the installed binaries. No patch applied.**
Prompted by two reports: *"Healing on a use-slot item becomes infinitely castable in fast combat"*
and *"Marksmanship on an item does nothing"*. Both reproduce from the §0.6 two-API seam, and **neither
is actually specific to the use slot** — see the A/B test below before designing around it.
**Second pass (deeper) added below as §3.0 and §3.6–3.8**: the *design* reason `itUse` behaves
differently, a third instance of the Healing bug (Dispel Magic), and a second, more fundamental
reason items never get per-turn upkeep.

### 3.0 ⚑ WHY `itUse` works differently — it is a distinct ABILITY-LEGALITY CATEGORY, by design

`itUse` is not "an equipment slot that happens to sit in the backpack". AoW1 gates ability
*acquisition* on a bitmask handshake, and each of the six item types is its **own bit**:

```
TAbility.CanExpand @0x5574e8b8 (ability, owner):
    if owner.vtable[0x4c](id):  return false                    ; GetAbSet — already has it
    return (owner.vtable[0x8c]() & ability[+0x20]) != 0          ; GetAbilitySelectionTypes & mask
```

Owner side (`GetAbilitySelectionTypes`, VMT **+0x8c**) — constants live-read from the installed DLL:

| Owner | mask | bit |
|---|---|---|
| `TAbilityOwner` (base) @`0x5574f144` | `0x0000` | — |
| **`TAbstractUnit` (all units)** @`0x5577ecc8` | **`0x0001`** | **0** |
| **`THero`** @`0x55786b18` | **`0x0200`** | **9** |
| `TItem` — one bit by type, `TItem.GetAbilitySelectionTypes@0x557944ac` | | |
| &nbsp;&nbsp;`itHead` @`0x5579450c` | `0x0002` | 1 |
| &nbsp;&nbsp;`itTorso` @`0x55794510` | `0x0004` | 2 |
| &nbsp;&nbsp;`itAttack` @`0x55794514` | `0x0008` | 3 |
| &nbsp;&nbsp;`itDefense` @`0x55794518` | `0x0010` | 4 |
| &nbsp;&nbsp;`itRing` @`0x5579451c` | `0x0020` | 5 |
| &nbsp;&nbsp;**`itUse`** @`0x55794520` | **`0x0040`** | **6** |
| &nbsp;&nbsp;**`itScroll`** → the `default:` arm @`0x55794524` | **`0x0000`** | **none** |

**`itScroll`'s mask is literally zero — no ability may ever live on a scroll.** That is exactly why
`THeroInventory`'s type gate is `== 6` and not `>= 5` (§0.7): scrolls are not ability carriers at all,
by construction. The gate and the mask are the *same* design decision expressed twice.

**Which abilities declare bit 6?** Exactly ten classes (dump with `re_tools/abmask.py --use`;
descendants inherit unless they rewrite `+0x20`):

| Class | mask | meaning |
|---|---|---|
| `TTouchAbility` (base) | `0x0040` | **use items ONLY — not even units** |
| `TRangedAttackAbility` | `0x0041` | unit + use |
| `TBoltsAbility` | `0x0041` | unit + use |
| `TWebAbility` `0x1B` / `TEntangleAbility` `0x28` / `TInvokeDeathAbility` `0x23` | `0x0041` | unit + use |
| `TWallCrushingAbility` `0x75` | `0x0049` | unit + Attack + use |
| **`THealingAbility` `0x2F`** / **`TDispelMagicAbility` `0x3C`** | `0x0241` | unit + hero + **use** |
| `TTurnUndeadAbility` `0x26` | `0x0277` | unit + hero + Head/Torso/Defense/Ring + use |

Every one is **activatable / targeted**. The passive stat-shaped abilities are explicitly excluded
from `itUse` and routed to the wearable slots instead:

| Ability | mask | legal on |
|---|---|---|
| **Marksmanship `0x20`** | `0x0237` | unit, hero, Head, Torso, Defense, Ring — **NOT Attack, NOT Use** |
| WallClimbing `0x24`, Vision `0x40`, Holy/Unholy Champion `0x92/0x93` | `0x0237` | same |
| PassWall `0x42` | `0x0037` | unit + the four wearables |
| `TMovementAbility` | `0x0021` | unit + Ring |
| `TImmunityAbility` | `0x0031` | unit + Defense + Ring |
| `TProtectionAbility` | `0x0231` | unit + hero + Defense + Ring |
| `TStrikeAbility` `0x15` | `0x0009` | unit + **Attack** |

**⇒ This is the whole answer to "why do Use items work differently".** `itUse` is the lane for
*"an item that grants an ability you invoke"* — a wand, potion, horn. The wearable slots are the lane
for *passive modifiers*. `THeroInventory`'s shape follows exactly: it aggregates **only abilities**,
and no stat bytes / immunities / protections / move types (§0.7) — because the only things legal on a
use item **are** active abilities. The two halves match; it is not an oversight.

**The installed `ITEMS.PFS` agrees**, which is strong confirmation the rule was actually followed:

| type | n | abilities carried |
|---|---|---|
| `itUse` | 10 | `0x18, 0x1B, 0x1F, 0x26, 0x2D, 0x78, 0x79, 0x7A, 0x7B, 0x7C` — **exactly one per item**, all active |
| `itAttack` | 28 | strikes: `0x15` ×25, `0x14` ×17, `0x0E/0x11/0x12/0x13`, `0x73/0x74/0x75` |
| `itDefense` | 14 | protections `0x46–0x4C`, `0x43` |
| `itRing` | 9 | movement `0x03/0x04/0x05`, immunities `0x0B/0x0C`, `0x1A/0x27/0x29/0x31/0x36/0x44/0x45` |
| `itTorso` | 14 | immunities `0x07–0x0C`, concealment `0x8A–0x91`, champions `0x92/0x93` |
| `itHead` | 8 | vision `0x27/0x29/0x40`, Leadership `0x2E`, champions, `0x43` ×4 |
| `itScroll` | **0** | — (cut content, see Feature 1) |

**Slot space** (`THero.AutoPlaceItem@0x5578901c`, `THeroInventory.GetSlot@0x55786284`): slots **0–5**
are `THeroItems` (equipment), slots **6–13** are the 8 `THeroInventory` backpack slots. AutoPlace
tries `GetItemTypePosition(type)` first and falls back to a free backpack slot — which is how
`itUse` (position `0x0F`) always lands in the backpack.

**There are TWO tables, not one, and they are not inverses** — this matters (§3.10):

| | table | direction | live bytes |
|---|---|---|---|
| `GetItemTypePosition@0x55786740` | **`0x558E8DB8`** | type → *default* position | `01 04 00 02 03 0f 0f` |
| `GetPositionItemType@0x55786734` | **`0x558E8DB0`** | position → required type | `02 00 03 04 01 04` |

Decoded: pos0 = `itAttack`, pos1 = `itHead`, pos2 = `itDefense`, pos3 = `itRing`, pos4 = `itTorso`,
**pos5 = `itRing` again — the hero's second ring slot.** (The 6 bytes are followed by `8b c0`
= `mov eax,eax` padding, so the table is exactly 6 entries, matching `CanPlaceItem`'s `slot < 6`.)
`AutoPlaceItem` only ever tries the *forward* table's position 3 for a ring, so a second ring reaches
pos5 by manual UI placement only; if pos3 is taken, auto-place sends it to the backpack instead.

### 3.0b ⚠ …but the mask is NOT enforced at runtime for items

`TAbilityOwner.ValidateOwnerTypeAbilities@0x5574f154` is the enforcer — it walks the owner's set and
`SetAbSet(id, false)` on anything whose mask doesn't intersect. It has **exactly one caller**:
`TUnitResource.ReadWrite@0x55784f5e` (whole-module rel32 xref scan). **Nothing ever validates a
`TItem`.**

So an ability the mask forbids is **kept on the item and silently ignored**, not stripped. Practical
consequences:

- Putting **Marksmanship on an `itUse` item** places an ability the engine declares illegal there. It
  is not removed — it simply has no consumer that can see it. Two independent causes stacked.
- Conversely, an ability the mask *allows* is not thereby guaranteed to work: **Marksmanship is
  declared legal on Head/Torso/Defense/Ring, yet the ranged getters still cannot see it (§3.1).**
  That upgrades §3.1 from "a seam" to **a genuine vanilla bug** — the ability registry advertises a
  placement the consumer cannot honour — and strengthens the case for the displacement fix.
- The mask is still the right thing to edit if you want a *design* change (e.g. make Marksmanship
  legal on `itUse`): it is a single word in each ability's `.Create`. But on its own that changes
  nothing observable — §3.1's fix is the part that makes it work.

### 3.1 Marksmanship (`0x20`) — items are invisible to the ranged-attack getters

Ranged attack and ranged damage are the *only* combat stats computed outside the
`GetSuperlativeEnabledAbOwner` machinery, and they query the **self-only** pair:

```
TRangedAttackAbility.GetAttackRA @0x5576e65c    ; ability=EAX, owner=EDX
  mov bl,[eax+0x2a]                 ; base ranged attack
  test esi,esi / je out
  mov edx,0x20 / call [ecx+0x88]    ; owner.GetAbEnabled(Marksmanship)   ← SELF-ONLY
  mov edx,0x20 / call [ecx+0x84]    ; owner.GetAbLevel(Marksmanship)     ← SELF-ONLY
  <level ladder: L1/L2 → +1, L3/L4 → +2>
TRangedAttackAbility.GetDamageRA @0x5576e614    ; same two calls at +0x14 / +0x27
```

and `owner` is pinned to the **source unit**, never to an item:

```
TRangedAttackAbility.fcExecuteCombatCommand @0x5576eb70
  call [param_2.vtable+0xb8]        ; TCombatUnit.GetAbilityOwner@0x55725000 → return [cu+0x4c]
  → CreateRangedAttackCA @0x5576eae4 re-fetches it 3× and feeds it to
    ability.vtable[0x114] (damage), [0x110] (attack), [0x11c] (damage types)
```

`[cu+0x4c]` is the strategic `THero`. `hero.GetAbEnabled(0x20)` → `hero.GetAbSet(0x20)` →
`TCustomAbilityList.GetAbSet` on the hero's own list → **false** for an item-granted Marksmanship, so
the whole ladder is skipped and the shot gets base attack/damage. **This affects equipped items and
use-slot items identically.**

⚠ **In the installed DLL this site is already hooked** — `cave_5580C240` (a pre-existing, previously
undocumented rework; see `Investigation_Combat.md`). Live bytes: the `test al,al / jz` after the
`+0x88` call is **NOP'd out** at `0x5576E678`, the `+0x84` level fetch runs unconditionally, and
`0x5576E689` is `call 0x5580c240`. The cave therefore receives **level 0 in EAX** for item-granted
Marksmanship and adds nothing. Any fix must be made *inside that cave* or upstream of it — do **not**
revert `.pre-*` backups to "restore" the site (§CLAUDE.md revert rule).

**Not fast-combat-only.** `AoWTCPCK.dpl` (manual tactical combat) imports the same
`TRangedAttackAbility.CreateRangedAttackCA` (IAT slot `0x0046E634`) — so manual combat runs the exact
same owner resolution and is equally blind.

**Fix (small, ~6 bytes + a few in the cave):** swap the two queries from the self-only pair to the
item-aware pair — `call [ecx+0x88]` → `call [ecx+0x148]` and `call [ecx+0x84]` → `call [ecx+0x144]`.
Both are `call dword ptr [ecx+disp32]` already (6 bytes, disp32 encoding), so it is a pure
displacement edit with **no length change and no cave needed**. Do it in `GetAttackRA` *and*
`GetDamageRA`. Caveat: `owner` here is only guaranteed to be a unit-hierarchy object — a `TUnit` also
has `+0x144/+0x148` (`TAbstractUnit.*`), so the change is safe for non-heroes too (it degenerates to
the same answer). Verify no *other* class reaches these getters before applying.

### 3.2 Healing (`0x2f`) — the once-per-turn flag is written to the hero and read from the item

Healing's "already used this turn" state is a `THealingAbilityData` record attached to an
**ability owner**, with the level/flag byte at `data+0xc`:

| Function | Live behaviour |
|---|---|
| `THealingAbility.GetEnabled@0x5576bf2c` (vt +0x74) | `owner.vtable[0x4c]` (**GetAbSet, self-only**); then `GetAbilityData(owner,0x2f)` — **if no record exists → `mov al,1` = ENABLED** |
| `THealingAbility.SetEnabled@0x5576beec` | `GetAbilityData(owner,0x2f)`; if absent, **creates** one via `AddAbilityData(owner,…)`; stores the flag |
| `THealingCA.Execute@0x5576bce0` | `SetEnabled(ab, [healerCU+0x4c], 0)` — writes the spent flag to the **source unit**, then `HealUnit(ab, [targetCU+0x4c])` |
| `THealingTE.Execute@0x5576c6f8` (strategic map) | same shape: `GetEnabled(unit)` → `SetEnabled(unit, 0)` |
| `THealingAbility.NewTurn@0x5576bf58` | `IsClass(owner, TAbstractUnit)` **gate**, then `SetEnabled(owner,1)` — **an item is not a `TAbstractUnit`, so an item's flag is never refreshed** |

And the fast-combat driver gates on the **item-aware** accessor:

```
TFastCombatUnit.fcExecute @0x55744268
  src = param_1[0x13]                       ; = combatUnit+0x4c → the THero
  n   = src.vtable[0x158]()                 ; THero.GetAbilityCount   (item-aware)
  for id = n-1 downto 0:
      if src.vtable[0x148](src, id):        ; THero.GetAbilityEnabled (item-aware) ← THE GATE
          ability.vtable[0xa0](ability, cmdList)     ; fcPrefetchCombatCommands
  ... list sorted; list[0] → ability.vtable[0xa4]    ; fcExecuteCombatCommand
```

**The loop, per round:**
1. Gate asks `THero.GetAbilityEnabled(0x2f)`. Order is self → equipped → inventory.
   `TAbstractUnit.GetAbilityEnabled(hero)` returns 0 (it calls `GetEnabled(hero)`, whose *first*
   test is the self-only `hero.GetAbSet(0x2f)` = false). It then falls through to the item, where
   `GetEnabled(item)` finds **no `THealingAbilityData` → returns 1 = enabled.**
2. Heal fires. `THealingCA.Execute` writes the spent flag **on the hero**.
3. Next round: the gate re-runs step 1 and the item **still** has no record → enabled again.

⇒ **the flag is written to one object and read from another, so it can never latch.** One heal per
round, forever. The `NewTurn` refresh gate is a second, independent guarantee that an item-held record
would never reset even if one were created.

**Also not use-slot-specific, and not fast-combat-specific in mechanism.** The same asymmetry holds
for an *equipped* Healing item (`THeroItems.GetAbilityEnabled` → `GetEnabled(item)` → no record → 1).
`AoWTCPCK.dpl` imports `THealingAbility.CreateHealingCA` (IAT `0x0046E63C`) and thus reuses
`THealingCA.Execute`, so manual combat should be re-clickable too — fast combat merely *exposes* it
because `fcExecute` re-queries the gate and auto-uses the ability every round with no player input.

**Fix options (pick one, none built):**
- **(a) Write the flag where it was read — 1 cave, ~15 instr.** In `THealingCA.Execute`, replace
  `mov edx,[edi+0x4c]` (@`0x5576BD1A`) with a call that resolves the *actual* owner:
  `[edi+0x4c].vtable[0x144-family]`… concretely `THero.GetSuperlativeEnabledAbOwner(hero, 0x2f)` —
  which is exactly the object the gate consulted — and pass that to `SetEnabled`. Then extend
  `THealingAbility.NewTurn` to drop the `IsClass(TAbstractUnit)` gate (or add an `IsClass(TItem)`
  arm) so the item's record is refreshed each turn. Do the same in `THealingTE.Execute` for the
  strategic-map heal. **Most correct; keeps items as first-class ability owners.**
- **(b) Invert `GetEnabled`'s default.** Make "no data record" mean *disabled* for non-unit owners.
  One-line-ish, but it makes item Healing permanently unusable rather than infinite — a nerf, not a
  fix, and it would break any owner that legitimately relies on the enabled-by-default path.
- **(c) Keep the state on the unit.** Patch `THealingAbility.GetEnabled` so that when `owner` is a
  `TItem`, it re-reads the flag from the item's holder. Needs an item→hero back-pointer;
  `item+0x24` is the array-owner index, not a hero pointer — would need `SetOwner@0x55793f18`
  traced first. Least attractive.

### 3.3 The general rule + the enumerated victims

Any ability granted by an item is invisible to a consumer that queries `+0x4c / +0x84 / +0x88`.
Scanning the whole CODE section of the installed `AoWEPACK.dpl` for `mov edx,<ability id>` followed
within 6 instructions by `call [reg+slot]` (script in scratchpad; resync sweep, not the naive
`capstone.disasm` that stops at the first bad byte) gives the complete list:

### 3.3b Two propagation facts — where item state is dropped on its way to the screen

Both came in from Inioch's `share4` (checklist rows S4-05 / S4-56 / S4-06) and were re-verified
against our own live `AoWEPACK.dpl` on 2026-08-28. Neither needs a patch here; both explain the
failure shape *"the patch works but the panel never changes"*, which has cost us sessions before.

**(a) `TAbstractUnit.ListAbilityInfo @0x5577FA50` hands the GRANTING OBJECT to the ability's info
call — and for an item-granted ability that object is the `TItem`, not the hero.**
The loop is item-aware for *membership* and item-scoped for *identity*:

| VA | call | meaning |
|---|---|---|
| `0x5577FA96` | `[unit.vmt+0x158]` | how many ability ids to walk (item-aware) |
| `0x5577FAB1` | `[unit.vmt+0x14C]` | does the unit have id *i* (item-aware ✓) |
| `0x5577FAC6` | `[unit.vmt+0x154]` | **which object grants it** — a `TItem` for an item grant |
| `0x5577FAEF` | `[ability.vmt+0x58]`, EDX = that object | build the name/description text |

So the overland unit window's ability list is built by asking the *item* about itself. A hook that
decorates an ability's name or description and keys on "the owner is a `THero`" is skipped here
while the party window — which goes through the merged hero-side query — shows the decorated
text. Add `+0x154` to the §3.3 consumer list: it is the only slot in that table that returns an
**owner**, and it is the reason a display can be right in one panel and stale in another.

**(b) `TAbilityOwner.UpdateDefaultAbilities @0x5574F518` — the merge that reconciles the several
live copies of a unit — is BIT-GATED.** Walking it live (EAX = dest, EDX = source):

```
5574F524  call [source.vmt+0x54]      ; id count; loop ebx = count-1 .. 0
5574F535  call [source.vmt+0x4C]      ; source HAS the bit for id ebx?
5574F53A  je   next_id                ;   no  -> THE ID IS SKIPPED ENTIRELY
5574F542  call [dest.vmt+0x4C]        ; dest has the bit?
5574F547  je   clone                  ;   no  -> clone the record across
5574F54D  call cave (source level)    ; both have it: compare levels
5574F55B  call cave (dest level)      ;   <-- our two patches, build_leadership_fix.py
5574F565  jle  next_id                ; clone only when source level > dest level
5574F59F  call [dest.vmt+0x50]        ; clone tail: SET the dest bit
```

A data record **without its owner bit therefore never propagates to any other live copy of the
unit**, even though `AssignAb` and `TAbilityOwner.ReadWrite` (the id-list, tag `0x31`) copy records
bit-independently — so a bit-less record survives save/load and assignment, and still never
reaches the panel you are looking at.

**Audit of our three participants in that function — no gap, no patch:**

| script | what it does there | depends on bit-less records? |
|---|---|---|
| `build_leadership_fix.py` | rewrites the two level calls (`0x5574F54D` / `0x5574F55B`) to read the *inherent* level | no — it never reaches the gate |
| `build_leadership_aura.py` | wraps the **caller** at `0x557854E0`, runs the merge then recomputes the stack aura | no |
| `build_copper_medal.py` | chooses which `TUnitResource` owner slot is passed as the source | no — editor-authored owners always carry their bits |

And we never mint a bit-less record in the first place: every Ziggurat grant goes through
`TAbilityOwner.ExpandAbility @0x5574F5B4` or `SetAbSet @0x5574E0BC`, both of which set the bit.
⚠ **Do not adopt his fix** (letting bit-less records through the gate): the medal and rank grants
run through this same function, and `build_leadership_fix.py`'s "GRANT MASKED" analysis exists
precisely to control which of them propagate. Loosening the gate would let medal-granted
abilities cross without their bits.

### 3.3c The overland unit window — listed item-aware, gated self-only (S4-07, 2026-08-28)

The same split as §3.3b(a), one window further on, and the reason it produces **no** live defect.

`TUnitWindow` (in `AoW.exe`) fills its ability list through the **item-aware** `ListAbilityInfo`,
then gates *activating* the clicked row on a **self-only** query. That mismatch is the whole bug:

| VA (AoW.exe) | what |
|---|---|
| `0x409397` / `0x40944B` | fill the list via `TAbstractUnit.ListAbilityInfo` (item-aware, §3.3b) — so the ability is listed and looks normal |
| **`0x409EF7`** | `UseAbility`: `call [ability.vmt+0x74]`; fail → `0x409FD7`, **silent return** ⇐ the single site to patch |
| `0x409F4C` | `call [ability.vmt+0xB4] Activate` — the only step after the gate |
| (`0x409874`) | `T1AbilityLBChange` runs the same gate for `T1UseBut`'s visibility — not the control the player uses; see below |

The gate resolves to a raw bit test on the unit's **own** array, with no item leg anywhere:

```
5574EEF4  TAbility.GetEnabled:  mov eax,[eax+0xC] ; xchg edx,eax ; mov ecx,[eax] ; call [ecx+0x4C]
5574E0E0  TCustomAbilityList.GetAbSet:  cmp edx,[eax+0xC] / jae 0 / mov eax,[eax+8] / bt [eax],edx
55788104  THero.GetAbSet:  call 0x5574E0E0 ; ret        <-- a bare passthrough: self-only for heroes too
```

Only **2 of the 82** classes in the `TAbility` hierarchy override `+0x74` — `THealingAbility`
`@0x5576BF2C` and `TDispelMagicAbility` `@0x5576CE58` — and both open with that same self-only
test before adding a *per-turn used* flag. `TSpellCastingAbility` (`0x34`) uses the base.

**⚠ So `+0x74` is not "has the ability" — for Healing and Dispel Magic it is "usable right now".**
That is why swapping in the item-aware `+0x148` as a fallback is not a free fix: the item leg of
`THero.GetAbilityEnabled @0x5578827C` validates the per-turn flag **on the item**, not the hero.
It is currently harmless only because `build_useitems.py` P1 hooks both `GetEnabled` bodies
(`jmp 0x55815060` / `0x55815070`) and redirects an item owner to its carrier — i.e. any future
patch here would be silently coupled to that feature staying installed.

**⚠ It IS reachable — on Ziggurat's own items.** Four ability classes are activatable in this
window (`GetControlType & acAction`, bit 0): `TSpellCastingAbility 0x34`, `THealingAbility 0x2F`,
`TDispelMagicAbility 0x3C`, `TConstructAbility 0x7D`. None of the four is granted by anything in
`Release/ITEMS.PFS` — **but that file is not the mod's item list.** Ziggurat ships its items in
the item library `User/Zig.ail` (325 records against ITEMS.PFS's 83), and there:

| ability | items | levels |
|---|---|---|
| **Spell Casting `0x34`** | **31** (26 worn, 5 `itUse`) | authored 1–5, all with `0x66` sub-records |
| **Healing `0x2F`** | **5** (Elixir of Life, Ring of Health, Ring of Life Power, Robe of Life, The Ankh) | none — bits only |
| Dispel Magic `0x3C`, Construct `0x7D` | 0 | — |

So a hero **without the innate ability** who wears e.g. the Wizard Ring (Spell Casting 4) or the
Ring of Health (Healing) gets the ability listed in the overland unit window by the item-aware
`ListAbilityInfo`, and then the self-only gate at `0x409874` hides the Use button. Three of the
five Healing items are worn (`itDefense`/`itHead`), so they have no item-use button to fall back
on either. **Not yet observed in game** — what the button does for each ability, and whether the
spellbook route makes the Spell Casting case moot, still needs the author's test.

**⚠ There are TWO routes into `UseAbility`, and only one of them goes through the button.** The
DFM binds it twice — verified by scanning the exe for the string `UseAbility`, 5 occurrences:

| file offset | binding |
|---|---|
| `0x6C8F` | the published-method table entry itself (`\x11\x00 \x90\x9e\x40\x00 \nUseAbility`) |
| `0x1EAFEE` | `OnClick` on a `TAOWButton` (the one before `T1SortName`, `Text = '####'`) |
| `0x1EAC43`, `0x1EC02F`, `0x1EC3BA` | **`OnDoubleClick` on the ability listbox** — all three window variants, each next to `OnChange = T1AbilityLBChange` |

So **double-clicking a listed ability calls `UseAbility` directly**, and the listbox is always
visible — it is filled by the item-aware `ListAbilityInfo`, so the item-granted ability is right
there to double-click. The button's visibility is irrelevant on that route.

⚠ **Do not repeat the mistake that produced the first version of this section.** A code-xref scan
for `E8`/`E9`/absolute references to `0x409E90` finds only the published-method-table entry and
concludes "invoked only as that button's OnClick" — but **DFM event bindings resolve by NAME
through that same table**, so a code scan cannot see them and cannot distinguish one binding from
four. Read the DFM. On that false basis this note previously called Inioch's patch "inert"; it is
not. Patching `0x409EF7` alone **does** fix the double-click route.

  (`TUnitWindow` VMT `0x0040710C`): `word count / dword classtable`, then entries of
  `dword offset / word classindex / pascal name`. ⚠ The offset field is a **dword**, not a word —
  getting that wrong yields plausible-looking garbage names.
- `[aowInt control vmt+0x6C]` = `AoWButton.TAOWBaseButton.SetVisible @0x59810EC0` (writes
  `[ctl+0x75]`, chains `TAoWComponent.SetVisible @0x59803004`).

  `[T1AbilityLB+0x120]` → list `[+0x114]` → `[+0x18]` → `TAbilityControl.GetAbility` — and gates
  the *button's* visibility on `GetEnabled(unit) AND (GetControlType & acAction)`
  (`0x409874` then `0x4098A6`). Useful if that button ever matters; it does not here.

**⚠ The cause is NOT multi-level-ness.** It is tempting to read it that way (Spell Casting is
multi-level; ranged attacks are not and do not misbehave), but `TAbility.GetEnabled @0x5574EEF4`
is `unit.GetAbSet(id)` — a raw bit test with no level involved, identical for every ability class.
Two consequences worth holding onto:

- **Healing `0x2F` is affected the same way**, despite being single-level. Its `GetEnabled`
  override adds the per-turn flag *after* the same self-only bit test. So the five Zig.ail Healing
  items are in the same position as the 31 Spell Casting ones.
- **Ranged attacks are unaffected for a different reason**: `TRangedAttackAbility.GetControlType`
  is `{acCombatAction}` (bit 1, no `acAction`), so they are never activated from this window at
  all — they fire through the attack path, whose item-blindness was a separate defect fixed by
  `build_useitems.py` / `build_marksmanship8.py`.

### 3.3d The rest of the item cluster, settled (S4-57/58/78/90, S5P-58, S5B-061, 2026-08-28)

**(a) ⚠ `+0xA8` is nil-guarded, `+0xB0` is NOT — and that asymmetry is the rule.** Live bytes,
byte-identical to pristine, so this is vanilla engine design:

```
; TCombatUnit.GetAbilityEnabled @0x55725004   (combat VMT +0xA8)
55725004  mov ecx,[eax+0x4C] / test ecx,ecx / je 0x55725016   <-- nil -> return 0
5572500F  call [ecx+0x148]                                     ; strategic, item-aware
; TCombatUnit.GetAbilityLevel @0x55725028     (combat VMT +0xB0)
55725028  mov eax,[eax+0x4C] / mov ecx,[eax] / call [ecx+0x144]  <-- NO nil check
```

So **a nil `[combatobj+0x4C]` is a normal engine state**, not a corruption, and
`GetAbilityLevel` is legal only *directly behind* a `GetAbilityEnabled` gate on the same object
in the same function. `GetAbilityCount` (+0xAC region, `@0x55725034`) is guarded like `+0xA8`.
On a wall the whole family degrades safely — `TCombatObject.GetAbilityOwner @0x557268D0`,
`GetAbilityEnabled @0x557268D4` and `GetAbilityLevel @0x557268DC` are all `xor eax,eax; ret`.

Our two live `+0xB0` sites, audited:

| site | verdict |
|---|---|
| `0x5576B56C` (`build_turnundead_res.py` reads it; the dispatch is **vanilla**, byte-identical to pristine) | ungated — no `+0xA8` call anywhere in `0x5576B380..0x5576B5C0`. Safe in practice (the attacker of a Turn Undead strike is never a wall) but it is the Generate-sets/Execute-reads shape, so **treat it as a hazard** if that ability is ever re-timed |
| `build_arena.py:676` `call [ecx+0xB0]` | ⚠ different class — that object is the army/unit list (`[edx+0x54]` count, then a UnitList Get), not a `TCombatUnit`. The rule does not apply. *An offset means nothing without its class.* |

**(b) Combat does not use the ability-side owner-finder — it queries the strategic unit.** Both
combat slots above forward through `[combatobj+0x4C]` to the strategic unit's `+0x148`/`+0x144`.
Those *are* item-aware, so items do reach combat; what combat never consults is the
`GetAbilityOwner` (`+0x154`) route the windows use. That is why a patch on the ability's own
`GetLevel` can make the unit window and the combat resolution disagree about the same ability —
the display resolved it through the owner-finder and combat through `+0x144`.

**(c) Item ability levels are DATA — sparse in vanilla, routine in Ziggurat.** ⚠ Census both
files: `Release/ITEMS.PFS` is the *vanilla* table and **not** what the mod ships.

| file | records | grant abilities | carry an `id+0x32` level sub-record |
|---|---|---|---|
| `Release/ITEMS.PFS` | 83 | 70 | **2** — Ankh of Turning (Turn Undead `0x26`), Helm of Eyes (Vision `0x40`) |
| `User/Zig.ail` (the mod's item library) | 325 | 313 | **61 items / 76 sub-records** |

Ziggurat's 76 sub-records use three ClassIDs — `0x00022001` `TMultiLevelAbilityData` (45),
`0x00022002` (24), `0x000202CE` (7) — and level: Spell Casting `0x34` (31), Vision `0x40` (14),
`0x62` (9), Leadership `0x2E` (7), `0x60` (7), `0x5D` (5), `0x5C` (3). Levels decode as sub-record
tag `0x0A` (with `0x0B` = the id), and ⚠ **the sub-record is parsed `top=True`** — it carries the
4-byte ClassID.

So Inioch's "the editor authors item abilities as bits only" is **wrong as a rule** and only
describes the vanilla table: the editor writes these records routinely, and this mod is 61 items'
worth of proof. What survives is the *consequence* for a bits-only grant — Crown of Kings
(vanilla, Leadership `0x2E`, no record) resolves at level 0. **No item in either file grants
Marksmanship `0x20`**, which is what makes the old claim in `build_marksmanship8.py` that "an
item-granted Marksmanship level works" vacuous — corrected at source on the same date.

**(d) ⚠ `THealingAbility.GetEnabled` and its Dispel twin are already hooked — by us.**
`build_useitems.py` P1 owns `0x5576BF40` (→ cave `0x55815060`) and `0x5576CE6C`
(→ `0x55815070`). Anything else that wants those functions must **extend that script in place**;
a second 5-byte owner on either site would silently clobber the first. Related risk in §3.3c.

**(e) Unverified, recorded as his claim only.** Inioch reports (from live heap probes, not from
any static evidence we can re-check) that the game keeps **several live objects per hero** —
server/world, client/UI, transient window copies — in addition to the `TFastCombatUnit`
strategic twins we already document. We have not confirmed the server/client/window split; if a
future symptom looks like "the data changed but this panel did not", it is the first thing to
test with `re_tools/live_ui.py`, and §3.3b(b)'s bit-gated merge is how state moves between them.

### 3.4 Cheap A/B test to run before designing anything

The analysis says both reported bugs are *item*-scoped, not *use-slot*-scoped. That is worth 5 minutes
in-game, because it changes which fix is right:

1. Put **Marksmanship** on an `itAttack` (equipped) item, give it to a hero with a ranged attack, and
   read the unit card / take a shot. **Prediction: still no bonus.** If it *does* work equipped, then
   `owner` is not always `[cu+0x4c]` and §3.1 needs re-derivation for that path.
2. Put **Healing** on an equipped item and fast-resolve a long combat. **Prediction: also infinite.**
3. Put a `+0x46` ATK bonus **and** Marksmanship on the same `itUse` item. **Prediction: neither the
   ATK byte nor Marksmanship shows; but a carried ability with a `GetAbAttack` term (e.g. Enchanted
   Weapon `0x9A`) *does* add its attack.** This separates Route A from Route B (§0.4) cleanly.

### 3.6 A THIRD instance of the Healing bug: **Dispel Magic (`0x3C`) is broken identically**

Predicted from the pattern, then confirmed. Only **two** ability classes in the whole DLL have a
`SetEnabled` at all — `THealingAbility` and `TDispelMagicAbility` — so this is the complete bug class,
and both members are broken:

| | Healing `0x2F` | Dispel Magic `0x3C` |
|---|---|---|
| owner-type mask | `0x0241` — **legal on `itUse`** | `0x0241` — **legal on `itUse`** |
| `GetEnabled` | `0x5576bf2c` — self-only `GetAbSet`, **no record ⇒ enabled** | `0x5576ce58` — *identical* |
| `NewTurn` | `0x5576bf58` — `IsClass(TAbstractUnit)` gate | `0x5576cec4` — *identical* |
| combat consume | `THealingCA.Execute@0x5576bce0` → `SetEnabled(ab, [healerCU+0x4c], 0)` | `TDispelMagicAbilityCA.Execute@0x5576cce4` → `SetEnabled(ab, [casterCU+0x4c], 0)` |
| strategic consume | `THealingTE.Execute@0x5576c6f8` | `TDispelMagicAbilityTE.Execute@0x5576d945` |
| fast-combat prefetch | `0x5576c48c` | `0x5576d460` (same shape) |

⇒ **A Dispel Magic use-item is infinitely usable, exactly like a Healing one.** Worth testing
alongside Healing — it is the cleanest confirmation that the defect is the write/read owner mismatch
and not something Healing-specific. Any fix must patch **both** classes (and both their CA and TE
consume sites), or add the correction once in `TAbilityOwner`-level shared code.

Note both are **intended** use-item content (mask bit 6 set), unlike Marksmanship. So this is
squarely a vanilla bug in shipped design space, not a consequence of unusual authoring.

### 3.7 ⚠ The deeper reason items get no per-turn upkeep: **the message never arrives**

§3.2 blamed the `IsClass(owner, TAbstractUnit)` gate in `NewTurn`. That gate is real, but it is the
*second* line of failure. The first is more fundamental: **a carried `TItem` never receives the
new-turn / new-day broadcast at all.**

The plumbing looks complete, which is what makes this easy to miss:

```
TAbilityOwner.MsgProc @0x5574ff10
    msg 0x20020001 (NewDay)  -> TriggerNewDay  @0x5574fda4
    msg 0x20020002 (NewTurn) -> TriggerNewTurn @0x5574fe14
TriggerNewTurn(owner, playerIdx):
    for id in 0..owner.vtable[0x54]():            ; GetAbCount, self-only
        if owner.vtable[0x4c](owner, id):         ; GetAbSet,  self-only
            ability.vtable[0xac](ability, owner, playerIdx)    ; NewTurn
TItem.MsgProc @0x55794878  ->  chains to TAbilityOwner.MsgProc   ; so an item WOULD trigger
```

But nothing delivers to it:

- **`THero.MsgProc@0x55788c04` → `TAbstractUnit.MsgProc@0x55781238` → `TAbilityOwner.MsgProc`** runs
  the trigger **on the hero only**. Neither ever forwards the message to `hero+0x70` (`THeroItems`)
  or `hero+0x74` (`THeroInventory`).
- **`TItemControl` is a plain `TEObject`** (`Create@0x55794b28` — a raw `Classes.TList` at `+8`, two
  `TEventList`s at `+0xc`/`+0x14`), with **no `MsgProc` override**, so it does not fan out to its
  registered items either. It is not a `TENode`, so the scene-graph broadcast misses it too.
- **`TAoWHSMap.SendMsg@0x5577855c`** broadcasts via `Engine.TENode.SendMsg` plus six explicit control
  lists (`map+0x188/+0x140/+0x144/+0xf4/+0xf8/+0x130`); carried items are in none of them.

⇒ **`TItem.MsgProc`'s chain into the ability trigger is dead code for a carried item.** Items get no
per-turn *or* per-day ability upkeep, ever — independent of the `IsClass` gate.

**Correction to §3.2's fix (a):** removing the `IsClass(TAbstractUnit)` gate **would not be enough on
its own**. Either also deliver the message (add a forward in `THero.MsgProc` to `hero+0x70`/`+0x74`,
which is the tidiest — one cave, and it fixes upkeep for *all* item abilities at once), or make the
consume site write the flag where the gate reads it (fix (a) as originally stated) so no upkeep is
needed on the item at all. The second is smaller; the first is what vanilla evidently intended.

**Generalisation worth remembering:** any per-turn/per-day ability state on an *item* is dead in this
engine. `TDurationAbility.NewTurn@0x55764d30` and `TUnitEnchantmentAbility.NewTurn@0x55765a50` tick
durations the same way — an item-carried duration ability would never expire.

### 3.8 Fix option (c) is now viable — items DO have a path back to their hero

§3.2 listed "re-read the flag from the item's holder" as least attractive because no back-pointer was
known. There is one, two hops:

```
item+0x4       = the CONTAINER   (TItem.SetOwner@0x55793f18 stores it; calls container.vtable[0x6c]
                                  Remove / [0x70] Add — so it is THeroItems / THeroInventory /
                                  TItemHS / the library, NOT the hero)
container+0x4  = the owning HERO (THeroItems.Create@0x557862c0 stores its param_3 there;
                                  THeroItems.GetLocation@0x5578633c proves it by calling
                                  TAbstractUnit.GetLocation([this+4], …))
```

So `[[item+4]+4]` is the hero — **guarded by an `IsClass` check on the container**, since it may be a
`TItemHS` (item lying on the map) or a library list instead. That makes fix (c) a real option, and it
is also the mechanism any future "item ability needs to know its wielder" feature will need.

### 3.10 ⚠ Does the §3.1 fix leak bonuses into the wrong slot? — audited, and there IS one caveat

Asked directly, so audited directly. The §3.1 fix changes only the *consumer*
(`GetAttackRA`/`GetDamageRA` querying `+0x148/+0x144` instead of `+0x88/+0x84`); it does not touch
either aggregate. Three cases:

**(a) A wearable item sitting in the backpack — SAFE, cannot happen.**
All four `THeroInventory` walkers hard-gate on `item+0x34 == 6`
(`GetSuperlativeAbOwner@0x557861f4`, `GetSuperlativeEnabledAbOwner@0x557860c0`,
`GetAbilitySet@0x557861a4`, `GetAbilityEnabled@0x55786154`). A helmet or ring in a backpack slot is
type 0/4 and is skipped before any ability is read. The flat bytes `+0x46..0x49` and the
immunity/protection/move-type words are equipped-only regardless (§0.7). Unchanged by the fix.

**(b) An item worn in the *wrong* equipment slot — SAFE, cannot happen at all.**
There is **no generic equipment slot**. `THeroItems.CanPlaceItem@0x5578674c` requires
`slot < 6` **and** the slot to be empty **and** `GetPositionItemType(slot) == item+0x34`;
`PlaceItem@0x55786788` calls it first and refuses on false. Membership in `THeroItems` therefore
already *means* "worn in a slot of its own type" — position 5 accepts a ring and nothing else. No
consumer needs to re-check the slot.

**(c) ⚠ A PASSIVE ability authored onto an `itUse` item — this one DOES leak, and it is the mirror
image of the question.** Today Marksmanship-on-a-use-item does nothing; after the fix it would
**work while merely carried in the backpack, never worn**. The chain: the inventory gate passes (the
item *is* type 6), and `GetAbilityEnabled`/`GetAbilityLevel` never consult the ability's own legality
mask — because `ValidateOwnerTypeAbilities` never runs on items (§3.0b). Marksmanship's mask `0x0237`
says "not legal on itUse", and nothing enforces it.

**If that matters, pair the fix with mask enforcement on the inventory path** — add
`ability[+0x20] & 0x0040` to the four `THeroInventory` gates (each already loads the ability; ~4 × 6
instructions), or call `ValidateOwnerTypeAbilities` on each item once at load. Either makes the
backpack honour the declared design while leaving worn items alone.

**Scope of the exposure today: zero shipped items violate the mask.** The `ITEMS.PFS` audit (§3.0)
found all 10 `itUse` items carrying exactly one *active* ability each and every wearable carrying
only slot-legal passives. So enforcement is needed only if abilities are authored outside the mask —
i.e. exactly the situation that prompted this investigation.

**Same decision point applies to Feature 2 Route 1.** If the `+0x4a`/`+0x4b` HP/MV aggregator walks
`hero+0x74` as well as `hero+0x70`, a use item's HP byte would count while its ATK byte (`+0x46`)
does not — inconsistent with every other stat in the game. **Recommend equipped-only**, mirroring
`THeroItems.GetAttack`.

### 3.9 Reusable lessons

- **Two ability APIs, one item-aware** (§0.6). Before hooking any ability consumer, check which VMT
  slot it calls. `+0x84/+0x88/+0x4c` = self-only; `+0x144/+0x148/+0x14c/+0x158` = item-aware;
  `+0xa8/+0xb8` on `TCombatUnit` = forwards to the source unit's item-aware pair.
- **Ability legality is a bitmask handshake** (`ability+0x20` × owner `vtable[0x8c]`, §3.0) — the
  fastest way to learn what a subsystem was *designed* to do. It answered "why do use items work
  differently" in one table after hours of behavioural reasoning had only produced symptoms.
  `re_tools/abmask.py` dumps it.
- **Declared-legal ≠ works.** The mask is enforced only by `ValidateOwnerTypeAbilities`, whose sole
  caller is `TUnitResource.ReadWrite` — never an item. So the mask states intent; it neither strips
  illegal abilities from items nor guarantees legal ones function. Check both sides.
- **Cross-check design claims against the shipped data.** The `itUse` "one active ability per item"
  rule was confirmed by dumping `ITEMS.PFS` (`re_tools/pfs.py`) — 10 use items, one active ability
  each, zero passives. A code-only reading would have left it a hypothesis.
- ⚠ **`Ability.pfs` record ids are NOT ability ids** — record `0x2F` holds Leadership's description,
  `0x20` a ranged-attack one. It is a description/metadata table with its own numbering; do not join
  it to ability ids. (Only 25 of its 149 records even parse with the standard directory reader.)
- ⚠ **Existing plumbing is not evidence of delivery.** `TItem.MsgProc` chains into the ability
  new-turn trigger and looks fully wired; nothing ever sends it the message (§3.7). Trace the
  *sender*, not just the handler, before concluding a path is live.
- **`aowsyms.get_symbols` strips the `@<unit-hash>` suffix** that Ghidra shows — match on
  `nm.endswith(".Create")`, not `".Create@23EDC2EF"`. A filter written from Ghidra's display names
  silently matches zero symbols.
- ⚠ **Locate editor patches by SIGNATURE, not by address.** `AoWDevEd.exe` and `AoWEd.exe` are
  different builds of the same source: the itUse gate is `0x0041349C` in one and `0x0041348C` in the
  other. Patching both at one VA lands on foreign code (byte `0xE0`). A unique byte signature plus a
  "exactly one match" assertion handles both and survives future rebuilds. Same caution applies to
  every `AoW.exe` ↔ `AoWDevEd.exe` pair (already a CLAUDE.md rule; this is a concrete instance).
- **A one-caller function can be replaced wholesale.** Checking callers first (7 rel32 xref scans,
  two minutes) turned what looked like "hook 7 functions and splice new logic into each" into
  "replace 7 self-contained functions", which is far easier to write and to verify.
- **`GetAbilityOwner` on a combat unit is not "the ability owner" in the `GetSuperlative*` sense** —
  `TCombatUnit.GetAbilityOwner@0x55725000` is a 4-byte `mov eax,[eax+0x4c]; ret` that always returns
  the source unit. Anything downstream of it has already lost item provenance.
- **`GetEnabled`-style flags default to "enabled" when no data record exists.** Any ability whose
  per-turn state lives in a `TAbilityOwner` data record will misbehave if the owner that receives the
  write differs from the owner that answers the read. Grep for the pair
  (`SetEnabled` caller's owner expression vs the gate's) whenever an ability is "infinitely usable".
- **`NewTurn` on ability classes is gated on `IsClass(owner, TAbstractUnit)`** — items never get
  per-turn upkeep. Any new ability with per-turn state has the same hole.
- Manual tactical combat is **not** a separate implementation of these abilities: `AoWTCPCK.dpl`
  imports `CreateRangedAttackCA` / `CreateHealingCA` from `AoWEPACK.dpl`. Checking its IAT (one
  `aowsyms.get_symbols` call) is far cheaper than assuming a second code path exists.

### ⚠ THE LIVE ITEM LIBRARY IS `User/Zig.ail`, NOT `Release/ITEMS.PFS`

325 records vs the stock 83. Same container, same `TItem.ReadWrite` tag map. `ITEMS.PFS` was left
untouched deliberately. Anything that authors item data in this install must target `Zig.ail`.

### Three findings that cost real time — do not re-derive

1. **`TItem.ReadWrite`'s TAIL IS NOT HOOKABLE.** At `0x55794726` the function does `mov ebx,[eax]`,
   overwriting the item pointer with the stream vtable — so at the `pop edi/esi/ebx/ret` at
   `0x5579472B`, **EBX is the item on one path and a vtable pointer on the other** (the
   `test al,4` at `0x55794718` skips tag `0x16` entirely). Hooking the tail would write through a
   garbage base pointer on one of the two paths. Hook `0x55794712` instead, where EBX is the item
   on both paths, and replay the displaced run in the cave.
2. **The `.pfs`/`.ail` directory does NOT require ascending tag keys.** Hooking before tag `0x16`
   emits `0x17`/`0x18` out of order. Measured across the shipped data: **50 of 50 `HEROES.PFS`
   records already have non-ascending key order**, plus 2 of 83 in `ITEMS.PFS`. The reader is a
   keyed scan, not a binary search.
3. **⭐ A record's directory CANNOT be re-derived — only appended to.** Entry widths and entry
   order follow no rule recoverable from the data: `Zig.ail` record 12 (Astral Vision Helm) stores
   tag `0x94` **wide** at offset 33 where a small entry would fit, and its twelve small entries are
   in neither key nor payload order. A first writer rebuilt bodies from "small if it fits, in
   payload order" and produced a valid-*looking* record 10 bytes shorter with a reordered
   directory. Because offsets are relative to the directory END, appending is safe and moves
   nothing: copy every existing entry verbatim, append yours. Its own self-test caught this.

### Tag space in an item record (settled)

```
0x00-0x06  TAbilityOwner        (0x02/0x03 = ability bitset)
0x07-0x16  TItem's own fields   (0x16 is the last vanilla writes)
0x17-0x30  FREE                 <- 0x17 HP, 0x18 MV
0x31       ability-id list the loader drives off
0x32+      per-ability data sub-records (tag = ability_id + 0x32)
```
Neither `.ail` nor `ITEMS.PFS` carries a magic header or a CRC (unlike `Unitres.pfs` /
`HERORES.PFS`) — never stamp one.

### THE TRAP — the getters sum in 8 bits, and the sum is ALREADY at the ceiling

This was not flagged in the 2026-07-30 draft and it is the one thing that will silently ruin the
feature. `GetHits` computes **`add dl, [eax+0x6d]` — an 8-bit add** — and only afterwards does
`movsx` + a signed 16-bit compare against the clamp.

`hero+0x6d` is not a small number. `fieldrefs` attributes it to `THero.SetUnitHits@0x557878A0`
(`inc byte [esi+0x6d]` / `mov [esi+0x6d],bl`), `UsedSkillPoints`, `ResetSkillPoints` — it is the
**skill-point-purchased HP upgrade**, and the hero level-up screen lets it grow until `GetHits`
reaches its ceiling. That ceiling is **100** since 2026-08-31 (`build_hero_clamps.py` ladder
80/120/100; it was 120 from the DAM/HP doubling). Base HP from `HERORES.PFS` tag `0x12` runs
10–30, and the purchase cap in `THero.SetUnitHits` matches at 100, so a maxed hero sits at
`base + 0x6d == 100`.

**At the old 120 ceiling an item bonus of just `8` overflowed** (`128` -> wraps to −128 -> the
floor clamp fires -> the hero returns 2 HP). Lowering the ceiling to 100 was done partly to buy
that margin back: the wrap now needs a **+28** item, so ordinary bonuses are safe. **The margin
is not the fix, though — it is only a bigger cushion.** A +28 HP item, or a second additive
term stacked on top, walks straight back into it, silently, and only on high-level heroes.

**So the cave MUST do the arithmetic in 32 bits** — `movzx` each of the three terms, add as dwords,
clamp, return `AL`. Do not extend the existing `add dl, ...` chain. `GetMoves` has the same shape
(ceiling 80, base 24–36) and needs the same treatment even though its wrap needs a +48 item.

This is the same defect class as `build_medal_hpmv.py` v2->v3 (`div cl` / `mov ebx,eax`) and the
DAM/HP doubling's byte-widening lesson: **a clamp is a stricter consumer than the byte store it sits
in front of.** Prove all 32 bits, or narrow explicitly first.

### Route 1 (RECOMMENDED) — flat bonus bytes, mirroring ATK/DEF/DAM/RES

Matches the existing authoring model exactly: a number typed on the item next to the other four.
Binary: **`AoWEPACK.dpl` only** for the mechanic. Position-independent caves (register-only).

1. **Storage:** `item+0x4a` = HP bonus, `item+0x4b` = MV bonus. Free zero-init bytes inside the
   existing 76-byte allocation — **no instance growth**, and every existing item/save defaults to 0.
2. **Two aggregator caves.** Clone the cave `build_useitems.py` installed at **`0x55815080`**
   (reached by the `jmp` that now replaces `THeroItems.GetAttack@0x55786354`). Its shape, read live:
   worn loop over `[items+8]->+4` with count from `vtable+0x54` and `add bl,[eax+0x46]`, then the
   backpack arm — `[items+4]` = hero, `[hero+0x74]` = `THeroInventory`, same loop with the
   `item+0x34 == 6` gate. Change the byte offset to `0x4a` / `0x4b` and that is the whole cave.
   **Decide deliberately whether the backpack arm is wanted here**; consistency with the applied
   `build_useitems.py` says yes.
   Warning: these are **new** caves called from the new getter caves — do **not** edit useitems'
   caves, and do not add `THeroItems` VMT slots (the four existing aggregators are reached by direct
   `call`, not virtually; each has exactly one caller).
3. **Two getter caves.** Hook `THero.GetHits@0x5578859c` and `GetMoves@0x557885c0` with a 5-byte
   `jmp` at the function head (displaces 6 bytes — `mov edx,[eax+0x40]; mov dl,[edx+0x27]` — pad 1;
   0 relocs, verified). Cave: `movzx` base `res+0x27`, `movzx` `hero+0x6d`, call the new aggregator
   on `[hero+0x70]`, sum in 32-bit, then **re-enter vanilla at `0x557885A7`** (`movsx edx,al`) with
   the sum pre-saturated to 0..127 in `AL`. That keeps `build_hero_clamps.py`'s immediates at
   `0x557885AD/B1/B8/BC` authoritative and untouched, so the two features compose and either can be
   undone independently.
4. **Persistence:** extend `TItem.ReadWrite@0x557945c8` with tags **`0x17` -> `+0x4a`** and
   **`0x18` -> `+0x4b`** using the byte reader `stream.vtable[0x30]` (the same one tags `0x0B`–`0x0E`
   use). The tagged-property format is old-save-safe: absent tags default to 0.
   `TItem.UpdateFromLibrary@0x55794438` copies library->instance via `item.vtable[0x3c]`, so the new
   bytes propagate from `ITEMS.PFS` automatically once `ReadWrite` knows them.

**Undo:** surgical — restore the two getter heads + the `ReadWrite` tail, zero the caves. No backup
copy needed.

### Display in game — `TItemBanner` (AoW.exe) — STILL NOT DONE, and cheaper than expected

The item info banner is `TItemBanner`; its published-field table (file offset `0x5D7E`) reads:

```
+0x44 ItemNameLbl   +0x48 IBannerPopup
+0x4C AttackIcon    +0x50 DefenseIcon   +0x54 DamageIcon   +0x58 ResistanceIcon
+0x5C Attack        +0x60 Defense       +0x64 Damage       +0x68 Resistance      (labels)
+0x6C DrawBox       +0x70 AbLB          +0x74 AbVSB
```

The paint routine runs `0x00406B06`–`0x00406E0x`: it hides all eight stat controls, then for each
**non-zero** stat byte emits `IntToStr` -> `TAOWLabel.SetGText` and positions an icon+label pair with
a **flow layout** (`esi` = x, `[ebp-8]` = y, `add esi,0x32`, wrap at `cmp esi,0x82` -> `esi=0x1e`,
`add [ebp-8],0x14`). Read order is ATK `0x46` -> DAM `0x48` -> DEF `0x47` -> RES `0x49`.

After the stat block the routine fills the listbox `AbLB` (`[ebx+0x70]->+0x114`,
`call [edi+0x38]` per line) with ability names, so a cave can append two lines
(`"+N Hit Points"`, `"+N Movement"`) with no new controls and no class growth. Adding two more
icon+label pairs instead needs 4 new published fields (`+0x78`…`+0x84`), a larger `TItemBanner`
instance and DFM component clones; the flow layout itself already handles any number of entries, so
the positioning code needs no change.

Measured 2026-09-13, on the icon-art question: **the six stat icons exist as DFM-embedded DIBs in
`AoWDevEd.exe` only.** Hits (16×16×24, 822 B) and Moves (32×15×24, 1494 B) live on `THEROEDITFORM`
as `Image11`/`Image12`, and Item Properties' new rows now reuse them verbatim — see
`08-editor.md` §12.10. **None of the six appears anywhere in `AoWz.exe`, not even the four the
banner already draws**, so `TItemBanner`'s `AttackIcon`/`DefenseIcon`/… are not embedded bitmaps and
the editor's art does not answer the banner's art question.

Warning: whichever is chosen, this is an **AoW.exe** patch and must be mirrored into
**`AoWCompat.exe`** in lockstep. The mechanic (DLL side) works without it — the hero's own card
shows the new totals immediately, because `GetHits`/`GetMoves` are patched at source.

### Route 2 — go through the ability system instead

Unchanged from the 2026-07-30 analysis and still the better choice **if** the goal is "gear *and*
spells/medals/skills that grant HP/MV" rather than "a number in the item editor". It buys equipped +
use-slot coverage, no new item field, no `ReadWrite` change, no editor patch and no `ITEMS.PFS` edit,
at the cost of an ability-id -> value table living cave-side rather than data-side (`TAbility` has no
HP/MV virtual to call). It also extends naturally to regular `TUnit`s, which Route 1 never can.
The two are not exclusive — the getter caves in Route 1 step 3 are the same hook point.

### Risks / open items

- **The 8-bit overflow above. This is the one that must not be got wrong.**
- **HP semantics.** `GetHits` is *max*. Equipping +HP raises the ceiling but does not heal; the hero
  reads e.g. 30/40 until healed. Un-equipping drops max below current and the next `SetHitPoints`
  clamps current down. Both benign, both worth stating in the manual.
- **Second-order: faster healing.** `TAbstractUnit.NewTurn@0x55780d4c` regenerates a fraction of
  `GetHits` per turn, so +HP gear also heals faster. Probably desirable; it is a balance change
  beyond the literal feature.
- **MV timing.** `NewTurn` opens with `SetMovePoints(GetMoves())`, so an MV bonus lands on the
  **next turn refill**. Equipping mid-turn shows the new max but the same remaining points.
- **Clamps saturate** at 100 HP / 80 MV (HP was 120 until 2026-08-31).
- **`TUnit` gets nothing** under Route 1 — units hold no items. `TUnit.GetHits@0x55782B68` is a
  different impl at the same VMT slot and is **already caved by `build_medal_hpmv.py`**
  (`0x5580BE00`–`0x5580BE73` plus the cap cave at `0x55818080`). Do not touch that cave from an item
  patch; note also its documented landmine — the MV twin at `0x5580BE6D` still returns a dirty EAX.
- **AI heroes never acquire items** (`Investigation_AI_Item_Pickup.md`) — the feature is
  player-facing only unless that is fixed first.
- Needs the user's in-game test on a **high-level hero at the HP ceiling** specifically, not a fresh
  one — that is the only configuration where the overflow trap shows.
