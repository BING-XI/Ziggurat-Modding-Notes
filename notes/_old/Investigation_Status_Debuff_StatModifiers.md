# Status debuffs — why stat modifiers sometimes don't apply (Webbed / Entangled / Frozen)

> **Offsets here are class-keyed and canonical in [`Ghidra_Field_Catalogue.md`](Ghidra_Field_Catalogue.md)** (generated by `re_tools/ghidra_fields.py`, bounds-checked against measured instance sizes). If this file and the catalogue disagree, the catalogue was measured and this was not. ⚠ An offset means nothing without its class — five aliasing traps were found on 2026-08-03 where one offset meant different things on sibling classes.


**Status: Defect A — CONFIRMED WORKING (2026-07-21).** User-validated in-game.
`build_scripts/build_debuffcache.py`, backup `AoWEPACK.dpl.pre-debuffcache`. Webbed and Entangled now
apply their −2 DEF to regular units immediately, as they always did to heroes. Defect B is

Triggered by the report: *"some debuffs (webbed/frozen) don't consistently apply their stat

## 2. The structural asymmetry: units cache, heroes recompute

This is the precondition that makes the defect in §3 invisible on heroes.

**`TUnit.Changed` @ `0x55782b34`** rebuilds a 4-byte cached modifier block:

```c
TAbstractUnit.Changed(unit);
*(byte*)(unit + 0x44) = TAbilityOwner.GetAbAttackAll(unit);      // ATK
*(byte*)(unit + 0x45) = TAbilityOwner.GetAbDefenseAll(unit);     // DEF
*(byte*)(unit + 0x46) = TAbilityOwner.GetAbResistanceAll(unit);  // RES
*(byte*)(unit + 0x47) = TAbilityOwner.GetAbDamageAll(unit);      // DAM
```

`TUnit.GetDefense` @ `0x55782a40` then only **reads** that byte — it never walks the ability list:

```c
def = DefenseRankProgression[rank] + unitRes[+0x2a] + unit[+0x45];   // clamp [0,30]
```

`TUnit.GetInherentDefense` @ `0x55782a24` is the same minus `[+0x45]`, which proves `[+0x45]` is the
*entire* "effective − inherent" delta for a unit.

**`THero.GetDefense` @ `0x557883e8` has no cache** — it sums abilities live on every call, via
`GetSuperlativeEnabledAbOwner` @ `0x55788144` (max across hero / items / inventory) + `GetAbDefense`
@ `0x5574fc60`, then adds items, `hero[+0x6b]`, and the morale table. `THero.Changed` @ `0x55786bdc`
writes no cache at all (it only notifies `THeroControl`).

`GetAbDefenseAll` @ `0x5574f674` has exactly **one** caller in the module: `TUnit.Changed`
@ `0x55782b4a`. Nothing else refreshes the cache — verified that `TCustomAbilityList.SetAbSet`
@ `0x5574e0bc` (bit flip only), `TAbilityOwner.AddAbilityData` @ `0x5574f278` and
`RemoveAbilityData` @ `0x5574f284` contain no `Changed` call, and there is no `SetAb` override.

`TCombatUnit.GetDefense` @ `0x5572549c` is a bare forward (`MOV EAX,[EAX+0x4c]` → underlying unit's
VMT `+0xc4`), so **the asymmetry is live in tactical combat**, not just on the strategic map.

## 3. Defect A — three apply sites skip `Changed()`

`TAbilityOwner.ExpandAbility` @ `0x5574f5b4` is the wrapper that keeps the cache coherent:

```c
ability = TAbilityControl.GetAbility(control, id);
result  = ability.VMT[0xd0](ability, owner);   // Expand
if (result != 0)
    owner.VMT[0x90]();                         // Changed()  <-- CACHE REFRESH
return result;
```

**Three combat-action sites call `Expand` (ability VMT `+0xd0`) directly and never call `Changed`:**

| Site | VA | Applies | Notes |
|---|---|---|---|
| `TWebCA.Execute` | `0x5576a06c` | Webbed `0x61` | only site that applies 0x61 |
| `TEntangleCA.Execute` | `0x5576a648` | Entangled `0x5e` | stamps `data+0x0f` after Expand |
| `TEntangleSpellCA.Execute` | `0x557f89f4` | Entangled `0x5e` | spell version; same stamp |

`TWebCA.Execute` disassembly — it returns immediately after the call, no `Changed`:

```
5576a0a1: CALL dword ptr [ECX + 0xd0]      ; ability.Expand(unit)
5576a0a7: POP ESI
5576a0a8: POP EBX
5576a0a9: RET
```

Decompiled: `GetAbility(...,0x61)` then `(**(code**)(*ab + 0xd0))(ab, *(int*)(combatUnit + 0x4c))` —
note `combatUnit+0x4c` is the underlying `TUnit`/`THero`, the same field `TCombatUnit.GetDefense` uses.

**Contrast — the correct path.** Every *other* status is applied by
`TAbstractUnit.ExecuteCombatDamageEffects` @ `0x55781ed8` through owner VMT `+0x94` = `ExpandAbility`:

```c
owner.VMT[0x94](owner, 0x5f);   // Frozen    -> Changed ✓
owner.VMT[0x94](owner, 0x5c);   // Stunned   -> Changed ✓
owner.VMT[0x94](owner, 0x60);   // Poisoned  -> Changed ✓
owner.VMT[0x94](owner, 0x5d);   // Cursed    -> Changed ✓
owner.VMT[0x94](owner, 0x62);   // Vertigo   -> Changed ✓
```

**Webbed and Entangled are the only two statuses applied outside that function, and both use the
broken path.**

### Observable signature

- On a **unit**: bit is set, icon shows, duration ticks — but `[+0x45]` is stale, so the −2 DEF has
  **zero effect**. It materialises later, at an arbitrary moment, when some *unrelated* event calls
  `Changed` (SetHitPoints / SetExperience / SetRank / a properly-applied enchantment).
- On a **hero**: always works immediately (live recompute).
- **Removal always works.** Expiry routes through `TAbstractUnit.RemoveAbility` @ `0x5577f6ec`
  (`BeginUpdate` → `TAbilityOwner.RemoveAbility` @ `0x5574f5ec` → `Changed` → `EndUpdate`).
  ⇒ **debuffs wear off reliably but turn on unreliably** — the diagnostic tell for this bug.
- Re-applying to an already-affected unit: both `Expand` variants return 0 in the else branch, so
  even the wrapper would skip `Changed` on a refresh.

## 4. Ruled out (do not re-derive these)

- **Sign / MOVZX bug — DEAD.** The four aggregators `GetAbAttackAll` `0x5574f624` /
  `GetAbDefenseAll` `0x5574f674` / `GetAbResistanceAll` `0x5574f6c4` / `GetAbDamageAll` `0x5574f714`
  are byte-identical apart from the VMT slot, and all accumulate with `ADD BL,AL` — 8-bit two's
  complement, no extension of any kind. Every clamp uses `MOVSX`. `0xFE` is never read as +254.
- **Leadership-style "bare bit, no data record" — DOES NOT APPLY.** Both `Expand` variants set the
  bit and add the record in the same branch; both `Remove` variants clear the bit in *both* branches
  (self-healing). Decisively, `GetAbDefenseAll` iterates the **bitset** (`GetAbEnabled`) and calls a
  constant-returning `GetDefense` — these abilities have no level (`TAbility.GetLevel` @ `0x5574e9b0`
  returns 0, unoverridden), so a bare bit would still grant the full modifier.
  *Inverse hazard (INFERRED, not observed):* a record **without** a bit yields no modifier and makes
  `Expand` return 0 forever, since `GetAbilityData` finds the record and the bit is never re-set.
- **Base-class split is NOT the stat bug.** `GetDefense` is ability VMT slot `0x60` in *both*
  families. `TDurationAbility` and `TUnitEnchantmentAbility` are **siblings** (proved: they assign
  different methods to the same slot `0x10C` — `GetDuration` vs `GetDurationMode`), both created
  directly from `TAbility.Create`. The split governs duration semantics and dispellability, not the
  modifier. (It does mean Webbed is not a dispellable enchantment: `TAbstractUnit.AbilityToEnchantment`
  @ `0x5577f3b4` gates on `IsClass(ability, TUnitEnchantmentAbility)`.)
- **`THero` item-omission precedent does NOT recur.** All four hero getters include the item term
  (`THeroItems.GetAttack/Defense/Damage/Resistance` = `0x55786354` / `0x55786388` / `0x557863bc` /
  `0x557863f0`). Clean negative result.

## 5. Defect B — the modifier values themselves

Census (all `GetDefense` bodies are a single `MOV AL,imm; RET`; a dash = no override, inherits
`TAbility` base `XOR EAX,EAX; RET`):

| Ability | id | Base class | DEF | ATK | RES | DAM | Total dur | Duration mode |
|---|---|---|---|---|---|---|---|---|
| Stunned | `0x5c` | TDurationAbility | **−2** | — | — | — | 1 | `+0x28`=2 combat turns |
| Cursed | `0x5d` | TDurationAbility | **−2** | — | **−2** | — | 3 | `+0x28`=1 days |
| Entangled | `0x5e` | TUnitEnchantmentAbility | **−2** | — | — | — | 2 | GetDurationMode=2 |
| **Frozen** | `0x5f` | TUnitEnchantmentAbility | **+2** ⚠ | — | — | — | 3 | GetDurationMode=2 |
| Poisoned | `0x60` | TDurationAbility | 0 | **−2** | 0 | **−2** | 4 | `+0x28`=1 days |
| **Webbed** | `0x61` | TDurationAbility | **−2** | — | — | — | 3 | `+0x28`=2 combat turns |
| Vertigo | `0x62` | TDurationAbility | **−2** | **−2** | — | — | 3 | `+0x28`=1 days |

Two consequences:

1. **`TFrozenAbility.GetDefense` @ `0x557ba0b4` = `MOV AL,0x02` → Frozen grants +2 DEF, a bonus.**
   Its sibling Entangled @ `0x557b9fec` is `MOV AL,0xFE` = −2.
   ⚠ **This is INTENTIONAL — a deliberate mod change (user-confirmed 2026-07-21): Frozen depicts the
   unit encased in a block of ice, so the bonus is the design.** Frozen's apply path is correct and
   was never part of Defect A. **Do not "fix" this byte.** It is listed here only because the +2 is
   the reason Frozen *looks* like a debuff that fails to land.
2. **Webbed / Entangled / Frozen / Stunned override `GetDefense` only.** ATK/RES/DAM are unimplemented
   for them — a design gap, not a defect.

**Codegen footnote (fragile, currently correct):** `TPoisonedAbility` alone uses
`OR EAX,0xFFFFFFFE` instead of `MOV AL,0xFE`. EAX holds the ability object pointer on entry, so
`AL = (ptr & 0xFF) | 0xFE`; this yields `0xFE` only because Delphi instances are ≥4-byte aligned.
Correct in practice; would silently become −1 for an odd-addressed object.

### Ability field semantics (resolved)
- **`+0x20`** `ushort` — display/selection flag mask (`TAbilityOwner.ListAbilitiesEx` @ `0x5574ff48`).
- **`+0x24`** `byte` — ability **type/category**, cosmetic only; indexes `TAbilityTypeRStr` via
  `TAbstractUnit.ListAbilityInfo` @ `0x5577fa50`. Not duration, cost, or level cap.
- **`+0x28`** `byte` — **duration mode**, duration-family only: 1=days, 2=combat turns, 3=entire
  combat. (`NewTurn` acts when ==1, `NewCombatTurn` when ==2, `CombatDone` expires when `(mode-2)<2`.)
  The enchantment family has no such field; it uses the `GetDurationMode` virtual (base 0 = never).
- `TDurationAbility.GetTotalDuration` = 4; `TUnitEnchantmentAbility.GetTotalDuration` = **−1**
  (permanent / strategic-persistent).

## 6. Unit morale→defense disabled — this mod's own change (previously undocumented)

Found while validating a suspected vanilla bug. **It is not vanilla — it is a 2-byte patch already
present in the live DLL.** Provenance **confirmed by the user 2026-07-21: it is their own change**,
made during AI-assisted modding *before* the `Modding Resources/` note-taking convention existed,
which is why nothing recorded it. **Intentional — do not "fix" it.**

`TUnit.GetDefense` @ `0x55782a40`, bytes at `0x55782a69`:

```
        8d90 e083 8e55   LEA EDX,[EAX+0x558e83e0]   ; &MoraleDefenseModifier[morale]
        58               POP EAX
ORIG:   02 02            ADD AL, byte ptr [EDX]     ; morale value added   <-- correct
NOW:    40 48            INC EAX ; DEC EAX          ; 2-byte no-op         <-- patched out
```

Byte-diff across every archived copy in `<game dir>`:

- `02 02` (original) — 11 files, `AoWEPACK - May 2025.dpl` … `AoWEPACK - Weakness1.dpl`
- `40 48` (patched) — 7 files, `AoWEPACK - Copy (12).dpl` … current `AoWEPACK.dpl`
- introduced between **2026-01-04** and **2026-03-18**

`TUnit.GetResistance` @ `0x55782ae8` keeps the identical `ADD AL,[EDX]` idiom in **all 18** copies,
and `THero.GetDefense` still applies its morale term (`ADD BL, byte ptr [EAX+0x558e83e0]`
@ `0x55788447`). So the change is narrow and deliberate-looking: **units lose morale-based defense;
unit morale-resistance, unit morale-attack, and hero morale-defense all remain.**

**Design intent not captured** — the *what* is confirmed above, but the reasoning for removing
morale-defense from units while keeping unit morale-resistance, unit morale-attack and hero
morale-defense was never written down. Treat the current behaviour as desired; ask before altering.

Same era and category as the undocumented combat caves `0x5580C150` / `0x5580C240` / `0x5580C390`
flagged in `Investigation_INDEX_2026-07-08.md` §Cross-cutting 1 (Life-Steal +2, marksmanship+height,
XP-on-hit), which are very likely from the same pre-note-taking period and equally intentional.
**There is no reason to assume this is the last such change** — anything in `AoWEPACK.dpl` that looks
like a vanilla bug should be byte-diffed against `AoWEPACK - May 2025.dpl` before being "fixed".
That diff, done systematically, would catalogue the whole pre-convention layer; it has not been run.

(Aside: `AoWEPACK.dll`, 2025-07-29, is a third variant with stat clamps of 1..50 instead of 0..30 on
both DEF and RES — a different lineage, not this install's.)

## 7. As-built fix (Defect A) — `build_debuffcache.py`, CONFIRMED WORKING 2026-07-21

Approach chosen: **fix the three call sites**, rather than making units recompute live. Rationale:
three sites is a minimal blast radius, whereas killing the cache would put a full ability-list walk
(`GetAb*All` — a virtual call per enabled ability) inside `TAbstractUnit.UpdateDefensiveStrength`
@ `0x5577f714`, which the AI calls in evaluation loops. Revisit the live-recompute option only if
more skip-sites turn up.

Each site's 6-byte `CALL dword ptr [ECX+0xd0]` (`FF 91 D0 00 00 00`) is replaced with
`E9 <rel32> 90` → a 26-byte cave:

```asm
call dword ptr [ecx + 0xd0]      ; original Expand(ability=EAX, unit=EDX)
mov  eax, dword ptr [ebx + 0x4c] ; EAX = target unit
test eax, eax
jz   .done                       ; nil guard — vanilla would already have faulted, but free
mov  edx, dword ptr [eax]        ; EDX = unit VMT
call dword ptr [edx + 0x90]      ; Changed() -> rebuilds unit+0x44..0x47
.done:
jmp  <call_va + 6>
```

| Site | CALL VA | cave VA | returns to |
|---|---|---|---|
| `TWebCA.Execute` | `0x5576a0a1` | `0x5580f900` | `0x5576a0a7` |
| `TEntangleCA.Execute` | `0x5576a68d` | `0x5580f920` | `0x5576a693` |
| `TEntangleSpellCA.Execute` | `0x557f8a44` | `0x5580f940` | `0x557f8a4a` |

**Why this register contract is safe (all three sites are identical at the call):**
`EAX`=ability, `EDX`=target unit, `ECX`=ability VMT, `EBX`=target **combat** unit, and `[EBX+0x4c]`
is the underlying unit. `EBX` is callee-saved and demonstrably survives the call — **vanilla itself
reloads `MOV EAX,[EBX+0x4c]` immediately after it** at both Entangle sites, which is also why the
`data+0x0f` source-side stamp still works untouched (the cave restores nothing it needs). None of the
three sites consumes the Expand return value in `EAX`: Web does `POP ESI/POP EBX/RET`, both Entangle
sites overwrite `EAX` at once. So the cave is free to clobber `EAX`/`ECX`/`EDX` (all caller-saved).

**`Changed` is called unconditionally**, unlike `ExpandAbility` which gates it on Expand's result.
Deliberate: it is idempotent (recomputes four bytes from the current ability set), and unconditional
also **heals a cache left stale by a pre-patch save** when the debuff is re-applied — the gated
version would skip the refresh forever on an already-webbed unit, since Expand returns 0 on refresh.

Cave is position-independent (register-indirect calls + one rel32 jmp, no absolute memory refs).
Cave space taken from the large zero run starting `0x5580f8c0` (~880 KB, running to `0x558e7a00`).
These three caves sit at the bottom edge of it, just above the crowded `0x5580C000`–`0x5580F8BF`
pocket where older caves were packed. **Allocate new caves from `0x55810000` instead** — space is
plentiful and there is no reason to keep crowding the low pocket.

Deliberately **not** touched: `TUnit.GetDefense` @ `0x55782a40` (carries the undocumented morale
no-op, §6) and `TFrozenAbility.GetDefense` @ `0x557ba0b4` (+2 is intentional, §5).

### Test procedure
Web or entangle a **non-hero unit** — its Defense should drop by 2 **immediately** on the unit card.
Heroes recompute live and mask this bug entirely, so a hero-only test gives a false pass. Also
confirm the penalty still lifts correctly when the duration expires (removal always worked; the fix
must not double-apply). Re-run the script with no args at any time to verify installed state.
