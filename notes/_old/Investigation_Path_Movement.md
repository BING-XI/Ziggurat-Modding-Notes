# Path abilities & movement-cost — investigation (AoWEPACK.dpl)

> **Offsets here are class-keyed and canonical in [`Ghidra_Field_Catalogue.md`](Ghidra_Field_Catalogue.md)** (generated by `re_tools/ghidra_fields.py`, bounds-checked against measured instance sizes). If this file and the catalogue disagree, the catalogue was measured and this was not. ⚠ An offset means nothing without its class — five aliasing traps were found on 2026-08-03 where one offset meant different things on sibling classes.


**Status: INVESTIGATION ONLY (2026-07-08). No binaries modified, no build scripts run.**
All addresses are preferred-base VAs (`AoWEPACK.dpl`, base `0x55700000`, rebased at runtime → any
cave must be position-independent per `[[aow1-dpl-rebasing]]`). Decompiled + disassembled from Ghidra;
raw bytes read from the on-disk DLL where noted.

This covers three requested features:
1. **Sandworm (or any tunneler) faster through desert** — a unit-keyed terrain move-cost cut.
2. **Path abilities: bigger radius + 50% per-hex proc.**
3. **Frostling↔snow / Azrac↔desert racial move-cost modifier.**

> **Framing correction (important):** the "Path of X" abilities are *terrain-changers*, not
> cost-reducers. "Call a unit ID into them to move faster" (Feature 1's wording) conflates two
> separate systems. Faster movement comes from the **move-cost table** (`CreateMovePointTable` /
> `MovePointCost`), which is a *different* code path from the Path callbacks. Features 1 and 3 hook
> the cost path; Feature 2 hooks the Path path. Both paths are triggered from the same per-step
> function, `TAbstractUnit.MovedTo`, so they are documented together here.

## 0. Shared architecture

### 0.1 The per-move-step trigger — `TAbstractUnit.MovedTo` @ `0x55780328`
Called **once per hex a unit enters** during movement. Register-call params:
`MovedTo(EAX=unit, EDX=param2, ECX=param3, [EBP+8]=param4=incoming cost cap)`.
- **param3 (ECX)** = the field the unit **entered** — its terrain(`+0x14`)/road(`+0x15`) are fed to
  `MovePointCost`; the result is deducted from the unit's MP (VMT `+0xd8` get MP, `+0xdc` set MP).
- **param2 (EDX, saved `[EBP-4]`)** = the field the **Path trail is centered on** (the hex just
  departed / previous). All Path terrain effects use `param2`'s coords (`+0x10`=x, `+0x11`=y,
  `+0x12`=level). If param2==0 (first placement) no Path effects fire.

Body, in order:
1. `iVar3 = MovePointCost(unit, param3.terrain, param3.road)` → clamp vs param4 → deduct from MP.
2. If `param3.terrain == 7` (EarthWall) → `map.VMT[0xd0](map,0,x,0xC,0,level,y)` collapse wall to
   Dirt (this is the **direct single-hex** terrain setter, `ChangeTerrainEx`).
3. If param2≠0 and the unit is **not** being transported:
   - if `param2.level == 0` (**surface only**): ability **0x45** (Path of Life) → else ability
     **0x44** (Path of Decay). Mutually exclusive.
   - ability **0x6d** (Path of Frost) — independent, no level gate.
   - ability **0x1a** (Trail of Darkness) → `ExecuteTrailOfDarkness` (un-explores hexes; separate
     mechanism, `InitHNWalk` 6-hex ring, not terrain change).

`GetAbilityEnabled` = unit VMT `+0x148` (called as `unit.VMT[0x148](unit, abilityId)`).

### 0.2 The Path area-apply call — map `VMT[0xd4]`
Each Path ability calls `map.VMT[0xd4]`. Resolving the VMT (map = `*(0x558fa040)`; strategic
`TAoWHSMap` vtable base `0x5590d4b8`):
- `VMT+0xd0` = `TAoWHSMap.ChangeTerrainEx` @ `0x55778dcc` — **direct single-hex** set
  (`map,0,x,newTerrain,0,level,y`). Used for the EarthWall collapse.
- `VMT+0xd4` = `TAoWHSMap.ChangeTerrain` @ `0x55778d84` — **callback-based area** version. Forwards
  to imported `HSEngine.THSMap.ChangeTerrain` (`0x557025cc` = `JMP [0x558fbc38]`, IAT thunk; the
  radius-loop implementation lives in the **HSEngine/HSEPack DLL, outside the Ghidra project**).

Call shape (Delphi reg-call, reconstructed from the three MovedTo sites + the storm sites):
```
map.VMT[0xd4]( Self=map, EDX=0, ECX=x,
               changedCb, changedData,     // post-change notify (0,0 if unused)
               changeCb,  changeData,      // per-hex terrain DECISION callback + its data
               radius,                     // <-- disk radius
               level, y )
```
- **`changeCb`** is invoked per hex in the disk as `changeCb(EAX=data, EDX=field, ECX=terrainBytePtr)`
  and mutates the terrain byte in place through ECX (same in-place pattern as the storms'
  `ChangeStormTerrain`, per `Terrain_Changing_Spells_Map.md`). `data` = the acting unit.
- **`radius` is hard-coded to 1** at all three Path sites. The **storms call the identical
  `VMT[0xd4]`** (`TBlastStorm.UpdateStorm` @ `0x557ccac0`) with **radius 1/2/3/4** at growing frames
  → proven that this arg drives a growing concentric disk (see the ring behaviour already documented
  for Ice Storm). Exact hex-count per radius is inside the imported HSEngine function (confirm
  in-game), but larger value = larger area is guaranteed by the storm precedent.

### 0.3 The Path callbacks (all leaf functions in AoWEPACK.dpl)
| Ability | id | changeCb (validator) | changedCb (notify) | Effect |
|---|---|---|---|---|
| Path of Life | 0x45 | `PathOfLifeTerrainChange` @ `0x557801a4` | — | terrain≠Ice(6)/Water(0) & field.level==0 → terrain=**1 Grass** |
| Path of Decay | 0x44 | `PathOfDecayTerrainChange` @ `0x557801c4` | — | same guard → terrain=**5 Wasteland** |
| Path of Frost | 0x6d | `PathOfFrostTerrainChange` @ `0x557801e4` (leaf, Ghidra didn't auto-define) | `PathOfFrostTerrainChanged` @ `0x5578024c` | water→ice; on Ice/CaveIce hex spawns/refreshes `TFrozenWaterHS` (countdown=2 @ `+0xc`, caster tag @ `+0xd`) |

`PathOfLifeTerrainChange(data, field, tPtr)`: `if (*tPtr!=6 && *tPtr!=0 && field[0x12]==0) *tPtr=1;`
`PathOfDecayTerrainChange`: identical but `*tPtr=5`.

### 0.4 The move-cost path
- **`TAbstractUnit.MovePointCost` @ `0x55780848`**: builds the unit's table into a stack buffer via
  `CreateMovePointTable`, returns `buf[1 + terrain*0x10 + road]`. The **`+1`** is the no-road column
  shift (road is a **signed** byte, −1 = no road); terrain & road & cost bytes are all signed (MOVSX).
- **`TAbstractUnit.CreateMovePointTable` @ `0x5577fdc4`** — *the authoritative per-unit cost-table
  builder* (used by MP deduction **and** by the v4 move-predictor cave, so any change here shows up in
  both executed movement and the on-screen arrows/X-marker — they stay consistent for free):
  1. `movetypes = unit.VMT[0xe8]()` (`GetMoveTypes` → `GetAbMoveTypesAll`).
  2. if `AoWHSMap+0x120 != 0`: `movetypes &= ~0x80` (strip Tunneling; mask `DAT_5577ffcc = 0x80`).
  3. `idx = MoveTypesToInt(movetypes)`; copy `0x100` bytes from `MovePointTables[idx*0x100]`
     (precomputed merged table, base `0x558EA040`) into the output buffer.
  4. If `unit.owner (byte [unit+9]) > 0`, apply modifiers (all iterate rows/cols of the copied table):
     - player flag `[[player+0x54]+0x44] & 2`: road-column tweak (cost 3→2).
     - abilities **0x17/0x01/0xa5** + player flags `+0x44&4`,`+0x45&4` → ±1/+2 over 13 columns
       (Enchanted/Cursed roads, per MovePredictor doc).
     - ability **0x98** (Haste-like): `cost-1`, clamped **≥2**, over 13×13.
     - ability **0x84**: `+2` to positive costs.
  - **It holds the unit (`param_1`) and already calls `GetAbilityEnabled` and reads owner/player** —
    so it trivially has access to add a race check or a resource-ID check. This is the injection point
    for Features 1 and 3.
- **Buffer layout** (256 bytes = 16 terrain rows × 16 overlay cols, `+1` shift): cell `(terrain,road)`
  = `buf[1 + terrain*0x10 + road]`. **Desert row = terrain 2** → `buf[1 + 0x20 + col]`;
  **Snow row = terrain 3** → `buf[1 + 0x30 + col]` (col 0 = no-road/None).

### 0.5 Key struct offsets & identifiers
- Unit → resource ptr: **`[unit+0x40]`** (`TUnitResource`).
- **Race** = byte **`[[unit+0x40]+0x20]`** (`TUnit.GetRace` @ `0x55782c90`; `TAbstractUnit.GetRace`
  @ `0x5577eddc` returns −1). It stores the **race index** (a byte).
- **Unit-type ID** = resource list index: `list.VMT[0x84](list, resource)` where `list = [resource+4]`
  (`TUnitResource.UnitResourceIndex` @ `0x55784d90`). Cheap alternative discriminator: **GFX resource
  index dword at `[[unit+0x40]+0x18]`** (`TUnit.GetUnitGFXResourceIndex` @ `0x55782c54`) — a direct
  read, effectively unique per unit type.
- **Move types are ABILITY-derived** — `GetAbMoveTypesAll` @ `0x5574f764` sets bits (values read from
  the DLL): ability 0→**0x01 Walk**, 1/0xa5/0x3b→**0x02 Fly**, 2/0x17/0xa4/0xa6→**0x04 Swim**,
  3→**0x08 Forestry**, 4→**0x10 Cave**, 5→**0x20 Mountaineer**, 7/0xa3→**0x40 Fire**,
  **0x2a→0x80 Tunneling**. So **"tunneling" = the unit has ability `0x2a`**, and it selects the
  Tunneling base table (idx 7 @ `0x558E8BFC`).
- Terrain bytes: Water 0, Grass 1, **Desert 2**, **Snow 3**, Steppe 4, Wasteland 5, Ice 6, EarthWall
  7, RockWall 8, Lava 9 (per `Terrain_Changing_Spells_Map.md`).

## FEATURE 1 — Sandworm faster through desert
**Verdict: FEASIBLE.** Confidence **85%** (tunneling-keyed variant, no external data needed) /
**75%** (exact-Sandworm-ID variant, needs one out-of-DLL lookup).

**Current mechanism.** A unit's desert cost = `CreateMovePointTable`'s copied Tunneling/merged-table
desert row (`buf[1 + 2*0x10 + col]`). Nothing keys cost to a specific unit; only the ability
modifiers in 0.4 touch the table. Tunneling itself is move-type bit `0x80` (ability `0x2a`), stripped
when `AoWHSMap+0x120 != 0` (i.e. tunneling disabled on that map).

**Proposed patch (one cave, one binary — AoWEPACK.dpl).** Hook the **tail of
`CreateMovePointTable`** (just before its `RET`, in the `0x5577ff..` range) with a
position-independent cave that runs after the table is built:
```
; EAX/ESI = unit (still live), param_2 = table buffer
if (terrain-of-interest cost should drop for this unit)
    buf[1 + 2*0x10 + col] -= N   for col in 0..12   (clamp >= floor, e.g. 2, like the Haste modifier)
```
Two ways to answer "is this a Sandworm":
- **(A) Unit-ID keyed (literal ask):** compare the unit-type index. Cheapest: read
  `[[unit+0x40]+0x18]` (GFX index) and compare to the Sandworm's value; authoritative:
  `UnitResourceIndex` (`list.VMT[0x84]`). **The numeric Sandworm ID is NOT in the DLL** (no
  "Sandworm" string; unit definitions live in the resource packs). It must be extracted once from
  game data — read `[[unit+0x40]+0x18]`/index of a placed Sandworm, or the AoWDevEd unit list.
- **(B) Tunneling keyed (no ID needed):** gate on `(movetypes & 0x80)` (has ability 0x2a). In vanilla
  the Sandworm is the archetypal tunneler, so "all tunnelers move faster on desert" is nearly
  equivalent and needs no external lookup. Recommended if the user is OK with the slight generality.

**Why it's clean.** `CreateMovePointTable` is the single authoritative builder, so the cut flows to
MP deduction *and* the move-predictor arrows automatically (no second hook, no desync between
prediction and execution — the exact trap the v4 predictor fix had to solve).

**Risks / unknowns.**
- Numeric Sandworm ID is out-of-DLL (must be read from game data; easy but not derivable here).
- `CreateMovePointTable` runs very frequently (per hex, per unit, and inside prediction loops) — keep
  the cave to direct field reads (prefer `[[unit+0x40]+0x18]` over the `VMT[0x84]` list search).
- Signed cost bytes: clamp the reduced cost to a floor (≥1 or ≥2) — negative/zero costs read via MOVSX
  will misbehave (mirror the Haste `min 2` clamp).
- The copied row is the **merged** table for the unit's move-types; a tunneling Sandworm's desert
  cell already comes from the Tunneling base table — verify in-game which desert cell (no-road col 0 =
  `buf[1+0x20]`) actually governs open-desert movement before tuning `N`.
- Position-independence: the cave may need `MovePointTables` only indirectly (it edits the already-copied
  buffer, which is on the stack — no absolute ref needed).

## FEATURE 2 — bigger Path radius + per-hex proc
**Verdict: FEASIBLE.** Confidence **90%** (radius) / **80%** (proc, mainly MP-determinism care).

> **IMPLEMENTED as "radius +1, 25% on the OUTER ring only" — CONFIRMED WORKING IN-GAME (2026-07-08).**
> Technique write-up: `HOWTO_PerHex_Ring_Detection.md`.
> `build_scripts/build_path_outerring.py`, backup `AoWEPACK.dpl.pre-pathring`. Not a uniform proc —
> inner disk (dist ≤1) stays 100%, the new outer ring (dist 2) rolls 25%. Needed true **per-hex ring
> detection**: (1) radius 3× `6A 01`→`6A 02`; (2) `cave_stash` @`0x5580DD30` hooks `MovedTo`
> @`0x5578041E` to stash the center (`[EBP-4]` coords) into a 2-byte scratch @`0x5580DD20`; (3) the 3
> terrain callbacks re-pointed (their pushes have `.reloc`) to proc-gates @`0x5580DD60/DDC0/DE20` that
> compute `HN = dHXtoHN(cx,cy, field.x,field.y)` (@`0x557026A4`; EAX=x1,EDX=y1,ECX=x2,push y2 → HN;
> **HN<7 = inner, 7..18 = outer**), and on the outer ring roll `AoWHSMap.Random(map,4)==0` (synced RNG,
> MP-safe). Frost's spawn-notify (`0x5578024C`) self-gates on the ice check → left alone. **The
> ring-detect (`dHXtoHN`+`HNtoRad`/threshold) is a reusable primitive for any ring/fading-edge/distance
> mechanic.** Confirm in-game (watch for a Random-guard popup — shouldn't occur, moves are synced).
>
> **BUG FIXED (2026-07-08): the scratch must live in a WRITABLE section.** First cut put the 2-byte
> center-scratch in the cave region (CODE @`0x5580DD20`), but AoWEPACK's **CODE section is read-only at
> runtime** (flags `0x60000020`) → the stash write faulted ("Exception occurred during
> TArmyDefaultMoveTE", move happens but Path change aborts). Moved the scratch to **BSS slack
> `0x558FA800`** (BSS flags `0xC0000000`=WRITE; committed via page-rounding of vsize, past the declared
> `0x10231` so unused; addressed from the caves via call/pop-delta since BSS & CODE share the rebase
> delta). **General rule: caves may EXECUTE from CODE but must never WRITE to it — put any static mutable
> scratch in DATA/BSS.**

**Current mechanism.** Each Path ability calls `map.VMT[0xd4]` (§0.2) with **radius = 1** and a per-hex
`changeCb`. The disk radius arg is the storm-proven knob (storms use 1..4).

### (a) Expand radius — trivial, **no cave**
Three 1-byte edits in `MovedTo` (each is `6A 01` = `push 1`, verified on disk):
| Site VA | ability | bytes |
|---|---|---|
| `0x5578044e` | Path of Life | `6A 01` → `6A 02`/`6A 03` |
| `0x55780495` | Path of Decay | `6A 01` → `6A 02`/`6A 03` |
| `0x557804da` | Path of Frost | `6A 01` → `6A 02`/`6A 03` |
Surrounding bytes confirm the callback pushes right after each (`68 a4017855`=Life, `68 c4017855`=Decay,
`68 e4017855`=Frost-change, `68 4c027855`=Frost-changed), so the `6A 01` is unambiguously the radius.
Path of Life/Decay keep their `field.level==0` guard *inside* the callback, so a bigger radius will not
bleed across the surface/underground boundary; Frost has no such guard.

### (b) 50% per-hex proc — small cave
The `changeCb` fires once per hex. Gate it with a random skip. Options:
- **Redirect the pushed callback pointer** (`0x557801a4`/`1c4`/`1e4`) to a cave that rolls RNG then
  either returns (no change) or tail-jumps the real callback, preserving the
  `(EAX=data, EDX=field, ECX=tPtr)` ABI. One cave can serve all three (pass the real target in).
- Or add the roll as a prologue inside each tiny leaf.

**RNG choice (the important caveat).** These callbacks run during **move execution**, a *synchronized*
game action — **not** a render/anim context. So the **synced** `AoWHSMap.Random` @ `0x5577827c` is the
**correct** choice for multiplayer determinism (all clients must terraform the same hexes) and its
sync-guard should pass here. Raw `System.RandInt` @ `0x55701080` (as used by the Ice-Storm skip gate)
is simpler but **not MP-synced** → clients could diverge on which hexes change. Recommend
`AoWHSMap.Random` for MP-safety; fall back to raw `RandInt` only if a guard trip is observed.

**Risks / unknowns.**
- Frost's `changedCb` (spawn `TFrozenWaterHS`) must be gated **together** with its `changeCb`, else you
  get ice hexes with no walkable-ice structure. Gate at whole-callback granularity, or skip both.
- Exact hex count per radius value is inside the imported HSEngine function (not in Ghidra) — confirm
  the r2/r3 footprint in-game; the storm ring behaviour guarantees it grows.
- Radius push is `push imm8`; values 1..127 fit the single byte. Keep it small (2–3); huge radii =
  huge terraform per step and many `changeCb` calls.

## FEATURE 3 — Frostling↔snow / Azrac↔desert racial move-cost
**Verdict: FEASIBLE.** Confidence **80%** (mechanism clean; only blocker = 2 numeric race values).

**Current mechanism.** Move cost is **move-type** based, never race based — a genuinely new modifier.
`CreateMovePointTable` has the unit and can read race (`[[unit+0x40]+0x20]`, a byte index).

**Proposed patch (same hook as Feature 1 — tail of `CreateMovePointTable`, AoWEPACK.dpl).** After the
table is built:
```
race = *(*(unit+0x40) + 0x20)
if race == FROSTLING:  reduce Snow row   buf[1 + 3*0x10 + col] -= N   (col 0..12, clamp)
if race == AZRAC:      reduce Desert row buf[1 + 2*0x10 + col] -= N
```
Because the hook is the shared builder, the bonus applies to both real movement and the predictor.

**Race values.** The **byte value for Frostling / Azrac is NOT a DLL constant** — races are enumerated
as resourcestring *names* (`FrostlingRStr`, `AzracRStr`, … 12 total: Azrac, DarkElf, Dwarf, Elf,
Frostling, Goblin, Halfling, Highman, Human, Lizard, Orc, Undead) but the numeric **race index is
assigned at resource-load time**, so it must be read from game data once. Method: read the race byte
`[[unit+0x40]+0x20]` of a known Frostling and a known Azrac unit in a debugger/CE session, or inspect
the race resource pack / editor. `TRaceResource.GetRaceIndex` @ `0x55759cd8` returns `[raceRes+0x14]`
if you walk the race list.

**Risks / unknowns.**
- The 2 race indices are out-of-DLL (must be extracted; easy).
- Same frequency / clamp / signed-byte cautions as Feature 1.
- Heroes: `THero.GetRace` @ `0x55786f9c` exists; verify a hero of that race reads the same
  `[[unit+0x40]+0x20]` path (hero resource layout may differ — `THero.GetRace` should be checked if the
  bonus is meant to include heroes).

## Failed / corrected leads (so they aren't retried)
- `map.VMT[0xd4]` was briefly mis-identified as `UpdateStaticScene`/a thin `ChangeTerrain` wrapper —
  there are several **sibling map-class vtables** (0x5570e8xx, 0x5590d5xx) that share method addresses.
  The **strategic map uses base `0x5590d4b8`**, where `+0xd0`=ChangeTerrainEx(direct) and
  `+0xd4`=ChangeTerrain(area/callback). Confirmed by the EarthWall(`+0xd0`) vs Path(`+0xd4`) call sites
  and by the storm using the same `+0xd4`.
- The area-loop body itself is **imported (HSEngine/HSEPack DLL), not in the Ghidra project** — do not
  look for it in AoWEPACK. Feature 2 does not need it: patch the call sites (radius) and the callbacks
  (proc gate), which are all in AoWEPACK.
- "Path abilities" ≠ movement speed. Feature 1's "make Sandworm faster via Path abilities" mixes two
  systems; the cost lever is `CreateMovePointTable`, unrelated to the Path terrain callbacks.
