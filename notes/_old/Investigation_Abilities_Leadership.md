# Investigation — Abilities & Leadership cluster (2026-07-08)

> **Offsets here are class-keyed and canonical in [`Ghidra_Field_Catalogue.md`](Ghidra_Field_Catalogue.md)** (generated by `re_tools/ghidra_fields.py`, bounds-checked against measured instance sizes). If this file and the catalogue disagree, the catalogue was measured and this was not. ⚠ An offset means nothing without its class — five aliasing traps were found on 2026-08-03 where one offset meant different things on sibling classes.


**Investigation only. No patches applied. No binary modified.**

Covers three requested features:

1. Semi-randomise the hero level-up ability choices each level.
2. Restore multi-level Leadership ability (cut content).
3. Bug: a unit that HAS Leadership (e.g. gold-medal) has its Leadership "disabled" when stacked
   under a hero that also has Leadership.

All three live primarily in **AoWEPACK.dpl** (Ghidra, image base `0x55700000`, rebased at runtime →
caves must be position-independent). The human level-up **dialog UI** for Feature 1 lives in
**AoW.exe / AoWCompat.exe** (fixed base `0x400000`).

Preferred-base VAs throughout. Ability IDs: **Leadership = `0x2e` (46)**, Spellcasting = `0x34`,
and a third expandable hero ability **id `0x7a` (122)** (identity not resolved here — the AI treats
it identically to Leadership: CanExpand/ExpandCost/ExpandAbility).

## 0. The ability model (shared foundation for all three features)

Abilities are **flyweights**: one shared `TAbility` object per ability id, held by
`TAbilityControl` (the global ability registry). Per-unit state is split in two:

- **Enabled bitset(s)** on the owner (unit/hero) — set/read via owner VMT slots
  `+0x50` SetAbilityEnabled, `+0x4c` GetAb (inherent set), `+0x14c` GetRawEnabled (enabled set).
- **Ability-data linked list** on the owner (head at `owner+0x10`, next at `data+0x8`), one
  `TxxxAbilityData` record per ability id, holding per-instance fields (levels, etc.).
  `TAbilityOwner.GetAbilityData(owner,id)` @ `0x5574f1c4` walks the list matching id via
  `data->vtable[0x4c]` (GetAbilityID). `AddAbilityData` @ `0x5574f278` prepends.

**Leadership is a multi-level ability.** Class chain `TLeadershipAbility : TMultiLevelAbility :
TAbility`. Key ability-object fields (the flyweight, offsets from the ability object):
- `+0x0c` = ability id (`0x2e` for leadership)
- `+0x20` = selection-type mask (used by `ListAbilities` filter)
- `+0x28` = **max level / expand cap** (int) — **this is the single-level cap, see Feature 2**
- `+0x2c` = `TIntegerList` of per-level expand costs (skill points), index = target level

> **The cap is now machine-readable for every ability**: `re_tools/ability_names.levels()` returns
> `{id: max level}` by scanning the live DLL — `[+0x28]` for `TMultiLevelAbility` descendants, plus
> the `cmp eax, imm` in the *own* `CanExpand` of the levelled classes that are NOT `TMultiLevelAbility`
> (Turn Undead, Dispel Magic — they descend from `TTouchAbility`). Reading the installed DLL is the
> point: it reports Leadership's post-patch **4**, not vanilla's 1. Full method, the two families and
> the scan's traps: `PFS_Format_CRC.md` § "Which abilities have a level, and how high".

`TLeadershipAbilityData` record fields (per-owner, confirmed via `ReadWrite` @ `0x55766130`):
- `+0x0c` = **own / inherent level** (byte) — the unit's *own* leadership level
- `+0x0e` = ability id (short)
- `+0x10` = **external-source level** (byte) — level borrowed from a stronger leader's aura
- `+0x14` = external-source name (Delphi string)

**Effective level rules** (`TLeadershipAbility.GetLevel` @ `0x557661c4`):
```
GetLevel(owner): data = GetAbilityData(owner,0x2e); if !data return 0;
                 return max(data[0x0c], data[0x10])          // max(own, external)
```
`GetInherentLevel` (`TMultiLevelAbility` @ `0x55765200`) returns only `data[0x0c]` (own).
`GetInherent` (`TLeadershipAbility` @ `0x55766384`) returns `data && data[0x0c]!=0` — i.e. the game
explicitly distinguishes **inherent leadership (own-level>0)** from **aura-borrowed leadership
(own-level==0)**. This distinction is the crux of Feature 3.

**Combat effect.** The leadership flyweight's `GetAttack` @ `0x557661fc` / `GetDefense` @
`0x55766210` return per-level bytes from packed tables:
- `GetAttack`: `AL = byte[0x558e83e7 + level]`
- `GetDefense`: `AL = byte[0x558e83eb + level]` (base = atk base + 4)

Raw bytes read from the live DLL (file offset `0x1e71e7`):
`00 02 02 02 | 02 01 01 01 | 01 03 …`. Interpreted as 4-byte tables (levels 0..3):
- **Attack table** `[0,+2,+2,+2]` → +2 attack at levels 1/2/3 (flat)
- **Defense table** `[_,+1,+1,+1]` → +1 defense at levels 1/2/3 (flat)

So the data **already contains three levels** of leadership bonus — strong evidence multi-level
leadership is cut content (Feature 2). The tables are packed only 4 bytes apart, so **3 levels is the
clean ceiling**; going to 4+ collides with adjacent data and would require relocating the tables.

## FEATURE 1 — Semi-randomise hero level-up ability choices

### Verdict: **Feasible — 82%** (DLL side fully mapped; exe dialog and injection point now pinned — see §1.4)

### 1.1 How level-up works now

Hero XP → level is driven by `THero.ValidateHeroUpgrade` @ `0x55787d54` (this is the function the
multi-turn spellcasting work already flagged as "hero-only, crashes units"). On the day a hero gains
a level it:
1. bumps level / experience (uses `HeroExperienceTable` @ data ref `AoWE_HeroExperienceTable_949BB8D8`);
2. creates a **`THeroUpgradeEventLog`** (VMT ptr `0x55711b48`) and distributes it to the owning
   player (`DistributeLocationEventLog`);
3. **if the player is an AI** (`player+0xa7 != 0`) it immediately calls
   `THero.ExecuteUpgradeHeroAI` @ `0x55787a24` to auto-pick the upgrade;
   **if the player is human** (`0xa7==0`) the event log is what pops the **upgrade dialog** on that
   player's client (rendered by AoW.exe).

The **candidate pool** is a fixed enumeration of up to **8 options**, revealed in full by
`ExecuteUpgradeHeroAI`:

| # | Option | Skill-pt cost gate | Cap gate |
|---|--------|--------------------|----------|
| 0 | Attack     | `points>3`  | `hero.atk + res[+0x24] < 10` |
| 1 | Defense    | `points>15` | `hero.def + res[+0x25] < 10` |
| 2 | Resistance | `points>7`  | `hero.res + res[+0x29] < 10` |
| 3 | Damage     | `points>7`  | `hero.dmg + res[+0x26] < 10` |
| 4 | Hits (HP)  | `points>2`  | `hero.hits + res[+0x27] < 30` |
| 5 | **Leadership 0x2e** | `ability.ExpandCost ≤ points` | `ability.CanExpand(hero)` |
| 6 | **ability 0x7a**    | `ability.ExpandCost ≤ points` | `ability.CanExpand(hero)` |
| 7 | **Spellcasting 0x34** | (always added if `CanExpand`) | `ability.CanExpand(hero)` |

Each eligible option is pushed to a `TDoubleItemList` with a weight (`AddAB(list,optId,weight)`);
weights: stats 10, defense 25, spellcasting 100/9999. The AI then does a **weighted random pick**:
```
seed = TAoWHSMap.Random(map,0xffffff); RandSeed = seed;
choice = TDoubleItemList.RandomChanceItemB(list,0);      // @0x5570300c
switch(choice) { case 0: SetUnitAttack(atk+1); … case 5/6/7: hero.ExpandAbility(id); }
```
Ability options resolve via `TAbilityControl.GetAbility(AoWHSSet+0x80, id)` then the ability VMT:
**`+0xc4` CanExpand, `+0xc8` ExpandCost, `+0xd0` Expand**; the hero applies with `hero.vtable[0x94]`
= `TAbilityOwner.ExpandAbility` @ `0x5574f5b4`.

The human dialog offers the **same eligible set** (stat +/- allocation plus the learnable/expandable
abilities). It packages the player's choices into a **`THeroUpgradeTE`** token event
(`Execute` @ `0x55785450`) whose byte fields carry the deltas —
`+0x15 atk, +0x16 def, +0x17 res, +0x18 dmg, +0x19 mov, +0x1a hits, +0x1c abilityOwner/set` — and
that TE is network-distributed so every peer applies the identical result. **The offered list is
therefore a purely local, presentational thing; only the chosen result is synchronised.**

### 1.2 RNG considerations (important)

`TAoWHSMap.Random` @ `0x5577827c` is the **MP-lockstep** RNG:
```
if (map[0x3c] & 8)==0:               // normal (synchronised) mode
   if !GetSynchronised(map): ShowMessage("Invalid AoWHSMap.Random use"); return 0
   RandSeed = map[0x230]; r = RandInt(range); map[0x230] = RandSeed   // advances SHARED seed
else: r = RandInt(range)             // "unsynchronised" bit set → plain global RNG
```
It advances a **shared per-map seed** and *asserts* when called outside a synchronised
turn-execution context. **Do NOT use it to randomise the offered list** — the dialog is a
local, per-client UI event; calling the shared RNG there would either trip the "Invalid use" guard
or desync MP (one client advances the shared seed, others don't).

→ For the offered-subset randomisation use the **plain local RNG**: `System.RandInt`
(`System__RandInt_51F89FF7`) seeded from the global `RandSeed`, which AoW.exe already links. This is
safe because the *outcome* (the `THeroUpgradeTE`) is still synchronised the normal way. Fairness note:
different clients could see different offered subsets, but that is exactly the intent ("semi-random
choices"), and it cannot desync because the applied TE is authoritative.

### 1.3 Proposed patch approach

Two viable layers:

**(A) Human dialog (AoW.exe) — preferred, matches the feature request.** Hook the option-population
in the upgrade dialog so that, after computing which options are *eligible*, it keeps only a random
subset (always ≥1). This affects what the human is *offered*; the AI path is untouched. Injection
point = the exe dialog's per-option enable loop (see §1.4). Use `System.RandInt`. Because AoW.exe
caves may use absolute addresses (fixed base), this is a normal exe cave (reuse the pattern from
`build_spellcast_book_exe.py` / `build_spellcast_card_v2.py`, incl. new `.sc` PE section if needed).
Patch **both** AoW.exe and AoWCompat.exe.

**(B) AI too (AoWEPACK.dpl).** If randomising the AI's considered set is also wanted, gate the
`AddAB` pushes in `ExecuteUpgradeHeroAI` @ `0x55787a24` behind a per-option coin-flip — but that path
already random-*picks*, so it is less necessary and must use `TAoWHSMap.Random` (it runs inside the
synchronised turn executor, so the shared RNG is correct there).

### 1.4 Exe injection point (AoW.exe / AoWCompat.exe, base 0x400000) — confirmed via re_tools

The dialog is **`THeroUpgradeDlg`** (VMT `0x4458C8`, instance size `0x1e0`, DFM form
`AoWHeroUpgradeDlg`, **singleton** at global `[0x45a0f0]`). It is a **point-buy allocator**, not a
"pick 1 of N": on open it copies the hero into an editable working copy and lets the player spend
skill points across **6 stat spinners** + an **ability add/remove** pair, then diffs the copy against
the original to build the `THeroUpgradeTE`. Confirmed by strings "Upgrade Hero" (`0xEF690`),
"Assign Skill Points" (`0xF301B`), "Skill Points left to spend" (`0xF0B84`).

Trigger wiring: `TMapEvents.TheMapExecuteEventLog` @ `0x44F1D3` does `IsClass(event,
THeroUpgradeEventLog classref [0x45dfcc])` → loads the singleton `[0x45a0f0]` → calls
`THeroUpgradeDlg.Setup` @ **`0x446268`**.

Key exe functions:
| VA | Role |
|---|---|
| `0x446268` | **Setup/show** — `FindUnit`→orig hero at dlg`+0x1d8`; `TEObject.Copy`→**edited copy at dlg`+0x1dc`**; then Refresh + PopulateLists. **Single once-per-open entry.** |
| `0x446954` | **PopulateLists** — rebuilds the ability list boxes; **holds the only option loop**. Re-run on every Add/Remove. |
| `0x4469B7…0x446A4D` | the **ability-option loop**: `GetAbility` → `[+0xC4] CanExpand` (`je` skip) → `test byte[ability+0x21],1` selectable flag (`je` skip) → **kept fall-through `0x4469F2`** (add name to AvailableAbilities `dlg+0x80`, cost via `[+0xC8] ExpandCost` to `dlg+0x98`); loop-next label `0x446A49`. |
| `0x447064` | `CanAffordAbility(idx)` = `CanExpand` && `ExpandCost ≤ GetSkillPoints(edited)`. |
| `0x446D6C…0x446F78` | 6 stat spin handlers (AttUp `0x446D6C`, DefUp `0x446DCC`, DamUp `0x446E2C`, ResUp `0x446E8C`, HitUp `0x446EEC`, MovUp `0x446F4C`, + Dn). Each edits a hero byte on the copy (att `+0x6a`, def `+0x6b`, dam `+0x6c`, hits `+0x6d`, mov `+0x6e`, res `+0x6f`) then Refresh. **No cap/skill check in exe — the DLL setters clamp**, so an unaffordable up-click just no-ops. Up-button field offsets: AttUp `dlg+0x164`, DamUp `+0x16C`, DefUp `+0x174`, ResUp `+0x17C`, HitUp `+0x184`, MovUp `+0x18C`. |
| `0x4472AC` | **DoneClick** — `THeroUpgradeTE.Create`/`Setup`, diffs edited(`+0x1dc`) vs orig(`+0x1d8`) into TE fields (`+0x15 att,+0x16 def,+0x17 res,+0x18 dam,+0x19 mov,+0x1a hits,+0x1c abilities`), submits via TokenManager (network dispatch). Matches the DLL `THeroUpgradeTE` map exactly. |

**Local RNG available:** `System.RandInt` is imported from VCL30.dpl (IAT `0x45D374`, thunk
**`0x401030`**); calling convention `mov eax,N; call 0x401030` → returns `[0..N-1]` in EAX. The exe
already uses it (e.g. `0x4581EA`). This is the process-local Delphi RNG — safe for local UI subsetting,
**no MP desync** (independent of the DLL's sync-guarded `AoWHSMap.Random`).

**Cleanest injection (recommended):**
- **Roll once in `Setup` @ `0x446268`** — insert a cave between `mov [ebx+0x1dc],eax` (`0x4462CC`)
  and `call Refresh` (`0x4462D4`) that (a) rolls a per-open **"offered mask"** with `RandInt` and
  stores it in a **new global** (the instance is full at `0x1e0`, but the dialog is a singleton so a
  global is fine — do NOT use an instance field), and (b) optionally disables the un-offered stat
  up-buttons (`[dlg+0x164/16C/174/17C/184/18C].SetEnabled(false)`).
- **Consult the mask in the ability loop** — one 5-byte hook at **`0x4469F2`** (the "kept"
  fall-through): call the cave; on "skip this ability" `jmp 0x446A49` (loop-next), else continue.
  This single hook covers all learnable abilities.
- **Roll once, not per-iteration:** PopulateLists is re-invoked on every Add/Remove, so a `RandInt`
  *inside* the loop would re-roll and flicker the list. Rolling in `Setup` and storing the mask fixes
  the offered set for the whole dialog session.
- If only *ability* subsetting is wanted, the `0x4469F2` hook + a mask rolled in `Setup` suffices;
  stat subsetting adds the ≤6 button-disable calls.

**Cave space:** the CODE section has only ~20 bytes of alignment slack → **a new PE section is
required** (reuse the project's exe-cave pattern from `build_spellcast_card_v2.py`). An existing `.sc`
section at `0x60C000` belongs to the spellcasting-book feature (7 callers into `0x60C000`/`0x60C0A8`);
it has ~214 free bytes and is reusable, but a fresh section keeps layered reverts clean per the
project convention. **Patch both AoW.exe and AoWCompat.exe** (same layout).

### 1.5 Risks / unknowns

- Must never empty the offered list (leave ≥1 eligible option, or the hero can't spend points and the
  event may loop). Keep a floor.
- Skill-point accounting: the stat/ability *apply* is unchanged; we only hide options. No accounting
  risk as long as we don't fake-eligibility (only ever *remove* from the eligible set).
- The AI weighting/ordering is not the human dialog — do not assume the exe mirrors the DLL weights;
  it mirrors the *eligibility gates*. Confirm in §1.4.

## FEATURE 2 — Restore multi-level Leadership (cut content)

### Verdict: **Feasible — 88%** (up to 3 levels; the only blockers are a 1-int cap and a missing cost table; combat data already present)

### 2.1 What limits it to one level

`TLeadershipAbility.Create` @ `0x5576616c` (disassembly):
```
55766182  call TMultiLevelAbility.Create        ; base sets [ESI+0x28]=4, [ESI+0x2c]=new TIntegerList
55766187  MOV  dword [ESI+0x28], 0x00000001      ; <-- OVERRIDES cap back to 1  (C7 46 28 01 00 00 00)
5576618e  MOV  dword [ESI+0x0c], 0x0000002e      ; ability id = Leadership
55766195  MOV  ECX,0x14 / MOV EDX,1 / MOV EAX,[ESI+0x2c] / call TIntegerList.Put   ; cost[1]=20
```
Two facts:
1. The **base** `TMultiLevelAbility.Create` @ `0x55765168` sets the cap `[+0x28] = 4`. Leadership's
   own ctor **stomps it down to 1**. That one immediate is the entire single-level cap.
2. The cost list gets **only index 1 populated** (`Put(list,1,20)`), i.e. only the 0→1 upgrade has a
   defined skill cost.

The cap is honoured everywhere via `+0x28`:
- `TLeadershipAbility.CanExpand` @ `0x557663a8`: `SETL AL` on `data[0x0c] (own level) < [ability+0x28]`
  (returns 1/can-expand when no data). Raise `+0x28` → CanExpand allows more levels automatically.
- `TMultiLevelAbility.Expand` @ `0x55765378`: creates data with `+0x0c=1` on first expand, else
  `if data[0x0c] != cap: data[0x0c]++`.
- `TMultiLevelAbility.ExpandCost` @ `0x557652e4`: `IntegerList.Get(list, level+1)`.
- `TMultiLevelAbility.GetSkillPoints` @ `0x55765348`: sums `IntegerList.Get(list,1..level)` — the
  total invested (feeds `THero.UsedSkillPoints`/`GetSkillPoints` accounting).

### 2.2 Combat data already supports 3 levels

The attack/defense tables (`0x558e83e7` / `0x558e83eb`, §0) already hold levels 1-3 (+2 atk / +1 def
flat). No new combat data needed for a 3-level restore. Note the per-level atk/def magnitude is
**flat** across levels — extra leadership levels do **not** raise the atk/def bonus; what a higher
level buys is **aura dominance** (a level-2 leader out-ranks a level-1 leader in `UpdateFormation`,
see Feature 3) plus whatever morale/other consumers key off the level.

### 2.3 Proposed patch approach (AoWEPACK.dpl)

Minimal restore to **3 levels**:

1. **Raise the cap:** at VA `0x5576618a` (the imm32 of `MOV [ESI+0x28],1`) change byte `01` → `03`.
   Single-byte patch, register-relative instruction — position-independent, no cave.
2. **Add the cost table entries for levels 2 and 3.** The existing `Put(list,1,0x14)` must be joined
   by `Put(list,2,cost2)` and `Put(list,3,cost3)`; otherwise `ExpandCost`/`GetSkillPoints` read a
   missing index (likely 0 → free upgrades and broken accounting). Cleanest: redirect the single
   `call TIntegerList.Put` at `0x557661a2` into a small cave that performs all three `Put`s then
   returns. `TIntegerList.Put` @ `0x55702eb4` is reachable by a **rel32 call** from a cave in the same
   DLL (PC-relative → survives rebase), so the cave is position-independent. Suggested costs mirror
   AoW's escalating skill costs, e.g. 20 / 40 / 60 (tune to taste).

That is the whole functional restore. Optionally also raise the base ctor is unnecessary (leadership
overrides it). Heroes will then be able to pour skill points into Leadership up to level 3 via the
normal Expand path (Feature 1 dialog), and medal/inherent grants that specify a higher level will be
honoured.

### 2.4 Risks / unknowns

- **4+ levels not clean:** the atk/def tables are packed 4 bytes apart; level 4 reads into the defense
  table / adjacent data. A 4-5 level restore needs the tables relocated to a cave and `GetAttack`/
  `GetDefense` retargeted (two more small patches). 3 is the safe ceiling.
- Confirm `TIntegerList.Get` behaviour on an absent index before relying on "missing = 0"; the cave
  approach avoids the question by populating 2 and 3 explicitly.
- UI: the level-up dialog and unit card should display level 2/3 fine (they read `GetLevel`), but the
  ability's `GetLevelName` (`0x557663d0`) loads a single "Leadership" resource string — level number
  display, if any, comes from the generic multi-level name formatting; worth an in-game look.
- Save compatibility: `TLeadershipAbilityData.ReadWrite` already serialises `+0x0c` as a byte, so
  higher levels persist without a format change.

## FEATURE 3 — Unit Leadership "disabled" under a hero with Leadership

### Verdict: **Root cause found (2026-07-19) — moved to its own doc.**

Full analysis, address map and fix options: **`Leadership_Disable_Bug_RootCause.md`**.

In one line: `UpdateDefaultAbilities` @ `0x5574F518` gates the medal/chassis grant on the
**effective** level (own ∪ aura-borrowed), so a unit that earns Leadership while inside another
leader's aura never receives its inherent record — and `ResetExternalSource` @ `0x557662E4` then
deletes the leftover aura-only record *and* the ability bit, permanently.

Note for Feature 2 planning: this bug and the level-1 cap are **independent**. Raising the cap does
not fix the disable bug.
