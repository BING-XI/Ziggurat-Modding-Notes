## PHASE 2 — the ranged path, as actually found (2026-07-08)
Unlike melee, **ranged has a single builder, no twin.** Both `TRangedAttackAbility.fcExecuteCombatCommand`
@0x5576eb70 AND `TBreathAbility.fcExecuteCombatCommand` @0x5576f182 call **`CreateRangedAttackCA`
@0x5576eae4**, once **per shot** (fcExecuteCombatCommand loops `GetAttackRepeatRA` times). So one hook
covers ranged + breath, per-shot. (xrefs to CreateRangedAttackCA = only those two callers + VMT + export.)

Inside `CreateRangedAttackCA` (EBX=ability, ESI=attacker[combat], [EBP-4]=target[combat], [EBP+8]=wall/cover):
- **attack** = `GetAttackRA`(VMT+0x114) − wall, computed @0x5576eb1a, **pushed @0x5576eb1d**.
- **damage** = `GetDamageRA`(VMT+0x110), in AL after the call @0x5576eb2e, **pushed @0x5576eb34**.
- VMT+0x110=damage / VMT+0x114=attack are **confirmed by `GetDamageValue`@0x5576e764**, which feeds both to
  `StatisticsToLimitedDV(attack, damage, …)`. VMT+0x110/0x11c take only register args, so the pushed attack
  survives to the CA setup.
- The setup `CALL [ESI+0x68]` is a **TStrikeCA-style `(ca, attacker, target, +3 stack)`** setter (like melee's
  CreateStrikeCA), NOT `TDamageCA.Setup` (@0x55729be4, RET 0x10, whose DL/CL byte params would mangle the
  attacker/target pointers). Its 3 stack args are `[attack, damage, r11c]`.
- ⚠ **Red herring:** `CA+0x18 = ability+0xC` (set after setup) is NOT the damage — it's the ability **id**,
  used by `TRangedAttackCA.Play`@0x5576e58c only to look up the attack **sound**. Don't bump it.

**The hook @0x5576EB34** (the damage `PUSH EAX`; there AL=damage and [ESP]=the already-pushed attack) →
`cave_rng`: 4 slayer checks on the combat attacker(ESI)/target([EBP-4]) — `GetAbilityEnabled`@VMT+0xa8,
alignment@VMT+0x90, hero via `*(target+0x4c)→IsClass`, exactly the melee cave_melee3 convention — each match
does `add byte[esp],1` (damage) + `add byte[esp+8],1` (attack), then replays the 3 displaced instrs
(`PUSH EAX; MOV EAX,ESI; MOV EDX,[EAX]`) and jmps 0x5576EB39. PIC via a `push edi` scratch + call/pop-edi
anchor. Register-clean (ESI/EBX/EBP preserved; EDI saved/restored; EAX/ECX/EDX are vanilla-scratch).

**Composes with — never touches — the user's existing ranged caves.** The Marksmanship-scaling rework AND
the Cave/Depths −2-attack malus (no Night Vision) both live UPSTREAM in `GetAttackRA`@0x5576e65c → its cave
`FUN_5580c240`: `ADD BL,AL` (adds the Marksmanship level to the attack), then if the attacker lacks Night
Vision (0x27 via strategic VMT+0x148) and is off the surface layer (`FUN_5577ed94` returns layer≠0),
`SUB BL,0x2`. All attacker-only, upstream of CreateRangedAttackCA → clean composition (base + marksmanship
− 2 malus + slayer bonuses).

## KEY FINDING — melee has TWO parallel slayer tables (the "only opportunities worked" bug)
The slayer bonuses (Monster Slaying, Holy/Unholy Champion) are **duplicated across three functions**, and a
melee attack reaches a *different* one depending on how it's delivered:
| function | who reaches it | objects / ability-check | Assassin cave |
|---|---|---|---|
| global `CreateStrikeCA` @0x557665e4 (block @0x557666a1) | Round Attack, attack-of-opportunity, ability strikes (Possess/Web/…) | combat objects, `VMT+0xa8` | **cave_melee** |
| `TMeleeRound.CalculateStrikes` @0x55767b24 (block @0x55767c5c) | **DELIBERATE melee** (`TStrikeAbility.fcExecuteCombatCommand → TMeleeRound.Calculate → CalculateStrikes`) | combat objects, `VMT+0xa8`, alignment `VMT+0x90` | **cave_melee3** |
| `TMeleeRound.CalculateUnitStrikes` @0x557677cc (block @0x55767904) | `CalculateFreeUnitSwing` + `CalculateUnit` — **opportunity / combat predictor** | **strategic units**, `VMT+0x148`, alignment `VMT+0xfc` | *(not hooked — wrong copy)* |

**Failed approaches (do not retry):**
1. **Global cave_melee only** → Assassin fired on attacks-of-opportunity & round attacks but NOT on a normal
   deliberate melee attack. Deliberate melee doesn't go through the global `CreateStrikeCA`.
2. **Adding `CalculateUnitStrikes` @0x55767904 (strategic twin, cave_melee2)** → changed nothing. That copy
   operates on strategic units (`VMT+0x148`) and serves the opportunity/predictor path, not the actual
   deliberate strike. It was removed.
3. **Registration via the strike factory `FUN_5576727c`** (TStrikeEnhancementAbility) → the ability
   registered, listed, and showed on the unit, but combat `GetAbilityEnabled(0x38)` returned FALSE for it, so
   NO bonus ever fired (proven with a `--diag` build that drops the hero check). **Fix: register via
   `CreateEnhancementAbility`@0x5576601c** (TEnhancementAbility, the Path-of-Sand factory) — it passes
   GetAbilityEnabled on the raw ability bit. Id/name/category/icon unchanged.

The resolution was to **trace the call chain** (`Calculate → CalculateStrikes`) rather than guess which
builder — the twin operates on combat objects exactly like the global cave, and hooking it fixed deliberate
attacks (both the attacker's offensive strikes and its defensive retaliation, since CalculateStrikes builds
both sides of the exchange).

## Background — how AoW1 "slayer" bonuses work (verified)
All melee "vs-type" combat bonuses are hard-coded in **`CreateStrikeCA` @0x557665e4** (the melee-strike
builder), each an `if (attacker has ability X) && (target matches) → +attack/+damage` block. Two flavours:
- **Marker-keyed** — reads a *tag ability* on the target. **Dragon Slaying `0x70`** vs the **Dragon `0x3F`**
  marker → **+3 attack / +3 damage**.
- **Alignment-keyed** — reads the target's built-in **alignment** (`target VMT+0x90`, low=good / high=evil).
  **Holy Champion** (ability `0x92` or enchantment `0xA0`) → +2/+2 vs evil `{4,5}`; **Unholy Champion**
  (ability `0x93` or enchantment `0xA1`) → +2/+2 vs good `{0,1}`. The `||` pair = innate ability OR
  enchantment-granted, both firing the same bonus.
- All gated on `GetAbilityEnabled(0x15)` (has melee) ⇒ **melee-strike only** in vanilla.

## Feasibility — FULLY FEASIBLE (investigated 2026-07-08). No "Hero" marker, no new DLL.

**Hero detection (for Assassin) — solved, no marker ability needed.** Heroes are the `THero` class.
The combat target is a combat object (its `GetAbilityEnabled` is at VMT+0xa8, alignment at VMT+0x90 —
NOT the strategic unit's VMT), and it links to its underlying strategic unit at **combat+0x4c** (proven
by `TCombatUnit.GetAbilityEnabled@0x55725004`). So: `underlying = *(target+0x4c); IsClass(underlying,
THero)` where **THero classref = `*0x55711fac`** and **`IsClass` = `0x557010c0`** (both from
`TArmy.Hero@0x5578df44`, which uses exactly this). Guard non-unit targets (walls) with an `IsClass(target,
TCombatUnit)` first, or only read +0x4c after confirming it's a unit. → Assassin keys off built-in
hero-ness, no `0x3F`-style marker.

**Melee — one new block in `CreateStrikeCA@0x557665e4`.** Monster Slaying (`0x70`) & the Champions
(`0x92/0xA0`, `0x93/0xA1`) already have their melee blocks there. Add an **Assassin** block alongside:
`if attacker.GetAbilityEnabled(ASSASSIN) && target-is-hero → attack += N, damage += N`.

**Ranged — one new block in `CreateRangedAttackCA@0x5576eae4`.** Confirmed
`CreateRangedAttackCA(ability, param_2=ATTACKER, param_3=TARGET, wallFlag)` (from its callers
`TRangedAttackAbility/TBreathAbility.fcExecuteCombatCommand`; target = `*(combatCmd+0x18)`). It finalizes
the attack (`cVar1`→hit) and damage before building the CA, with BOTH attacker & target in scope → inject
blocks for ALL FOUR slayers (Monster Slaying vs `0x3F`; Holy/Unholy Champion vs alignment `VMT+0x90`;
Assassin vs hero) that bump attack/damage by the (lesser) RANGED amounts. Called in a per-shot loop, so
the bonus applies per shot.
- ⚠ NOTE: the per-attacker ranged attack value is `GetAttackRA@0x5576e65c` (base `ability+0x2a`, modified
  by the attacker's Marksmanship `0x20`) — and it ALREADY contains the user's Marksmanship-rework cave
  **`FUN_5580c240`**. But `GetAttackRA` has NO target, so the target-conditional slayer bonus must go in
  `CreateRangedAttackCA` (has the target), composing cleanly with the `0x5580c240` cave. Don't clobber it.
