# In-game UI — combat log, dialogs, cursor, mouse wheel

This file covers the **game's** UI: `AoWz.exe`/`AoWzCompat.exe` windows and dialogs, the `aowInt.dpl`
widget toolkit they're built from, cursor/input handling on the strategic map, and mouse-wheel
delivery across all four game-facing binaries. It does **not** cover the map editor's UI
(`AoWDevEd.exe`/`AoWEd.exe` dialog directories, toolbar rows, terrain palette) — see `08-editor.md`.
Combat *mechanics* (the to-hit formula, the damage roll, which RNG generator is correct where) belong
to `01-combat-maths.md`; this file documents only how the combat log captures and displays that data,
not the formulas themselves.

## 1. Combat log

Two cooperating patches: `build_combatlog_dll.py` captures combat data inside `AoWEPACK.dpl` and
formats complete text lines at capture time; `build_combatlog_exe.py` adds a cloned chat-style window
plus a ring buffer to **both** `AoWz.exe` and `AoWzCompat.exe` (byte-identical builds, differing only at
file offset `0x3BB7C`) and drains the ring into the window's memo. `build_replaylog.py`,
`build_effectroll.py` and `build_touchlog_gate.py` are additive DLL patches layered on afterwards.
Offsets below are class-keyed; where this disagrees with `12-re-toolchain.md`, the catalogue
was measured and this wasn't — an offset means nothing without its class (five aliasing traps were
found 2026-08-03 where one offset meant different things on sibling classes; the `+0x4C` trap in
§1.7 is the one that bit this feature, twice).

```
AoWEPACK.dpl (rebases!)                          AoWz.exe / AoWzCompat.exe (fixed base 0x400000)
┌──────────────────────────┐                     ┌───────────────────────────────────────────┐
│ capture caves: tail      │  absolute writes    │ .clog @ VA 0x60D000 (RWE):                │
│ hooks on Generate/Ex,    │ ───────────────────>│  ring: hdr 0x20 + 64 slots × 128 B        │
│ the touch family, ….     │                     │  clone VMT 'TCombatLogWin' + method table │
│ format line via IDStr/   │                     │  RCDATA dir (82 entries) + new DFM        │
│ IntToStr/LStrCat thunks  │                     │  cave_createwin / cave_drain (memo pump)  │
└──────────────────────────┘                     └───────────────────────────────────────────┘
```

The DLL formats **complete lines** at capture time; the exe side only drains ring slots into the
memo's `TStringList`. No structured data crosses the module boundary — the DLL writes finished
strings to fixed exe VAs (the exe never rebases), guarded so the cave is inert in any other host
process (the DLL also loads into `AoWDevEd.exe`, which has no `.clog`).

### 1.1 Capture side — hooks, fields, strings

**CA hierarchy** (damage family): `TCombatAction@0x557160B4 → TSingleTargetCA@0x557161CC →
TDamageCA@0x557162F4 → {TStrikeCA@0x5571E344, TRangedAttackCA@0x5571E7EC,
TSelfDestructCA@0x55721084, TTurnUndeadCA@0x5571FD18, TCombatSpellCA@0x557F3CC8 →
TTurnUndeadSpellCA@0x557F41D0}`. A class's export address **is** its VMT (self-ptr `V-0x40`, name
`V-0x20`, parent via `*[V-0x18]`). VMT slots on the family: `+0x50` Execute, `+0x54` Play, `+0x58`
ShowObject, `+0x64` Setup, `+0x68` Generate, `+0x6c` GenerateEx.

**The two generation funnels, tail-hooked at their epilogues** (no bypassing override reaches
either): `TDamageCA.Generate @0x55729C20`, epilogue `0x55729C8C` (5 pops), ret 0xC @`0x55729C91`
(`eax`=CA, `edx`=attacker, `ecx`=target, `[ebp+8]`=types, `[ebp+0xc]`=damage, `[ebp+0x10]`=attack;
only override `TStrikeCA.Generate` calls base, so the hook composes); `TDamageCA.GenerateEx
@0x55729C98`, epilogue `0x55729D08` (5 pops), ret 0x10 @`0x55729D0D`, same args + extra byte
`[ebp+8]`, zero overrides — `TCombatSpellCA` does **not** override Generate/GenerateEx, so damaging
spells already arrive here (only `Play`, §1.6, needed a second entry point). At the epilogues:
`EBX`=CA, `ESI`=target, `[EBP-4]`=attacker.

**CA field map**: `+0x0c` flags (bit0 retaliation), `+0x0d` attacker id, `+0x0e` target id, `+0x10`
rolled damage (0=miss), `+0x11` effective types (`&~immunity`), `+0x13` effect-landing bits, `+0x15`
actual applied damage, `+0x18` spell id **on `TCombatSpellCA` only** — `TStrikeCA` reuses the same
offset for strike flags, so any read must gate on `IsClass(CA, TCombatSpellCA)` first (the same
aliasing idiom as the `+0x4C` trap in §1.7, one level up the object graph). Combat-object virtuals:
`+0x6c` GetAttack, `+0x70` GetDefense, `+0x74` GetResistance, `+0x88` GetHitPoints; object `+0x47`
bit0 dead, `+0x4C` strategic unit (`TCombatUnit`-only, §1.7), `+0x46` printable id, `+0xC` `FindID` id.

**Which defensive stat — the v1 bug.** `ExecuteDamageRole`/`ExecuteDamageRoleEx` (the mechanic is
`01-combat-maths.md`'s) roll vs Defence, except the `Ex`/GenerateEx path (Turn Undead, combat spells)
rolls vs **Resistance**. v1 printed GetDefense unconditionally on every line; `stub_genex` now reads
the same extra-byte switch that mechanic uses and computes `useRes` from it. Full immunity is free at
the hook regardless of which stat applies: `word[CA+0x11]==0` means fully immune, print "immune",
skip the maths.

**Roll capture, not `rolled==max`.** The 5-byte `call RandInt` inside `ExecuteDamageRole` at
`0x55725EBC` is repointed to a cave (`call RandInt; store EAX -> SCRATCH_R; ret`) so crit/fumble come
from the *actual* roll: formula rounding alone lands on max damage ~15–20% of the time even without
an auto-max branch, so `rolled==max` would over-report by roughly 2×. The Generate/GenerateEx tail
classifies the stored roll and resets `SCRATCH_R=-1` ("no roll"), which the touch-family worker
(§1.5) reuses safely on a path that never calls `RandInt`. Full to-hit/damage-roll derivation is
`01-combat-maths.md`'s territory.

**BSS scratch** (page slack; declared BSS ends `0x558FA231`, page mapped RW to `0x558FAFFF`):
`0x558FA800` simfly (unrelated) · `0x804`/`808`/`80C` raze (unrelated) · `0x810` `SCRATCH_R` ·
`0x814..81F` free · `0x820` `SC_T1` (touch roll 1: `+0` ok/−1 `+4` diff `+8` stat) · `0x82C` `SC_T2`
(roll 2, same layout) · `0x838+` free.

**Strings.** `TCombatUnit.IDStr @0x5572551C` (`eax`=unit, `edx`=out LStr) → `"A(<id>)=<name>"`,
NIL-safe. Thunks: `0x55701140 @LStrClr`, `0x148 @LStrArrayClr`, `0x150 @LStrAsg`, `0x158 @LStrLAsg`,
`0x160 @LStrFromChar`, `0x188 @LStrCat`, `0x190 @LStrCat3`, `0x198 @LStrCatN`, `0x5570 11A8
@LStrAddRef`, `0x11B0 @LStrToPChar`, `0x5570158C IntToStr`, `0x557015E4 Format`. Discipline: pre-zero
out slots, `@LStrClr` before returning, cave literals use refcount `-1` so the VCL never frees them
from RX memory.

**Ring protocol** (`@0x60D000`, exe-hosted): `+0` magic `'CLG1'` · `+4` `wrIdx` (DLL-owned) · `+8`
`rdIdx` (exe-owned) · `+0xC..1F` reserved · `+0x20` 64 slots × 128 B (Delphi shortstrings). Writer
drops the line if `wrIdx-rdIdx>=63`; reader drains to `rdIdx=wrIdx`. Ring size `0x2020`; clone VMT at
`0x60F060`, clear of it.

**Current cave address.** Originally split across small pockets in the crowded
`0x5580Cxxx..0x5580Fxxx` region, **relocated 2026-07-22 to `0x55811000`** after it grew enough to
silently overlap `build_tierresearch_dll.py`'s `cave_grant` at `0x5580ED80` (harmless padding
overlap that nonetheless made verify report "cave zone not free" forever). One cave image at
`CAVE=0x55811000` now covers all seven hooks (both epilogues, roll capture, Turn Undead touch, three
v9 touch hooks). `LEGACY_CAVE=0x5580E440` (zero with `--vacate`), `LEGACY_LIMIT=0x5580ED80` (never
write at/past). Per-version sub-addresses quoted later (`cave_touch @0x5580E798`, `trole
@0x5580E7E8`) are the pre-relocation layout, historical only — the fixed **hook sites**
(`GEN_HOOK`/`GENEX_HOOK`/`ROLL_HOOK`/`TOUCH_HOOK`/`TOUCHROLE`/`TR1_HOOK`/`TR2_HOOK`) never moved; the
script's own constants are the current address authority. PIC via one `call $+5; pop` anchor; only
the exe's addresses (`0x40003C`, `0x60Dxxx`) are absolute, correctly.

**Host-process guard** (the DLL also loads into `AoWDevEd.exe`): PE header check
(`[0x40003C]→e_lfanew`, SizeOfImage `>=0x20E000`) then magic `'CLG1'` at `0x60D000` — safe no-op in
the editor.

### 1.2 Window side — creation, cloning, append/show-hide

Entry `0x45995C`; 78 consecutive `TApplication.CreateForm` calls @`0x4599F1..0x459FA8`, then
`Application.Run` @`0x459FAF` (thunk `0x401764`). `CreateForm` thunk `0x40175C` (`eax`=Application,
`edx`=classref, `ecx`=`@instance-global`). DFM resolves via `FindResource(HInstance, ClassName,
RT_RCDATA)` (name = uppercased class name) and `FindClassHInstance = VirtualQuery(VMT).AllocationBase`
— a VMT in any exe section resolves.

**The clone recipe** (reused, with variations, by every exe feature in this file): (1) copy the
donor's VMT block `[V-0x40,V+0x28)` (`TChatWindow @0x412D5C`, 0x68 B) into the new section; patch the
self-ptr and ClassName pointer; keep TypeInfo/FieldTable/Parent shared with the donor (fields bind,
palette works, exe is fixed-base). (2) Clone the method table (donor's 7 entries + `CombatLogUpdate →
cave_drain`; format `count:word` then `{size:word, code:dword, name:shortstring}`; the DFM binds
`OnUpdate=CombatLogUpdate` by name). (3) Author the DFM from a copy of the donor's, dropping
donor-only children (their fields stay nil, harmlessly) and donor-only handlers. (4) `cave_createwin`:
a 5-byte patch at the `Run` call turns it into one more `CreateForm` + the original call, created
**after** all 78 vanilla forms so cross-form fixups already resolve. (5) Smoke-test first with `edx`
pointed at the donor's own VMT — a second copy of the donor window proves the hook before any
resource surgery.

Donor facts: `TChatWindow` VMT `0x412D5C` (instance size `0x74`), self-ptr slot `0x412D1C`,
FieldTable `V-0x2C→0x412D84` (fields `+0x44..0x6C`), MethodTable `V-0x28→0x412E23` (7 handlers),
ClassName `V-0x20→0x412EB2`. Instance globals: the 78 vanilla instances occupy `0x45B034..0x45B2D0`;
clone instance global `GVAR_INSTANCE=0x45B2E0` (free BSS slack). New section VA `0x60D000` (RVA
`0x20D000`), file-appended at `0x207A00` (pre-patch EOF).

**Append a line**: instance ptr → `ChatMemo +0x48` → `TStringList +0x118` → `call [vmt+0x34]` (`Add`,
`eax`=list, `edx`=LStr) → set `instance+0x70=1` (scroll flag). `Add` fires `OnChangeText` → dirty →
re-wrap next tick; safe while hidden. `TAOWMemo`: `+0x118` FStrings, `+0x188` wrapped list (derived),
`+0x120` scrollbar, `+0x2E` layout-valid. `Classes.TStringList` VMT (`vcl30.dpl @0x4131BC98` — **VCL30
ships symbols; dump by symbol, never by Delphi declaration order**, which wrongly predicts `Add` at
`+0x54`): `+0x0C` Get, `+0x14` GetCount, `+0x18` GetObject, `+0x34` **Add**, `+0x40` **Clear**, `+0x44`
Delete, `+0x50` IndexOf, `+0x54` Insert.

**Show/hide**: control at `instance+0x44`, visible byte `ctl+0x75`, `SetVisible=[vmt+0x6C]`.

### 1.4 Effect-landing roll (§11) — 🔨 APPLIED, UNTESTED (2026-07-21)

The log said *whether* an effect landed but never the odds, and a **resisted** roll was invisible —
no roll, no odds. A repeat hit on an already-afflicted target also prints nothing (the engine
short-circuits before rolling), so "no suffix" was ambiguous between resisted and already-afflicted.

`TAbstractUnit.ExecuteDamageEffectsRole @0x55781BA4` (combat `vmt+0x118` → strategic unit) rolls once
per landed type, in order, on the same `HitRole` curve as to-hit (`01-combat-maths.md`):

| order | type bit | status id (`vmt+0x148`) | effect | `call HitRole` |
|---|---|---|---|---|
| 1 | `0x01` fire | 7 | burning | `0x55781C37` |
| 2 | `0x04` lightning | 9 | stunned | `0x55781C97` |
| 3 | `0x10` poison | 10 | poisoned | `0x55781CE9` |
| 4 | `0x20` death | 11 | cursed | `0x55781D3B` |
| 5 | `0x40` holy | 12 | vertigo | `0x55781D8D` |
| 6 | `0x02` cold | 8 | frozen | `0x55781DED` |

Lightning/holy carry an extra `vmt[0x114]()!=2` guard. Fully-immune types drop first (`vmt+0xEC`);
partial protection (`vmt+0xF0`) is a flat +2 effective resistance for that type; already-afflicted
(`vmt+0x148`) skips the roll.

**Fix.** Each roll site is a standalone 5-byte `call HitRole` (odds in EAX, outcome in AL) — repointed
to a stub that calls `HitRole` and immediately emits its own line (`vertigo 30% vs res 7 - landed` /
`poisoned 50% vs res 5 - resisted`). No BSS table or clear-hook needed: each stub emits immediately,
so the plan of appending to the damage line (which would have meant patching the log worker) proved
unnecessary. The roll happens inside `Generate`, before the epilogue hook, so an effect line appears
just above its damage line. Cave `0x5580F600` (above `build_replaylog.py`'s, which ends
~`0x5580F4A3`); own backup, one layer deep.

**Needs the user's in-game test:** a status-inflicting hit shows the odds/outcome line above the
damage line; a resisted roll reads "resisted" with odds rather than staying silent; an
already-afflicted target shows no suffix (expected).

**Still open, not built:** `CA+0x18` strike flags (panicked/entangled/lifesteal) are set by
`TStrikeCA.Generate` *after* the base tail, reading 0 at existing hooks — needs a fourth hook at its
exit `0x55766969`. Same shape: `HitRole(5−RES) @0x5576691B` (Cause Fear `0x33`, skipped if target is
Fearless `0x43`), `HitRole(7−RES) @0x55766955` for ability `0x77` (Entangle Strike, applying Entangled
`0x5E`). Per-ability bonus attribution was **deliberately dropped** (user decision 2026-07-16): the
printed atk/dam already include every bonus.

### 1.5 Touch-attack logging — v8 (Turn Undead) + v9 (whole family)

**Why misses were invisible.** A touch attack is a two-stage roll; only stage 2 was hooked before v8:

| stage | where | rolls | logged before v8? |
|---|---|---|---|
| 1 — lands | `CreateTurnUndeadCA@0x5576B528` | attacker GetAttack − target GetDefense → `HitRole` | no |
| 2 — damage | `GenerateEx`→`ExecuteDamageRoleEx` | `GetTouchAttack(level)` vs **Resistance** | yes |

A stage-1 miss stores ids and stops — `GenerateEx` never runs, so it structurally can't reach the
damage-funnel hooks; and a *landed* touch's stage-2 line rolls vs RES, not DEF, so ATK-vs-DEF never
appeared either way.

**v8 — `cave_touch`.** Hooks the stage-1 `call HitRole` directly (`TOUCH_HOOK=0x5576B55C`, computed
original bytes, never read live). Registers: `EAX`=diff, `EDX`=defense, `ESI`=attacker, `EBP`=target,
`EDI`=CA, `EBX`=ability. Calls `HitRole` itself, passes AL through, and on a miss reuses the
**normal formatter** by doctoring a fresh CA rather than duplicating line-building: force `+0x11`
types to `0xFFFF` (else "immune" prints wrongly) and `SCRATCH_R=-1` (else a stale value could fumble),
both restored after. Result: `Hero misses Zombie  (70%, 9 ATK vs 4 DEF)`. Scope: Turn Undead only —
the shared virtual `CombatTouchRole@0x557681B0` has zero rel32 callers and `CreateTurnUndeadCA` inlines
its own roll instead.

**v9 — one hook, 16 classes.** `CombatTouchRole` is VMT slot `+0x110`; walking every descendant's
parent chain confirms **none** overrides it: `TCharmAbility TCommandAbility TDispelMagicAbility
TDominateAbility TEntangleAbility THealingAbility TInvokeDeathAbility TPossessAbility
TPossessedAbility TRoundAttackAbility TSeduceAbility TSelfDestructAbility TTouchAbility
TTurnUndeadAbility TWallCrushingAbility TWebAbility`. Their `Create*CA` methods all call `[ebx+0x110]`
— hooking the function covers the family (chasing call sites is useless, that vtable offset collides
with unrelated classes). `CreateHealingCA` stays outside correctly (healing never rolls);
`TTurnUndeadAbility` inlines its own roll (v8).

`CombatTouchRole` is a two-roll gate: `ROLL 1 @0x557681D6` ATK−DEF→`HitRole`, fail→0;
`GetTouchAttack==-10`→0 (cannot-touch sentinel); `ROLL 2 @0x55768216` self-`GetTouchAttack`−RES→
`HitRole`, fail→0 — two distinct failure causes (missed vs resisted), now distinguished. Both sites
share Turn Undead's `sub eax,edx`/`call HitRole` shape, captured into `SC_T1`/`SC_T2` the same way.

As-built (pre-relocation address; §1.1's note on current location applies): `trole` unit at
`0x5580E7E8` (943 B) — `_entry` trampoline, `_stub_orig` (7 relocated bytes + `jmp 0x557681B7`),
`_troll1`/`_troll2` (roll captures), `_tworker` (sentence builder), `_tstats` (shared stats emitter).
Output conjugates the ability name's last letter (`Possess`→`Possesses`):

```
Incarnate Possesses Giant  (70%, 9 ATK vs 4 DEF)  (60%, 8 ATK vs 5 RES)
Saint fails to Charm Swordsman  (70%, 9 ATK vs 4 DEF) - missed
Saint fails to Charm Swordsman  (70%, 9 ATK vs 4 DEF)  (30%, 8 ATK vs 5 RES) - resisted
```

A stage-1 miss shows only stage 1 (stage 2's scratch stays −1). Ability name from `TAbility.GetName`
(VMT `+0x58`), called virtually since `THealingAbility` overrides it.

⚠ **The trap: four independent PIC anchors in one unit.** A single shared anchor across
`_entry`/`_troll1`/`_troll2`/`_tworker` would have silently corrupted three of the four displacement
sets. Fix: one base per section, pass-1 emits with distant dummy bases so every displacement encodes
`disp32` (unit size can't move between passes), locate anchors by byte pattern, re-emit with real
bases, assert size and anchor offsets unchanged. **Generalises: one PIC anchor per section, never
shared.**

**Needs the user's in-game test:** a Turn Undead touch miss shows the stage-1 roll + ATK-vs-DEF; a
landed touch still shows the stage-2 roll vs RES; each of the 16 touch-family abilities prints a line
in tactical combat, distinguishing "missed" from "resisted"; the log clears on battle end / replay
close (reuses §1.6's `_m_none` transition, no new hook needed).

### 1.6 Replay re-display (§12) + spell labelling

**Why a re-opened replay was blank.** The log hooks damage *generation*, but a replay never
regenerates — it only plays back actions already stored in the battle's `TCombatLogbook`. Worse, the
drain's `_m_none` transition (v6) both clears the memo *and* discards pending ring slots on
replay-close, so the first viewing consumed the content and deleted it.

**Fix — one hook on the playback path.** 5 B @`0x55729D97` (`mov edx,[ebx+8]; mov eax,esi`) inside
`TDamageCA.Play @0x55729D78`, on the single trigger-tick branch (a `jne` two instructions earlier
guards it, so it fires **exactly once** per action). `ESI`=CA, `EBX`=`TCombatViewer` (`[EBX+8]`=the
playback `TCombat`, `[[EBX+8]+0xc]`=its `TCombatData`). `Play` is dispatched only from
`TCombatViewer.Update`; the exe imports no CA methods and `AoWTCPCK` imports neither
`GetCombatActions` nor `TCombatViewer`/`TCombatLogbook`, so `Play` **never** runs live — zero
double-logging by construction. (`Execute` was rejected: runs in both contexts, and
`SetPosition` re-executes actions 0..pos−1 on every slider drag.)

**The starvation bug.** `live_ui.py` on a running replay showed the hook firing and the ring filling
(`wrIdx=67 rdIdx=48`), but `cave_drain` pumps off `MapWindowUpdate`, which doesn't tick while the
fast-combat replay window animates — 19 pending lines never drained, then discarded on close. Fix:
since `Play` always runs on the main thread during a replay, the cave writes each line **directly
into the window's memo** via `TStringList.Add` — the same call `cave_drain` makes, just relocated to
where the data already is. Self-refreshing, no ring, no exe patch; live combat still uses ring+drain
untouched.

Own cave `0x5580F180`, own backup (additive, touches nothing already confirmed). IDs→objects via
`TCombatData.FindID @0x55728C68`. Names via `combatObj+0x4c`, type-gated (§1.7) first. **No `(N%,
ATK vs DEF)` tail, ever** — closed decision, 2026-07-25: the attack value is a transient stack
argument, never persisted by `TDamageCA.ReadWrite`; and any defensive stat available at replay is the
**battle-start roster snapshot**, so a mid-battle Curse/Bless would make both the stat and the derived
hit% wrong — silently, since the numbers are right often enough to be trusted. A spell-only partial
tail (spell ATK is exact static data; only RES would be a snapshot) was considered and rejected for
the same reason. The live tactical log carries the true tail; combat-math verification belongs there.
Format: `Valkyrie hits Shadow for 5 damage +vertigo` / `Shadow hits back at Valkyrie for 3 damage` /
`Valkyrie misses Shadow`.

**Spell labelling — second entry point (2026-07-25).** `Play` is VMT `+0x54`; `TCombatSpellCA`
(`0x557F3CC8`) **overrides it** at `0x557F6A6C` and never calls base, so spells never reached the
original hook. An earlier claim ("the three `Play` overrides all call base") had checked
`TStrikeCA`/`TTurnUndeadCA`/`TRangedAttackCA` and missed this fourth one. **When a hook's coverage
rests on "all overrides call base", enumerate the VMT slot across every descendant — never
spot-check.**

Fix: 6 B @`0x557F6A72` (`cmp dword [ebx+0x14],0 ; jne`). ⚠ The original target,
5 B @`0x557F6A78` (`A1 imm32`), was **unusable** — a `.reloc` HIGHLOW entry at `0x557F6A79` means the
loader's rebase fixup would corrupt a `jmp rel32` written there. **In the DPLs, always scan `.reloc`
for the exact displaced range before choosing a hook site** (the same rule §2.3 states for `.exe`
displacement, here inside a DLL instead). `0x557F6A72..77` is reloc-free; the cave replicates the
trigger-tick test and rejoins at `0x557F6A78`/`0x557F6A97`. `TTurnUndeadSpellCA` inherits the
override (verified `VMT+0x54`) — covered free.

Route: caster classref → `TCombatSpell.CreateCA @0x557F72C0` → `TCombatSpellCA` → `CA+0x18:=spell id`
→ `CAvmt+0x6C` (un-overridden GenerateEx, so the live-log hook fires too). `TSpell+0x08`=name (plain
LStr value). `GetSpell @0x55779AC8` **raises on a negative id** — sign-check first. Control via
`[AoWHSSet 0x558FA044]→+0x84`. Both loggers emit `<caster> casts <Spell> on <target> for N damage` /
`… but misses …` (separate connector so a miss can't read as a hit); `"Wall"` instead of `"?"` in both.

As-built: DLL worker 1169 B (3022 B total @`0x55811000`), spell slot `[ebp-0x2C]` with its own
`@LStrArrayClr`. Replaylog cave 1128 of 1152 B ceiling (entries `0x5580F180`/`0x5580F18F`, worker
`0x5580F1A4`) — only 24 B slack left; further growth needs a cave move.

**Non-damaging spells still produce nothing anywhere** — see Open items.

**Needs the user's in-game test:** live-tactical spell labelling (replay-side already confirmed) —
needs a full restart, since the DLL maps at process start. If it fails, the worker's fast-combat gate
(added on a disproven theory, never verified not to misfire) is the prime suspect — revert it
regardless of outcome.

### 1.7 The "Blt Error" wall-hit freeze — ✅ CONFIRMED WORKING (2026-07-22)

**Symptom.** A modal `Error - FCWin` / `Blt Error` dialog on **any** damage to a combat wall
(confirmed with cannons — not touch-specific, not overkill). Damage still landed; the dialog froze
the flow.

**Root cause.** `build_replaylog.py`'s cave fetched a name via `[combatObj+0x4C]`→strategic
unit→`GetName`, NIL-guarded only:

```
mov  eax,[ebp-0x20]  ; combat object      test eax,eax / jz fallback
mov  eax,[eax+0x4C]  ; -> strategic unit  <-- UNGUARDED BY TYPE
test eax,eax / jz fallback                ; NIL check only
mov  ecx,[eax]       ; -> unit VMT        <-- ACCESS VIOLATION on a wall
call dword ptr [ecx+0xF8]                 ; GetName
```

`TCombatObject+0x4C` is `TCombatUnit`-only — `TCombatWall` has a smaller instance and reuses `0x4C`
for packed setup bytes. On a wall the read is nonzero garbage; it passes the NIL test and the
dereference faults.

**Fix** — `System.@IsClass` before the read: `lea edx,[edi-delta]` to the `TCombatUnit` VMT
(`0x55715A94`, PIC-relative), `call 0x557010C0` (`eax`=obj, `edx`=classref → AL), only then dereference
`+0x4C`; not a unit → `"?"` fallback. `@IsClass` preserves EDI. Cave rewritten in place (825/1152 B);
no revert touched a backup.

**Why the message was useless — two nested catch-alls destroying the evidence:**

```
build_replaylog cave           access violation
  └─ AoW.exe 0x435E7C  TFastCombatForm.FCWinDrawSurface
       except @0x435F26: Exception.Create('Exception during FastCombatWin.DrawSurface')
                          @RaiseExcept          <-- ORIGINAL EXCEPTION DESTROYED
         └─ aowInt 0x59807BC6..0x59807D48 (component draw try)
              except @0x59807D55: MessageBox(body="Blt Error", caption="Error - "+Name)
```

Five arms in that one aowInt routine, each a **fixed label, not a description**: "Verify Surface
Error" (`0x598077F4`), "Draw Error" (`0x59807967`), "Blt Error" (`0x59807D55`), "SB Draw Events Error"
(`0x59807EA5`), "Exception during DrawSurface" (`0x59807EE8`). **An error string beside a `MessageBox`
in this codebase is a label on an `except` arm, not a description of the fault — probe the handler,
never interpret the string.** Reading "Blt Error" as "a blit failed" was actively wrong: the blit loop
never ran on this path (BltRect count `[self+0xE4]`=0; the try head short-circuited to the "not
dirty" virtual draw).

**The probe technique that found it (reusable).** Static reading gave three wrong theories in a row;
instrumenting both handlers with diagnostic-only, cleanly-revertible caves worked
(`build_bltprobe.py` in aowInt on the "Blt Error" arm; `build_bltprobe_exe.py` in `AoWz.exe` on
`FCWinDrawSurface`'s except arm **before** `Exception.Create` destroys the original;
`re_tools/read_bltprobe.py` reads both live). Rules worth reusing next time:

- **Dumb cave, smart reader.** Record raw pointers + a raw stack image, dereference almost nothing —
  a stray read inside an `except` arm is a *nested* exception, a hard failure in Delphi 3. All
  pointer-chasing happens out-of-process via `ReadProcessMemory`, which errors instead of faulting.
- **The dialog is modal, so the process holds still** — no debugger needed; captured values persist
  until the game exits.
- **Dump the whole stack.** The break came from a return address landing inside a cave with no
  business in that call path — one dword cracked it after every other approach failed.
- **EAX is not the exception object at a bare `except`.** Measured EAX pointed at non-module memory —
  not a VMT. Hunt the stack for a pointer whose class metadata validates (but check the class — the
  scan also turns up ordinary live objects).

**Why this took so long.** An A/B toggling only `build_combatlog_dll.py`'s seven hooks reported "all
off → error persists" and was written up as exonerating the DLL; three wrong theories were built on
it. The test measured the wrong thing — `build_touchlog_gate.py` only knows its own seven hooks, and
`build_replaylog.py`'s hook stayed live through every run. **A gate tool's negative result is only as
good as its inventory.** An earlier A/B had also contradicted the user's report of *when* the bug
began, on a single RNG-dependent trial where the control never triggered the condition. **When an A/B
contradicts direct user observation of timing, suspect the test first.**

crash — an Assassin carrier attacking a walled structure AVs in `System.@IsClass` with the wall's
packed `+0x4C` dword `0x00002802` as the object pointer. Both `build_assassin.py` caves and all three
`build_magebane.py` caves now route through the shared `guard_hero`/`guard_unit` cave at
`0x55849000`. Full record: `03-abilities-added.md`, Assassin section.

**Reusable: when can a wall be a damage target at all?** `TCombatWall.GetImmunityTypes @0x55725C40`
computes `~0x0100 & allTypes` — **a wall is immune to every type except bit `0x0100`** (siege
damage), and full immunity zeroes the value upstream. For any damage-gated call path: only an attack
carrying `0x0100` can reach a wall. ⚠⚠ **Do not read that as "walls cannot reach strike code".**
Immunity is applied when the damage *lands*; the strike CA is BUILT first, and `CreateStrikeCA` /
`TMeleeRound.CalculateStrikes` / `CreateRangedAttackCA` all run with the wall as the target object
long before any immunity test. That distinction is exactly what the 2026-09-11 crash proved.

Text renders via `Ilpack.dpl`'s `TImageLibraryFont` (bitmap fonts, no GDI). Frame pump is `Dcpack`'s
`TCustomDisplay.UpdateFrame`/`StartUpdateFrameLoop`. ⚠ **The installed `Ilpack.dpl` is not vanilla
and not ours** — it differs from the GOG hash and carries a third-party ShowScene patch (owner,
2026-09-07). No `build_*.py` writes it. Treat it as a patched baseline: it ships with the mod, and a
byte-diff against the GOG manifest will always flag it. (`AoWInterface.dpl` at base `0x400000` is a
near-duplicate — believed the setup/menu shell's own copy; the in-game toolkit is `aowInt.dpl`.)

⚠ **`TAOWLabel` is strictly single-line.** `ImageLib.ParseFontText @0x552147A0` does split on
CR/LF/space but has **no callers anywhere** — dead code. The renderer actually used,
`TAOWLabel.Draw`, is a per-character loop indexing the font's glyph table by byte value and
**silently skips any byte with no glyph, CR and LF included** — a CRLF-joined string draws as one
long line and runs off the panel edge. Multiple lines of text need multiple real label controls,
i.e. cloning `TAOWLabel` components — the same DFM-clone-and-relocate technique §2 documents in full.

**Exe game windows are DFM-streamed Delphi forms** throughout: a VMT scan of `AoW.exe` finds 84
classes (`TChatWindow`, `TResultsWin`, `TFastCombatWindow`, `TUnitWindow`, `TMWindow`, `TSWindow`,
`TIWindow`, `TNewTurnDlg`, `THeroUpgradeDlg`, …) whose published methods are event handlers, wired by
a DFM resource. Tactical combat plays on the map screen, so floating game windows are available (and,
per §1.7, dangerous to blit) during combat.

**Post-battle report machinery — decoded, never built, still valid if wanted.** `TCombatLogbook`
holds two `TCombatData` roster snapshots (`+0xc` initial, `+0x10` final) and is itself **saved**
(`ReadWrite@0x55728EA0`). Header text is `finalData+0x48`. Adding per-strike lines would need a
strings container + a `ReadWrite` extension (a save-format touch) + `TResultsWin` DFM/code extension.
Precedent for carrying strings through the CA pipeline already exists in vanilla:
`TUpdateHeaderCA` (from `TCombat.SetLogbookHeader@0x5572759C`) carries an LStr at `CA+0xc` through
`ExecuteCombatAction` — the model if log lines ever need MP replication rather than local capture.

**File logging** would be nearly free if ever wanted: `kernel32!CreateFileA`/`WriteFile`/`CloseHandle`
are already in AoWEPACK's IAT, plus `EngineP.TEngine.OutputDebugMessage`/`OutputDebugStr`.

## 2. Hero level-up dialog — the reference for any AoW1 dialog restructure

`THeroUpgradeDlg` went through two staged rebuilds: doubled in height first, then rebuilt entirely
into five category columns, which now **owns** the dialog's geometry and absorbed the height script's
machinery. **This is the load-bearing reference for restructuring any AoW1 dialog** — the
clone-DFM/reuse-handler-names technique, the class-growth recipe, and the resize-clamp fix all
generalise to the other 78 DFM-streamed forms in the exe.

### 2.1 What it does

The single "Upgrades" list becomes **five category columns, each with its own Cost column** — ten
list columns — in two framed boxes: box A ("StatePnl": portrait, stats, Current Abilities) above box
B ("UpgradePnl": Remove/Add/Done/Cancel as its header row, the five columns below). Dialog
407×432 → **960×525** by default (8 rows/column), re-tunable.

| column | count | contents |
|---|---|---|
| Wayfaring | 27 | movement, terrain, the 8 Concealments, vision/invisibility |
| Resistances | 18 | 8 Immunities, 8 Protections, Fearless |
| Melee | 21 | the 7 Strikes, Charge/Parry/Round Attack/Extra Strike/…, the Slayings |
| Ranged | 20 | Archery/Marksmanship, thrown+shot, the 5 Breaths, the 5 Bolts |
| Magic | 16 | Spell Casting, mind control, Healing, Leadership/Bard's, Doom Gaze |

Counts drift as abilities are added (`herodlg_cats.py` prints live counts). They no longer size the
dialog — see §2.1a. Unlisted ids fall into `DEFAULT_CAT` (Magic). **Category assignment is a design
decision, not a decode** — the game has no category data anywhere; edit `herodlg_cats.py` and
`--apply` to change it. ⚠ **Re-run `--apply` after any edit** — the 256-byte lookup table that
actually drives the fill loop lives in the two executables, written by this script; a Python-only
edit with no re-apply leaves the ability silently in `DEFAULT_CAT`.

**"My new ability doesn't appear" is almost never this feature's category table.** More likely: (1)
its selection mask lacks `0x100 astHeroUpgrade` or `0x200 astEditor` (two gates — the fill cave and
`TAbility.CanExpand`; `Ability.pfs` tag 9 overwrites whatever registration passed, but **only when a
record exists** — `rwData` leaves the field alone on a missing tag); (2) not multi-level and the hero
already has it. Check with `re_tools/pfs.py` (record key = ability id + 10), not by eye.

⚠ **A missing tag 6 is NOT one of the reasons** — that claim used to sit here and is wrong. An
ability with no tag 6 (or no record at all) has `ExpandCost` = 0 and appears **normally, for free**;
tag 6 gates nothing. Reforming Flesh `0xB1` shipped exactly like that for ten days. `rwInteger`
zeroes the field when the tag is absent, so a registration-time store cannot rescue it either —
`03-abilities-added.md`, "Level-up cost".

### 2.1a The vertical budget — `--height` buys list rows and nothing else

```
height = FURNITURE_H + ROW_H * rows  =  389 + 17 * rows        (default 8 rows -> 525)
```

389 px is fixed whatever the dialog holds: 53 title knotwork, **224 box A** (portrait + "made a
level" banner 4+142, the six stat rows with their spinners 150..220, skill points, Current
Abilities at 11 rows), 8 gap, 47 box B header (Remove/Add/Done/Cancel then the five sort headers),
4 pad, 45 bottom knotwork band, 8 list `BorderHeight`. Per row = `ItemHeight` 17. `layout()` derives
`FURNITURE_H` from the box constants and asserts `list_h == height − FURNITURE_H + LIST_BORDER`, so
the figure cannot drift from the arithmetic. **Box A is rigid** — going below ~440 means restructuring
box A, not re-tuning `--height`.

**Sized to the offer, not to the catalogue (2026-09-10).** It was 860 px / 27 rows so the tallest
category (Wayfaring, 27) never scrolled. `build_heroskill_race.py`'s per-race gate made that premise
obsolete: a hero is offered ~16-22 of the 102 abilities, ~3-5 per column, so 22 rows per column stood
empty. It went to 474 px / 5 rows — **vanilla's own list depth**, since vanilla's single Upgrades
list was `WinHeight 107` = `(107−8)/17` = 5 rows — and then, the same day and at the owner's request
("about 10% taller"), to **525 px / 8 rows**. A literal quarter of 860 is 215 px, 174 px *below* the
furniture alone, so it is not reachable at any row count.

Chance that at least one of the five columns overflows and must be scrolled, computed over the live
race table (`heroskill_races.matrix()` × `herodlg_cats`, Poisson-binomial per column, worst race
Undead): 5 rows 50%, 6 rows 23%, 7 rows 8.7%, **8 rows 2.7%**, 9 rows 0.7%. Heights: 474 / 491 / 508
/ **525** / 542. Overflow **scrolls, never truncates** — `cave_setfmax` drives all five scrollbars off
their own `GetCount()−1`, and an empty column is already a reachable, working state.

⚠ **The height quantises to whole rows, so a percentage lands on a rung or it lands nowhere.**
474 × 1.1 = 521.4; `--height 521` would store 521 in the DFM and still show 7 rows, with 4 px of dead
space. 525 is the rung. Always convert a requested height back through `(h − 389) / 17` before
believing it.

⚠ The old `assert rows >= max(CATS.counts())` is gone; the floor is now `MIN_ROWS = 3`. Re-adding a
catalogue-derived floor would re-impose an 848 px dialog.

### 2.2 The reference recipe — clone DFM components, keep the donor's handler names

Column 0 reuses the existing `AvailableAbilities`/`…Cost`/`…SB`/`…Sort`/`…CostSort`. Columns 1–4 are
**byte-clones**: copy the donor's byte span, patch name/position/height/caption — every other
property stays exactly as the original's.

⭐ **The clones keep the donor's ORIGINAL event-handler names** — identical `OnChange`/`OnClick`/
`OnMouseDown` across all five columns — rewritten by caves to read **`EDX`=Sender** (Delphi's
register convention; still live at every hook site since vanilla's prologues only touch EAX/EBX).
Net effect: **no method-table extension, no new published methods** — the single biggest
simplification, and it generalises to any "N copies of one control" change: clone the DFM span, keep
the handler name, make the handler Sender-aware.

**Reparenting is just the `AOWWindow` ident property.** All controls are DFM-root siblings; parenthood
is a name reference, so moving a control to a different box is a one-property edit and children follow
automatically. Forward references resolve fine — the DFM reader binds by name only after the whole
form is read (vanilla itself already depends on this).

**A panel becomes a visible framed box via `ILFrame` + `ILIndexFrame` together** — ⚠ both required, or
nothing draws (one vanilla panel has an index but no `ILFrame` and is invisible for exactly that
reason). `ILIndexFrame` selects a *set* from `GenericF`'s catalogue: 32 `DialogFr` 22px, 40 `FrThin`
1px (listboxes), 48 `FrameLight` 2–4px, 56 `FrGoldSq` 3px, 64 `ScenFr` 1px (stat rows), **88
`NGFrOut` 3px** (chosen here — the New-Game screens' outer grouping frame), 96 `NGFrThin` 1px, 105
`FrThinD` 2px.

**The knotwork band is two stacked components**: a `TAoWFrame` (`FrameType=frHorizLine`,
`ILLine=CeltDeco`, `ILIndexLine=55` — tiles a rule across its width) plus a `TAOWImage` of CeltDeco
image 3 stretched wide, which the toolkit **tiles** on its own into the swirl. Vanilla's bottom band
used the rule but three discrete medallions instead of the tiled image (why it looked bare once
buttons moved off it) — fixed by cloning the wide image and hiding the loose medallions (left
visible, they'd collide with the tiling and look doubled). A third copy sits behind box B's header
row, costing no extra height since it shares that row's space.

⚠ **Higher `Priority` draws on top** (vanilla: Done=250 over a medallion=100 over the rule=0). A
cloned control keeps the donor's priority, which can silently **tie** with a control in its new
z-context — here the wide image's inherited 100 tied with a button's 100 and had to be forced to 1.
**Always re-check priority when cloning into a new parent.**

Geometry is computed once in `layout()` and **asserted** — it refuses a size that can't hold the
columns, the header buttons, or the tallest category, naming which one and which flag to raise.

### 2.2a ⚠⚠ The one property a byte-clone must NOT inherit: `VScrollBar` (fixed 2026-09-10)

The owner reported two things after playing the five-column dialog: *"the mousewheel only works in
some of these columns"* and *"the costs aren't scrolling alongside the names"*. **One defect, three
symptoms**, and it was a single ident in the DFM: `AvailCost2..5` each carried
`VScrollBar = AvailableAbilitiesSB`, copied straight off the donor, so **four of the five Cost lists
pointed at column 0's scrollbar.**

Vanilla hangs the bar off the **Cost** list, never the name list — `AvailableAbilitiesCost.VScrollBar
= AvailableAbilitiesSB`, and the name list has none and is driven by the form's
`AvailableAbilitiesSBChange` handler instead. That asymmetry is deliberate and it is why the bar sits
at the *pair's* right edge rather than inside the names.

In `aowInt.dpl` that one reference drives three separate mechanisms (addresses verified by
disassembling the live `Ziggurat/aowInt.dpl`):

| routine | what it does with `[lb+0x118]` | symptom when it points at the wrong bar |
|---|---|---|
| `TAOWListBox.SetSize` (…`0x59816892`) | **positions, sizes, shows and feeds** the bar: `SetFMin/FMax/FPos/FNum`, `SetLeft(list.left+list.width−bar.width)`, `SetTop`, `SetHeight`, `SetVisible(list.visible)`, priority = list+1, and the `VanishWhenFull` hide | `AvailSB2..5` were never positioned and **never made visible** (their DFM `Visible` is False — vanilla's is too; this path is what shows column 0's). `AvailableAbilitiesSB` was dragged to whichever Cost list ran `SetSize` last |
| `TAOWListBox.Update` `0x59817138` | force-assigns `ListOff := VScrollBar.FPos`, then clamps to `count − NumberVisible` | every scroll of columns 2-5's costs was undone on the next repaint — *"the costs aren't scrolling"* |
| `WheelScroll` case 1 (`build_wheel_aowint.py`) | takes the hovered list's own bar **before** trying the sibling search | a notch over any Cost column scrolled column 0 — *"only works in some columns"* |

**The wheel foundation was correct and needed no change.** The name lists always worked, because
they have no bar and fall through to case 2's geometric sibling search, which finds each column's own
bar (dx = +152 to its own, −30 to the previous column's, and a negative dx is skipped).

**Fix:** `AvailCost{n}.VScrollBar = AvailSB{n}` — one ident per clone. Each column then becomes
structurally identical to vanilla's single column, which is the whole argument for it being right.
`build_dfm()` asserts the wiring **both ways**: every Cost list points at its own bar, and **no name
list owns one** — a name list that did would make `SetSize` drag the bar to `name.left + 126 − 17`,
on top of the Cost column, and inset the name text by 17 px.

⭐ **The general rule: when you clone a DFM component, audit its *ident-typed* properties for
references to the donor's siblings.** Handler names (`OnChange`, `OnClick`, `OnMouseDown`) are
supposed to be shared — that's §2.2's whole trick — and resource idents (`ILFrame`, `AOWFont`,
`PopupMenu`) are globals. A reference to another **control** is the one that must be re-pointed. Here
`VScrollBar` was the only one out of 13 ident properties on the Cost clone; a dump of every
ident-typed property across all clones takes a minute and would have caught it at build time.

**Post-repopulate sync, added at the same time.** `cave_setfmax` now re-clamps each bar and pushes
its position into **both** of that column's lists. Needed because `TAOWScrollBar.SetFMax
@0x5980C9D8` does **not** touch `FPos`, and `TAOWListBox.Update`'s clamp only reaches a list that
owns a bar — so a Remove that shrinks a scrolled column clamps the Cost list and leaves the name list
where it was, putting the two on different rows. The clamp uses the list's own `NumberVisible`
(`+0x11C`, the same bound `Update` uses), not the bar's `FNum`, which is only correct once `SetSize`
has pushed it. `SetFPos` is inlined (write `[bar+0x148]`, clear the dirty byte `[bar+0xA4]`) because
the exe imports `SetFMax` and `SetListOff` but not `SetFPos`, and those two writes are its entire
body. **This latent desync exists in vanilla too** — vanilla's name list has no bar either.

**Needs the user's in-game test** (nobody has played any of this):

1. Level a hero up. The dialog is **960×525, 8 rows per column**; count the rows.
2. Give a column more than 8 offers (an Undead or High Men hero is likeliest). **Each** of the five
   columns that overflows shows **its own** scrollbar, at the right-hand edge of its own Cost list —
   before this fix only column 1's was ever visible.
3. Wheel with the pointer over **each** of the ten lists in turn — five name lists and five Cost
   lists. Every one scrolls **its own** column, and the names and costs move together. Nothing
   should move in a column the pointer is not over.
4. Drag each column's scrollbar thumb: names and costs move together.
5. Add an ability from a column that is scrolled down, then Remove it. After each, the names and
   costs are still on the same rows, and a column that just got shorter than the visible rows has
   scrolled itself back into range rather than showing blanks.
6. Click a Cost header and a name header on each column: only that column re-sorts, and its names
   and costs stay paired.
7. Shrink the game window below 640×480, enlarge it again, reopen the dialog: both boxes render
   correctly (§2.5 — `UpgradePnl` is a clamped panel again at 525).
8. Confirm the per-race offer gate still fires — the offer set should still vary by hero race.

### 2.3 Class surgery — growing a Delphi class with no compiler

- DFM grows 52 987 → 70 540 B (121 components), **relocated to a new RWX section** `.hcol @ VA
  0x612000` (0x1C000). Original bytes stay in `.rsrc` untouched, making `--undo` a pure resource
  repoint.
- Field table rebuilt in `.hcol` (96→120 entries, same class palette) and `[VMT-0x2C]` repointed;
  **instance size `[VMT-0x1C]` grows 480→576.** New fields: `+0x1E0..1EC` `AvailAb2..5`,
  `+0x1F0..1FC` `AvailCost2..5`, `+0x200..20C` `AvailSB2..5`, `+0x210..21C` `AvailSort2..5`,
  `+0x220..22C` `AvailCSort2..5`, `+0x230` `StatePnl`, `+0x234`/`238`/`23C` `BCelt`/`MCeltL`/`MCelt`.
- **Two idempotency traps, both hit and fixed:** `state_of()` doesn't pin the exact instance size,
  only "differs from vanilla" — pinning it broke re-apply the moment the layout gained a control.
  `--apply` doesn't short-circuit on "already the requested size" — a taxonomy change can rewrite the
  DFM at the *same* dimensions, and a size-based short-circuit silently skipped it. Always undo +
  rebuild; idempotent regardless.
- ⚠ **`.hcol` has five other tenants**, the lowest being `build_heroskill_race.py` at
  `0x00628000..0x0062A000`; the rest sit at `0x0062A000`, `0x0062D000`, `0x0062D020`, `0x0062D100`.
  This layout tops out around `0x0062417B` today — headroom, but the end-of-section assert would
  **not** catch a squatter collision, so growth is bounded by `SQUATTER_FLOOR` (now `0x00628000`)
  instead. Check before growing this DFM materially. `add_section()` returns early once `.hcol`
  exists, so an ordinary re-apply doesn't clobber the squatters — only a rebuild after `.hcol` is
  removed entirely would. Canonical list: `12-re-toolchain.md` §6.2.
- ⚠⚠ **`apply_to()` zeroes `[SEC_VA, SQUATTER_FLOOR)` before writing the blob** (added 2026-09-09).
  It did not, and `add_section()` returns early over an existing section, so a blob that ever
  *shrank* left the previous one's tail alive above its new end. **That has already happened twice**:
  the installed `AoWz.exe` carries 15 such bytes — 3 in the DFM's alignment pad at `0x0062338C` and 12
  at `0x00623D64` that disassemble as `push edx ; inc eax ; inc esi ; cmp esi,5 ; jb 0x623D3C`, the
  tail of an older `cave_fill`. Inert today (verified: `3d 00 01 00 00` and `46 ff 4d f0` each occur
  exactly once below the floor), but a remnant that happens to present either pattern makes
  `build_heroskill_race.find_sites()` match twice and abort. The zeroing stops exactly at
  `SQUATTER_FLOOR`; the region below it is this script's alone.
- ⚠⚠ **`--apply` UNLINKS `build_heroskill_race.py`'s hook, and now re-chains it.** That feature's
  gate lives *inside* `cave_fill`, which this script regenerates from source every time; without
  repair it would be silently dropped (the Magebane/Shield failure mode). `relink_racegate()` runs
  between `apply_to()` and `save()` and prints `race-offer gate: re-chained` or `not installed` on
  every run. `--undo` is deliberately not re-chained — the vanilla fill loop leaves that cave inert.
  ⭐⚠ **A failed re-chain now RAISES, so `save()` is never reached** (2026-09-09). It used to print
  `re-chain FAILED` and carry on, writing an exe whose gate was unlinked — the vanilla bytes back at
  `cf_gate` — while the cave, tails and 4 KB table still sat in `.hcol` looking installed. **Loud is
  not the same as safe**: the message scrolls past and the broken file stays. Same rule for a failed
  *import* of `build_heroskill_race.py`: `.hcol` is scanned for the `RGT1` magic, and the run aborts
  if it is there (a gate that exists and cannot be repaired) rather than if it is not.
- Two base relocations (`0x446995`, `0x4469B8`) fall inside the displaced fill loop; set to type 0 on
  apply, restored on undo. **Generalisable: always scan `.reloc` for the ranges you displace in an
  EXE, not only a DLL** — §1.6's spell-logging hook trap is the same rule inside a DPL.
- ⚠ **Never hand-transcribe hook-site bytes.** Five of the first nine sites' hand-written
  expectations were wrong; verify-before-write caught it, but only because expectations were
  regenerated from the binary rather than trusted as typed.

### 2.4 Caves (`.hcol @ 0x623D40..0x624200`, 1216 B)

| cave | replaces | does |
|---|---|---|
| `cave_fill` | `0x446972..0x446A53` (fill loop) | clears all 10 lists, walks ability ids, filters `CanExpand`+`[ability+0x21]&1`, categorises via `[ability+0xC]`, adds name (ability id as item object) + cost |
| `cave_setfmax` | `0x446BB2..0x446BD1` | `SetFMax` on all five scrollbars, then re-clamp each bar's `FPos` to `count − NumberVisible` and `SetListOff` **both** lists of the column to it (the post-repopulate name/cost sync, §2.2a); finally drop a `Selected` the refill pushed out of range (§2.4a) |
| `cave_sortone`/`cave_sortall` | `sub_4468A0` | sort one column / loop all five (refill only) |
| `cave_sortclick_name`/`_cost` | the two vanilla sort-click handlers | identify column from Sender, toggle only that column's mode, re-sort it |
| `cave_change` | list `OnChange` | identifies column from Sender, mirrors index to its cost list, clears the other four |
| `cave_sbchange` | scrollbar `OnChange` | identifies column from Sender, `SetListOff` |
| `cave_activelist` | `mov esi,[ebx+0x80]` | returns the column whose `Selected` is not −1, **derived by scanning, never cached** (§2.4a) |

Plus two 6-byte edits in `AvailableAbilitiesMouseDown` (use Sender directly for the info popup). The
cave data area holds the 256-byte category table, per-column offset tables, the sort-function table,
`activecol`, and a `calltmp` slot to stage virtual-call targets (`GetName`/`AddObject` fill
EAX/EDX/ECX, leaving nowhere else for the vtable pointer) — why the section is RWX. Cross-cave calls
make the assembler two-pass (placeholder targets, then real VAs — converges since `call rel32` is
always 5 B). No recursion risk from `cave_change`: `SetIndex` does not raise `OnChange`.

**Column sorting shipped two bugs, both found in play:** (1) the sort mode is 0..3 not 1..4 — read
off the vanilla click handlers (0↔1 name, 2↔3 cost), not the dispatch's `sub edx,1;jb`, whose `jb`
arm *is* mode 0; compensating for that imaginary offset put every mode one step out of phase. (2) a
shared mode field sorted every column at once — with five independent columns the mode must be
**per column**, resolved purely from Sender in EDX. The click caves also reproduce vanilla's click
sound call — dropping it would silently lose audio feedback.

### 2.4a ⚠⚠ Never cache which column a button acts on — 🔨 APPLIED, UNTESTED (2026-09-10)

**Symptoms, both reported in play, both from one cause:** "adding more than one level of a
multilevel ability no longer works" and "after an Add and a Remove, Add won't re-add it until I
deselect, select something else and reselect". Neither is a scrollbar bug.

`AddAbilityBtnClick @0x004470D0` decides what to add from **one number** in **one list**:

```
004470E3  call cave_activelist       -> esi = a column's name list
004470E9  mov  edi,[esi+0x120]       -> that list's published `Selected`
004470EF  cmp  edi,-1 / je 0x44712E  -> -1 means "do nothing"
```

`cave_activelist` used to answer from a cached `activecol`, and `cave_fill` — the head of
`PopulateLists @0x446954`, which Add **and** Remove both call — reset that cache to 0 on every
repopulate. The refill clears each list's **Strings**, never the listbox, so `Selected` survives:
after any Add the only real selection is still in column *c* while the cache says column 0.

**Why re-clicking could not repair it, which is what made a wrong button look like a dead one.**
`TAOWListBox.CheckMouseDown @0x598171C4` fires `OnChange` only when the clicked row *differs* from
`Selected`:

```
59817300  cmp ebx,[esi+0x120]
59817306  je  -> no OnChange        (ebx = row + ListOff[+0x15C])
```

Clicking the row that is already highlighted is a no-op, so `cave_change` never ran and the cache
stayed on column 0 — whose `Selected` is −1, because `cave_change` had cleared it. Only a click that
*changed* a selection rebuilt it, which is exactly the deselect/reselect ritual the owner found.

Multi-level abilities are the sharp case. `TMultiLevelAbility.CanExpand @0x55765308` keeps the row
listed while `level < [ability+0x28]`, so the **only** route from Vision II to Vision III is a second
Add against a row the hero already partly owns — precisely the Add that read the wrong column. Base
`TAbility.CanExpand` rejects anything already owned, so single-level abilities leave the list anyway
and merely felt awkward. One cause, two severities.

**The fix, and the rule: derive the active column, do not cache it.** `cave_activelist` now scans the
five name lists for the one whose `Selected ≠ −1`, falling back to column 0 (whose −1 then stops the
handler at its own `cmp edi,-1`). That is exact by construction — the pristine DFM ships every list
`Selected = -1`, `cave_change` clears the four it did not land on, and a repopulate leaves the field
alone — and it needs no `OnChange` to have fired, so the CheckMouseDown latch stops mattering at all.
`cave_fill`'s reset is deleted. `cave_setfmax` gained a companion guard: if a refill shrank a column
past its selected row, both of that column's lists go to −1, because `AddAbilityBtnClick` feeds the
index straight to `Strings.Objects[]` with no exception frame of its own.

**Field facts** (`aowInt.dpl`, verified 2026-09-10):

| field | is | proof |
|---|---|---|
| `TAOWListBox` `+0x120` | published `Selected` | RTTI record, GetProc `FF000120` (direct field), SetProc `0x598168B8` = `SetIndex` |
| `TAOWListBox` `+0x15C` | `ListOff`, the scroll offset | `SetListOff @0x598168F4` writes only this; floors at 0, so it can never hold −1 |
| `TAOWControl` `+0xA4` | repaint flag | set to 0 by `SetIndex`, `SetListOff` and `TAOWListBox.Update` after each changes its own field; carries **no** selection state |

**Two suspects cleared, both by measurement rather than argument** — worth repeating because both
looked far more likely than the real cause:

* **`cave_setfmax`'s scroll sync, added the same day, is innocent and was kept.** It writes

### 2.5 The dialog resize clamp — generalises to every oversized AoW dialog

**Applied 2026-08-08, 🔨 UNTESTED in play.** Shrink the game window, enlarge it again: the dialog comes
back mangled — outer frame gone, box A sitting *inside* box B — permanently.

Measured live (`re_tools/dlg_geom.py --tree`) at the then-current 860 px height: `Dlg` 960×860 →

**The rule: any axis that overflows the parent resets to offset 0 and the parent's full extent; an
axis that still fits is left alone** — why box A ends up *inside* box B rather than clipped (its
bottom still fit in 432, so Top/Height survived). `640×432` is the window manager's client area at
640×480 minimum resolution, less the 48px toolbar strip (`mgr+0x120`) — not a vanilla size. The clamp
writes rects **in place**, permanently for the session.

⚠ **Not `ReAlign`** (`0x598030FC`) — `Dlg` is `awCenter/ahCenter`, the boxes `awLeft/ahTop` with zero
percentages, so `ReAlign` only rewrites Left/Top and would have restored `Left`; it reads 0. Some
other pass writes the sizes; not worth hunting further — almost certainly what keeps the blitter
inside its surface (§1.7 already paid for one out-of-bounds hunt).

**Fix: self-heal on open.** `cave_geom` runs from the head of `cave_fill` (every `FillLists`) and
rewrites `Dlg`/`UpgradePnl`/`StatePnl`'s rects from a `{offset, W, H, Left, Top}` table generated by
`layout()` itself, so `--width`/`--height` can never drift from the heal. Then zeroes `+0x2d`
(aligned)/`+0x2e` (sized) on each panel and `+0x2d` on children — the "re-lay-me-out" signal. Field
offsets: `Dlg +0x44`, `UpgradePnl +0x74`, `StatePnl +0x230`. `Dlg`'s own Left/Top are −1 ("leave
alone" — it's centred, `ReAlign` owns its origin).

**Generalises to every oversized AoW dialog**: any window bigger than the manager's 640×480 client is
flattened the same way, permanently, the first time the game window shrinks that far. **Any patch
enlarging a dialog should carry a heal like this one** — no way found to disable the clamp itself.

- A DFM **cannot grow in place** (the next resource starts one byte later). Here, 8 values needed

  properties** (`Left`/`Top`/`Height`/`Width`, −33 B) — deleting a property is always safe (readers
  keep defaults for absent ones; it's *unknown* properties that raise `EReadError`). Net −25 B,
  zero-padded past the root terminator. **Every exe-form root carries ~30 free bytes this way.**
- **State recognition without a backup layer**: pristine slot by SHA1; a patched slot (any height) by
  *inverse-transforming* it (restore the four deleted properties + the sixteen vanilla values) and
  SHA1-checking the result. Re-tune = `untransform → transform(N)` from any state, no backup touched
  — the pattern the columns script's own re-tune inherited.
- **AOW alignment semantics**: `ahTop`/`ahBottom` = edge pinned, size fixed; `ahBoth` = both edges
  pinned, size derived; `ahCenter` = centred. Patch both the stored value **and** the anchor offset
  so either runtime semantic agrees. `VanishWhenFull=True` scrollbars auto-hide when a list fits;
  linkage is code-side.

percentage — so moving a rung again needs no CSS edit. Four steps on the page's own accent green

|---|---|---|---|---|

already on screen and never the only carrier. The calibration table's four count rows carry the

⚠ `:root` now declares **`color-scheme:light`**. The palette is parchment-light throughout with no
dark variant, and a dark-themed WebView2 repaints unstyled form controls grey — which would erase

### 2.9 The build cache — an unchanged Manual opens in 0.43 s (2026-09-10)

Opening the Manual to **read** it used to cost a full rebuild: 7.5 s of re-deriving 189 units,
116 passives, 108 spells and 178 portraits from `Release/*.pfs`, `AoWEPACK.dpl` and the workbook,
producing a byte-identical 2.5 MB page. Measured now: **cold (something changed) 8.3 s, warm
(nothing changed) 0.43 s** — of which ~0.32 s is importing openpyxl and ~0.06 s is the check
itself.

⚠⚠ **This re-introduces the 2026-08-14 staleness hazard, and "the exe always rebuilds so it cannot
be stale" was the reason the old design was what it was.** The cache is therefore built to be
airtight rather than fast, and the rules below are the feature:

- **Content hashes, never mtimes.** A copy, a restore or a checkout rewrites mtime without moving
  a byte — and worse, can leave old bytes carrying a new mtime. `touch`ing an input is verified to
  still be a cache HIT; changing one byte of it is verified to rebuild.
- **Any doubt rebuilds.** No sidecar, unparseable sidecar, `v` mismatch, a recorded input tag that
  will not resolve to a path, a file that exists but will not read, a missing / truncated /
  one-byte-altered HTML — every one of those was tested and every one rebuilds. The cache may only
  say "skip" from a complete positive match.
- **Inputs = the declared floor ∪ what the last build actually opened.** The floor (`_cache_floor`)
  is everything whose *content decides what else gets read*: this script, every `re_tools/*.py`,
  `heroskill_races.py/.json`, `herodlg_cats.py`, the workbook, `AoWEPACK.dpl` **and** the pristine
  copy, `Release/*.pfs`, `User/*.ail`, `Release - Vanilla/*.pfs`, `Images/FACES/*.ILB`,
  `SpellIcn.ILB`, `GenericI.ILB`, `spell_names.json`, `face_offset.json`, `manual_text.json`. 107
  files, 17.4 MB, ~37 ms to hash. The trace comes from the `builtins.open` spy that already fed
  `--watch`; it is what lets the five face ILBs a build reads be watched without hashing all 630
  under `Images/` (75 MB).
- **Files that may legitimately be absent hash as `absent`**, so *creating* one is a change.
  `manual_text.json`, `heroskill_races.json` and `face_offset.json` are all in that class.
- **The sidecar stores root-relative tags, never absolute paths** — `game/release/ability.pfs`,
  `shop/re_tools/pfs.py`. It sits in the game tree, so absolute paths would carry the author's
  profile directory into anything shipped (project rule), *and* the frozen exe's `_MEIPASS`
  changes on every single launch, which would miss on every run.
- **The mid-build race is closed.** Digests are taken before *and* after the build; if an input
  moved while the build was running the page holds the old bytes, so nothing is cached and the
  next run rebuilds. Hashing only afterwards would record the new digest against a page built from
  the old data — a cache entry stale the moment it is written.
- **Warnings survive a skip.** They are this project's test suite, so they go into the sidecar and
  a cached run reprints them tagged `(cached)`.
- **The page stamps its own key** in `<meta name="zm-build">`, and no build date — a date would
  make two builds of the same data differ and destroy the byte-identity check. `--force` rebuilds
  unconditionally; `--watch` passes `--force` to every child, because a cached child writes no
  trace file and the watch set would silently shrink to the floor.

⚠ **The old claim that the six-pass dash normaliser was the build's cost is wrong** — it is out by
three orders of magnitude. Measured 2026-09-10: **2.9 ms** over the finished 2.5 MB page, and
**9.4 ms** on a 2.6 MB page seeded with 26,437 real dash occurrences, which is far more than the
page ever carries. The real cold cost, by cProfile, is `bytes.find` scanning `AoWEPACK.dpl` for
VMTs (**3.3 s** over 6390 calls, via `aowsyms._vmts` / `enchant_mods.all_vmts`), openpyxl parsing
the workbook (~3.2 s) and decoding 178 unit portraits (~1.5 s).

Two single-pass replacements were written and verified byte-identical on that seeded page, then
**both discarded**: `str.translate` + 3 replaces is **43 ms**, four times *slower*, because it
rebuilds the whole string unconditionally where `str.replace` returns early on a miss; one
compiled alternation ties at 9.3 ms. Neither is worth a behaviour risk for 0.1 ms. Do not revisit.

## 3. Unit-window party arrows — 🔨 APPLIED, UNTESTED (2026-09-03)

`TUnitWindow`'s prev/next arrows cycle the displayed unit's stack, but only appeared from the party
side window — not the events-window portrait or the items-found pickup dialog. Ported from a
third-party drop (Inioch share6), every address re-verified on this project's own `AoWz.exe`, three
deviations from the source, one fixing a real regression it had.

**Root cause.** All 15 entry paths funnel through `UpdateUnitWindow @0x00407DB8`, whose arrow
decision (`0x00407E52..0x00407EAC`) **hides** if: tactical combat is active; no army is selected on
the map (`[G+0xA4]==nil`); the displayed unit isn't in that army (`PartyIndexOfUnit<0`); or the
selected army has under two visible units. `G=[[0x0045A420]]=0x0045B2C0` (`TGeneral`).
**`TMapEvents.TheMapArmySelected @0x0044EC30` is the sole writer** of those party-slot fields — they
describe the army **selected on the map**, not the unit being displayed. The events-portrait and
item-pickup paths only set the displayed unit and refresh, so if no army (or the wrong one) is
selected on the map, arrows correctly hide per vanilla's own logic — nothing wrong with those
callers. ⚠ Never repurpose those fields to fake a selection: `Unit1FrameMouseDown` reads the same
array to map a control-bar frame to a unit.

**The fix — drive the arrows from the unit's own army.** `army:=[unit+4]` (`TEObject.Owner`), guarded
by a Delphi-3 VMT-header walk for `"TArmy"` (name at `[vmt-0x20]`, self-ptr at `[vmt-0x40]` as a
validity guard, parent via `[vmt-0x18]`). The exe imports `TArmy` methods but no `TArmy` classref, so
the walk needs no new import.

⭐ **`[vmt-0x18]` needs a double dereference — the bug fixed from the ported version.** Measured:
`[0x557130EC-0x18]=0x55710E88`, and `[0x55710E88]=0x55710EC8` (the `TUnitList` VMT). A single deref
makes the walk match only the exact class, and AoWEPACK has **three** `TArmy` descendants
(`TArmyView@0x55713210`, `TDefendersArmy@0x557C12B4`, `TPrisonersArmy@0x557C53F4`) that would
silently get no arrows under it. Two smaller deviations: engine accessors throughout instead of raw
field reads (count via VMT `+0x54`, members via exe thunk `0x004026C4`, concealment via VMT `+0xB8`);
and every handler is **vanilla-first** — asks `PartyIndexOfUnit` before anything else, falling
through to the own-army path only when vanilla's chain would have done nothing, so the party-window
path runs completely unmodified code and can never regress.

⚠⚠ **There is no ownership gate, and there must not be one.** `TheMapArmySelected` has no ownership
test, so clicking an **enemy or independent** stack fills the party slots and vanilla shows working
arrows for it. The ported source *did* gate on "unit's player == local player", producing
arrows-visible-but-clicks-dead on any non-owned stack — deliberately not reproduced. **General
lesson: when replacing a handler, the reachability of the code being replaced is a superset of the
cases a new gate imagines — enumerate who populates the state before inventing a safety condition it
never had.**

**Patch sites** (reloc-free, byte-identical across `AoWz.exe`, `AoWzCompat.exe`, and the pristine
2025-03-21 reference):

| site | steals | → |
|---|---|---|
| `0x00407EAD` (hide block) | 8 B `8B 06 8B 80 14 02 00 00` | `E9 rel32 + 90 90 90` |
| `0x0040ABF0` (`PPrevClick`) | 5 B `53 56 8B F0 A1` | `E9 rel32` |
| `0x0040AC9C` (`PNextClick`) | 5 B `53 56 8B F0 A1` | `E9 rel32` |

Both click handlers' resume points are instruction boundaries, asserted against the pristine exe; a
code-wide scan confirms nothing branches into the stolen bytes besides the hide block's four known
chain-exit jumps.

**Cave — new PE section `.pyar`**, VA `0x0062F000`, size `0x1000`, characteristics `0x60000020`
(code/exec/read, **no write** — no mutable state). Sections 11→12, `SizeOfImage 0x22F000→0x230000`.
Body 653 B: a 3-slot jump table, then `_armyof`/`_viscount`/`_vis`/`_prev`/`_next`/`_stepwork`.

⚠ **The method table is deliberately NOT repointed** — `PPrevClick`/`PNextClick` entries still hold
`0x0040ABF0`/`0x0040AC9C`; only the bodies moved. `build_wheel_ext.py` (§4) identifies the arrow
buttons by comparing `OnClick` against exactly those addresses, so patching bodies (not the table)
keeps the wheel extension working — repointing the table would have broken it silently.

**Section-append rules this depends on**: `SizeOfImage` must be recomputed as `align_up(max over ALL
sections of rva+max(vsize,rsize))`, never from just the new section, or a later section can be
under-counted and unmapped. Re-apply overwrites `.pyar` in place when the body still fits; rebuilding
from scratch would destroy anything appended after it. `--undo` leaves the header inert rather than
truncating (removing it would renumber sections and could unmap another feature's cave). If another
feature appends a section first, `ensure_section` refuses with an actionable message rather than
silently colliding.

**Lockstep**: both exes patched identically; asserts the one-byte build-number difference at
`0x3BB7C` survives.

**Needs the user's in-game test:** arrows appear and cycle from the events-window portrait and the
items-found dialog; the party side window is unchanged; arrows **work** on an enemy and an
independent stack (the regression this port avoids); a concealed-unit stack cycles only visible
units, one visible unit shows none; site defenders/prisoners get arrows if reachable; the mouse-wheel
unit preview over the arrow buttons (§4) still works.

## 4. Mouse-wheel scrolling — spans four binaries

**🔨 APPLIED, UNTESTED (QA pass 2026-09-02).** One source doc for this feature carried a header
reading "SPEC … NOT BUILT" while its body was a full "AS BUILT — QA" record with measured addresses;
the body is current — the scripts exist, apply cleanly, and round-trip `--undo` — but **none of it
has been played**. In-game rendering (`aowInt.dpl` + `vcl30.dpl`) is patched separately from the
editor's Win32 scrollbars (`vcl30.dpl`, a different hook) and from two optional extensions
(`aowInt.dpl`) — four deliverables across two binaries, apply order matters, and the design exists
because two simpler approaches don't work.

### 4.1 DO NOT TRY (recorded failures)

1. **`WH_MOUSE` thread hook at `TApplication.Run`, for in-game delivery.** Never fires — the game
   receives **zero `WM_MOUSEWHEEL`**, confirmed with a live MessageBox diagnostic, because its render
   window is never the focused window. No queue/`WndProc`/thread-hook design can see the wheel
   in-game; only `WH_MOUSE_LL` does.
2. **Owning `WH_MOUSE_LL` on the game's own render thread.** ~1000 callbacks/s from a gaming mouse
   cost visible frame rate and ghosted the cursor; install-only-while-hovering mitigated but didn't
   fix it. A dedicated owner thread is the actual fix.
3. **Driving a parallel-list listbox directly.** The level-up *name* lists (§2) have no scrollbar of
   their own; scrolling the hovered list leaves the cost column and thumb behind. Drive the
   **governing sibling** `TAOWVScrollBar` instead.
   ⚠ **The sibling search is case 2 — case 1 runs first and takes the list's own `[lb+0x118]`
   without checking that it is the right bar.** That is not a wheel bug and cannot be fixed in the
   wheel: whatever owns the DFM must wire each list to the correct bar. The level-up dialog did not,
   for four of its five Cost lists, and the wheel faithfully scrolled the wrong column until
   2026-09-10 (§2.2a).
4. **Gating the pump on a signature byte of the helper's prologue.** Silently stopped scrolling the
   moment that prologue changed for an unrelated reason. Replaced by an explicit, versioned contract
   header (§4.2).
5. **Absolute IAT references inside a `.dpl` cave** (`ff 15 <abs>`). A rebased `vcl30.dpl` would
   crash instantly. Every `.dpl` cave here uses the `call $+5; pop; sub reg,<VA>` delta idiom.

### 4.2 Architecture

`aowInt.dpl` (`build_wheel_aowint.py`) owns hover tracking and the scroll action; `vcl30.dpl`
(`build_wheel_vclpump.py`) owns delivery via a dedicated `WH_MOUSE_LL` owner thread — the only hook
type the game process sees the wheel through. They share a **contract header** in aowInt CODE at
`0x59824000` (32 B, the only aowInt address vcl30 hard-codes):

```
+00 dd 0x48575A41   magic "AZWH"        +08 dd 0x0003E040  latch block RVA
+04 dd 0x00010000   version (major hi)  +0C dd 8           latch count
+10 dd 0x00024200   helper slot 0 = WheelScroll   +14/18/1C  slots 1-3 (extensions, else 0)
```

Helper ABI: `stdcall(delta)`, `ret 4`, `eax=1` handled, preserves ebx/esi/edi/ebp; runs on the game
thread inside `ProcessMessage`. Bad magic/version → the pump never creates the owner thread and never
calls anything — a changed helper prologue can no longer silently break delivery (fixes DO-NOT-TRY
item 4).

**Latch block** (aowInt DATA slack `0x5983E040`, 8 dwords, cleared every mouse-move sweep by G3):
`[0]` hovered listbox/memo, `[1]`/`[2]` leader-setup portrait hover, `[3..6]` extensions, `[7]` spare.

**Gates:** **G1** lazy thread creation — the owner thread spins up only the first time the header is
valid *and* any latch is non-zero. **G2** LL-proc arming, in order: `nCode==0`,
`wParam==WM_MOUSEWHEEL`, header valid, any latch non-zero,
`GetWindowThreadProcessId(GetForegroundWindow())` matches this process, and
`GetWindowThreadProcessId(WindowFromPoint(GetCursorPos()))` also matches — only then is the event
queued and swallowed, else `CallNextHookEx` (another app's wheel is never swallowed). Uses
`GetCursorPos` (logical pixels, what a DPI-unaware process sees), not `MSLLHOOKSTRUCT.pt` (physical)
— mixing the two breaks at any scaling ≠100%. **G3** the CLR hook zeroes the whole latch block at the
start of every move sweep. **G4** (not built) — would zero latches on `WM_ACTIVATEAPP` if in-game
testing shows stale-latch scrolling.

**Pump drain**: the LL proc posts a raw delta into `G_PENDING` and wakes the game thread
(`PostMessageA(G_HWND, WM_NULL)`); the pump converts whole notches (`n=G_PENDING/120` toward zero,
`|n|<=8`) and calls the header's helper slots once per notch — avoiding over-scroll on touchpads that
post many sub-120 deltas. `G_HWND` refreshes from every non-zero `msg.hwnd` seen, not captured once
(else the wake-up silently breaks the moment that window is destroyed).

## 5. City flagpole bauble lag — ✅ CONFIRMED WORKING (2026-08-29)

**Symptom.** The flagpole's golden spheres show the *old* upgrade level after an upgrade completes —
verified a **vanilla** defect (every function involved is byte-identical to the pristine reference
DLL), not a Ziggurat regression.

**One-line cause.** The upgrade-completion path bumps the city's level but never recomputes the
cached flag id; Fortify calls the refresh, Upgrade doesn't.

**Data path.** `TCity+0x54` = cached flag id (bits 0–4 race, bit 5 `0x20` independent, bits 6–7 =
`upgradeLevel−1` = the bauble count, `0x3F` = draw nothing). `TCity+0x4D` = the real, saved level
(ReadWrite id `0x10`). Sole producer: `TCity.UpdateFlagID @0x557AC8B0` (VMT `+0x1FC`). Sole consumer:
`TCity.Show @0x557ACA88` → `TFlagControl.ShowStructureFlag @0x5575A34C` →
`ImageLib.Get(lib, flagID>>6)`. `TCity.UpdateImages @0x557AC494` ends with `call [vmt+0x1FC]`, so
calling it always refreshes the flag — one cache, one path to correct it. (One-hex cities go through
`ShowFlag` instead, hard-coded to pole image 4 regardless of level — structurally immune, hence
invisible there.)

**Two paths change `+0x4D` without calling the producer.** Primary:
`TCityProductionControl.NewTurn @0x557A82A8`, case 2 (Upgrade, `0x557A8346`) calls
`SetUpgradeLevel @0x557AC75C` (writes `+0x4D`, rebuilds production — nothing else) then only does
relation bumps/event log/`EndUpdate` — no `UpdateImages` call anywhere in the case. Case 3 (Fortify),
same function, *does* call `UpdateImages` ten instructions later — the missing call, and why new
walls appear instantly but baubles don't. Secondary, rarer: `TCity.BuildingDone @0x557A97D8`
(rebuilding a razed city) writes `+0x4D=1`/`+0x4C=0` directly and calls `SetRace`, which **early-outs**
if the race is unchanged — a rebuild with a builder of the city's existing race skips `UpdateImages`
entirely, so a rebuilt level-1 city can keep its old, higher bauble count.

**Why it looked intermittent.** `+0x54` is **not saved** (`ReadWrite@0x557ACBCC` persists `+0x44/45/
48/4C/4D/50/58/74`, not `+0x54`), so `Activate`→`UpdateImages` rebuilds it correctly on every map
load — save/reload always "fixed" it. In-session it also happens to catch up on owner change,
migration, terrain change, raze, or the contested bit toggling — none correlating with upgrading,
hence the apparent randomness.

**The fix — retarget the call, no instruction displacement.** Each site is an existing 5-byte
`call rel32`; only the 4-byte rel32 changes, repointed at a thunk that performs the original call and
then refreshes the images. Cave `0x55819000`, 0x40 B reserved, 45 used:

| site | original callee | thunk does |
|---|---|---|
| `0x557A8354` (upgrade completes) | `SetUpgradeLevel` | `push eax / call SetUpgradeLevel / pop eax / call UpdateImages / ret` |
| `0x557A980B` (razed city rebuilt) | `TPlayerStructure.BuildingDone` | `push eax / call BuildingDone / pop eax / call UpdateImages / ret` |

Both callees are Delphi `register` procedures, Self in EAX, no stack args, plain `ret` — the
push/pop is balanced and `UpdateImages` needs only EAX. At site 2, `UpdateImages` runs *after* the
inherited `BuildingDone`, so `UpdatePlayer` has already settled the contested bit before the flag is
recomputed — ordering that falls out for free from wrapping rather than duplicating. No `.reloc`
entry falls inside either rel32 or the cave. Verified: `--undo` round-trip is **0 bytes different**
from pre-apply, both sites end up byte-equal to `AoWEPACK_original_backup.dpl`.

**⭐ Reusable idiom: wrapper-thunk on an existing `call rel32`, not an `E9` displacement hook.** Worth
reaching for whenever the fix shape is "this call site should also do X":

```
cave:  push eax / call <original target> / pop eax / call <the addition> / ret
```

Buys: a 4-byte footprint (just the rel32), **nothing displaced** (no prologue to replay, no
resume-address hazard), PIC for free, no `.reloc` exposure (a `call rel32` is never relocated — scan
anyway), and `--undo` = "write the old rel32 back, zero the cave". Preconditions: the callee takes
arguments in registers and ends in a plain `ret` (a `ret imm16` would eat the pushed slot — check the
tail), and the fix owns the **call site**, not the callee, so every other caller stays untouched —
usually exactly the point.

⭐ **The diagnostic shape that led here, also reusable**: a UI value that "sometimes lags" is usually
a **cached field with exactly one producer**, missing from exactly one state-change path. Find the
consumer, find the producer, enumerate the producer's callers — the missing path falls out. The tell
for *why* it read as intermittent: the cache wasn't in `ReadWrite`, so a map load silently
recomputed it, hiding the bug from anyone who saved and reloaded to check.

## 6. Strategic-map cursor dead zone — ✅ CONFIRMED WORKING (2026-07-06)

**Symptom.** On a small map (~64 hexes + 6-hex padding/side, ≈74–76 wide) in a window **wider than
the map**, the cursor stops updating per-hex and clicks stop registering over a growing strip on the
right, though terrain there renders correctly. Large maps (≥ the viewport) never show it.

**Root cause.** A map smaller than the viewport is centred via a negative scroll origin
(`[map+0x80]`/`[+0x84]=−leftMargin`). `HSEngine.THSMapMouse.Move @0x5560B8F8` (HSEPack.dpl) rejects
on `viewport-x > GetMaxXhp` (`0x5560C3EC` = the map's own pixel width, ignoring the centring offset)
and stores the invalid sentinel `0x80000000` — pre-empting the otherwise-correct, world-based
accessors `GetXhx`/`GetYhx`/`GetXhp`/`GetYhp` (all compute `world=scroll+mouse` and reject only on
real bounds). So the map's right portion — real, in-bounds hexes — is wrongly killed before the
accessors ever see it. Dead-strip width = `(viewport−map)/2`.

**Fix.** Neuter only `Move`'s two upper-bound rejections so it stores the real mouse whenever
`x,y>=0`; the accessors then validate correctly on their own, symmetric with the map's already-working
left side. Lower-bound checks (`x>=0`/`y>=0`) stay intact.

```
@ 0x5560B917  7F 14 (jg, x>GetMaxXhp) -> 90 90
@ 0x5560B923  7F 08 (jg, y>GetMaxYhp) -> 90 90
```

4 bytes, in place, position-independent (`HSEPack.dpl` rebases). Also fixes the editor, which loads
`HSEPack.dpl` too.

⚠ **`build_mapcursor_fix.py --revert` is NOT surgical** — a whole-file copy from `.pre-mapcursor`,
no longer the newest `HSEPack.dpl` layer (a later render-gate performance fix sits above it), so
running it would silently destroy that unrelated feature. Revert surgically instead: write the two
original words back by hand (`7F 14` @`0x5560B917`, `7F 08` @`0x5560B923`). **A script flag reading
"revert" is not evidence the revert is safe** — read the implementation before trusting any
`--revert`/`--undo` in this project.

**Reusable:** the map-cursor coordinate flows `AoWEPACK.dpl` (`TAoWHSMap.MouseMoved`) → `HSEPack.dpl`
(`THSMapMouse`) — validity is decided **inside HSEPack**, in world coordinates, not in the display
layer (`DCPACK.dpl`) that renders the surface. A plausible-looking display-layer bounds check can be
entirely the wrong layer even when it looks like it explains the symptom (see Failed approaches).

## 7. Face ILBs — the `_` prefix is AoW1's HALF-RESOLUTION set — 🔨 APPLIED, UNTESTED (2026-09-04)

### 7.1 The rule, because it reads exactly like damage

**Every image library ships as a pair: `Images/<NAME>.ILB` at full size and `Images/_<NAME>.ILB` at
exactly half.** The engine picks one by screen resolution. Measured over the whole `Images/` tree:
**86 pairs, 85 parse, and all 85 are exact half-size** — `_Combat` 13×1 vs `Combat` 25×2, `_City1`
28×32 vs 56×63, `_SpellIcn` 20×18 vs 40×35, faces 52×64 vs 103×128. Halving is ceil-per-axis
(103 → 52).

⚠ **A `_` file whose images are half the size of its twin is CORRECT.** Opening `_H_Faces.ILB`
alone shows 67 portraits at 52×64 next to a "pristine" 103×128 copy, and reads as an accident that
halved them. It is not. Restoring the `_` set to full size would destroy the low-resolution artwork
for all five face files. Check the twin, and check the tree-wide pair scan, before believing any
"these got halved" story:

```bash
python - <<'PY'
import sys, os; sys.path.insert(0, "Modding Resources/re_tools"); import ilb
for root,_,fs in os.walk("Images"):
    for fn in fs:
        if not fn.lower().endswith(".ilb") or fn.startswith("_"): continue
        lo = os.path.join(root, "_"+fn)
        if not os.path.exists(lo): continue
        try:
            H = {i["id"]:(i["w"],i["h"]) for i in ilb.parse(open(os.path.join(root,fn),"rb").read())["images"]}
            L = ilb.parse(open(lo,"rb").read())["images"]
        except Exception: continue
        bad = [i["id"] for i in L if i["id"] in H and (i["w"],i["h"]) != tuple((v+1)//2 for v in H[i["id"]])]
        if bad: print(fn, "MISMATCH", bad[:6])
PY
```

### 7.2 The actual defect — the mirror image of the reported one

### 7.3 ILB v4.0 splice — the format facts the writer relies on

28-byte header, then the directory, then **contiguous** pixel data with no slack and no gaps. Header
dwords at 16/20 are `imgdir` (absolute data start) and `filelen`. **Image `offset` is relative to
`imgdir`, so inserting directory entries and bumping `imgdir` keeps every existing image valid** —
the same property `build_copper_medal.py` splices on. The directory ends with a lone `-1` dword.

Every face entry is type 16 (Picture16), `info` 3, non-composite, raw RGB565 with `size == w*h*2`.
Field offsets from `dir_off`, with `N = len(name)`:

```
0 id | 4 type | 8 info(u8) | 9 nlen | 13 name[N]
13+N    w, h, xsh, ysh, subid      (5 dwords)
13+N+20 unknownA (u8)
13+N+21 size | +25 offset | +29 totw | +33 toth
13+N+37 drawmode | +41 blend | +45 pixfmt | +49 trailer(-1)
entry length = 13+N+53
```

⭐ **The writer re-derives every one of those fields with `ilb.parse()` and aborts on the first
disagreement**, on every entry it touches, before it writes a byte — so a format surprise stops the
run instead of corrupting an ILB. Reuse that guard for any future ILB splice.

### 7.4 Undo needs no snapshot

After `--apply` the full-size pixels for ids 396–407 live in `H_Faces.ILB`, so `--undo` copies them
back into `_H_Faces.ILB` and strips the 12 entries from `H_Faces.ILB`. Round-tripped 2026-09-04:
both files came back **byte-identical** to their pre-apply state. Re-apply is deterministic (the
Lanczos downscale reproduces byte-for-byte), and `--apply` on an applied install is a no-op.
A `.pre-faces_hires` snapshot is still minted in `<game dir>\backups\`.

## 8. Taskbar button icon — 🔨 APPLIED, UNTESTED (2026-09-13)

Owner: `build_taskbar_icon.py`. Targets `AoWz.exe`, `AoWzCompat.exe`, `AoWDevEd.exe`; the live editor
`AoWzEd.exe` comes from `build_zigeditor.py --apply` afterwards, which is **mandatory** — the patch
verifies clean against `AoWDevEd.exe` whether or not the derive was run.

### 8.1 The defect — `ICON_BIG` was already correct; `ICON_SMALL` was 0

Win11 drew the grey placeholder on the taskbar button. The icon *resource* was never the problem:
`MAINICON` (RT_GROUP_ICON, length-prefixed UTF-16 name) is present in all four exes and `LoadIconA`
finds it. The button belongs to Delphi 3's hidden owner window, class `TApplication`. Measured live
on that window **before** the patch (`AoWzEd.exe`, hwnd `0xA0594`, ctypes probe):

| query | result |
|---|---|
| `GCL_HICON` | 0 |
| `GCL_HICONSM` | 0 |
| `WM_GETICON ICON_SMALL` | 0 |
| `WM_GETICON ICON_BIG` | a real HICON — 32×32 32bpp, 664 opaque px, md5 `a7d4500a…`, **byte-identical to `MAINICON` RT_ICON id 1 in the exe** |
| `WM_GETICON ICON_SMALL2` | a real HICON — 16×16, 189 opaque px, a downscale of the same image |

So `ICON_BIG` was already set and already `MAINICON`. **`Forms.TApplication.CreateHandle
@0x4133ACB0` is what sets it.** At `0x4133ADB6` it tests `Controls.NewStyleControls`
(`mov eax,[0x413E2504]` → BSS flag `0x413E3738`; `cmp byte ptr [eax],0`; `je` past), and when true
runs `0x4133ADC0..0x4133ADD3`:

```
4133ADC0  mov  eax,ebx
4133ADC2  call 0x4133B754        ; the TApplication icon handle
4133ADC7  push eax               ; lParam = hIcon
4133ADC8  push 1                 ; wParam = ICON_BIG
4133ADCA  push 0x80              ; WM_SETICON
4133ADCF  mov  eax,[ebx+0x24]    ; hWnd = FHandle -- the OWNER WINDOW, not a form
4133ADD2  push eax
4133ADD3  call user32!SendMessageA
```

It targets `[ebx+0x24]`, the same window this feature's cave targets. That flag is evidently true at
runtime, since the probe found the icon set.

**What is missing is `ICON_SMALL`.** vcl30.dpl has 14 `push 0x80` sites in CODE; the three inside
`TApplication` all push wParam **1**, never 0:

| send | host | lParam |
|---|---|---|
| `0x4133ADCA` | `CreateHandle @0x4133ACB0` | the icon handle |
| `0x4133C337` (call at `0x4133C340`) | `IconChanged` | the icon handle — same shape, same `NewStyleControls` gate |
| `0x4133AC5E` | `TApplication.Destroy @0x4133AC5A` | **0** — clears it on shutdown |

Delphi 3 never sends `ICON_SMALL` at all, and no module in the process imports `SetClassLongA`, so
`GCL_HICONSM` stays 0 too. The taskbar resolves `ICON_SMALL2 → ICON_SMALL → GCL_HICONSM`, and the
only non-zero answer available to it was DefWindowProc's synthesised SMALL2.

⚠ **Why Win11 rejects that synthesised SMALL2 is not measured — do not assert it.** What is measured:
`ICON_BIG` set and correct, `ICON_SMALL` and `GCL_HICONSM` zero, taskbar grey. The change this patch
makes is the **`ICON_SMALL` send**; the `ICON_BIG` send is belt-and-braces (harmless, and it makes the
cave independent of `NewStyleControls`). The in-game test decides.

### 8.2 The patch — call-retarget, 4 bytes of operand per binary, nothing displaced

Each exe's program block calls `Forms.TApplication.Initialize` exactly once, immediately before its
first `CreateForm`. That `call rel32` is retargeted to a cave which sets both icons on
`Application.Handle` and tail-jumps to the real import thunk. No host instruction is overwritten, so
there is no orphan tail and `--undo` is a 5-byte restore (`aow1-call-retarget-thunk`).

| binary | hook VA | file off | vanilla bytes | cave VA | Initialize thunk |
|---|---|---|---|---|---|
| `AoWz.exe` | `0x004599DE` | `0x058DDE` | `e8 71 7d fa ff` | `0x0062B000` (`.hcol`, file `0x225200`) | `0x00401754` |
| `AoWzCompat.exe` | `0x004599DE` | `0x058DDE` | `e8 71 7d fa ff` | `0x0062B000` | `0x00401754` |
| `AoWDevEd.exe` → `AoWzEd.exe` | `0x0042EE52` | `0x02E252` | `e8 d1 24 fd ff` | `0x00590180` (`.vgo`, file `0x18A380`) | `0x00401328` |

96 bytes assembled, identical body in all three; only four immediates differ:

| | `AoWz.exe` / `AoWzCompat.exe` | `AoWDevEd.exe` / `AoWzEd.exe` |
|---|---|---|
| `VCL30!Forms.Application` (data) | `0x0045D5F4` | `0x00432224` |
| `VCL30!Forms.TApplication.GetExeName` | `0x0045D56C` | `0x00432178` |
| `kernel32!GetModuleHandleA` | `0x0045D39C` | `0x00432160` |
| Initialize thunk | `0x00401754` | `0x00401328` |

`TApplication.FHandle` is at **`+0x24`**, proven from `SetHandle @0x4133B900`
(`cmp esi,[ebx+0x24]` … `mov [ebx+0x24],eax`) rather than assumed.

### 8.3 Why the cave reaches into `vcl30.dpl`

**`LoadIconA` is in no exe's IAT**, so the delta is needed whatever else is available. `SendMessageA`
is the one that differs per binary:

| binary | user32 imports | `SendMessageA`? |
|---|---|---|
| `AoWz.exe` / `AoWzCompat.exe` | **1** — `UnionRect @0x0045D3A8` | no |
| `AoWDevEd.exe` / `AoWzEd.exe` | **19** | yes, `@0x00432248` |

The editor could call its own `SendMessageA` and skip one of the two vcl30 loads. It does not,
deliberately: routing both through vcl30 keeps **one** cave body across all four files with only four
immediates differing, which is what makes the lockstep check and the editor derive cheap to verify.
It costs 6 bytes.

vcl30 is a package and rebases, so its runtime addresses are recovered from an import the exe already
has:

```
delta = [<exe IAT slot for Forms.TApplication.GetExeName>] - 0x4133C0F8
```

`0x4133C0F8` is that export's preferred VA in `Ziggurat\vcl30.dpl` (ImageBase `0x41300000`), read out
of its `.edata`. Everything else is `[edx + <preferred VA>]`:

| preferred VA | what |
|---|---|
| `0x413E46F8` | vcl30 IAT slot, `user32!LoadIconA` (confirmed by import-table walk) |
| `0x413E468C` | vcl30 IAT slot, `user32!SendMessageA` (confirmed by import-table walk) |
| `0x4133ABCC` | vcl30's own `"MAINICON\0"` — so the cave carries no string of its own |

That literal is the exact pointer `TApplication.Create` pushes at `0x4133AAE1` when it loads
`Application.Icon`. Precedent for the idiom: `08-editor.md` §9.3 (WinExec via vclx30.dpl).
⚠ §6.1's `vcl_delta` worked example does **not** reproduce — use the GetExeName anchor.

### 8.4 The cave

```
0062B000  60             pushad
0062B001  8b0df4d54500   mov  ecx,[0x45d5f4]        ; &Forms.Application
0062B007  8b09           mov  ecx,[ecx]             ; the TApplication object
0062B009  85c9           test ecx,ecx
0062B00B  744d           je   0x62b05a
0062B00D  8b5924         mov  ebx,[ecx+0x24]        ; FHandle = the owner window
0062B010  85db           test ebx,ebx
0062B012  7446           je   0x62b05a
0062B014  8b156cd54500   mov  edx,[0x45d56c]
0062B01A  81eaf8c03341   sub  edx,0x4133c0f8        ; edx = vcl30 rebase delta
0062B020  8bb2f8463e41   mov  esi,[edx+0x413e46f8]  ; user32!LoadIconA
0062B026  8bba8c463e41   mov  edi,[edx+0x413e468c]  ; user32!SendMessageA
0062B02C  8d82ccab3341   lea  eax,[edx+0x4133abcc]  ; 'MAINICON'
0062B032  50             push eax
0062B033  6a00           push 0
0062B035  ff159cd34500   call [0x45d39c]            ; GetModuleHandleA(NULL); trashes edx
0062B03B  50             push eax
0062B03C  ffd6           call esi                   ; LoadIconA(hInst,'MAINICON')
0062B03E  89c6           mov  esi,eax               ; hIcon
0062B040  85f6           test esi,esi
0062B042  7416           je   0x62b05a
0062B044  56 6a01        push esi / push 1          ; ICON_BIG
0062B047  6880000000     push 0x80                  ; WM_SETICON
0062B04C  53 ffd7        push ebx / call edi
0062B04F  56 6a00        push esi / push 0          ; ICON_SMALL
0062B052  6880000000     push 0x80
0062B057  53 ffd7        push ebx / call edi
0062B05A  61             popad
0062B05B  e9f466ddff     jmp  0x401754              ; the real Initialize thunk
```

**Register discipline is the part that was wrong in the first draft.** `EDX` holds the delta and
`EDX` is caller-save under stdcall, so `GetModuleHandleA` is free to trash it. Both vcl30 IAT slots
are therefore loaded into `ESI`/`EDI` **before** the first call, and `EDX` is never read afterwards.
`EBX` holds hWnd; `ESI` becomes hIcon. `pushad`/`popad` brackets everything, so the program block sees
no register change — which matters, because in `AoWz.exe` the surrounding code keeps the Application
pointer in `EBX`.

One `LoadIconA` handle serves both `ICON_BIG` and `ICON_SMALL`. The group has no 16×16, so a
`LoadImageA` call for a "real" small icon would downscale the identical 32×32 bitmap user32 already
downscales — and `LoadImageA` is imported by zero modules here. Per §8.1, `ICON_SMALL` is the send
that does the work; `ICON_BIG` restates what `CreateHandle` already set.

**The keystone imm8 trap does NOT land on `0x80`** — measured on the installed keystone, `push 0x80`
→ `68 80 00 00 00`, the correct 5-byte form. The standing trap (§12 `12-re-toolchain.md` §5.2) is real
but applies to sign-extension cases: `push 0x7F` → `6a 7f` and `push 0xFFFF` → `6a ff`, both
re-measured here. `0x80` is not one of them, because it does not round-trip through a signed imm8.

The explicit `.byte 0x68, 0x80, 0x00, 0x00, 0x00` emission and the self-disassembly guard are kept as
**defence in depth**, not as a workaround for an observed miscompile: `WM_SETICON` *is* `0x80`, so a
`6A 80` would mean message `0xFFFFFF80` with every byte check still passing. The guard costs 0 bytes
of cave and fails the build unless both pushes decode as a 5-byte `push 0x80`. QA fault-injected it
four ways and it raised every time. (`WM_SETICON` = `0x0080`, `WM_GETICON` = `0x007F` — do not
transpose.)

### 8.5 Cave space and the `.vgo` VirtualSize edit

`.hcol` `0x0062A200..0x0062D000` is an 11.5 KB verified-zero run; `0x0062B000` takes `0x100` of it.
⚠ Everything below `0x00628000` in that section is unusable — `build_herodlg_columns.py` zeroes
`0x00612000..0x00628000` on every `--apply`; see `12-re-toolchain.md` §6.2.

`.vgo` in `AoWDevEd.exe` had `SizeOfRawData 0x200` but `VirtualSize 0x16D`, with `build_validation_goto.py`
owning `0x00590000..0x0059016C`. The cave sits at `+0x180`. Rather than rely on "raw bytes past
VirtualSize are mapped anyway", `--apply` raises VirtualSize to `0x200` and `--undo` puts it back;
`SizeOfImage` (`0x19A000`) already covered it, so no other header field moves and the file length is
unchanged. `build_validation_goto.py` is a no-op once `.vgo` exists and does not read VirtualSize, so
it will not disturb this.

`.reloc`: a `call rel32` displacement never carries a base relocation, confirmed per binary —
`AoWz.exe` has entries at `0x004599BE` and `0x004599E5` with nothing in `0x004599DF..0x004599E2`;
`AoWDevEd.exe` has `0x0042EE4C` and `0x0042EE58` with nothing in `0x0042EE53..0x0042EE56`; zero
entries anywhere in `0x0060C000..0x00630000` or in `.vgo`. `build_relocfix.py` reports the same
7/7/1 entries and "0 to change" before and after.

No roll — no generator, no P1–P5 pattern, `rng_audit.py` not applicable.

### 8.6 Ruled out, each with its reason

- **`SetClassLongA/W`** — in no IAT, would need `GetProcAddress`, and Win11 reads `WM_GETICON` rather
  than `GCL_HICONSM` anyway.
- **Reading `Application.Icon.Handle`** instead of calling `LoadIconA` — D3's `TIcon` holds a shared
  `TIconImage` indirection, not a bare `HICON`: two unverified offsets plus a lifetime question.
- **Patching vcl30's `WNDCLASS` template at `0x413E19A4`** (hIcon at `+0x14`) — `hIcon` must be a
  runtime `HANDLE`; any static non-zero there is a garbage handle.
- **A new PE section in `AoWDevEd.exe`** — `e_lfanew 0x100`, 13 headers end at exactly file `0x400` =
  CODE's raw start. Room for zero. (`AoWz.exe` has room for exactly one; not worth 96 bytes.)

### 8.7 The alternative not taken

**One PIC cave in `Ziggurat\vcl30.dpl` at `TApplication.Run`** would have fixed `AoWz.exe`,
`AoWzCompat.exe` and `AoWzEd.exe` in a single patch with no rebase delta, since all three load that
package. Rejected for three reasons, in order of weight:

### 9.1 The renderer is unrolled, not a table

`TItemBanner` lives **only** in the exe pair — the class name is in no `.dpl` and in neither editor
binary. Its stat renderer is the published `OnShow` of the `IBannerPopup` menu:

```
TItemBanner        VMT 0x00406950   [VMT-0x1C] instsize 0x78   [VMT-0x2C] field table 0x00406978
                   13 entries, 210 B, ending at the method table 0x00406A4A -- so it cannot grow
                   in place and has to be relocated
IBannerPopupShow   0x00406AE8 .. 0x00406E5D

  +0x44 ItemNameLbl  +0x48 IBannerPopup  +0x4C AttackIcon  +0x50 DefenseIcon  +0x54 DamageIcon
  +0x58 ResistanceIcon  +0x5C Attack  +0x60 Defense  +0x64 Damage  +0x68 Resistance
  +0x6C DrawBox  +0x70 AbLB  +0x74 AbVSB
```

0x406B39..0x406B88 hides all eight stat controls, then four ~0x7A-byte **identical** blocks run in
the order ATK `0x46`, DAM `0x48`, DEF `0x47`, RES `0x49`:

```
cmp byte [item+0xNN],0 / je next
IntToStr(movsx byte) -> TAOWLabel.SetGText @0x403254
SetVisible(label,True) ; SetVisible(icon,True)      VMT +0x6C, DL = bool
SetLeft(icon, esi+0x0A) ; SetLeft(label, esi+0x1E)  VMT +0x58, EDX = int
SetTop (icon, y)        ; SetTop (label, y+5)       VMT +0x5C, EDX = int
add esi,0x32 / cmp esi,0x82 / jne next / esi = 0x1E / y += 0x14
```

esi is the column x (starts `0x1E`), `[ebp-8]` the row y (starts `0x64`), `[ebp-4]` the item,
`[ebp-0xC]` the IntToStr scratch string the host function's own finally frees. The wrap
(`cmp esi,0x82` after `add esi,0x32` from `0x1E`) makes it a **2-column × N-row flow layout** that
already reaches a third row and already repositions the ability listbox under it — so the layout
needed **no** change to take two more rows. Icon x is 40/90, label x 60/110, rows y = 100/120/140.

### 9.3 What is written

1. **New RWX section `.ibnr`**, VA `0x00630000`, `0x3000` B, appended after `.pyar`;

   this patch `AoWz.exe` has no room for a 14th section: a future exe feature must squat in `.ibnr`'s
   or `.hcol`'s zero tail, or `--undo` here first (the undo *removes* the section and gives the slot
   back). `add_section()` asserts it rather than corrupting CODE's raw data.
2. **DFM grown by four byte-clones of `TUNITBANNER`'s nodes** — measured spans `HitsIcon` 565 B,
   `MovesIcon` 566 B, `Hits` 461 B, `Moves` 462 B = **2054 B**; `TITEMBANNER` goes 7411 → **9469 B**

### 9.3a ⚠⚠ A new control must be added to the RESET SWEEP as well as shown

**The first build of this script shipped without this and every static check passed** — byte
verification, cave disassembly, a byte-exact `--undo` round trip, `relocfix --audit`, `rng_audit`.
Caught by QA on the installed bytes, 2026-09-13.

`IBannerPopupShow` opens with `SetVisible(ctrl, False)` on exactly eight fields
(`0x00406B39..0x00406B88`: `+0x4C, +0x54, +0x50, +0x58, +0x5C, +0x64, +0x60, +0x68`). Three
measurements make that sweep load-bearing rather than decorative:

- `AoWComp.TAoWComponent.Create @0x59802318` does `mov byte [esi+0x75], 1` — **every component is
  constructed visible** — and none of the popup's children carries a `Visible` property in the DFM
  (only `IBannerPopup` itself does, `False`).
- `AoWComp.TAoWComponent.SetVisible @0x59803004` and `AoWBaseWin.TAOWBaseWindow.SetVisible
  @0x598083CC` write only `[self+0x75]` and walk no child list, so hiding the popup in
  `IBannerPopupMouseDown @0x00406E60` does **not** reset its children.
- `TUnitBanner.BannerPopupShow @0x00403F60` has no `call [ecx+0x6c]` at all, because a unit always
  has all six stats. **Do not read that absence as permission to skip the sweep here** — the item
  banner has one precisely because item bonuses are optional, and HP/MV bonuses are optional too.

Without the hide: on a fresh launch the first popup for *any* item draws `HitsIcon` at `(30,95)` and
`MovesIcon` at `(76,95)` with blank labels, on top of the stat rows at y=100/120; and after one bonus
item the icon and its stale number persist on every later item that lacks the bonus, in whatever grid
slot the previous item left them.

**The four hides sit at the head of `cave_hpmv`, not in a third `E9` over the sweep**, because the
two are provably equivalent here and one hook is cheaper to verify and to undo. Measured with
capstone over the live function:

- **EBX is written once**, at `0x00406AF6` (`mov ebx,eax`, Delphi EAX = Self), and never again
  through `0x00406D7D` — so `[ebx+0xNN]` in the cave is the same base the sweep itself uses.
- **Every branch edge landing in `[0x406B89, 0x406D82]` originates at `≥ 0x00406B9C`**, i.e. after
  the sweep; **zero** edges land inside the sweep; and the only edge from before it is
  `0x00406B25 je 0x00406E3A`, the nil-item exit, which skips the whole body.

⇒ every path that reaches `0x00406D7D` has already run all eight calls, so running four more at the
top of the cave has the same predecessors and the same guarantee. **Re-run that sweep if this
function is ever re-hooked.**

### 9.4 ⚠ The 200 px popup clamp had to move, and why it is still behaviour-neutral

`AbLB` is `Alignment.AlignHeight = ahBoth` with `BottomOffset 24`, and the renderer writes its
`TopOffset := y + 10` at `0x00406DA3`, so the **visible ability list is `popupHeight - (y+10) - 24`**.
`0x00406E19` sets the popup height to `count*ItemHeight + y + 0x32`, then `0x00406E24` clamps it
**down** to `0xC8` = 200.

| stats shown | final y | list height at a 200 px clamp | 12-px rows |
|---|---|---|---|
| 0 | 100 | 66 | 5 |
| 1–2 | 120 | 46 | 3 |
| 3–4 | 140 | **26** | **2** ← today's four-stat case |
| 5–6 | 160 | **6** | **0** |

So an item carrying an HP or MV bonus *and* an ability would have shown an **empty** ability list.
The clamp becomes `max(200, y + 60)` — algebraically `0xC8 + (y - 0x8C)`, i.e. one row's worth of
height per extra stat row. It is **200 for every y ≤ 140**, so every item that does not gain a row is
bit-identical to before, and 220 for the 5/6-stat case, which restores exactly the 26 px a four-stat
item gets today. `0x00406E26..0x00406E39` is left intact but unreachable (the only inbound edges in
the function are to `0x00406E3A`).

- **PIC is not used and not wanted.** Fixed base `0x400000`, so absolute addresses are correct here.
- **`.reloc`: zero fixups in either hook window.** Whole-table scan (11902 entries): the five inside
  this function are at `0x406AFC / 0x406B07 / 0x406B15 / 0x406DBD / 0x406E43`, all outside
  `0x406D7D..0x406D82` and `0x406E21..0x406E26`. Nothing is displaced or moved.
  `build_relocfix.py --audit` reports `total: 0` after apply.
- ⚠ **`0x00406DEF` belongs to `build_abilityid_ceilings.py`** (`cmp esi,0xB3`, was `0xAA`) and sits
  **inside this function**, 0x6D bytes past the first hook. Nothing here moves it; `--apply` asserts
  it still reads `81 fe b3 00 00 00` and aborts before save if not. Re-checked after apply: all 8 of
  that script's sites still report `already at 0xB3`.
- **`.ibnr` at `0x00630000` is claimed by no other script** (`grep -rl` over `build_scripts/`).
- **The relocated field table carries one absolute with no `.reloc` entry**, deliberately: the
  class-table VA `0x00406AA0` at `0x00632502`, whose original at `0x0040697A` did have a HIGHLOW
  entry. Precedent, not a defect — `build_herodlg_columns.py` relocates `THeroUpgradeDlg`'s table
  with the byte-identical shape and is CONFIRMED WORKING — and safe because AoWz.exe is
  `RELOCS_STRIPPED=0 / DYNAMIC_BASE=0` (DllCharacteristics `0x0000`), so the image always loads at
  `0x00400000`. ⚠ `build_relocfix.py` detects only **stale** relocations, never a **missing** one, so
  its clean audit says nothing about this either way.
- Item bytes are **signed**, and the new blocks use `cmp byte,0` + `movsx` exactly like the four
  vanilla ones, so a cursed −2 item shows `-2` rather than being hidden.
- Apply/undo round-trips to a **byte-identical** exe, and a second `--apply` over an applied exe is
  byte-identical to the first (verified in memory before writing).

### 10.3 Design sketch

- **Trigger** (`AoWEPACK.dpl`): in the day-1 block, before the research check at `0x55756B94`,
  raise `TPlayerMagicEventLog` mode 3 when `map[+0x13A] == 2` (PBEM), the player is human
  (`[+0xA7] == 0`), has a leader (`[+0xD4]`) and `[leader+0x9C] > 0`. One byte at `0x5577C3FE` so
  mode 3 executes.
- **Show** (`AoWz.exe` + `AoWzCompat.exe`): retarget `0x44F183` to a cave that, for mode 3, runs the
  §10.1 recipe against `player[+0xD4]` with mode 6, max picks unchanged and locked count 0, keeps
  the completion callback, and falls through to `0x44F51E` otherwise.
- **Apply** (`OnDone`, on `lssDone`): vanilla's own copy-back, `UpdateFromLibraryBegin` →
  `live.Assign(control[+0x14])` → `UpdateFromLibraryEnd`. That carries stats, abilities and spheres
  in one step. Run it inside `SynchroniseBegin/End` (`0x557755F8`/`0x55775600`, the bracket
  `TPBEMPlayerControl` itself uses around engine work in a UI callback), run the deferred day-1
  grant, then fire the completion callback so the research prompt follows with the new spheres.
- **Defer the grant**: `cave_day1` skips under exactly the trigger's predicate, and becomes callable
  as a routine for the apply step. Re-tune in place in `build_tierresearch_dll.py`.
- **Suppress the leader's turn-1 level-up prompt** under the same predicate: add a guard to
  `C_TURN1 @0x5584B000` (`build_hero_turn1_upgrade.py`) so it skips `TLeader`s. Other heroes keep it.
- **Offer roll** (`AoWz.exe` + `AoWzCompat.exe`): gate the page's available-ability loop after the
  mask test at `0x4161AF` and before `CanExpand` at `0x4161D1`, skipping to the loop's next-index
  label (`0x416251`, where both existing rejects already go). Pattern **P4 DERIVED HASH**, for the
  reason `build_heroskill_race.py` records: the list is rebuilt on every Add/Remove, `CanExpand`
  drops owned abilities so the set shrinks, and reopening the incoming PBEM file must not re-roll.
  Use **the level-up dialog's exact hash** — `rngstd` over `map[+0x22C]` (`[[0x0045DF7C]]+0x22C`),
  `[hero+0x18]`, `movzx [hero+0x4C]`, ability id → `range_n(100)` — and compare against
  `min(2·pct, 100)` from the **same baked table** the level-up cave reads. Same key, doubled
  threshold, so the leader page always offers a superset of what that hero's level-up would offer at
  the same level. The window's copy `[dlg+0x2E4]` (a fresh `TLeader.Create` filled by `Assign`)
  carries the live leader's hash keys: `[+0x18]` is streamed (tag 5, `0x55782107`) and so is
  `[+0x4C]` (tag `0x16`) (QA 2026-09-23).

⚠ Forward hazards, all couplings:

- **One predicate, three sites.** The event raise, the grant deferral and the `C_TURN1` guard must
  test the same thing. Otherwise a player gets two grants or none, or two dialogs editing one leader.
- **The copy-back overwrites the live leader with the snapshot**, and the snapshot is taken when the
  dialog opens. Anything that changes the leader in between is undone — a `THeroUpgradeTE` still in
  the token queue (the reason for the `C_TURN1` guard), or a move made on the map while the dialog is
  up, which would refund its movement.
- **PBEM only.** The apply step mutates state without a token, so in network MP it would desync.
- **The offer roll reads `build_heroskill_race.py`'s baked table and copies its hash.** That script
  locates its own sites by pattern on every run; if it relocates or re-shapes the table, the leader
  cave must follow. A re-bake of `heroskill_races.json` changes both dialogs at once — intended.

**Copying a live leader is static-clean (QA 2026-09-23).** `Assign` from the live leader only reads
the source's fields; the copy registers nothing, and destroying it unregisters nothing, because every
unregister is guarded by an unstreamed field or by pointer identity. Leader integrity after the
window closes still needs the game.

### 10.4 Unsettled — needs a launched prototype

⭐ **`LeaderPnl` is not a free-standing window.** Its DFM gives `AOWWindow = TitleWindow.TitleWin`,
Priority 10, `ILTexture = IntGfxMod.TitleScreen` index 4, 640×480 centred. `TitleWin`

(`TCombatEventLog.ViewLocation @0x55729274`).

### 11.2 Where the event is born

`THero.ValidateHeroUpgrade @0x55787D54` is the only creator: classref `0x55711B48` has two readers,
this and the class registration in `TAoWEngine.Create+0x4A6`; nothing derives from the class and
AoWz.exe only `IsClass`-tests it (`0x0044F1DB`). It reads `GetLocation(hero)` into a 3-byte local on
entry and creates **no** event for an unplaced hero (`0xFF`) or owner 0. Then:

```
55787F46  TEventLog.Create(THeroUpgradeEventLog)
55787F4F  [+0x1C] old level, [+0x1D] new level
55787F6F  [+0x20] := player[+0x5C]           the owner's turn counter
55787F7B  [+0x18] := hero id
55787F93  DistributeLocationEventLog(event, owner, x, y, level, 1)
```

`DistributeLocationEventLog @0x557FE558` gives the owner, and every player the hex is not fogged for
(`FoggedForPlayer(x,y,level)`), a `TEObject.Copy` of the event through `TEventLogbook.AddEvent`, then
`Execute`s it for the seated human. ⭐ `TEObject.Copy` (EngineP `0x55519270`) streams the object out
and back in (`WriteEObject`/`ReadEObject` → `TEObject.MainReadWrite 0x555193B1` → VMT `+0x18`), so
each per-player copy carries exactly what `ReadWrite` serialises and nothing else.

### 11.3 ⚠ `[+0x20]` is NOT spare — the class grows instead

Inioch's note calls `[+0x20]` "serialised but otherwise unused" and stores the hex there. In our DLL
(byte-identical to vanilla at every site involved) it holds `player[+0x5C]`, the turn counter
`TPlayerControl.NewTurn` increments at `0x55755524`, and `THeroUpgradeEventLog.Execute` reads it at
`0x55785757` when the hero has no upgrade pending (`[hero+0x54] == 0`): equal →
`CanOnlyUpgradeHeroOnceRStr`, different → `CanOnlyUpgradeOnTheDayALevelIsMadeRStr`. Overwriting it
makes the double-click message wrong on the day of the level-up.

So the instance grows `0x24 → 0x28` and the hex goes in a new dword streamed as property **`0x1D`**:
`+0x24` x, `+0x25` y, `+0x26` map level, `+0x27` valid flag = 1. Chain ids read from the bytes:
`TEObject.ReadWrite` is a bare `ret`, `TEventLog` uses `0x0A`–`0x0C`, `THeroUpgradeEventLog`
`0x19`–`0x1C`. Old saves lack `0x1D`, so their events keep a zeroed field and follow the hero as
before; after `--undo` the reader ignores `0x1D`.

### 11.4 What is written — capture at the creation call, not in `AddEvent`

| site | bytes | change |
|---|---|---|
| `0x55711B6C` instance size `[VMT−0x1C]` | 4, no `.reloc` | `0x24` → `0x28` |
| `0x55711BA0` VMT `+0x18` ReadWrite | 4, HIGHLOW kept | `0x55785508` → `C_RW` |
| `0x55711BFC` VMT `+0x74` ViewLocation | 4, HIGHLOW kept | `0x557857E0` → `C_VIEW` |
| `0x55787F93` `call DistributeLocationEventLog` | rel32, no `.reloc` | → `C_CAP` |

Caves, exclusive `0x5584D000..0x5584D0FF`, register/rel32 only, no anchor:

- **`C_CAP` `0x5584D000`, 28 B.** EAX = event, CL = x, `[esp+8]` = level, `[esp+0xC]` = y (Delphi
  pushes the stack arguments left to right). Stores the four bytes, saving EDX round them, and
  tail-jumps to `DistributeLocationEventLog`; its `ret 0xC` returns to `0x55787F98`.
- **`C_RW` `0x5584D040`, 29 B.** Calls the original `ReadWrite`, then `rwInteger(&self[+0x24], 0x1D)`.
- **`C_VIEW` `0x5584D080`, 28 B.** Flag set → `CenterViewTo(self, DL=[+0x24], CL=[+0x25], push
  [+0x26])`, the same roles vanilla replays from its local; flag clear → `jmp 0x557857E0`.

The brief's site was the `GetSynchronised` call in `TEventLogbook.AddEvent` (`0x557FDB9D`). That
function has 37 callers — every event class, the raze-event cave at `0x5581452D` and
`DistributeCombatEvent` among them — so a capture there needs a PIC VMT test, `FindUnit` and
`GetLocation` on every event. At `0x55787F93` the engine has already computed the hex and passes it
as arguments; no other event class can reach the cave. It stamps the hex the fog test uses, so an
event only reaches a player who could see that hex, and it points there.

A captured event centres on its hex even after the hero has died (vanilla did nothing then). The hex
is where the hero stood when `ValidateHeroUpgrade` ran: the start of the owner's turn, when the event
appears.

### 11.5 Multiplayer

Deterministic, and there is no remote-side capture to get wrong. `AddEvent` asserts
`TAoWHSMap.GetSynchronised` (`0x557FDB9D`), true only inside `SynchroniseBegin/End`
(`map[+0x234]`, bracketed by `TAoWHSMap.MsgProc` and the PBEM controls). Every peer therefore runs
`ValidateHeroUpgrade → DistributeLocationEventLog → Copy → AddEvent` as one call chain with the hero
on the same hex, and nothing adds a level-up event to a logbook later. The field streams as `0x1D`,
so saves and PBEM files carry it. No RNG; `rng_audit.py --owners` output unchanged.

### 11.6 Forward hazards

- `0x55711B6C` and `0x55787F93` are one unit: `C_CAP` writes `+0x24..+0x27`, past a `0x24`-byte
  instance. The script writes and removes all four sites together and refuses a mixed state.
- A further field on `THeroUpgradeEventLog` starts at `+0x28` and needs an id other than
  `0x0A`–`0x0C`, `0x19`–`0x1D`; a duplicate id raises `PropertyExistError` on the first save.

Revert: `build_levelup_eventloc.py --undo` (4 sites back, 85 cave bytes zeroed; round-trip
byte-identical 2026-09-24). Snapshot: `backups\AoWEPACK.dpl.pre-levelupeventloc`.

   Right-clicking the event centres on the level-up hex, not the hero.
2. MP or PBEM: an enemy hero seen levelling, then moving. Right-clicking centres on the level-up
   hex.
3. Save, reload, and hand a PBEM turn over: new level-up events still centre on their level-up hex.

## 12. Resuming a multiplayer save with Customize Leaders ticked no longer hangs — 🔨 APPLIED, UNTESTED (2026-09-24)

`build_mpresume_customize.py`, ported from Inioch's `build_mpreload_customize_fix.py`; a vanilla
bug.
- **The hang:** the host's start barrier `hValidateSetupMap 0x557E1168` passes a human slot only
  when it has loaded the map (`TPlayerSetupSettings+0x19` bit 8). While Customize Leaders is on
  (`TSetupSettings+0x2A`), it also requires the slot to have customised its leader (bit 4).
  `MapLoaded 0x557E0614` skips customisation for a game in progress (`TSetupSettings+0x20 != 0`),
  so bit 4 never comes and every machine waits on "Waiting for other players" forever.

- **The fix:** hook `0x557E11AA` (`cmp byte [ebx+0x2A],0 / je`, 6 B; `ebx` = `TSetupSettings`) →
  cave `0x5584D200` (22 B). A game in progress, or Customize Leaders off, counts as satisfied
  (`0x557E11C3`); otherwise it runs the vanilla bit-4 check (`0x557E11B0`).
- No bearing on §10's PBEM window, which has no network handshake. Surgical `--undo`.

In-game checklist:
1. Host a network game with Customize Leaders ticked, save, and resume it with the same players:
   everyone gets past "Waiting for other players".

## Failed approaches — do not retry

- **Combat log v1** — driving the exe-side drain off the log window's *own* memo `OnUpdate`. Circular:
  a hidden component never ticks, so it never drains, so it never shows itself. Fixed in v2 by
  pumping off the always-ticking `TMWindow.MapWindowUpdate` instead (§1.3).
- **Combat log v4** — shrinking the stock unit card via an in-place DFM edit, to make room for the log
  window. Futile: v5's live-process measurement proved the game re-lays-out stock sidebar windows at
  runtime (~3× their DFM values, alignment offsets reset), so **no resource edit can move or resize a
  stock sidebar window** — only a window the game doesn't touch, like the log's own clone, obeys its
  DFM (§1.3).
- **Mouse wheel** — the five-item DO-NOT-TRY list in §4.1 in full (`WH_MOUSE` thread hook for in-game
  delivery; owning `WH_MOUSE_LL` on the render thread; driving a parallel-list column directly instead
  of its governing scrollbar; gating the cross-module contract on a signature byte; absolute IAT
  references inside a `.dpl` cave).
- **Strategic-map cursor — the DCPACK `GetMousePos` hypothesis.** `TDisplayCtrl.GetMousePos
  @0x55103FC0` (DCPACK.dpl) has its own geometric bounds-reject at `0x551040B6`; a candidate patch
  neutering it (`build_cursor_fix.py`, 3-byte `83 3F 00 → EB 1D 90`) was built, applied, and had **no
  in-game effect** — proving the map cursor doesn't route through this function at all. The real
  fault was one layer down, inside HSEPack's own `THSMapMouse.Move` (§6). Reverted; the script and its
  backup deleted after confirming byte-identity with vanilla — do not re-derive this path for the map
  cursor. (`0x55103FC0` may still gate other windowed mouse input — menus, dialogs — never tested,
  since the real bug turned out to be elsewhere.)
